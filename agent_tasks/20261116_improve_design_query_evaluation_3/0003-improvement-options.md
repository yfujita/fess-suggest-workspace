# 0003 改善案の比較(フェーズ2)

担当: tech-advisor(報告をメインエージェントが記録)。コード・既存ファイルの変更なし。OpenSearch は `_analyze` / 読み取りのみ。ユーザーの採用決定は末尾「承認結果」に追記する。

## 1. 前提と見積もりの方法

- コーパスはフェーズ1と同一(はてなブックマーク100文書、suggest 索引 `fess.suggest.20261115085528534` の18,144候補。断片11,825件、連結語6,319件)。分類 C1〜C7 はフェーズ1の定義(0002 §3)。
- 分析実測: `fess_suggest_analyzer` の既存要素を名前で参照し、フィルタだけをインラインで差し替えた `_analyze`(100文書・1,633チャンク)。オフライン等価判定: Java 側ルールを Python で再現し、索引の候補テキストに適用。A、B、J の C1/C2 では両者が一致(J の一部のみ1件差)。
- 限界: 50%ランダム読み取りの1回分で再生成ごとに変動する。単一コーパス(はてブ一覧ページ)。「有用語」の判断は主観(推測)。1文字入力の露出は入力文字自身が返る分(C5 24/59、C6 3/61)で過大。検索ログ経路は実データで断片0のため定量していない。連結語の再現に使った jar は PR #107 初期版(`ー` の扱いは main と同じ)。

## 2. 案の一覧

### 案 A: stoptags に `形容詞-自立` を追加(アナライザ側)
- 変更: `fess-suggest/.../suggest_analyzer.json`、`fess/.../suggest_analyzer.json`、`fess/.../_vanilla/suggest_analyzer.json` の `pos_filter` に1語(各ファイル1箇所。4アナライザで共有)。
- 効果: C3 72 + C4 104 + C7a(形容詞の基本形)132 = 308件が消える。
- 巻き添え: 基本形132件(docFreq 計3,359。`ない` 375、`いい` 189、`すごい` 137、`良い`、`かわいい`、`おいしい`、`新しい`、`難しい`)を失う。検索ログ経路でも `安い`、`おいしい` を検索した履歴が候補にならない(`isExcludeSearchword` が1トークンも残らない語を除外するため)。動詞(`食べる`)は現状すでに除外。
- 連結語・読み: 影響なし。
- 反映: アナライザ索引の再作成が必要。規模: JSON 3か所の1行。

### 案 A'(活用形だけ Java 側で除外)
- 内容: `形容詞-自立` かつ `inflectionForm` が `基本形` 以外のトークンだけを断片として落とす。explain 最終段(`limit_token_count_filter`)のトークンにも `partOfSpeech`・`inflectionForm`・`baseForm` が付く(ローカルで確認。`なかっ` は連用タ接続・base=ない、`大きい` は基本形)。
- 変更(fess-suggest のみ): `DefaultContentsParser.parseDocument`(`:371` のループで index 単位に `continue`)、`AnalyzerSettings.DefaultContentsAnalyzer.analyzeTokenizerStage` と `analysis/TokenizerStageResult` を拡張して最終段のトークンも返す。設定は `fess.suggest.*` システムプロパティ。
- 効果: 176件(C3 72 + C4 104、docFreq 計1,472)が消える。巻き添え0件(基本形132語は残る。名詞用法がある `うま`、`多`、`強` など12語は部分的に残る)。読み・検索ログ経路への影響なし。
- 反映: jar 更新と次回 suggest ジョブのみ。規模: 中〜大(fragment と explain 結果のチャンクごとの対応付けが必要。連結語用の explain 呼び出しを共用でき、呼び出し回数は増えにくい〔推測〕)。
- リスク: `analyzeTokenizerStage` が `null` のとき(他言語・取得失敗)は現行どおりフィルタ無しに縮退させる。`_vanilla`(標準 `kuromoji_tokenizer`)の最終段に属性が付くかは未確認。

### 案 B: `fess_japanese_baseform` で基本形に寄せる(アナライザ側)
- 変更: 案 A と同じ3ファイル(contents 系アナライザの `pos_filter` の後、`content_length_filter` の前に挿入。動作確認済み)。
- 効果: 表層176件(C3 72、C4 104)が消え、ユニーク語は15,760 → 15,598(-162)。基本形の新規候補が56〜68件増える(`ちいさい`、`憎い`、`つまらない`。`おもしろ` 370 → `おもしろい` 371 は良い方向)。
- 副作用: 誤った基本形のゴミが出る(`うい` 51、`こい` 60)。`reading_form` は表層の読みを返し baseform は読みを更新しないため、基本形に別表層の読みが付く(`なかっ`→`ナカッ`、`大きく`→`オオキク`。表層→基本形の対は188)。`ない` の頻度が375 → 約533に上がり、#7 の汎用語が上位に出やすくなる。有用語の損失は0。
- 反映: アナライザ索引の再作成が必要。規模: JSON 3か所。連結語には影響しない。

### 案 J: 文書経路の断片フィルタ(Java 側)
- 変更(fess-suggest のみ): `DefaultContentsParser.parseDocument` の `:373`(`isBlank(word)` の直後)に `isNoiseFragment(word, lang)` を置いて `continue`(`readingTokens` は index 対応なので整合は保たれる)。規則は `fess.suggest.fragment.*` のようなシステムプロパティで切り替える。文字種は `Character.isLetterOrDigit`。長音 U+30FC は Lm で letter のため C1 は別規則にする。ja 以外(zh の単漢字、ko など)で最小長が効きすぎないよう `lang` で適用範囲を絞る。
- 検索ログ経路: C1/C2 だけは `parseSearchWords` / `isExcludeSearchword`(`:860`)にも数行で足せる。最小長はログ経路に入れない。
- 反映: jar 更新と次回 suggest ジョブのみ。規模: 小(30〜60行 + テスト)。
- 規則パッケージ(§3 の表): N=C1+C2 / M1=N+英数1文字+かな1文字 / M2=M1+英数2文字以下 / W1=M1+単漢字 / W2=M2+単漢字。

### 案 J': アナライザ側で文字種・最小長(`pattern_replace` + `length`)
- 分析実測: `pattern_replace`(`^[ッっーｰｯ]+$`、`^[^\p{L}\p{N}]+$` を空文字に)+ `length min:1` で C1/C2 の198件が消える(巻き添え0、docFreq 計17,608)。`content_length_filter` に `min: 2` だけでは不十分(C1 は4件中2件、C2 は194件中68件。`ーー`、`!!!` が残る)。
- 欠点: `content_length_filter` は96個のアナライザ(48言語 × contents/contents_reading)が共有し、言語非依存で危険。contents だけ変えて reading 側を変え忘れると、30文書300チャンク中 A で267、C_P1 で299 がトークン数不一致になり `readingTokens=null` で変換器へ静かに縮退した(両方変えれば0件)。検索ログ経路でも `length`/`pattern` が `isExcludeSearchword` に効き、`月`、`人`、`ai`、`x` の検索履歴も除外される。3ファイル × 4アナライザの編集とアナライザ索引の再作成が必要。
- 位置づけ: C1/C2 だけなら有効だが、J の方が副作用が小さい。

### 連結語 `ー…`(#2 との整合)
- 実測: 促音長音のみのトークンを含む連結語は現索引に16件(先頭が `ー` 13件: `ーquiet` 79、`ー美少女` 11、`ーだい` 11 など。末尾が `ー` 3件: `ゆー` 29、`ょりー` 6、`ぁいこぬー` 2。docFreq 合計約170)。
- 規則: `trimSymbolTokens` と同様に両端の促音長音のみのトークンを外す。15件が消えるか短くなる(`ー警視庁編ー`→`警視庁編`、`ーめん才遊記`→`めん才遊記`)。`ぴー先生` は中間なので残る。「トークンごとに run を切る」規則だと `ぴー先生` まで失うため、端トリムを推奨。
- #2 の例語(`新型コロナ`、`大統領選`、`高市早苗`、`石破首相`、`ワクチン接種`、`円安`、`togetter.com`、`神奈川県`)は、トリム規則を入れても全て連結語が出る(再現済み)。
- 実装: `isSymbolToken` を呼ぶ位置(`:664`、`:677`)の判定に条件を足すだけ。規模: 小。

### 案 D: 取得時の除外・スコア調整
- 位置: `SuggestResponseCreator.createResponse` のループ(`:89`)で `continue`。検索は `size*2` 件取得(`SuggestRequest.java:333`)。
- 効果(1文字入力72種、返却1,067語): P2b で63語(5.9%)、P4 で120語(11.2%)を除外。
- 欠点: 索引に断片が残る。除外後に num 件を満たせない場合がある(P4 で58/72入力)。手動登録(USER)・elevate word を除外しない分岐が要る。連結語の `ー…` は直らない。
- 位置づけ: 作り直しを待てない場合の暫定策のみ。

### 案 E: 既存環境への反映
- 確認(コード): `SuggestCreator.create()` は毎回 `createNextIndex()` で新しい空の suggest 索引を作り、`switchIndex()` で切り替え、`removeDisableIndices()` で旧索引を消す。Java 側の変更は jar 更新と次回 suggest ジョブで反映され、既存索引の断片削除は不要。
- アナライザ索引 `fess_suggest_analyzer` は存在しない場合にだけ作られる(`AnalyzerSettings.init`、`updateAnalyzer`〔`:275`〕の呼び出し元なし)。案 A、B、J' は既存環境で索引の削除 → 再作成 → suggest 再生成が必要(手順は推測。未実行)。
- badword は使えない: 部分一致で、`ー` や `/` を登録すると `ラーメン` や URL 系の語まで消える(`SuggestItem.isBadWord`、`WordManagementOperations.addBadWord` は `*word*` のワイルドカード削除)。
- 一時的な手動削除(推測): suggest 索引への `_delete_by_query` で可能だが、ジョブで再生成されるので通常は不要。

## 4. 「断片」の定義

- 狭い定義(C1〜C4): 374件。巻き添えは A' + N ならほぼ0。1文字入力の露出は 5/1067(0.5%)。空クエリ(`q=` num=30)の先頭30語に記号5語(`/` 1位、`.` 2位、`-`、`:`、`|`)が入っており、C2 は含めた方がよい。
- M1(N + 英数1文字 + かな1文字): 443件。有用語の巻き添えは出ない(主観)。誤分割の `ろ`(72)、`ガ`(105) も落ちる。露出は3.2%まで下がる。
- M2(C5 を含める): `jp`(724)、`co`(299)、`ne` などのゴミが消えるが、`ai`、`pc`、`tv`、`cm` などの略語を失う。頻度では区別できない(`ai` 737、`jp` 724)ので許可リストが要る。#8 の領域。
- W1(C6 を含める): 単漢字771を含む。#7(汎用語・1文字語)の領域。`月` の932は意味が薄いが、`米`(284)は news で米国の意味があり有用の余地がある。上位候補の構成が大きく変わるので #7 の判断と同時にすべき。
- 推奨: 既定は M1。M2、W1 は設定で切り替えられる実装にして、#7 や #8 の判断と合わせて決める。

## 5. 品詞で落とせない断片

- 頻度の足切りは選択的でない(実測): docFreq<2 で全体の35%、<10 で83%が消え、連結語の47%・C7 の30%も巻き込む。`おもし`(62)は閾値10でも残る。頻度は分離に使えない。
- `おもし`(名詞-一般)は誤分割で、品詞では落とせない。相方の `ろ`(72)は M1 で落ちる。辞書側(Y-08 のユーザー辞書など)の課題。
- `ハンバーガ` は取り込み元の表記で、#9(長音の表記ゆれ統合。19組)の領域。
- 所見: どちらも #3 のスコープに入れない。

## 6. 推奨(tech-advisor)

「J + A' + 連結語の端トリム」をすべて fess-suggest の Java 側で行う。理由: jar 更新だけで効く(suggest ジョブは毎回新しい索引を作るため)、巻き添えの有用語がほぼ出ない、検索ログ経路のユーザー意図(`ai`、`月`、`安い` を検索した事実)を壊さない。
- 代替: A' が重い場合は A(基本形132語を失い、アナライザ索引の再作成が要る)。活用形を基本形に寄せたい場合は B(読み汚染と誤った基本形)。実装の軽さを最優先するなら、J の C1/C2 だけを先に出し、活用形は後続に回す。

## 7. 確認できた事実と、推測・未確認

確認: A、B、J の C1/C2 は分析実測とオフライン判定が一致。`isExcludeSearchword` は文脈解析で1トークンも残らない語を除外する(A では `なかっ`、`安い`、`おいしい` が、J' では `月`、`人`、`x` も除外。現状でも `食べる` は除外)。毎回の新規索引作成。explain 最終段のトークンに品詞・活用形が付く(`fess_japanese_tokenizer`、ローカル)。
推測・未確認: A' の実装規模は読解からの見積もり。`_vanilla` 構成と `SuggestTestServer` で最終段の属性が付くかは未確認。「有用語」の判定と略語リストは主観。アナライザ索引の再作成手順は未実行。デモ環境の `ーッッ` が同じ機構かは未確認。
