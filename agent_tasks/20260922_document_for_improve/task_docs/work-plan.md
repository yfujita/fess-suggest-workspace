### 事前フェーズ: 既存テスト失敗の修正（`SettingsIndexCreationRaceTest`。Q12）
- 目的: 着手時点で失敗している `SettingsIndexCreationRaceTest.test_concurrentInitOnFreshCluster` を直し、全テストが通る状態からフェーズ 0 を始める。
- 症状 [確認]: `test_concurrentInitOnFreshCluster` が 5 回中 5 回、ラウンド 2〜3 で失敗する。ほかの 5 テストは通る。例外は `AnalyzerSettings.init` → `getFieldAnalyzerMapping` → `PitOperationHelper.createPit` で発生する `SuggesterException: Failed to create a point in time on fess_suggest_analyzer: no shard is available`。
- 原因 [確認]: 4 スレッドが同時に `init()` すると、`fess_suggest_analyzer` を自分で作らなかったスレッド（resource_already_exists を受けた側、または既存と判定した側）は、yellow 待ち（`AnalyzerSettings.java:155-160`）だけで読み出しに進む。OpenSearch は、作成直後で primary がまだ起動していない index を YELLOW と報告する（OpenSearch 3.9.0 `ClusterShardHealth.getInactivePrimaryHealth`）。そのため待ちはすぐに返る。PIT は部分作成を許可しているので ID なしで返り、`PitOperationHelper.java:209` で例外になる。`SuggestSettings` は同じ問題を get のリトライで回避している（`SuggestSettings.java:266`）が、`AnalyzerSettings` にはこの対策がない。
- 検証 [確認]: PIT の読み出しを 100ms 間隔でリトライする仮の修正を入れると、3 回中 3 回通った。どの回も 1 回のリトライで回復した。
- 制約 [確認]: fesen-httpclient の `ClusterHealthRequestBuilder` には `setWaitForYellowStatus()` しかない。`wait_for_active_shards` と green 待ちは builder からは指定できない。green 待ちは `auto_expand_replicas: 0-1` のため、複数ノードでは replica を待つことになり、本番には向かない。
- 修正方針 [提案]: `SuggestSettings#getSettingsDocument` と同じ方式で、間隔を伸ばしながら clusterTimeout までリトライする処理を `AnalyzerSettings.init` の読み出し（`getAnalyzerNames` / `getFieldAnalyzerMapping`）に入れる。リトライするのは「shard が使えない」失敗だけにする。現状の `SuggesterException` はメッセージでしかこの失敗を見分けられないので、見分け方を実装時に決める [要確認]。
- 横展開: `ArraySettings` も yellow 待ち（`ArraySettings.java:341-346`）の後に PIT で読み出すので、同じ競合が起こりうる [推測]。本フェーズで起こりうるかを確認し、起こりうるなら同じ修正を入れる。3 箇所の待ち処理の共通化はフェーズ 2（集約）で行う。
- 変わる挙動: 複数プロセスが同時に起動したとき、例外で失敗していた `init()` が成功するようになる。戻り値と、正常に起動した場合の挙動は変わらない。
- 完了条件: 共通条件に加えて、`SettingsIndexCreationRaceTest` を単独で 5 回続けて実行し、すべて通ること。
- 担当: code-implementer → code-reviewer（並行性とタイムアウト）/ test-reviewer。

| fess との互換 | fess-suggest で `mvn install -DskipTests` を実行した後、`modules/fess` で `mvn -nsu compile` と `mvn -nsu test -Dtest=SuggestHelperTest` を実行する。fess は親 POM の `suggest.version=15.9.0-SNAPSHOT` を参照する [確認]。`-nsu` はリモートの SNAPSHOT に置き換わるのを防ぐため [推測]。fess の `antrun:run` が compile に必要かどうかは [要確認] |
| カバレッジ（参考） | `mvn clean jacoco:prepare-agent test jacoco:report`。数値の低下は J-06 の分だけ許容する（Q6） |

**git commit**: フェーズの区切りでも commit しない（Q11）。区切りごとにユーザーへ報告する。

**レビューの流れ**（各フェーズ）: code-implementer / test-io-verifier が実装 → code-reviewer と test-reviewer が並行してレビュー → 指摘を修正 → 作業履歴を記録（doc-writer が補助）。task-reviewer はゲートで実施する（フェーズ 0 の後、設計書 v2 の時点、最終）。

**作業履歴**: フェーズごとに `agent_docs/tasks/20260922_document_for_improve/00NN-<phase>-<作業名>.md` を採番して記録する（その時点の最大番号 + 1）。
