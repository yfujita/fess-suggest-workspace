## 3. 指摘 2 [Blocker]: R1 手順が `SuggestCreator` の制御フローと合っていない

### 3.1 指摘の内容と検証

**指摘は正しい** [確認]。**第 14 版の §10.6.1 は次の順で手順を並べていた。**

```text
4. 再構築を起動し、完走を待つ
5. 切替可否を判定する（G1 / G2 / G3）
6. switchIndexRetainingPrevious() で切り替える
```

**ところが同じ文書の §4.3 が定める `create()` の制御フローはこうである** [確認]。

```text
createNextIndex (S1) → S2 全件再投入 → G3 → G1 / G2 → switchIndexRetainingPrevious → removeDisableIndices
```

**ガードも切替も `SuggestCreator.create()` の内側にある。** したがって **「ジョブが完走した」時点では判定も切替も既に終わっており、手順 5・6 を人が実行する余地は無い。** **第 14 版の手順は字義どおりには実行できなかった。**

### 3.2 反映 — **手順書を実装に合わせた**

**`0003` を第 15 版に上げ、§10.6.1 を書き直した。**

| # | 手順 | 実行主体 |
| --- | --- | --- |
| 1 | 運用者への説明 | 人 |
| 2 | **サービス停止**（外部アクセスと crawler を遮断。fess プロセスは稼働） | 人 |
| 3 | 両モジュールを同時更新 | 人 |
| **4** | **SuggestJob を 1 回起動する** | 人（起動）→ **以降は `SuggestCreator`** |
| 4-1〜4-6 | `createNextIndex` → 全件再投入 → **G3** → **G1 / G2** → **`switchIndexRetainingPrevious`** → `removeDisableIndices` | **`SuggestCreator`** |
| 5 | **ジョブ結果の確認**（切り替わったか／ガードで止まったか／異常終了か） | 人 |
| 6 | 切替後の検証（`aliasState()` ＋ 代表語の検索） | 人 |
| 7 | 異常なら `rollbackToPrevious()` | 人 |
| 8 | サービス開始 | 人 |
| 9 | `.prev` の保持期間の管理 | 人 |

**あわせて 2 つの節を新設した。**

| 節 | 内容 |
| --- | --- |
| **§10.6.1.1** | **採らなかった案**（再構築だけ実行して止め、人が G1 / G2 / G3 を確認してから切替を実行する）と却下理由 — **`SuggestCreator` を途中で止める制御点が要り、MO-1（fess-suggest に高水準の再構築 API を置かない）から外れる**。**加えて G1 / G2 は自動判定として既に設計されており、人が同じ判定を繰り返す価値が無い** |
| **§10.6.1.2** | **ガード不合格時の対応** — **切り替わっていない**（§4.3 により `switchIndexRetainingPrevious()` に到達しない）／ 原因を除去して手順 4 からやり直す ／ **その状態でサービスを開始してはならない**（新バイナリが旧世代へ書き込む状態が続く） |

> **レビューの推奨（「SuggestCreator に全部やらせる」）をそのまま採った。** **逆向き（手順を分けて人が判定する）は MO-1 に反するというレビューの指摘も正しい** [確認] — §4.3 の根拠 2 が「fess-suggest に再構築を束ねる高水準 API を新設すると `0001` §2.2 に遡及改訂が発生する。公開契約を手順書の都合で広げるのは順序が逆である」と明記している。
