## 1. 何が成立しなかったか [確認]

**`0003` §4.2 の G1 は「次世代の登録語数が 0 でないこと、かつ旧世代の件数の一定割合（既定 50%）以上であること」と定めつつ、その取得方法欄には新旧を区別せず `getAllWordsNum()` だけを挙げていた**（第 15 版まで）。**この API では次世代を数えられない。**

| # | 事実 | 実物 |
| --- | --- | --- |
| 1 | `getAllWordsNum()` は `getNum(matchAllQuery())` へ委譲する | `(sug) Suggester.java:424-426` |
| 2 | **`getNum()` は `setIndices(getSearchAlias(index))` で検索する** | `(sug) Suggester.java:444-453`（`:446`） |
| 3 | **検索エイリアスは素のインデックス名、更新エイリアスは `index + ".update"` である**（いずれも private） | `(sug) Suggester.java:455-457` / `:459-461` |
| 4 | **`createNextIndex()` は更新エイリアスだけを新インデックスへ付け替え、検索エイリアスに触れない** | `(sug) Suggester.java:235-268`（`:263` で `addAlias`、`:265` で `removeAlias`） |
| 5 | **次世代への書き込みは更新エイリアス経由である** | `(sug) Suggester.java:408` の `indexer()` |
| 6 | **検索エイリアスが次世代を指すのは `switchIndex()` の後である** | `(sug) Suggester.java:282-` |
| 7 | **更新エイリアス側を数える API は fess-suggest に存在しない** | 件数 API は `getAllWordsNum` / `getDocumentWordsNum` / `getQueryWordsNum` の 3 つのみで、いずれも `getNum()` 経由。`SuggestIndexer` に件数 API は無い |

**G1 の判定位置は `0003` §4.3 の制御フローどおり `switchIndex()` の前である。その時点で検索エイリアスは旧世代を指したままである。**

### 1.1 字義どおり実装した場合の帰結 [確認]

| # | 帰結 |
| --- | --- |
| 1 | S1 直前に取る「旧世代件数」と S3 で取る「次世代件数」が**どちらも旧世代の件数**になる |
| 2 | 割合判定は**常に 100%** となり、既定 50% の下限に掛かることが原理的に無い |
| 3 | 「次世代の登録語数が 0 でないこと」も**旧世代について**判定する。**次世代が空でも合格する** |
| 4 | **G1 が無条件合格の no-op になる** — プラン A-3 の DoD「次世代件数 0 で切替が中止される」を満たせず、A-6 の T-S2 相当テストも書けない |

**したがってこれは実装上の細部ではなく、切替可否ガードの片方が機能しないという性質の欠陥である。** プラン §2.1 の区分表の「**設計どおり実装すると成立しない**」に該当する。

### 1.2 設計書が見落とした形 [推測]

**`0003` §4.2 は G2 について「更新エイリアスに対して実行する」と初版から明記している一方、G1 の行にはエイリアスの別が 1 語も書かれていなかった** [確認]。**エイリアスの指し先という論点は G2 を書くときにだけ意識され、G1 には及ばなかった**と見るのが自然である [推測]。

**本件は R0 で現行 API を流用することに固有の問題である。** R1 の To-Be（`lifecycle.wordCountStats()`）は次世代の統計を返す API であるため、この問題は消える [推測]（`0001` §2.2）。**`0003` 第 15 版 §10.1 の「R0 で G1 に現行 API を使うことは設計の妥協ではない」という記述が成立しない条件を突いている** — この記述は第 16 版で書き換えた。

## 2. 選択肢と決定 [確定]

**`0015` §3.4 が挙げた 3 案について、2026-09-04 にユーザーが (a) を採ることを決定した。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a)** | **fess 側で更新エイリアス（`suggester.getIndex() + ".update"`）に対して直接カウントする。** 件数取得は fess 側に閉じる | **採用** [確定]。**C-01（`modules/fess-suggest` 無変更）と MO-1（fess-suggest に高水準の再構築 API を置かない）を両方守れ、R0 のスコープ（`modules/fess` のみ）も守れる。** **DoD を緩めない** — 曲げるのは実装の側である |
| (b) | fess-suggest に更新エイリアス向けのカウント API を追加する | **却下**。**R0 =「fess 本体側の安全網のみ。fess-suggest は現行のまま変更しない」というリリース段の定義（`0003` §10.1 の R0 行）を破る。** R0 を fess 単独でリリースできなくなる |
| (c) | R0 では G1 を落とし、G3 のみで出す | **却下**。安全網が半分になるうえ、**実装可能な代替（(a)）があるのに DoD を緩めることになる**（`0007` §2.11 の 8 ／ `0010` §2.4 が確立した規律） |

### 2.1 (a) の代償と、その解消時期 [確認]

**更新エイリアスの命名規約（`index + ".update"`）を fess 側に複製する。** `getUpdateAlias` は `(sug) Suggester.java:459` の **private** であり参照できない [確認]。

- **複製している旨をコード側のコメントに明記し、R1 での撤去対象であることを示す。**
- **R1 で `lifecycle.wordCountStats()` へ移す際に解消される**（`0003` §10.1 の R0 / R1 差分表）。

### 2.2 (a) が成立する前提の確認 [確認]

**カウントは refresh 後の可視状態に依存する。G1 の判定時点で次世代が refresh 済みであることを実物で確認した**（`0015` §3.5 の再掲）。

| # | 事実 | 実物 |
| --- | --- | --- |
| 1 | **更新エイリアスは S3 の時点で必ず次世代インデックスを指している** | `(sug) Suggester.java:263`。`createNextIndex()` が S1 で実行される |
| 2 | 文書取り込み経路が `refresh()` を呼ぶ | `(fess) helper/SuggestHelper.java:295` |
| 3 | 検索ログ経路が `refresh()` を呼ぶ | 同 `:258` |
| 4 | 語管理経路（`ForRebuild`）の private 実装がループ外・末尾で `refresh()` を呼ぶ | 同 `:627` / `:677` / `:795` |
| 5 | **`refresh()` は `prepareRefresh()` を引数なしで発行するため全インデックスが対象になる** | `(sug) Suggester.java:176-180` |
