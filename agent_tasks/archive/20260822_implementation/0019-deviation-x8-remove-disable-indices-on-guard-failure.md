## 1. 何が問題か

### 1.1 MO-2 の第 16 版までの内容 [確認]

> **MO-2**: 切替可否ガードを `SuggestCreator.create()` に置く。`exitCode != 0` または検証不合格なら**切替と `removeDisableIndices()` を実行せずに終了する**

**初版以来、不合格時の行動は「切替」と「`removeDisableIndices()`」を 1 つに束ねていた。**

### 1.2 その束ね方が防いでいるもの [確認]

**D-b だけである**（`0003` §1.3）:

> **D-b**: **切替直後の `removeDisableIndices()` によるロールバック先の消失** — `switchIndex()` 直後の旧インデックスはエイリアス 0 個になる。同メソッドはそれを**無条件に物理削除**するため、**戻り先が同一実行内で消える**

**D-b は「切替が走った後」にしか成立しない** [確認]。

### 1.3 見落とされていた責務 [確認]

**`removeDisableIndices()` はもう 1 つの責務を担っている — 孤児インデックスの回収である。** 設計書は少なくとも 4 箇所でこの回収に依存している:

| 箇所 | 記述 |
| --- | --- |
| `0003` §2.4（中断状態表） | 「エイリアス 0 個の孤児インデックスが残る」→ 回収欄が「次回 `removeDisableIndices()` が回収」 |
| `0003` §2.4（復旧手順） | 「前回の中途インデックスは次回の `removeDisableIndices()` で回収される」 |
| `0003` §3.2（孤児インデックスの発生窓） | 「実害は次回 `removeDisableIndices()` まで残るディスク使用のみ」 |
| `0003` §3.2（`SuggesterException` の行） | 「次回実行で S1 からやり直せる。孤児は次回の `removeDisableIndices()` が回収する」 |
| `0003` §10.6.1.2 の 2 | 「孤児は `removeDisableIndices()` が回収する」 |

**そして `removeDisableIndices()` の呼び出し元は `(fess) exec/SuggestCreator.java` の 1 箇所しか無い** [確認]（`0003` §3.4 ／ §4.3 の根拠 1 ／ 本タスク `0003-deviation-x3-l1-interim-state.md` §3）。**したがって不合格時にこの 1 行を飛ばすことは、回収機構そのものを止めることと同義である。**

### 1.4 止めた場合に何が起きるか [確認]

**`createNextIndex()` は実行のたびに無条件で新しいインデックスを作り、更新エイリアスをそこへ移す**（`(sug) Suggester.java:235-267`）。

| # | 経過 |
| --- | --- |
| 1 | 1 回目の不合格 → 次世代インデックス **A** が更新エイリアスを持ったまま残る |
| 2 | 2 回目の実行 → `createNextIndex()` がインデックス **B** を作り更新エイリアスを B へ移す。**A はエイリアス 0 個の孤児になる** |
| 3 | 2 回目も不合格 → `removeDisableIndices()` は走らない → **A は回収されない** |
| 4 | 以降、**不合格が続く限り実行のたびに 1 つずつ孤児が増える** |

> **これは例外的な状況ではない** [確認]。**`0003` §4.2.2 は「不正行が 1 件でも残る間は運用者が直すまで世代を更新させない」ことを意図しており、その意図どおりに動いている間がまさにこの状況である。** 日次ジョブ（`0 12 * * *`）なら 1 日 1 インデックスずつ増える。

**影響の見積もり** [推測]: **ディスクの単調増加**である。suggest インデックスは `number_of_shards: 1` で通常は小さいが、放置期間に比例して増える。**シャード数の上限（既定 1000/ノード）に達すればクラスタ全体のインデックス作成が止まるため、影響は suggest 機能に閉じない。**

## 3. 採った案と採らなかった案

| 案 | 内容 | 区分 | 判定 |
| --- | --- | --- | --- |
| **A（採用）** | **ガード不合格時も `removeDisableIndices()` を実行してから `return` する。** MO-2 を改訂する | **区分 I** | **採用**（2026-09-07・ユーザー判断） |
| B | 現状維持のまま `0003` の「次回回収される」記述 4 箇所に条件を書き足し、運用周知（ガードが落ち続ける間はディスクを監視する）に載せる | 区分 II | **却下** |
| C | B を R0 で実施し、A は R1 の後続タスクへ送る | 区分 II ＋ 申し送り | **却下** |

**B / C を却下した理由** [確定]: **回収されないこと自体に運用者の手当ての手段が無い。** `removeDisableIndices()` を単独で叩く経路は fess の管理画面にも API にも存在せず（呼び出し元は `SuggestCreator` の 1 箇所のみ [確認]）、運用者にできるのは孤児インデックスを OpenSearch へ直接 `DELETE` することだけである。**周知は問題を運用者へ移すだけで解かない。** 加えて **§4 のとおり是正の実体は 1 行の移動であり、リスクとコストが釣り合わない。**

## 4. 不合格時に実行しても安全である根拠 [確認]

| # | 根拠 | 一次情報 |
| --- | --- | --- |
| 1 | **削除判定は「エイリアスを 1 つも持たない suggest インデックス」である** | `(sug) Suggester.java:338-359`（`isSuggestIndex(s)` かつ `getAliases().get(s)` が `null` または空） ／ `0003` §1.4 |
| 2 | **ガード不合格の時点で `switchIndex()` は実行していない。** したがって**検索エイリアスは旧世代を、更新エイリアス `{baseIndex}.update` は次世代を指したままである** | `(fess) exec/SuggestCreator.java` のガードは `switchIndex()` より前にある ／ `createNextIndex()` は更新エイリアスだけを付け替える（`(sug) Suggester.java:263`） |
| 3 | **旧世代・次世代のどちらもエイリアスを持つため削除対象にならない。** R1 では 2 世代前が `.prev` を持つため同じく対象外である | `0003` §5.1 |
| 4 | **D-b は成立しない。** D-b は「`switchIndex()` 直後に旧世代がエイリアス 0 個になること」を前提とする障害であり、切替を飛ばした状態ではその前提が無い | `0003` §1.3 の D-b |

> **回収は同一実行内で完了する** [確認]。§1.4 の経過 2 の時点で A は既に孤児であるため、**2 回目の不合格時の `removeDisableIndices()` が A を回収する。** **不合格が続いても孤児は常に高々 0 個で安定する。**

### 4.1 判定不能（`SuggestAliasStateUnknownException`）との境界 [確定]

**本件は `SuggestAliasStateUnknownException` の経路には及ばない。そちらでは従来どおり `removeDisableIndices()` を呼んではならない**（`0003` §12 の K-18 ／ §11.1 の **T-S12**）。

**理由**: §4 の根拠 2 が成立しない。**切替が適用されたかどうかが確定していないため、エイリアス 0 個の世代がロールバック先でありうる。**

> **この境界は `0018` が提示していない論点である** [確認]。**`0018` §2.4 は「G3 / G1 不合格でも `removeDisableIndices()` は実行してから `return` する」と一般形で提案していたが、`0003` は T-S12 / K-18 として「呼んではならない経路」を別に持っている。** 一般形のまま実装すると T-S12 と矛盾する。**本書はこれを 2 つの排他な経路として分離した。**

**2 つの経路が排他であることの確認** [確認]:

| 経路 | 送出元 | `create()` のどこを通るか |
| --- | --- | --- |
| **ガード不合格** | ガード判定そのもの | ガード判定に到達し、`switchIndex()` へは進まない |
| **判定不能（S1）** | `createNextIndex()` | **ガードより前**で `create()` を抜ける（R0 では例外が `main()` の `catch (Throwable)` まで伝播する — `(fess) exec/SuggestCreator.java:197`） |
| **判定不能（S4）** | `switchIndexRetainingPrevious()`（R1） | **ガードを通過した後**で抜ける |

> **「ガードが不合格を返した」という状態と「エイリアス状態が判定不能である」という状態が同時に成り立つことはない** [確認]。
