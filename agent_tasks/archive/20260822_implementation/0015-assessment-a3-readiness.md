## 3. ブロッカー: G1 の「次世代件数」は `getAllWordsNum()` では取得できない [確認]

### 3.1 事実

プラン §4 ステップ A-3 の作業内容 2 と `0003` §4.2 の G1 行は、**旧世代と次世代の件数を同じ `suggester.getAllWordsNum()` で取れ**という前提で書かれている（`0003` §4.2 の取得方法欄 = 「`(fess) helper/SuggestHelper.java:340`（`getAllWordsNum()`。To-Be は `lifecycle.wordCountStats()`）。**旧世代の件数は S1 の直前に取得して保持する**」）。

**この API は検索エイリアスしか見ない** [確認]:

| # | 事実 | 実物 |
| --- | --- | --- |
| 1 | `getAllWordsNum()` は `getNum(matchAllQuery())` へ委譲する | `(sug) Suggester.java:424-426` |
| 2 | **`getNum()` は `setIndices(getSearchAlias(index))` で検索する** | `(sug) Suggester.java:444-453`（`:446`） |
| 3 | **検索エイリアスは素のインデックス名、更新エイリアスは `index + ".update"` である** | `(sug) Suggester.java:455-457` `getSearchAlias` ／ `:459-461` `getUpdateAlias` |
| 4 | **`createNextIndex()` は更新エイリアスだけを新インデックスへ付け替え、検索エイリアスには触れない** | `(sug) Suggester.java:235-268`（`:263` で新インデックスへ `addAlias`、`:265` で旧インデックスから `removeAlias`。いずれも `getUpdateAlias(index)`） |
| 5 | **次世代への書き込みは更新エイリアス経由である** | `(sug) Suggester.java:408` `indexer()` が `getUpdateAlias(index)` を渡す |
| 6 | **検索エイリアスが次世代を指すのは `switchIndex()` の後である** | `(sug) Suggester.java:282-` |
| 7 | **更新エイリアス側を数える API は fess-suggest に存在しない** | `getAllWordsNum` / `getDocumentWordsNum` の 2 つのみ（いずれも `getNum()` 経由）。`SuggestIndexer` に件数 API は無い [確認] |

**G1 の判定位置は G3 の後・`switchIndex()`（`:301`）の前である**（`0003` §4.3 の制御フロー図 ／ プラン作業内容 2）。**その時点で検索エイリアスはまだ旧世代を指している。**

### 3.2 帰結

**設計どおりに実装すると G1 が無条件合格の no-op になる** [確認]:

| # | 帰結 |
| --- | --- |
| 1 | S1 直前に取る「旧世代件数」と S3 で取る「次世代件数」が**どちらも旧世代の件数**になる |
| 2 | 割合判定は**常に 100%** となり、既定 50% の下限に掛かることが原理的に無い |
| 3 | 「次世代の登録語数が 0 でないこと」も**旧世代について**判定してしまう。**次世代が空でも合格する** |
| 4 | **プラン A-3 の DoD「次世代件数 0 で切替が中止される」を満たせない**。A-6 の T-S2 相当テストも書けない |

**したがってこれは実装上の細部ではなく、A-3 の DoD を 1 件閉じられなくする性質の欠陥である。** プラン §2.1 の区分表の「**設計どおり実装すると成立しない**」に該当し、**区分 I の逸脱として発火する見込みである** [提案]。**X 番号の採番と `0003` の改訂は、§3.4 の方針が決まってから行う**（プラン §2.1 の手順「版を上げて改訂 → 独立ファイルで記録 → **その後で実装**」）。

### 3.3 設計書が見落とした形 [推測]

**`0003` §4.2 は G2 について「更新エイリアスに対して実行する」と明記している一方、G1 の行にはエイリアスの別が 1 語も書かれていない** [確認]。**エイリアスの指し先という論点は G2 を書くときにだけ意識され、G1 には及ばなかった**と見るのが自然である [推測]。

**R1 の To-Be（`lifecycle.wordCountStats()`）ではこの問題は消える** [推測] — `0001` §2.2 の `SuggestIndexLifecycle` は次世代の統計を返すことが前提の API だからである。**本件は R0 で現行 API を流用することに固有の問題であり、`0003` §10.1 の「R0 で G1 に現行 API を使うことは設計の妥協ではない」という記述（同 `:859`）が成立しない条件を突いている。**

## 4. 作業内容 3「旧世代不在の初回」の実際の形 [確認]

**プランの表現（「旧世代不在」）を字義どおり実装してはならない。**

- **`createIndexIfNothing()` は `SuggestHelper` の初期化時に呼ばれる** [確認]（`(fess) helper/SuggestHelper.java:155`）。**同メソッドは検索エイリアスと更新エイリアスの両方を同一の新インデックスへ付ける**（`(sug) Suggester.java:215-216`）。
- **したがって `SuggestCreator` が動く時点で検索エイリアスは必ず存在する。** 「旧世代のインデックスが無い」という状態は通常経路では起こらない。
- **初回に実際に起こるのは「検索エイリアスは存在するが件数が 0」である。**

**帰結**: 作業内容 3 は **「S1 直前に取得した旧件数が 0 なら割合判定を適用しない（`0` でないことの検査だけを行う）」** として実装するのが正しい [提案]。**エイリアスの存在検査を入れる必要は無い。**

## 5. A-3 の中で明示的に決める必要がある事項（ブロッカーではない）

**`0007` §2.11 の 11（`0014` §2.2 ／ 3 回目レビューの指摘 2）を A-3 の作業内容 5 の中で処理する必要がある** [確認]。

- `deleteOneElevateWordRow` は**正規化キーと生キーで 2 回の削除を発行する**。**2 回目は A-1 / MO-24 が入れた移行期クリーンアップであり、行データの妥当性とは無関係である。**
- **発火経路**: `(sug) index/operations/WordManagementOperations.java:127` の `settings.elevateWord().delete(...)` が `try` の外にあるため、`SuggestSettingsException` が `deleteOneElevateWordRow` の外へ伝播し、その行が `failedIds` に入る [確認]。writer 層は `(sug) index/writer/SuggestIndexWriter.java:83-91` で例外を握るため寄与しない [確認]。
- **論点**: `0003` §4.2.2 の「不正行を運用者が直すまで世代を更新させない」という意図は**正規化キー側の失敗にしか合わない**。生キー削除の失敗まで世代切替の阻止へ昇格させるかを、A-3 が明示的に判断する。
- **発火確率は低い**（設定インデックスへの書き込み障害時に限られる）[推測]。**A-2 の実装バグではない**（MO-25 の規則 1・3 のとおり動いている）。
