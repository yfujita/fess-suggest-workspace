## 5. 指摘 4 — `mvn -o compile` の食い違いを実測で解消した

### 5.1 食い違いの内容

| 文書 | 記述 |
| --- | --- |
| プラン **F-5** の作業内容 3 | **`mvn -o compile` ＋ `mvn -o test`**（オフラインを明示的に要求） |
| `0004` **§1.4 の 2** | 0-1 で `-o` が失敗したため `-o` を外した。**「以降のフェーズでの fess 側検証も `-o` を前提にしない」** |

**`-o` を外した 0-1 の判断自体は正しい**（失敗理由は依存の未取得であって fess 側の問題ではない）。**残っていたのは「では F-5 の `-o` はどうするのか」が未決だったことである。**

### 5.2 実測

**レビューの「一度 `mvn -o compile` を再実行してしまうのが一番簡単」に従い、実行した。**

```
cd modules/fess && mvn -o compile
  → BUILD SUCCESS / EXIT=0 / Total time: 40.455 s / Warnings: 0, Errors: 0
  （2026-08-31 06:03 ／ ブランチ feature/suggest-l1-precede ／ 作業ツリー clean）
```

**結果: 通った** [確認]。**0-1 時点の失敗はオンライン取得前であったことが原因と確定した。** `0004` §1.4 の 2 が [要確認] としていた「オンラインで 1 回取得した後は `-o` でも通る見込み」は**実測で裏づけられた。**

### 5.3 決めたこと

> **`-o` は再現性のための既定として使う。ただし DoD は「ビルドが成功すること」であって「オフラインで成功すること」ではない。**

**新たな依存が upstream に入って `-o` が失敗した場合は `-o` を外して実行してよく、その旨を作業履歴に記録する。** 0-1 で起きたのはまさにこれであり、**同じ状況が F-5 で再発したときに判断で止まらないよう、プラン側に明文化した。**
