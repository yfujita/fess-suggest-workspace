## 3. 指摘 2（High）— WordAdmin の部分適用と収束

### 3.1 指摘の検証 [確認]

**レビューは「記載された二段更新から導いた設計上の推論」と自己申告しているが、推論は正しい。**

- `docs/0001` §3.5.1 の手順表が明示的に 2 段（`policy.remove(word)` → `store.updateExcluded(...)`）である。
- `BadWordPolicy.add` / `remove` の Javadoc に「集合の更新と再読み込みを内包する」とあり、**設定インデックスへの書き込みを含む**。
- 第 5 版 `docs/0001` §4.2 の契約は「設定更新失敗・更新クエリ失敗 → `SuggesterException`」までであり、**部分適用状態への言及が無い**。
- `docs/0002` DM-18 は `excluded == true` の意味を「現在の bad word 集合のいずれかに該当する」と定義しており、**2 段目の失敗はこの同値関係を破る**。

**これは elevate word 側（`addElevateWord` / `deleteElevateWord` / `restoreElevateWords`）にも同じ形で存在する** — レビューは bad word だけを挙げていたが、契約は 7 メソッド全体に及ぼした。

### 3.2 採った方針

**レビューの提案（再実行可能・収束型）をそのまま採った。** 分散トランザクションも補償トランザクションも採らない。

> **`SuggestWordAdmin` の全メソッドは、同一引数での再実行が安全であり、かつ収束する。**
> **前段は「その状態にする」（既にその状態でも成功する）**、**後段は呼び出し時点の bad word 集合から条件を再計算する。**
> **後段が失敗した場合、操作は部分適用状態になりうる。同一操作の再実行により正しい状態へ収束する。**

**収束が成立する理由は、2 段目の入力が「1 段目で何が変わったか」ではなく「現在の bad word 集合」だからである。** `releaseCondition(removed)` の定義（§3.5.1）がまさにそれであり、**D-25 の是正が結果的に収束性の前提を作っていた**。今回の作業は、その性質を契約として書き出したものである。

**補償トランザクション（2 段目失敗時に 1 段目を巻き戻す）を採らなかった理由**: 巻き戻し自体が同じ 2 段問題を持ち（巻き戻しが失敗したらどうするか）、状態が増えるだけである。収束型は「壊れた状態が残らない」ことは保証しないが、「同じ操作を繰り返せば直る」ことは保証する。**運用手順として書けるのは後者だけである。**

### 3.3 反映内容

| 変更先 | 内容 |
| --- | --- |
| `docs/0001` §0 | **D-29** を新設 |
| `docs/0001` **§2.3.1（新設）** | 2 段書き込みの一覧・破れる不変条件・収束表・却下した代替案 |
| `docs/0001` §3.5 | `BadWordPolicy.add` / `remove` の Javadoc に「既にその状態なら何もせず成功する」を明記 |
| `docs/0001` §3.5.1 | 手順表の直後に部分適用と収束の注記を追加 |

**順序（設定更新 → インデックス反映）は変えていない。** `releaseCondition` が削除後の集合を必要とするためであり（§3.5.1）、**結果として「設定だけ進んだ」方向の部分適用しか起きない**。逆順にすると「除外されるべき語が一時的に検索に出る窓」と「集合更新失敗時に解除だけが残る」の両方が生じる。この非対称は意図したものである旨を §2.3.1 に明記した。

## 4. 指摘 3（Medium）— `SuggestSource.kind()` の削除

### 4.1 指摘の検証 [確認]

第 5 版の形では次が書けてしまう。

```java
class FooSource implements SuggestSource<X> {
    Kind kind() { return Kind.DOCUMENT; }                                    // 宣言
    Stream<SuggestCandidate> produce(X in, SourceContext ctx) {
        return Stream.of(SuggestCandidate.document(..., Set.of(Kind.QUERY))); // 実値
    }
}
```

**第 5 版の `docs/0001` 全体を検索したところ、`source.kind()` を読む記述は 1 つも存在しなかった** [確認]（`kind()` の出現は IF 定義・§3.1 の C-11 注記・§8.2 の MIG-19 行の 3 箇所のみで、いずれも「持っている」と書いているだけである）。**削除しても失われる情報が無い。**

### 4.2 3 案の比較と採否

| 案 | 判定 |
| --- | --- |
| **(A) `kind()` を削除し Candidate を唯一の正とする** | **採用。** `SuggestCandidate` は D-19 で「それ自体で完結した更新の意思」として定義された型であり、Kind もその一部である。レビューも「現在の設計思想なら一番自然」としていた |
| (B) `kind()` を正とし `indexFrom` が Kind を付与する | 却下。**1 ソースが複数 Kind を供給できなくなる**。MIG-19（同義語/関連語）は将来 `QUERY` と `DOCUMENT` の両方を返しうる |
| (C) 両方残し `indexFrom` が一致を検査する | 却下。冗長な宣言を残したまま実行時検査を足すだけで、同じ情報を 2 箇所に書く状態は解消しない |

### 4.3 反映内容

| 変更先 | 内容 |

| `docs/0001` **§3.1.2（新設）** | 二重の権威の具体例・3 案の比較・`deleteByKind` / `WordCountStats.byKind` が影響を受けない理由 |

## 6. V7（文書間整合）の再発と検査手順の追加

**3 回連続で V7 の取りこぼしが Blocker になった。ただし今回は前 2 回と型が違う。**

| 回 | 型 | 検出手順 |
| --- | --- | --- |
| 第 1・2 回 | **手順書が要求する操作が、公開契約に存在しない** | `../0016` §5 が追加した逆引き検査で検出できる |
| **第 3 回** | **手順書と公開契約が同じ規則を主張しているのに、適用対象の列挙が食い違う** | **上記では検出できない**（`createNextIndex()` は公開契約に存在する） |

**追加する検査手順**:

> **規則を導入したときは、その規則が適用されるべき対象を全列挙したことを確認する。**
>
> 1. 導入した規則の**適用条件**を 1 文で書く（例: 「下位に aliases request を発行するメソッド」）。
> 2. その条件に**当てはまる公開メソッドを、規則の記述とは独立に列挙する**（IF 定義から機械的に拾う）。
> 3. 規則の対象リストと 2 の列挙を突き合わせる。**差分があれば、対象外とする理由を明記するか対象に含める。**
> 4. 他文書が同じ規則に言及している箇所（「この規則は〜にも適用する」形の文）を grep し、**対象リストが一致することを確認する。**

**今回の Blocker は手順 4 だけで検出できた** — `0003` が「S1 にも適用する」と書いている一方で `0001` の対象リストに S1 が無い、という食い違いである。
