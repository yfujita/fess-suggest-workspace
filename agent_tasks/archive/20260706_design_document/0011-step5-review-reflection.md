## 2. 指摘 1 — 人気語経路の除外フィルタ

### 2.1 検証（コードを実読した結果）[確認]

**指摘は成立する。** `request/popularwords/PopularWordsRequest.buildQuery()`（`:210-235`）は suggest 本体インデックスを読む第 2 の検索経路であり、初版の `0002` §6.2 は `request/suggest/SuggestRequest.java:346` しか定めていなかった。

MIG-13 は物理削除を論理除外に置き換える（C-02）ため、**除外された語はドキュメントとして残存する**。人気語側にフィルタが無ければ、`queryFreq` の高い bad word がそのまま人気語として露出する。**現行（物理削除）では起きない事象が、MIG-13 の適用によって新たに生じる**ため、これは移行に伴う退行にあたる。

### 2.2 選択肢 (b)（既存の `excludeWords` 機構で足りる）を却下した根拠 [確認]

指摘は 2 案を提示していた。**(b) は成立しない**ことをコードで確定した。

`PopularWordsRequest` には既に除外機構がある。

| 位置 | 内容 |
| --- | --- |
| `:87` | `private final List<String> excludeWords = new ArrayList<>();` |
| `:165-166` | `addExcludeWord(String)` |
| `:229-230` | `if (!excludeWords.isEmpty()) { queryBuilder.mustNot(QueryBuilders.termsQuery(FieldNames.TEXT, excludeWords)); }` |

**却下の理由 1: 判定意味論が違う。** `:230` は `termsQuery(TEXT, ...)` による**完全一致**である。bad word の意味論は**正規化後テキストの部分一致**であり（C-02 / `0001` §3.5 の D-6、原典は `improvement-proposal.md:380` / `:499` / `:211` / `:132`）、完全一致では bad word を部分文字列として含む語を捕まえられない。**`excludeWords` を bad word で埋めても、部分一致すべき語が人気語に残る。**

**却下の理由 2: 語の集合が違う。** `excludeWords` に積まれるのは fess の静的プロパティ `suggest.popular.word.excludes`（`(fess) mylasta/direction/FessConfig.java:1732`）を `(fess) helper/PopularWordHelper.java:104`（`getSuggestPopularWordExcludesAsArray()`）→ `:118`（`addExcludeWord` のループ）で展開したものであり、**管理画面が管理する bad word 集合とは無関係**である。両者を混ぜると、`BadWordPolicy` が bad word 集合の唯一の所有者であるという `0001` §3.5（D-7）の設計が崩れる。

> **`excludeWords` は廃止せず、現行の用途（人気語表示から特定の語を静的に外す）のまま残す。** MIG-13 の論理除外とは目的が異なる独立した機構である。この点も `0002` §6.2 に明記した。

### 2.3 反映内容: (a) を採り DM-14 を一般化した

指摘の推奨どおり (a) を採った。**DM-14 の理由づけ（旧世代共存における否定形必須）はそのまま第 2 の経路にも適用できる**ためである。

`0002` §6.2 に次を追加した。

1. **適用範囲の宣言**を「suggest 本体インデックスを読む**すべての**クエリ経路」に一般化。
2. **経路が 2 つしかないことの確認** [確認]: `request/` 配下の実装は `request/suggest/` と `request/popularwords/` の 2 系統のみである。**「すべて」が有限で列挙可能であることを示さないと、一般化した宣言が検査できない。**
3. **組み込み位置の表**: `SuggestRequest.java:346`（`filterList`、合成は `:370`）と `PopularWordsRequest.java:211-235`（トップレベル `BoolQueryBuilder`。`:213` の `mustNot(existsQuery("reading_1"))` と並ぶ位置）。
4. **(b) を却下した根拠**（§2.2 の 2 点）。
5. `0002` §0 の **DM-14 の行を書き換えた**。

### 2.4 `previewBadWordImpact` の件数の定義

指摘の後段（「`matchCondition` と `excluded` の合成として一行定義しておくと実装の迷いが消える」）に応じ、次を `0002` §6.2 に定めた。

> **`BadWordImpact.matchedCount`（`0001` §3.2）は `BadWordPolicy.matchCondition(word)` に一致する全ドキュメントの件数であり、`excluded` の現在値では絞り込まない。** すなわち他の bad word によって既に `excluded = true` になっている語も件数に含む。

**根拠 1（設計上の強制）**: `matchCondition` は「`excluded` の付与・解除とドライランが共有する」条件である（`0001` §3.5 の Javadoc、`0001:491`）。**解除（`true` → `false`）は既に `excluded = true` の語を対象にするため、条件そのものに `excluded` の絞り込みを含めると解除経路が動かない。** これは選好ではなく、`0001` が定めた共有の帰結である。

**根拠 2（意味の妥当性）**: 「この bad word を適用すると何語が除外されるか」の答えは、その bad word が支配する語の総数である。既に除外済みの語を数から外すと、bad word を 1 つ削除したときに何が戻るかが分からなくなる。総数であれば **bad word の追加順序に依存せず冪等**である。

**内訳（「うち新たに `false` → `true` に変わるのは何件か」）は設けない。** 設けるなら `BadWordImpact` にフィールドを足すことになり、`0001` §3.2 の改訂にあたるためである。この線引きも本文に書いた。

## 3. 指摘 2 — `userBoost` の「指定あり／なし」は公開契約に波及する

### 3.1 検証 [確認]

**指摘は成立する。** 初版の申し送り 5 は型選択（`Double` の null 許容 / `OptionalDouble`）を実装判断としていたが、**「指定なし」を作る手段は `entity/SuggestItem` の公開コンストラクタ経路に現れる**。

- コンストラクタ（`entity/SuggestItem.java:113-141`）は `final float userBoost` を受け取り、`:131-135` で「1 以下なら 1」に丸める。
- パーサ経路（`index/contents/DefaultContentsParser.java:107-108`, `:144`）はここに `-1` を渡す（＝センチネル）。
- `entity/ElevateWord.java:147` は `getBoost()` を渡す（＝指定あり）。

**センチネル `-1` を廃止するには、コンストラクタのシグネチャを変えるか、生成 API を分けるしかない。** `float` のままでは「指定なし」を型として表現できない。

**`SuggestItem` は `0001` の公開契約に含まれる型である** [確認]。`0001` §2.2 の `bulkUpsert(List<SuggestItem> items, SuggestItemMergePolicy policy)`（`0001:183`, `:631`）と §3.4 の `initialize(SuggestItem)` / `merge(SuggestItem, SuggestItem)`（`0001:461-467`）に現れる。したがって型表現の変更はライブラリ利用者に見える。

### 3.2 反映内容

`0002` §9 の申し送り 5 を書き換え、**引き継ぎ先を「実装タスク」から「ステップ 7（`0001` の改訂として決定し、`0000` §8.2 の着地確認表に反映）」へ格上げした。** 本文に上記の経路（パーサ側＝指定なし / elevate word 側＝指定あり）と、`SuggestItem` が公開型である根拠を明記した。

> **本書（`0002`）は挙動の正であって公開契約の正ではない**（`0001` §3.4 / D-8）。DM-11 が要求する表現力を満たす型を決めるのは `0001` の職務である。初版はこの境界を踏み越えて「実装判断」と書いていた。

## 4. 指摘 3 — INV-1 強制と `ElevateWord` 修正のコードレベルの同時性

### 4.1 検証 [確認]

**指摘は成立する。** 初版の `0002` §4.7 は「同一の再構築に束ねる 4 変更」として**データ移行**の束ねを定めていたが、**コード変更の順序制約**は書いていなかった。

`0009` §5.2 の★は順序依存を指摘していたが、その前提（`ElevateWord` の正しい修正形）自体が本ステップで覆っている（`0010` §3）。**訂正の過程で順序制約そのものが落ちていた。**

制約の内容: 現行の `entity/ElevateWord.java:143-149` は k ≠ W のとき INV-1 を破る。**コンストラクタでの強制だけを先行させると、読みトークン数と語数が食い違う elevate word の登録が実行時にすべて失敗する。** `(fess) helper/SuggestHelper.java:464-487` は管理画面の「読み」入力を空白分割して渡すだけであり、k ≠ W は実運用で普通に発生する。

### 4.2 反映内容

3 箇所に入れた。

1. **`0002` §5.2 に注記を新設**（強制場所の指定の直後）。**「1 回の再構築に載せる」話（§4.7）と「1 回のリリースに入れる」話は別である**ことを明示的に書き分けた。両者を混同すると、移行手順だけ守ってリリースを分割する事故が起きうる。
2. **T-4 の前提**に「§5.4 の `ElevateWord` 修正が同一リリースに入っていること」を追記。
3. **申し送り 7b を新設**（引き継ぎ先: `0003` のリリース手順 ／ 実装タスク）。
