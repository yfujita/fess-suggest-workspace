### 2.1 指摘 1 — D-6 の差し戻し（完全一致 → 部分一致）

#### 検証（提案書を実読した結果）[確認]

指摘のとおり、提案書は部分一致の維持を**要件レベルの前提**として 4 箇所で明記している。

| 位置 | 記述 |

| 同 `:499` | §5.2 の [確定] 行の前提節: 「**部分一致は要件どおり維持（全て bad word 扱い）を前提に**」 |
| 同 `:211` | Q3: 「**部分一致（要件どおり全て bad word 扱い）を維持したまま**、不可逆な巻き添え物理削除を可逆な論理除外に置換。マッチ実装の二重化も解消」 |
| 同 `:132` | ISS-04 本文: 「※**部分一致自体は要件上「意図した挙動」であり課題ではない**」 |

**`0007` §2.5 に記録した完全一致化の判断は誤りであった。** ISS-04 が課題と認定したのは (a) 不可逆性、(b) `contains`/`wildcard` 二重化に伴う保守負担とメタ文字誤爆であって、部分一致という判定意味論ではない。設計書の職務は MIG-03 を実装することであり、その定義を再解釈することではない。判定意味論を変えるなら提案書側の訂正（E 番号の起票）とユーザー判断が要る。

**内容面でも `0007` §2.5 / 旧 §3.5 の論拠は自壊していた**（レビュー指摘のとおり）:

- 旧理由①は「不可逆な巻き添えを排除する安全側」を根拠にしていたが、旧理由③が自ら認めるとおり **C-02 により適用は既に可逆（`excluded`）**であり、fess 経路では物理削除がそもそも発火しない（`improvement-proposal.md:132`、F-07）。**不可逆性の危険は完全一致化しなくても既に消えている。**
- 一方で完全一致化は**偽陰性**（不適切語を部分文字列に含む複合語の露出）を新たに生む。bad word では偽陰性のほうが偽陽性（可逆な巻き添え除外）より明確に悪い失敗モードである。
- 旧理由②「複数登録で表現できる」は、複合語が無限に生成される日本語では実用的な代替にならない。

#### 反映内容

**1. D-6 の行**（§0）

> bad word の判定意味論を**正規化後テキストの部分一致 1 つ**に統一する（提案書の [確定] 前提を維持）。`BadWordPolicy` が唯一の所有者となり、取り込みフィルタとストア問い合わせ条件の両方を同一クラスから導出する。**メタ文字のエスケープを規則内に必須化する**

### 2.3 指摘 3 — future 完了スレッドの契約

**検証**: 指摘のとおり、§4.4 は `Executor` を構築時注入と定めただけで「どのスレッドが future を完了させるか」を規定していなかった。§9.2 の `:294-297` の旧置換例 `.thenAccept(r -> { refresh(); success.accept(true); })` の `refresh()` は、同じ §9.2 の `:538-539` の行の置換により**内部で `lifecycle.refresh().join()` する**。実装がトランスポートスレッド上で future を完了させると、そのスレッドがブロックされる。

#### 採った方針: (a) と (b) の**両方**を課す

レビューは (a)（実装契約）か (b)（fess 側を `*Async` に統一）のどちらかを選べとしたが、**片方だけでは不十分であるため両方を採った**。理由を §4.4.1 として新設した。

- **(a) だけでは不十分**: (a) を守っても、`thenAccept` で登録した継続は完了スレッド＝**ライブラリの `ExecutorService` 上**で走る。そこで同一プールの別操作を `join()` すればプール枯渇の可能性が残る（プールサイズが小さいほど危険）。
- **(b) だけでも不十分**: 呼び出し側の規律に依存するため、規律が破れたときの被害が「アプリのスレッドが 1 本止まる」ではなく「**ライブラリ全体が止まる**」になる。

§4.4 の表に 2 行を追加した。

| 項目 | 契約 |
| --- | --- |
| **完了スレッド（実装契約）** | 実装は基盤のトランスポート／コールバックスレッド上で future を完了させてはならない。必ず構築時に受け取った `ExecutorService` へディスパッチしてから `complete` / `completeExceptionally` する |
| **継続内でのブロック（呼び出し側契約）** | 継続の中で `join()` を呼ばない。待ち合わせが必要なら `thenCompose` で合成するか、呼び出し側の `Executor` を明示した `*Async` を使う |

#### §9.2 の置換例を契約適合に修正

`join()` を継続内で呼ばない形（`thenCompose` による合成）に変えた。**`refresh()` の呼び出し自体を継続から外している**ため、(b) の契約に適合する。

| 位置 | 修正後 |
| --- | --- |
| `(fess) helper/SuggestHelper.java:294-297` | `.thenCompose(r -> lifecycle.refresh()).thenAccept(v -> success.accept(true)).exceptionally(t -> { error.accept(unwrap(t)); return null; })` |

`(fess) helper/SuggestHelper.java:294-297` は `.then(response -> { refresh(); success.accept(true); }).error(t -> error.accept(t))` であること、`:295` が `refresh()` であることを実ファイルで再確認した [確認]。§9.2 の当該行に「**継続の中で `join()` を呼ばない**（§4.4 / §4.4.1）ため、`thenCompose` で合成する」という理由も併記した。

なお `(fess) helper/SuggestHelper.java` の他の置換箇所（`:314,331` / `:340-358` / `:367-397` / `:438-450` / `:482-493` / `:509-531` / `:155`）はいずれも**継続の中ではなく同期メソッドの本体で `join()` する**形であり、(b) の契約に違反しない [確認]。§9.3 / §9.4 の `join()` も同様に継続外である。

### 2.4 指摘 4 — `promise()` の追記漏れ
