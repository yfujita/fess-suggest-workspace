改善提案ドキュメント群では、OpenSearch/Lucene の数値バージョンが「未解決（**TBD-01 [要確認]**、`fess-parent:15.7.0` 依存でワークスペース外ゆえ断定不可）」という前提で多くの記述がなされていた。**OpenSearch のバージョンが 3.7.0 で確定した**という事実を反映し、以下3ファイルの TBD-01 関連記述を「バージョン未確定前提」から「OpenSearch 3.7.0 で確定（[事実]）」へ更新した。

既存の記法（[事実]/[提案]/[要確認] 凡例、ISS/TBD/MIG 番号体系、トーン・表構造）は踏襲。確定した事実は [事実] ラベルで扱った。

## OpenSearch 3.7.0 での各 API 可否の技術的判断（更新の根拠）

3.7.0 は 2026 年リリースの新しめのバージョン。WebSearch で 3.7.0 のリリースノート・k-NN/neural-search プラグインの 3.7.0 リリースを確認し、下記のとおり主要 API はいずれも利用可能と判断した。

| API / 機能 | 3.7.0 での可否 | 根拠 |
| --- | --- | --- |
| `scripted_upsert`（Update API） | **利用可** | Elasticsearch 初期から続く Update API の標準機能で、全 OpenSearch 系に存在。バージョン起因の可否問題はない。慎重理由は「バージョン」ではなく **Painless スクリプトの複雑度** |
| `script_score` / `function_score` / `rescore` | **利用可** | コア Query DSL。全バージョンで利用可 |
| Painless スクリプティング | **利用可** | 標準スクリプトエンジン |
| `knn`（ベクトル/セマンティック） | **利用可** | 3.7.0 の k-NN プラグインは成熟（バイナリ base64 docvalue、1-bit スカラー量子化、KNN 検索タイムアウト、SQL Vector Search 等の改良を含む）。残る要件は API 可否ではなく **埋め込みモデル/推論基盤の用意・容量・QPS 別レイテンシ** |
| `fuzzy` | **利用可** | コア Query DSL。要調整は方式・誤補正率であってバージョンではない |

→ 結論: **TBD-01（バージョン未確定）が閉じるだけでなく、TBD-01 に依存していた API 可否の要確認がすべて解消**。残る不確実性は「バージョン可否」から「script 複雑度・埋め込み基盤・実測（負荷試験/A/B）」へ移動した。

## フォールバック経路（multiGet）の要否整理

`scripted_upsert` が確定的に利用可能となったため、「`scripted_upsert` が使えない場合の代替」というバージョン起因のフォールバック理由は消滅した。ただし **MIG-15 を「第1段=multiGet／第2段=scripted_upsert」の段階構成にする価値はバージョンと無関係に残る**旨を明記した:

- `scripted_upsert` は Painless script が複雑化しやすい。低リスクの multiGet で往復削減の大半（N回 Get→1回）に到達してから原子的集約へ進む方が安全。
- 可用性・後方互換の観点でも multiGet 経路の保持は無駄にならない。

## Phase 0（技術検証 PoC）の位置づけ見直し

「バージョン未確定を閉じる目的の PoC」は不要になったため、**Phase 0 を「技術検証」から「性能・実現性検証（任意）」へ改称**し、目的を下記へ差し替えた:

- `scripted_upsert` の script 挙動・実スループット（multiGet 比）の実測
- セマンティック(`knn`)の QPS 別レイテンシ・容量の実現性検証

これらは Phase 3（性能）・Phase 4（新機能）の設計判断材料として残る別目的である。
