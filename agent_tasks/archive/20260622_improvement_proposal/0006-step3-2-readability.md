## 1. 「可読性」の評価軸の定義（何をもって"読めばわかる"とするか）

可読性を抽象論で終わらせないため、本書では「読めばわかる」を次の5つの具体的な評価軸に分解する。各設計判断は「どの軸で読み手の理解を助けるか」で評価する。

| # | 評価軸 | 定義（"読めばわかる"の具体） | 主に効く現行課題 |
| --- | --- | --- | --- |
| **R1** | **公開面の小ささ（Minimal Surface）** | 公開 API を見ただけで「何ができるモジュールか」「どこを読めば目的の機能に辿り着くか」が分かる。読むべき範囲が狭い。 | ISS-13, ISS-17 |
| **R2** | **単一の真実（Single Source of Truth）** | ある規則（マージ・ランキング・権限）の定義が1箇所にしかなく、「この挙動を知るにはここを読めば足りる」と言える。複数箇所を突き合わせて整合を検証する必要がない。 | ISS-05, ISS-06, ISS-14 |
| **R3** | **死蔵物の不在（No Dead Weight）** | 読み手が遭遇するコード・フィールドはすべて「生きている」。「これは使われているのか？」を grep で確かめる必要がない。デッドパス・死蔵フィールド・過渡シムが目に入らない。 | ISS-01, ISS-14, ISS-16, ISS-17 |
| **R4** | **命名と型による自己説明（Self-describing by Name & Type）** | API 名・型・パッケージ構造そのものが意図を語る。「この呼び出しで detail が返るか」「このメソッドは同期か」を、フィールド既定値や実装本体を読まずに、シグネチャから判断できる。 | ISS-03, ISS-13 |
| **R5** | **設定の自己記述性（Self-describing Configuration）** | 設定項目の意味・単位・既定値が、コメントに頼らず型・名前・構造から分かる。コメントと実装が乖離する余地が構造的にない。 | ISS-02 |

> 補足: R1〜R5 は独立ではなく相補的である。例えば「死蔵物の不在（R3）」は「公開面の小ささ（R1）」を助け、「単一の真実（R2）」は「自己説明（R4）」の前提になる。3-1 §1 の設計原則（公開 API 最小化／拡張点ファースト／単一の真実／死蔵物を持たない）が、ここで言う可読性軸とほぼ一対一で対応している点に注意。可読性は 3-1 設計の副産物ではなく、設計原則そのものに織り込まれている。

## 2. 各設計判断 × 可読性の整理

3-1 のレイヤ設計（§3〜§10）を、可読性観点で読み解く。各項に **(a) どう読みやすくなるか（評価軸 R1〜R5 で）** / **(b) 解消される ISS** / **(c) 漸進案との可読性対比** を添える。テキスト処理（§5）はこのレイヤ自体が現状でも健全で直接の可読性 ISS を持たないため、参考として末尾に短く触れる。

### 2.1 §3 用途別 API 分離 — 公開面の小ささと自己説明

3-1 §3.2 は、肥大化した単一ファサード（`Suggester` 507行/public約18、`SuggestIndexer` 547行/public約28、出典: ISS-13, `0005` §3.1）を、用途別の4インタフェース（`SuggestIndexLifecycle` / `SuggestQueryService` / `SuggestWordAdmin` / `SuggestIngestService`）へ再編する。Operations 群・Writer・Serializer・Store 実装は `internal` 化して非公開にする。

- **(a) どう読みやすくなるか**
  - **R1（公開面の小ささ）**: 読み手は「人気語の取り方を知りたい → `SuggestQueryService` を読む」「bad word の扱いを知りたい → `SuggestWordAdmin` を読む」と、用途名から読むべき1インタフェースに直行できる。現状の「public 28メソッドが並ぶ `SuggestIndexer` を端から端まで読んで目的のメソッドを探す」必要がなくなる。**読むべき範囲が API 構造によって最初から区画化される**のが本質。
  - **R4（自己説明）**: インタフェース名が責務を語るため、「このクラスは何のためにあるか」をコメントや実装本体を読まずに把握できる。さらに 3-1 §3.2 は detail 取得を API 名/型から自明にする（例: `suggestWithDetail(...)` と最小レスポンス版を分ける）方針なので、「items が返るか」をフィールド既定値の追跡なしに判断できる（ISS-03 対応、後述 2.3）。
  - **R3（死蔵物の不在）**: `@Deprecated` 委譲シム（ISS-17）を最初から作らないため、`SuggestRequest` に「抽出済みだが互換のため残った」過渡メソッド（`buildQuery`/`buildFunctionScoreQuery` 等、出典: `SuggestRequest.java:243-326`）が目に入らない。読み手が「これは現役か、抽出後の抜け殻か」を判別する負荷が消える。
- **(b) 解消される ISS**: ISS-13（ファサード肥大）、ISS-17（Deprecated 委譲シム残存）、ISS-03（detail 暗黙結合の一部 — 2.3 で再掲）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §3.3(c)）は「28メソッドを用途別インタフェースへ切り出して `Suggester` から委譲し、`@Deprecated` シムを段階削除する」。可読性の観点では、移行過渡期に**「内部委譲構造（Operations）」と「新公開インタフェース」と「旧ファサード」の三層が一時的に併存**するため、その期間はむしろ読むべき面が増える。ゼロベース To-Be は最初から三層併存がない分、可読性のゴール状態が明快。ただし過渡期コストの実際の重さは移行戦略（ステップ4）の論点。

### 2.2 §4 データソース抽象 — デッドパスを「読み手が遭遇しない」構造に

3-1 §4.2 は、現行4経路を `SuggestSource` プラグイン抽象へ再設計し、**未使用のクエリログ経路（ISS-01）を標準実装として持たない**（将来必要なら `QueryLogSource` を追加するだけで載る拡張点にする）。

- **(a) どう読みやすくなるか**
  - **R3（死蔵物の不在）**: 現状はライブラリに `indexFromQueryLog(...)` のコードパスが存在するが、fess 本体の標準フローからは到達しない（`SuggestHelper` もラップしない、出典: ISS-01, `legacy/05` 5.1）。読み手は「この経路はいつ使われるのか？」を fess 本体側まで追って初めて「使われていない」と分かる — つまり**死んでいることを確認するために生きているコードと同じだけ読まされる**。To-Be では未使用経路が最初から存在しないため、この確認作業そのものが不要になる。「ソースが N 個ある」と見えたら N 個とも生きている、という保証が読み手の信頼を支える。
  - **R1（公開面の小ささ）**: サジェスト語の供給が「閉じた4経路の `indexFromXxx` メソッド群」から「`SuggestSource` 実装の一覧」へ集約され、「どこから語が来るか」を1つの抽象の実装クラス一覧で把握できる。
- **(b) 解消される ISS**: ISS-01（クエリログ経路のデッドパス）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §4.3(c)）は「②を削除し残り3経路を `SuggestSource` に後付け切り出し（アダプタで包む）」。デッドパス削除そのものは漸進でも達成でき、ISS-01 の可読性改善（R3）は移行コスト低く得られる。差が出るのは R1: アダプタ経由だと「抽象の純度が落ちる」（旧 `indexFromXxx` の形が透けて見える）ため、ゼロベースの素直な `SuggestSource` 実装一覧ほどには読みやすくならない。

### 2.3 §3.2 detail 設計（再掲・深掘り）— 暗黙のデフォルト依存を命名で断つ

ISS-03 は「`SuggestWordsHandler` が `items`（text/tags）を参照するが `setSuggestDetail(true)` の明示呼び出しを持たず、`SuggestRequest.suggestDetail` の既定値 `=true`（出典: `SuggestRequest.java:103`）に暗黙結合している」課題である。1箇所の既定値変更が、明示呼び出しを持たない Handler をサイレント破壊しうる。

- **(a) どう読みやすくなるか**
  - **R4（自己説明）**: 3-1 §3.2 は「detail を返すことが API 名・型から自明になる」設計（`suggestWithDetail(...)` と最小版を分ける、または返却型を明示する）を採る。これにより、**Handler のコードを読んだだけで「items が返る」ことが分かる**。現状は「items が返る根拠」を確認するのに `SuggestRequest` のフィールド初期化子（別クラスの遠い行）まで追わねばならず（実際、この確認のために TBD-02 が立てられ、ステップ2でようやくクローズされた経緯がある、出典: `0002` TBD-02）、読み手が「呼び出し点に書かれていない暗黙の前提」を探索させられていた。命名/型で自明化すれば、この探索が消える。
- **(b) 解消される ISS**: ISS-03（detail 既定値への暗黙結合）。
- **(c) 漸進案との可読性対比**: 漸進案は「Handler 側で `setSuggestDetail(true)` を明示呼び出しする」。これだけでも暗黙結合は解消し、可読性（R4）は改善する — 呼び出し点に意図が書かれるため。ゼロベース案との差は「明示呼び出しを**書き忘れられる**余地が残るか否か」。型で分ける（`suggestWithDetail` を呼ばないと items 型が手に入らない）と、書き忘れがコンパイル時に防がれ、読み手は「items を使っている＝detail 版を呼んでいる」と型から逆引きできる。漸進案のフラグ明示は実行時の約束にとどまる。

### 2.4 §6 スキーマ設計 — 死蔵フィールドを持たない

3-1 §6.2.1 は、ランキングを検索時 function score 単系統（§9）に統一するため、**書き込み専用の事前計算 `score` フィールドをスキーマから除外する**（または「持つなら検索で必ず使う」の二択にし、「持つが使わない」現状は採らない）。

- **(a) どう読みやすくなるか**
  - **R3（死蔵物の不在）**: 現状 `score` は書き込み4箇所（`SuggestItemSerializer.java:73,182,217` ほか）＋ mapping（`mappings-default.json:36-38`, double）に存在するが、検索/人気語/ソートのいずれからも参照されない（出典: ISS-16, [[project-suggest-scoring]]）。読み手は `score` を見ると「スコアに使われるのだろう」と推測するが、実際は死蔵 — **名前が嘘をついている**。これは R3（死蔵物）と R4（自己説明）の両方を毀損する最悪のパターンで、「スコアの算出を理解しようとして死蔵フィールドを追う」という誤った読解に時間を奪う。To-Be では存在しないため、`score` という名前を見て function score 計算（§9）を探しに行くだけで済む。
  - **R2（単一の真実）への波及**: score 死蔵の排除は、後述 2.7 のスコア源一系統化（ISS-14）と表裏一体。スキーマから死蔵 score が消えることで「ランキング源は検索時 function score ただ一つ」が**スキーマを読むだけでも裏付けられる**。
- **(b) 解消される ISS**: ISS-16（死蔵 score フィールド）、ISS-14（スコア源の混乱 — §9 と連携、2.7 で詳述）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §6.3(c)）は「`score` フィールドだけ mapping から削除」または「sort に使うよう変更」。可読性（R3/R4）の改善は漸進でもほぼ完全に得られる — 死蔵フィールドを消すこと自体は局所変更。ただしスキーマ変更は再構築を伴うため移行コストは別問題（ステップ4）。可読性観点では「漸進でもゴールに到達できる課題」の好例。

### 2.5 §7 マージ — 単一マージ規則化

3-1 §7.2.1 は、現状2クラスに重複実装されたマージ規則を、**ただ一つの `SuggestItemMergePolicy`** に統一する。

- **(a) どう読みやすくなるか**
  - **R2（単一の真実）**: 現状、マージ規則は `SuggestItemMerger.merge`（`:59-96`、オブジェクト同士）と `SuggestItemSerializer.toUpdatedSource`（`:142-185`、item と OpenSearch Map）に**二重実装**され、readings の走査基準が非対称（前者=text 語数 `:70-75` / 後者=新 item の reading 配列長 `:146-158`、出典: ISS-05）。「同一語をマージしたら頻度や reading がどうなるか」を正確に理解するには**両クラスを開いて突き合わせ、走査基準の違いが結果に与える差まで検証**しなければならない（実際この検証から `mergeReadings` の取りこぼし疑いが指摘されている、出典: `0002` ISS-05）。To-Be では規則が1箇所にあるため、**「マージ挙動を知る＝1つの `SuggestItemMergePolicy` を読む」**で完結する。二段（バルク内マージ／既存doc マージ）はあっても、適用する規則は同一の単一定義を参照する。
  - **R3（死蔵物の不在）への波及**: 二重実装の片方が「微妙にずれている」状態は、読み手に「どちらが正なのか」を判断させる。単一化はこの判断負荷を消す。
- **(b) 解消される ISS**: ISS-05（マージ規則の二重実装・走査基準非対称・取りこぼし疑い）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §7.3(c)）は「2クラスのマージ規則を共通ヘルパに抽出して呼び分ける」。可読性（R2）の改善は漸進でも本質的に達成できる — 規則本体が1箇所に集約されれば、呼び出しが2箇所でも「規則を知るには共通ヘルパを読む」で足りる。ゼロベースとの差は小さく、ここも「漸進でゴールに到達しやすい」課題。なお、走査基準の非対称が結果に与える差（取りこぼし疑い）は品質課題でもあり、品質観点での扱いはステップ3-4 の領分。

### 2.6 §8 同期/非同期モデル — 自己説明による「同期か非同期か」の即判

3-1 §8.2 は、独自 `Deferred`/`Promise` を標準機構（`CompletableFuture` 等）へ統一し、同期/非同期境界の規則を一本化する（I/O 操作は非同期を基本、同期版は非同期版の `.join()` ラッパとして一箇所で提供）。

- **(a) どう読みやすくなるか**
  - **R4（自己説明）**: 現状は「検索は常に非同期、登録は Reader 系のみ非同期、単発系は同期」と**API ごとに境界が不均一**（出典: ISS-09）。読み手は各メソッドの戻り値型や実装を見ないと同期/非同期が判断できない。標準型へ統一し境界規則を1つにすると、**戻り値型（`CompletableFuture<T>` か `T` か）を見るだけで同期/非同期が判別**でき、しかも「I/O は非同期」という単一規則を覚えれば毎回調べる必要がない。
- **(b) 解消される ISS**: ISS-09（同期/非同期境界の不均一）。可読性カバレッジ上 ISS-09 は主に変更容易性軸（3-3）だが、「戻り値型から同期/非同期が読める」点は R4 の可読性にも寄与するため本書でも触れる。可読性 ISS の必達9件には含まれない（3-3 の主担当）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §8.3(c)）は「独自 `Deferred`/`Promise` を維持しつつ境界規則だけ統一」。可読性（R4）は「境界が統一される」点で改善するが、独自型が残るため「`Promise` の意味を独自基盤のドキュメントで学ぶ」コストは残る。標準 `CompletableFuture` なら Java 開発者の既存知識で読めるため、新規読み手の学習コストが低い（要件の課題感「高度な Java スキルを要する」に直接効く）。

### 2.7 §9 スコアリング・語管理 — ランキング源の一系統化

3-1 §9.2 は、事前計算 `score` を廃止し、**ランキング源を検索時 function score の単系統に統一**する（「ランキングは検索時に決まる」を唯一の真実にする）。

- **(a) どう読みやすくなるか**
  - **R2（単一の真実）＋ R3（死蔵物の不在）**: ISS-14 は「事前計算 score と function score の二系統に見える」課題だが、ステップ2の確認で実態は「ランキングは function score 単系統、事前計算 score は死蔵」と判明している（出典: ISS-14/ISS-16, [[project-suggest-scoring]]）。つまり現状の可読性問題は「**二つあるように見えて片方は死んでいる**」という、最も誤読を招く状態である。読み手は登録時の `score=(queryFreq+docFreq)*userBoost` を見て「これがランキングに効く」と誤解し、実際に効く検索時 function score（`SuggestQueryBuilder.java:141-167` の LOG2P modifier 等）との関係を整理しようとして混乱する。To-Be では死蔵 score が消え、ランキングロジックが §9 の function score 1箇所に集約されるため、**「サジェストの並び順を理解する＝function score の構成を読む」**で完結する。
  - **R4（自己説明）への波及**: スコアリングを `ScoringStrategy` 抽象として明示する（`0005` §9.2）と、「どの要素（前方一致 weight・freq の modifier・userBoost）がどう効くか」が抽象の構造から読める。
- **(b) 解消される ISS**: ISS-14（スコア源の混乱）、ISS-16（死蔵 score — §6.2.1 と連携、2.4 と表裏）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §9.4(c)）は「`score` フィールドを廃止 or sort 利用に倒す」。可読性（R2/R3）の改善は漸進でも達成できる — 死蔵 score を消すか「必ず使う」に倒せば、「二系統に見える」誤読は解消する。ゼロベースとの差は `ScoringStrategy` 抽象化（R4 の自己説明強化）の有無で、これは構造変更を伴うため新機能(3-6)/ステップ4 と連携。なお bad word 誤削除（ISS-04, `0005` §9.3）は品質課題のため 3-4 が主担当（本書の可読性9件には含まれない）。

### 2.8 §10 権限・フィルタ — 二重担保の解消

3-1 §10.2 は、権限フィルタの責務を**単一の `AuthorizationFilter`**（Domain Core）へ集約し、ライブラリ側とアプリ側で同じフィルタを二重に組まない設計にする（fess 本体は「ロール集合を渡す」責務、ライブラリは「ロール集合をクエリへ反映する＝`_guest_` 補完含む」責務、と1回ずつに分ける。デフォルト deny をフェイルセーフとして要件化）。

- **(a) どう読みやすくなるか**
  - **R2（単一の真実）**: 現状は権限フィルタが二重担保 — ライブラリ側 `_guest_` 補完（`SuggestRequest.java:354-356`）＋ API 側 `RoleQueryHelper` の `addRole`（`SuggestWordsHandler.java:83`、出典: ISS-06）。読み手は「結局どのロール条件で検索されるのか」を理解するのに**ライブラリ側とアプリ側の二箇所を読んで合成結果を頭の中で組み立てる**必要がある。安全側ではあるが責務境界が曖昧で、「なぜ二箇所にあるのか／どちらが本体か」が読み取れない。To-Be では権限条件構築が `AuthorizationFilter` 1箇所に集約され、「権限フィルタの挙動を知る＝`AuthorizationFilter` を読む」で完結する。アプリ／ライブラリの責務が「渡す／反映する」と一文で言えるため、境界が読み手に自明になる。
- **(b) 解消される ISS**: ISS-06（権限フィルタの二重担保）。
- **(c) 漸進案との可読性対比**: 漸進案（`0005` §10.3(c)）は「二重担保の一方を残し他方を薄くして責務を片側に寄せる」。可読性（R2）は「責務が片側に寄る」ことで改善するが、ゼロベースの「単一 `AuthorizationFilter` への明確な集約」ほどには境界が綺麗にならない（fess 連携 API を変えない範囲に留めるため、責務の分担が中途半端に残りうる）。ただしフェイルセーフ（デフォルト deny）の維持が前提で、可読性のために安全性を犠牲にしないこと（`0005` §10.2）。

### 2.9 §5 テキスト処理（参考）— 可読性 ISS なし、踏襲資産

3-1 §5 のテキスト処理パイプライン（Normalizer→ReadingConverter→Analyzer の Strategy+Composite）は**責務分割が良好で直接の可読性 ISS を持たない**（出典: `0005` §5.1, `0003` §3.1/§3.3）。むしろ「単機能の小さな converter/normalizer が Chain で合成される」構造は、本書の R1（読むべき範囲が小さい）・R4（クラス名が処理内容を語る）を**既に満たしている好例**である。To-Be はこれを踏襲（`TextProcessor` 抽象として明文化）するため、可読性は維持・微増。可読性課題の解消対象ではないが、「ゼロベースでも捨てない可読性の良い資産」として位置づけられる。

## 3. ISS-02: コメントと実装が乖離しない設定設計（設定の自己記述性 R5）

ISS-02 は 3-1 では構造設計の直接対象外とされ「3-2 で扱う」と明記された（出典: `0005` §12, 378行）。本ステップで**設定設計の可読性として正面から扱う**。

### 3.1 現状（アンチパターンの実例）

- **[事実]** `suggest.popular.word.cache.expire` は `PopularWordHelper.java:77` で `TimeUnit.MINUTES`（既定60 → 60分）として実装されているが、`fess_config.properties` のコメントは「秒」と記している。**実装値（分）が正だが、コメントが誤っている**ため、ドキュメント/運用判断を誤らせる（出典: ISS-02, `legacy/05-issues.md` 5.2, `legacy/04` 4.2）。

これは「設定の意味（単位）が**コメントという、実装と独立に存在し独立に腐る注釈**に依存している」ことが根本原因である。コメントは型システムやコンパイラの検査を受けないため、実装が分単位に変わってもコメントが秒のまま放置され、両者が静かに乖離する。読み手はコメントを信じると誤り、実装まで読まないと正しい単位が分からない — R5（設定の自己記述性）の毀損である。

### 3.2 To-Be 設計判断 [提案] — コメントに頼らず「読めばわかる」設定

ゼロベース設計では、設定の意味・単位・既定値を**コメントではなく型・名前・構造で表現**し、コメントと実装が乖離する余地を構造的に消す。具体策は次の3点。

1. **単位を型で表現する（Typed Settings）** [提案]
   - `int expire`（単位不明、コメント頼み）ではなく、`Duration cacheExpiry`（`java.time.Duration`）のような**単位を内包する型**で設定を保持する。`Duration.ofMinutes(60)` と書けば単位が型に焼き込まれ、コメントが不要になる。読み手は型を見れば単位を誤解しようがない。
   - プロパティ文字列から読む場合も、`PT60M`（ISO-8601 Duration）や `60m` のような**単位サフィックス付きの値**でパースし、生の数値＋コメントを排除する。
   - **[要確認]** fess 本体の設定基盤（`fess_config.properties` / Lasta 系 Config 生成）が `Duration` 型や単位付き文字列をどこまでサポートするかは連携依存。型化の具体手段はステップ4/連携部の確認。方向性として「単位を型に持たせる」を採る。
2. **単一の設定ソース（Single Source of Truth for Config）** [提案]
   - 設定の「名前・型・既定値・説明」を**1箇所**（設定スキーマ/定数定義）に定義し、プロパティファイルのコメントとコード内の参照が二重に意味を持たない構造にする。R2（単一の真実）の設定版。これにより「コメントと実装」という二系統が存在しなくなり、乖離の発生源が消える。
3. **既定値と単位をコードに集約し、プロパティはオーバーライドのみ** [提案]
   - 既定値（60分）と単位を型付きでコード側に持ち、プロパティファイルは「上書きしたい場合だけ書く」位置づけにする。プロパティ側のコメントが一次情報になることをやめ、一次情報をコード（型）に寄せる。

- **(a) どう読みやすくなるか（R5）**: 設定の単位・意味が型と名前から読め、コメントを読む必要も信じる必要もない。`cacheExpiry: Duration` を見れば「これは時間量だ」と分かり、`Duration.ofMinutes(60)` を見れば「60分だ」と分かる。**コメントと実装の不一致という事象が、コメントに意味を持たせない設計によって構造的に発生しなくなる**のが本質。
- **(b) 解消される ISS**: ISS-02（cache.expire のコメントと実装の不一致）。
- **(c) 漸進案との可読性対比**: 漸進案は「コメントを実装に合わせて『分』に修正する」。これは即座に乖離を直すが、**乖離を再発させない構造的保証はない** — 将来また実装が変わればコメントが再び腐る。型化（`Duration` 化）は「コメントに単位を書く必要がない＝乖離しようがない」状態を作るため、可読性の持続性で優る。漸進案のコメント修正は応急処置、ゼロベースの型化は再発防止。なお ISS-02 は単体では体感重大度「低」（出典: `0002` §4.1）だが、「コメント頼みの設定」という同型の脆さは他設定項目にも潜在しうるため、型化は ISS-02 単体の修正を超えた予防的価値を持つ。
