## 1. 設計原則（全レイヤ共通の North Star）

ゼロベース設計の各判断を貫く原則を先に定義する。個々の設計判断はこの原則の具体化である。

1. **公開 API 最小化（Minimal Surface）**: ファサードに機能を足し続けるのではなく、用途別に分離した小さなインタフェースを公開する。読み手が「どこを読めば何が分かるか」を API 構造から理解できること。（主に ISS-13, ISS-17 を回避）
2. **拡張点ファースト（Pluggable by Default）**: サジェストソース・スコアリング・テキスト処理は、新規追加が「後付けの改造」ではなく「最初から想定された拡張」になる抽象を持つ。（主に ISS-01, ISS-11, ISS-12 を回避し、新機能(3-6)の土台になる）
3. **単一の真実（Single Source of Truth）**: マージ規則・ランキング源・権限フィルタは、それぞれ**一箇所**に定義する。同じ規則を二重実装しない。（主に ISS-05, ISS-06, ISS-14 を回避）
4. **デッドコード・死蔵データを持たない（No Dead Weight）**: 使われないコードパス・フィールドを残さない。書くなら読む、読まないなら書かない。（主に ISS-01, ISS-14, ISS-16, ISS-17 を回避）
5. **バルク効率優先（Bulk-first I/O）**: 1件ずつの同期往復を基本にしない。書き込み・取得は一括化を既定とする。（主に ISS-08, ISS-10 を回避）
6. **一貫した同期/非同期境界（Uniform Concurrency）**: API ごとに同期/非同期がばらつかない。標準機構で統一する。（主に ISS-09 を回避）
7. **流用価値ある資産は踏襲する（Reuse over Rewrite）**: ゼロベース＝全置換ではない。テキスト処理パイプライン・充実したテスト群など、責務分割が良好な資産は「あるべき姿でも踏襲・再利用する資産」として明示的に残す。

この全体像の要点は2つ。

- **縦の分離**: Consumer → 用途別 API → Domain Core → Storage という層を明確にし、特に Storage を `SuggestStore` 抽象で隔離する（OpenSearch 直結を避ける）。
- **横の拡張点**: Domain Core 内で「サジェストソース」「テキスト処理」「スコアリング」をそれぞれ差し替え可能な抽象として並置する。新機能はこの横の拡張点に載せる。

## 3. レイヤ1: コンポーネント構造（公開 API 境界）

### 3.1 現状（アンチパターンの実例）

- **[事実]** `Suggester.java` 507行 / public 約18メソッド（ライフサイクル + 検索 + indexer 取得 + エイリアス/getter）。`SuggestIndexer.java` 547行 / public 約28メソッド（index/delete/badWord/elevateWord/Reader 系）。出典: ISS-13, `0003` §2/§3.1。
- **[事実]** `SuggestIndexer` は4 Operations（`IndexingOperations`/`DeletionOperations`/`WordManagementOperations`/`ContentIndexingOperations`）へ委譲する構造は維持されているが、**公開 API 表面積（特に Indexer の28メソッド）**が主課題。出典: ISS-13。
- **[事実]** `SuggestRequest`（392行）に `buildQuery`/`buildFunctionScoreQuery`/`createResponse`/`isHiraganaQuery` 等の `@Deprecated` 委譲シムが残存（抽出済みだが過渡コードが残る）。出典: ISS-17, `SuggestRequest.java:243-326`。

### 3.2 To-Be 設計判断 [提案]

**用途別に分離した4つの公開インタフェースに API を再編する。** 単一の巨大ファサードを廃し、利用シーン（lifecycle / query / word-management / indexing）ごとに最小の公開面を持たせる。

| To-Be インタフェース | 責務 | 主な利用者 |
| --- | --- | --- |
| `SuggestIndexLifecycle` | インデックス作成・切替・破棄・エイリアス管理（`createIndexIfNothing` / `switchIndex` 相当） | `SuggestCreator`（バッチ）、起動時初期化 |
| `SuggestQueryService` | サジェスト検索・人気語取得（`suggest` / `popularWords` 相当） | `SuggestWordsHandler`（API）、リアルタイム検索 |
| `SuggestWordAdmin` | bad word / elevate word 等の語管理 | 管理画面 |
| `SuggestIngestService` | ドキュメント・検索語の取り込み（`indexFromDocument` / `indexFromSearchWord` 相当） | バッチ再構築、リアルタイム検索ログ反映 |

設計の補足:

- **公開しないものは内部に隠す**: Operations 群・Writer・Serializer・Store 実装は `internal` パッケージ等で非公開とし、公開面を上記4インタフェースの必要メソッドだけに絞る。「公開 API 最小化」原則の具体化。
- **`@Deprecated` 委譲シムは存在しない**: ゼロベースのため過渡コード（ISS-17）は最初から作らない。クエリ構築は `SuggestQueryService` の実装詳細として隠蔽し、`SuggestRequest` に委譲メソッドを残さない。
- **暗黙のデフォルト依存を断つ**: 詳細レスポンス（items=text/tags 等）は「detail を返す」ことが API 名・型から自明になるよう設計する（例: `SuggestQueryService.suggestWithDetail(...)` と最小レスポンス版を分ける、または返却型を明示的にする）。`SuggestRequest.suggestDetail` のフィールド既定値（`=true`）に呼び出し側が暗黙結合する構造（ISS-03）を作らない。

### 3.3 (a) 設計意図 / (b) 解消される課題 / (c) 漸進案との対比

- **(a) 設計意図**: 公開 API を用途別に分割し表面積を抑えることで、(1) 読み手が役割を API 構造から理解でき（可読性）、(2) 変更影響が1インタフェースに局所化される（変更容易性）。
- **(b) 解消される課題**: ISS-13（ファサード肥大・公開28メソッド）、ISS-17（Deprecated 委譲シム残存）、ISS-03（detail 既定値への暗黙結合）。
- **(c) 漸進案との対比**: 既存構成を維持する漸進案は「`SuggestIndexer` の28メソッドを用途別インタフェースに**切り出して `Suggester` から委譲**し、`@Deprecated` シムを段階削除する」アプローチ。後方互換を保ちやすく移行コストは低いが、内部の委譲構造（Operations）と公開面の二重構造が一時的に残る。**移行経路としての具体化はステップ4。**

## 4. レイヤ2: データソース抽象（サジェストソース）

### 4.1 現状（アンチパターンの実例）

- **[事実]** サジェスト語の供給は **4経路**: ①ドキュメント本文 / ②検索クエリログ / ③検索語 / ④elevate word。出典: `legacy/03` 3.2。
- **[事実]** **② 検索クエリログ経路（`indexFromQueryLog`）は fess 本体から未使用のデッドパス**（`SuggestHelper` もラップしない）。出典: ISS-01, `legacy/05` 5.1。
- **[事実]** 同義語辞書は独立データソースではなく OpenSearch アナライザ側の解析の一部。新規ソースの追加は「経路の改造」であり、拡張点として設計されていない。出典: `legacy/03` 3.2。
- **[事実]** 蓄積属性（reading/kinds/freq/roles 等）は豊富だが UI 活用は text/tags のみ。出典: ISS-11。

### 4.2 To-Be 設計判断 [提案]

**「サジェストソース（`SuggestSource`）」をプラグイン可能な第一級の抽象として定義する。** 各ソースは「外部入力 → `SuggestItem` ストリーム」への変換責務だけを持ち、書き込み・集約・スコアリングはソースに依存しない共通機構（§7〜§9）が担う。

```
interface SuggestSource {
    String kind();                         // DOCUMENT / SEARCH_WORD / ELEVATE / [新]SYNONYM / [新]SEMANTIC ...
    Stream<SuggestItem> produce(SourceContext ctx);   // バッチ/逐次の両対応
}
```

- **標準実装**: `DocumentSource`（①）、`SearchWordSource`（③）、`ElevateWordSource`（④）。
- **②クエリログ経路は標準実装として持たない**: 現行のデッドパス（ISS-01）は「未使用なら最初から存在させない」。ただし将来 fess 本体が必要とするなら `QueryLogSource` を**追加する**だけで載る拡張点を用意しておく（=デッドパスではなく「未実装の拡張点」になる）。
- **新規ソースは追加だけで載る** [提案]: 同義語(`SynonymSource`)、関連語(`RelatedWordSource`)、セマンティック(`SemanticSource`)を、共通機構に手を入れずに `SuggestSource` 実装を足すだけで追加できる。新機能(3-6)はここに載る。
  - 同義語を「アナライザ任せ」ではなく独立ソースにできるため、同義語サジェストを語管理・スコアリングの対象にできる（ISS-12 のカバレッジ拡張の素地）。
- **蓄積属性を活かす拡張点**: ソースが produce する `SuggestItem` の属性（reading/kinds/freq 等）を、レスポンス整形側（§3 `SuggestQueryService`）が選択的に露出できるようにし、ISS-11 の「死蔵属性」を新機能に転用可能にする。

### 4.3 (a)(b)(c)

- **(a) 設計意図**: サジェスト語の供給を「閉じた4経路」から「開いた拡張点」へ転換し、新機能を後付け改造でなく最初から追加可能にする。
- **(b) 解消される課題**: ISS-01（デッドパスを最初から作らない）、ISS-11（蓄積属性の活用余地）、ISS-12（人気語/ソースのカバレッジ拡張の素地）。
- **(c) 漸進案との対比**: 漸進案は「現行4経路のうち②を削除し、残り3経路を `SuggestSource` インタフェースに**後付けで切り出す**」。既存の `indexFromXxx` メソッド群をアダプタで包む形になり、抽象の純度は落ちるが既存テスト資産を活かしやすい。**移行はステップ4。**

## 5. レイヤ3: テキスト処理パイプライン（踏襲する資産）

### 5.1 現状（**良好な資産**）

- **[事実]** 共通テキスト処理は **Normalizer(Chain) → ReadingConverter(Chain) → SuggestAnalyzer** の Strategy + Composite 構成。converter + normalizer + analysis で計約1,369行。各 converter/normalizer は単機能で小規模＝**責務分割が良好**。出典: `0003` §3.1/§3.3。
- **[事実]** 実体（確認済み）: `converter/`（`ReadingConverter`, `ReadingConverterChain`, `KatakanaConverter`, `KatakanaToAlphabetConverter`, `AnalyzerConverter`）、`normalizer/`（`Normalizer`, `NormalizerChain`, `ICUNormalizer`, `FullWidthToHalfWidthAlphabetNormalizer`, `HankakuKanaToZenkakuKana`, `AnalyzerNormalizer`）、`analysis/`（`SuggestAnalyzer`）。
- **[事実]** ドキュメント側とクエリ/メタ側で別々の `ReadingConverter`（`readingConverter` / `contentsReadingConverter`）。出典: `legacy/02`。
- **[事実]** テキスト処理は専用テストが手厚い（converter 群 / normalizer 群 / `SuggestAnalyzerTest` 等）。出典: `0003` §3.2。

### 5.2 To-Be 設計判断 [提案]

**このパイプラインは「あるべき姿でも踏襲・再利用する資産」として位置づける。** Strategy + Composite（Chain）構成は拡張容易性が高く、ゼロベースでも同型の設計を採用する。安易な全置換はしない（原則7）。

理想形としての整理（既存の良さを保ったまま明確化する点）:

- **`TextProcessor` 抽象として一段抽象化** [提案]: Normalizer / ReadingConverter / Analyzer を「テキスト → テキスト/トークン」の `TextProcessor` 系として統一的に扱い、Chain（Composite）で合成する現行思想を明文化。新しい言語処理（多言語形態素・別読み変換）を Chain に足すだけで拡張できる拡張点として位置づける。
- **多言語拡張点** [提案]: 現行の日本語特化（カタカナ→アルファベット等）に加え、言語別の Normalizer/Converter セットを切り替え可能にする（言語判定 → 言語別 Chain 選択）。新機能(3-6)の多言語強化の土台。
- **ドキュメント側/クエリ側の二系統** [事実踏襲]: `readingConverter`/`contentsReadingConverter` の使い分けは合理的なので踏襲する。

### 5.3 (a)(b)(c)

- **(a) 設計意図**: 良好な資産を保全しつつ、拡張点（多言語・新処理）として明確化する。再利用により品質・テスト資産を温存する。
- **(b) 解消される課題**: 直接解消する ISS はない（このレイヤは現状でも健全）。間接的に「変更容易性」「品質（読み変換精度）」「新機能（多言語）」に寄与。**踏襲・再利用資産の明示**という完了条件をこのレイヤが担う。
- **(c) 漸進案との対比**: 漸進案＝現行パイプラインをそのまま維持。To-Be 案との差は「`TextProcessor` 抽象としての明文化と多言語拡張点の追加」程度であり、**このレイヤはゼロベースでも漸進でもほぼ同一**（＝全置換不要の好例）。

## 6. レイヤ4: インデックス設計（スキーマ・シャード・エイリアス）

### 6.1 現状（アンチパターンの実例）

- **[事実]** `number_of_shards=1`, `number_of_replicas=0`, `auto_expand_replicas=0-1`, `refresh_interval=10s`（`suggest.json`）。単一シャード前提の小規模専用設計 [推測]。出典: ISS-07 / TBD-05。
- **[事実]** 二重エイリアスによるゼロダウンタイム再構築: 物理 `{base}.{timestamp}`、検索エイリアス `{base}`、更新エイリアス `{base}.update`。出典: `legacy/02`。
- **[事実]** 決定的 ID（`SuggestUtil.createSuggestTextId`）で同一語を1ドキュメントに集約。出典: `legacy/02`。
- **[事実]** mapping に `score: double` があるが read/sort/query から一切参照されない**死蔵フィールド**。出典: ISS-14 / ISS-16, `mappings-default.json:36-38`。
- **[事実]** `text` は `keyword`（非解析）。多語フレーズは単一スペース区切りで1値。出典: ISS-04, `mappings-default.json:48-50`, `SuggestConstants.java:37`。

### 6.2 To-Be 設計判断 [提案]

#### 6.2.1 スキーマ: 死蔵フィールドを持たない

- **事前計算 `score` フィールドを持たない** [提案]: ランキングは検索時 function score 単系統（§9）に統一するため、書き込み専用の `score` フィールドはスキーマから除外する。原則4「死蔵データを持たない」の具体化。
  - **代替の選択肢（性能トレードオフ）** [提案/要確認]: もし検索時計算コストを下げたい場合は、`score` を**検索で実際に sort/rescore に使う**設計（書くなら読む）にする。「持たない」か「持って必ず使う」の二択にし、「持つが使わない」現状は採らない。どちらが最適かは QPS・鮮度要件次第で**ステップ3-5/要確認**。
- **`text` 周りの設計** [提案]: 完全一致削除・前方一致サジェストを両立するため、`text` は keyword を維持しつつ、bad word 削除は keyword 完全一致（term）で行えるよう語管理側（§9.3）を設計する。多語フレーズの扱いは現行の単一値踏襲だが、誤削除を招く `*badword*` 部分一致を機構から排除する（§9.3）。

#### 6.2.2 シャード/レプリカ: 規模に応じた可変設計

- **シャード数を「規模に応じて選べる」設計** [提案/要確認]: 単一シャード固定（ISS-07）をやめ、語彙規模・QPS に応じて `number_of_shards` を構築時に決定できるようにする。サジェストは前方一致が主で集約は決定的 ID で完結するため、複数シャードでも整合する（クロスシャード集約は不要）。ただし**最適シャード数の根拠と、現行が「意図」か「デフォルト」か（TBD-05）は要確認**。
  - **ルーティングとホットスポットの検証観点** [要確認]: 決定的 ID（`createSuggestTextId`）ベースの更新は、OpenSearch デフォルトの ID ハッシュルーティングにより同一語が常に同一シャードへ集約されるため、複数シャードでも集約整合は保たれる（カスタムルーティングやクロスシャード集約は不要）。一方で、人気サジェスト語への更新集中が特定シャードへの書き込みホットスポットを生まないかという検証観点を持つ。定量検証は**ステップ3-5（性能）**で扱う。
- **レプリカ**: 検索可用性のため `number_of_replicas>=1` を選べるようにする（現行 0 は単一ノード前提 [推測]）。**[要確認]** 運用ノード構成に依存。

#### 6.2.3 ゼロダウンタイム再構築: 二重エイリアスは踏襲

- **二重エイリアス（検索/更新）方式は踏襲する** [提案]: ゼロダウンタイム再構築の仕組みとして合理的なので、ゼロベースでも採用する。ただし「物理インデックス世代管理」を `SuggestStore` 抽象（§2）の責務として明確化し、`SuggestIndexLifecycle`（§3）の公開面に限定して露出する。

### 6.3 (a)(b)(c)

- **(a) 設計意図**: 死蔵フィールドを排し（可読性・性能）、規模拡張余地を持たせ（性能・スケール）、ゼロダウンタイム再構築の良い資産は踏襲する。
- **(b) 解消される課題**: ISS-16（死蔵 score フィールド）、ISS-14（スコア源の混乱）、ISS-07/TBD-05（単一シャード固定のスケール上限）。bad word 誤削除（ISS-04）は §9.3 と連携。
- **(c) 漸進案との対比**: 漸進案は「`score` フィールドだけ mapping から削除（または sort に使う）」「`suggest.json` のシャード数を設定可能にする」など局所変更。インデックススキーマ変更は再構築を伴うため、移行コスト（再構築・後方互換）は**ステップ4**で扱う。

## 7. レイヤ5: 書き込み／集約モデル

### 7.1 現状（アンチパターンの実例）

- **[事実]** `SuggestIndexWriter.write` は mergedItems を1件ずつループし、各件で `prepareGet().get()` を**同期実行**（`SuggestIndexWriter.java:54-55`）。N件登録で **N回 Get + 1回 bulk**（multiGet でない）。出典: ISS-10。
- **[事実]** マージは二段: 第1段=同一バルク内 `SuggestItemMerger.merge`（オブジェクト同士）、第2段=既存doc との `SuggestItemSerializer.toUpdatedSource`（item と OpenSearch Map）。**マージ規則が2クラスに重複実装**され、readings の走査基準が非対称（前者=text 語数、後者=新 item の reading 配列長）。`mergeReadings` に取りこぼし疑い [推測]。出典: ISS-05。
- **[事実]** document バッチの1リクエスト件数が極小（`suggest.update.doc.per.request=2`）。出典: ISS-08。

### 7.2 To-Be 設計判断 [提案]

#### 7.2.1 マージ規則は単一実装（Single Source of Truth）

- **マージ規則を1クラス/1関数に統一する** [提案]: 「集合和（reading/fields/tags/roles/languages/kinds）/ 加算（queryFreq/docFreq）/ 最新置換（userBoost/@timestamp）」という規則を**ただ一つの `SuggestItemMergePolicy`** に定義し、同一バルク内マージも既存doc マージもこの単一規則を使う。原則3「単一の真実」の具体化。これにより ISS-05 の「二重メンテナンスによる不整合・走査基準の非対称・取りこぼし疑い」が構造的に消える。

#### 7.2.2 書き込みは「アプリ側 Get 排除」または「multiGet バルク化」

- **第一候補: OpenSearch 側集約（upsert / スクリプト集約）** [提案/要確認]: アプリ側の Get-then-update をやめ、`update` API の `scripted_upsert` 等で「既存があれば加算、なければ新規」を OpenSearch 側で原子的に行う。N回 Get を**ゼロ**にし、bulk update 1回に集約。これが理想形。**ただしスクリプト集約・upsert の利用可否は OpenSearch バージョン依存（TBD-01）で要確認。**
  - **スクリプトは静的に保つ** [要確認]: scripted_upsert を採る場合、スクリプト本体は語ごとに変えず**静的（不変）に保ち、`params` のみ動的に渡す**実装方針とする。インジェスト流量が多いときに語ごとの動的スクリプトを生成するとスクリプトのコンパイル/実行キャッシュが枯渇し CPU 負荷を招くため。定量的な負荷検証は**ステップ3-5**で扱う。（TBD-01 依存のため断定はしない）
- **第二候補（フォールバック）: multiGet バルク化** [提案]: スクリプト集約が使えない場合でも、1件ずつ同期 Get を `multiGet` 1回にまとめ、N回往復を1回にする。ISS-10 の往復線形コストを解消。
- **バルク件数の適正化** [提案]: `doc.per.request=2`（ISS-08）のような極小デフォルトをやめ、CPU 負荷調整（`calibrateCpuLoad` 相当）と両立する適切な既定値・動的調整にする。**[要確認]** 適正値は実測依存で TBD-04（CPU 負荷調整の設計意図）と関連。

### 7.3 (a)(b)(c)

- **(a) 設計意図**: マージ規則を一本化して不整合リスクと読解コストを排し、書き込み I/O をバルク化して性能ボトルネックを解消する。
- **(b) 解消される課題**: ISS-05（マージ規則の二重実装・取りこぼし疑い）、ISS-10（1件ずつ同期 Get）、ISS-08（バッチ件数極小）。
- **(c) 漸進案との対比**: 漸進案は「(1) `SuggestItemMerger` と `toUpdatedSource` のマージ規則を共通ヘルパに抽出して呼び分ける」「(2) Get を multiGet 化する」。既存の二段構造とテストを保ったまま不整合とコストを減らせる。upsert/スクリプト集約への全面移行はインデックス挙動が変わるため**ステップ4**で移行可否を判断。

## 8. レイヤ6: 同期／非同期モデル

### 8.1 現状（アンチパターンの実例）

- **[事実]** 非同期基盤は独自の `Deferred`/`Promise`。**検索は常に非同期**、登録は Reader 系のみ非同期、単発系（`index`/`indexFromSearchWord` 等）は同期。**API ごとに同期/非同期境界が不均一**。出典: ISS-09, `legacy/01`/`02`。

### 8.2 To-Be 設計判断 [提案]

- **標準機構（`CompletableFuture`）へ統一する** [提案]: 独自 `Deferred`/`Promise` をやめ、Java 標準の `CompletableFuture`（または同等の標準非同期型）で同期/非同期境界を一貫させる。原則6「一貫した同期/非同期境界」の具体化。
  - **方針**: 「I/O を伴う操作（検索・書き込み）は非同期 API を基本とし、同期版は非同期版の `.join()` ラッパとして一箇所で提供する」など、境界規則を1つに統一する。利用側が「このメソッドは同期か非同期か」を毎回調べなくて済む。
  - **独自基盤を完全に捨てるか** [要確認]: 既存利用側（fess 本体）が独自 `Promise` の API（コールバック形式等）に依存している可能性があり、標準型への全面置換の互換影響は**ステップ4で要確認**。ゼロベース理想形としては標準機構を採る。
- **[事実踏襲]** 「検索は非同期が基本」という現行思想自体は合理的（UI のレスポンス性）なので、非同期を基本とする方針は踏襲する。変えるのは「不均一さ」であって「非同期であること」ではない。

### 8.3 (a)(b)(c)

- **(a) 設計意図**: 同期/非同期の境界を標準機構で一貫させ、利用側の認知負荷と誤用（性能/挙動の誤り）を減らす。
- **(b) 解消される課題**: ISS-09（同期/非同期境界の不均一）。
- **(c) 漸進案との対比**: 漸進案は「独自 `Deferred`/`Promise` を維持しつつ、同期/非同期境界の規則だけ統一する（全メソッドに非同期版を用意し同期版はラッパ）」。基盤置換を伴わないため互換影響が小さい。標準機構への置換は**ステップ4**で互換性込みで判断。

## 9. レイヤ7: スコアリング機構・語管理

### 9.1 現状（アンチパターンの実例）

- **[事実]** ランキングは**検索時 function score 単系統**で決まる。`SuggestQueryBuilder.buildFunctionScoreQuery`（`:141-167`）は DOC_FREQ/QUERY_FREQ（LOG2P modifier）+ USER_BOOST + 前方一致 weight を都度評価。`boostMode=REPLACE`, `scoreMode=MULTIPLY`。人気語（`PopularWordsRequest:210-246`）も QUERY_FREQ factor + random rescorer。**両者とも事前計算 `score` フィールドを参照しない**。出典: ISS-14, `0003` §2。
- **[事実]** よって「二系統が併存」ではなく「**ランキングは function score 単系統、事前計算 score は死蔵**」が実態。出典: ISS-14/ISS-16, [[project-suggest-scoring]]。
- **[事実]** `userBoost <= 1` はコンストラクタで強制的に1へ丸め。document/query 経路は実質 userBoost=1、USER 経路のみ boost>1 を保持。boost 表現力が制約される。出典: ISS-15, `SuggestItem.java:131-135`。
- **[事実]** bad word 削除は `wildcardQuery(TEXT, "*badword*")`（keyword 非解析・両端ワイルドカード・物理削除）で**誤削除が機構上不可避**。出典: ISS-04。

### 9.2 To-Be 設計判断: スコアリングは検索時単系統 [提案]

- **ランキング源を検索時 function score の単系統に統一する** [提案]: 事前計算 `score` フィールドを廃止（§6.2.1）し、「ランキングは検索時に決まる」を唯一の真実にする。原則3/4 の具体化。これにより「スコア源が二つあるように見えて片方は死んでいる」誤解（ISS-14/16）が構造的に消える。
- **スコアリングを差し替え可能な抽象にする** [提案]: function score の構成（前方一致 weight・freq の modifier・userBoost の効かせ方）を `ScoringStrategy` として抽象化し、調整・実験・新機能（セマンティック類似度の加点など）を載せられるようにする。新機能(3-6)のスコアリング拡張点。
- **boost 表現力の制約を外す** [提案]: `userBoost<=1` の一律丸め（ISS-15）をやめ、ソース種別に依存しない連続値の boost を扱えるようにする（負値の扱い等のサニタイズは別途定義）。スコアリング調整の自由度を上げる。**[要確認]** function score の重み設計は OpenSearch バージョン依存 API に関わるため TBD-01。
- **性能トレードオフの明示** [提案/要確認]: 検索時計算が重い場合は §6.2.1 の「sort 用に score を持って必ず使う」案へ倒す。**「単系統」を保ったまま、計算を検索時にするか書き込み時にするかの一択**にする（両方持って片方死蔵は採らない）。判断はステップ3-5/要確認。
  - **サジェスト特有のレイテンシ/QPS 要件** [要確認]: サジェスト API は逐次入力に追従するため、通常検索よりシビアな低レイテンシ・高 QPS が求められる。検索時 function score（や `script_score` 等）の実行時計算はクエリごとにコストが増えるため、**想定 QPS 下でレイテンシ要件を満たせるかの検証が、検索時計算 vs 書き込み時計算の選択を左右するステップ3-5 の最重要論点**である。本書では単系統という方向性のみ示し、定量評価は後続へ送る（TBD-01 依存のため断定はしない）。

### 9.3 To-Be 設計判断: 語管理（bad word）の誤削除排除 [提案]

- **bad word 削除を完全一致（term）化する** [提案]: `*badword*` 部分一致ワイルドカード削除（ISS-04）をやめ、keyword 完全一致（`termQuery(TEXT, badword)`）で対象語だけを削除する。誤削除を機構から排除する。
- **論理削除（フラグ）化の検討** [提案]: 物理 `deleteByQuery`（不可逆）ではなく、`excluded` フラグ等で論理削除し、検索クエリ側で除外する。誤操作からの復元可能性を持たせる。**[要確認]** インデックス容量・クエリコストとのトレードオフ。
- **削除前ドライラン** [提案]: 管理操作として「この bad word は N 語に影響する」を事前提示できる API を持たせる（`SuggestWordAdmin` の責務、§3）。

### 9.4 (a)(b)(c)

- **(a) 設計意図**: ランキング源を一系統に統一して理解・調整を容易にし（可読性・品質）、語管理から誤削除を排除する（品質・変更容易性）。
- **(b) 解消される課題**: ISS-14（スコア源の混乱）、ISS-16（死蔵 score）、ISS-15（boost 表現力制約）、ISS-04（bad word 誤削除）。
- **(c) 漸進案との対比**: 漸進案は「(1) `score` フィールドを廃止 or sort 利用に倒す」「(2) bad word を term 完全一致に変更」「(3) userBoost 丸めを撤廃」。いずれも局所変更で既存テストを活かせる。スコアリング抽象化（`ScoringStrategy`）は構造変更を伴うため**ステップ4/新機能(3-6)**と連携。

## 10. レイヤ8: 権限・フィルタ

### 10.1 現状（アンチパターンの実例）

- **[事実]** 権限フィルタが**二重担保**: ライブラリ側 `_guest_` 補完（`SuggestRequest.java:354-356`）＋ API 側 `RoleQueryHelper` の `addRole`（`SuggestWordsHandler.java:83`）。安全側だが責務境界が曖昧で、変更時に二箇所の同期が必要。出典: ISS-06。

### 10.2 To-Be 設計判断 [提案]

- **権限フィルタの責務を一箇所に定義する** [提案]: 「誰がどのロールで検索するか」の権限条件構築を**単一の `AuthorizationFilter`**（Domain Core、§2）に集約する。ライブラリ側とアプリ側で同じフィルタを二重に組まない。原則3「単一の真実」の具体化。
  - **境界の明確化**: アプリ（fess 本体）は「呼び出しユーザのロール集合」を渡す責務、ライブラリは「そのロール集合を検索クエリへ正しく反映する（`_guest_` 補完含む）」責務、と責務を1回ずつに分ける。安全性（フェイルセーフ）は維持しつつ、二重実装をやめる。
  - **フェイルセーフを要件化する** [提案]: 二重担保を `AuthorizationFilter` へ一元化するにあたり、**デフォルト deny（ロール情報が未指定・受け渡し漏れの場合に全件露出せず、明示的な権限付与がないとマッチしない）**を `AuthorizationFilter` の設計要件として明文化する。現状の二重担保が結果的に担保していた「アプリ側のロール受け渡しが漏れても露出しない」安全性を、一元化後も失わないための防御的設計意図。
- **[要確認]** fess 本体側 `RoleQueryHelper` との責務再配置は連携 API の変更を伴うため、互換影響は**ステップ4**。fess 連携部のテストは手薄な可能性（`0003` §3.2）があり、移行時のテスト補強が必要。

### 10.3 (a)(b)(c)

- **(a) 設計意図**: 権限フィルタの責務境界を明確化し、二重実装による同期コスト・読解コストを排す。
- **(b) 解消される課題**: ISS-06（権限フィルタの二重担保）。
- **(c) 漸進案との対比**: 漸進案は「二重担保のうち一方を残し他方を薄くする（責務を片側に寄せる）」で、安全性を保ちつつ段階的に一本化。fess 連携 API を変えずに済む範囲で進められる。**移行はステップ4。**
