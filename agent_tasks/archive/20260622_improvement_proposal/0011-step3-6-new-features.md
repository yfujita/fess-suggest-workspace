## 0. 本ドキュメントの位置づけ・前提・読み方

### 0.1 位置づけ

本ドキュメントは、fess-suggest 抜本的改善提案タスク（`20260622_improvement_proposal`）の **ステップ3-6「新機能を前提に組み込んだ設計」** の成果物である。

- **目的**: ステップ3-1（`0005-step3-1-to-be-architecture.md`）で設計したゼロベース To-Be アーキテクチャが、要件目的⑤「**サジェスト関連の新機能の検討**」を、**後付け（既存への改造）ではなく設計の最初から内包している**ことを示す。
- **主眼**: 新機能そのものを完成仕様まで詰めることではない。**3-1 が用意した拡張点（データソース抽象 §4・スコアリング機構 §9・インデックス設計 §6・テキスト処理パイプライン §5・用途別公開 API §3）に、主要な新機能候補が「載る」形で設計できることを示す**ことが本ステップの役割である。3-1 自身が §4.2／§9.2／§5.2 で「新機能(3-6)はここに載る」と拡張点を明示的に予約している事実（`0005` §4.2 162行目・§9.2 299行目・§5.2 190行目）を起点に、その予約席に各新機能を割り付ける。
- **3-6 の固有の立場（新機能を設計に内包する）**: 本書は「**新機能を、後付け改造ではなくゼロベース設計の拡張点に最初から内包する**」立場で各機能を導く。これは、現行の内部品質課題（ISS/TBD）を起点に品質を作り込む 3-4、現行の内部性能課題を起点に性能を最適化する 3-5、外部ベンチマーク（Google 検索サジェスト）との比較を起点に差分と打ち手を導く 3-7 とは役割が異なる（役割分担は §5 に明記）。
- **スコープ**: 提案（設計の検討と文書化）。コード実装・各新機能の完成仕様化はスコープ外。**移行戦略そのものはステップ4の領分**であり、本書では「あるべき姿への内包」に集中し、移行可能性・既存資産流用は対比メモ程度にとどめる。
- **ゼロベース＝全置換ではない**: 新機能の多くは、流用価値ある既存資産（テキスト処理パイプライン §5・決定的 ID 集約・roles/reading/kinds/freq 等の蓄積属性・@timestamp）の**上に載る**。安易に作り直さず、既存資産を新機能の土台として活かす（原則7, `0005` §11）。

## 1. 「新機能を設計に内包する」の枠組み（拡張点 → 新機能のマッピング軸）

新機能を「アーキテクチャと無関係な機能リスト」にしないため、本書では **3-1 が用意した5つの拡張点（E1〜E5）** を評価の骨格に置く。各新機能は「**どの拡張点に載るか（実装位置）**」で整理し、これにより「後付けでなく設計に内包されている」ことを構造的に示す。3-2 が可読性を R1〜R5、3-4 が品質を Q1〜Q5、3-5 が性能を P1〜P5 に分解したのと対をなす、**新機能の拡張点軸 E1〜E5** である。

| # | 拡張点（3-1 の該当設計） | 何を差し替え／追加できるか | この拡張点に載る新機能 |
| --- | --- | --- | --- |
| **E1** | **データソース抽象 `SuggestSource`**（`0005` §4.2） | 「外部入力 → `SuggestItem` ストリーム」への新しい語源を、共通機構（書き込み/集約/スコアリング）に手を入れず追加 | 同義語/関連語ソース、セマンティックソース、人気急上昇語ソース、（復活させるなら）クエリログソース |
| **E2** | **スコアリング機構 `ScoringStrategy`**（`0005` §9.2） | function score の構成（前方一致 weight・freq の modifier・userBoost）を差し替え、新しいスコア要素を加点 | セマンティック類似度加点、鮮度/急上昇の time-decay、パーソナライズ重み、タイプミス許容のスコア |
| **E3** | **インデックス設計・スキーマ**（`0005` §6.2.1/§6.2.2） | サジェスト用の新フィールド・アナライザ・シャード戦略を構築時に選択 | ベクトル(`knn`)フィールド[要確認]、edge n-gram/fuzzy 用フィールド、時系列 freq/timestamp、ペルソナ/履歴属性 |
| **E4** | **テキスト処理パイプライン `TextProcessor`**（`0005` §5.2、踏襲資産） | Normalizer/ReadingConverter/Analyzer の Chain に言語別・新処理を追加 | 多言語強化（言語別 Chain）、タイプミス正規化、読み変換の拡張 |
| **E5** | **用途別公開 API・レスポンス整形 `SuggestQueryService`**（`0005` §3.2/§4.2） | 蓄積属性の選択的露出、検索コンテキスト（ロール・ペルソナ）の受け取り | 蓄積属性を活かした UI/API（種別バッジ・頻度可視化・読み活用）、パーソナライズの入力経路 |

各新機能（§2）には、作業プランが必須とする次の4点を必ず付す。

- **(a) 期待効果**: 何が良くなるか（サジェスト品質・UX・カバレッジ等）。
- **(b) 実現難易度**: 低/中/高 と、その根拠（既存資産で済むか／新基盤・バージョン依存が要るか）。
- **(c) あるべき姿アーキテクチャでの実装位置**: 3-1 のどの拡張点（E1〜E5＝`0005` の節番号）に載るか。
- **(d) 要確認の前提**: TBD（特にセマンティック系は TBD-01）・プライバシー・運用前提など断定できない事項。

> **設計に内包されている根拠 [事実]**: 3-1 は新機能のために**後から拡張点を足したのではない**。`0005` は §4.2 で「新規ソースは追加だけで載る…新機能(3-6)はここに載る」（162-164行）、§9.2 で「新機能（セマンティック類似度の加点など）を載せられるように…新機能(3-6)のスコアリング拡張点」（299行）、§5.2 で「言語別の Normalizer/Converter セットを切り替え可能に…新機能(3-6)の多言語強化の土台」（190行）と、**主軸設計の段階で拡張点を予約済み**である。本書はその予約席に各新機能を割り付けるだけであり、これが「後付けでなく設計の最初から内包する」（完了目的）の具体である。

## 2. 各新機能 × 3-1拡張点の設計

作業プランが挙げる新機能候補を、E1〜E5 への割り付けとして設計する。各機能に (a)期待効果 / (b)実現難易度 / (c)実装位置（3-1 §番号）/ (d)要確認の前提 を付す。

### 2.1 同義語／関連語サジェスト（E1 中心）

**現状 [事実]**: 同義語辞書は**独立したデータソースではなく**、OpenSearch アナライザ（`suggest_analyzer.json` 等）側のテキスト解析の一部にすぎない（`legacy/03` 3.2、32行）。サジェスト語そのものを供給するのは4経路（ドキュメント本文/クエリログ/検索語/elevate word）のみで、同義語・関連語は「語管理・スコアリングの対象になる第一級の候補」にはなっていない。

- **(a) 期待効果**: 「車」と入力したとき同義語「カー/自動車」、関連語「中古車/車検」を候補に出せる。同義語をアナライザ任せにせず**独立ソース化**することで、(1) 同義語候補そのものを `SuggestItem` として語管理（bad word 除外・elevate）でき、(2) スコアリング（§9.2 `ScoringStrategy`）で同義語/関連語の重みを制御でき、(3) 由来（kinds）を区別して提示できる。サジェストのカバレッジ（出すべき良質候補の取りこぼし防止）を語源の面から広げる。
- **(b) 実現難易度**: **中**。同義語は fess 本体に既に辞書資産がある（アナライザ用辞書）ため、それを `SynonymSource` として読み込み `SuggestItem` 化する設計は現実的。関連語（co-occurrence/関連クエリ）は検索ログからの共起計算という新規ロジックが要るため、同義語より重い。いずれも共通機構（書き込み/集約/スコアリング）には手を入れない。
- **(c) 実装位置**: **E1 = `SuggestSource` 抽象（`0005` §4.2）** に `SynonymSource`／`RelatedWordSource` を追加実装するだけで載る（`0005` 162-163行が明示的に予約）。スコアリング上の重み付けは **E2 = `ScoringStrategy`（§9.2）**。同義語候補の表記ゆれ吸収は **E4 = テキスト処理（§5）** の踏襲資産が支える。
- **(d) 要確認の前提**: 関連語の生成ロジック（共起ウィンドウ・閾値）は実データ依存で要設計。同義語を「展開してからサジェスト候補化」するか「クエリ時に同義語展開してマッチ」するかの方式選択は、前方一致サジェストとの整合（§6.2.1 の keyword 設計）を要確認。
- **ISS との関係**: ISS-12（人気語/候補のカバレッジ拡張）の**新機能展開側**。なお「現行人気語条件の硬直を緩める」品質側は 3-4 §2.6 が主担当（再掲せず参照）。

### 2.2 パーソナライズ（ロール・履歴）（E5/E2/E3）

**現状 [事実]**: `SuggestItem` は `roles`（空なら `_guest_` 補完）を持ち（`legacy/03` 3.5、73行）、検索時は権限フィルタとして roles でマッチを絞る（`0005` §10、二重担保 ISS-06）。一方、**ユーザ個人の検索履歴・文脈に基づくパーソナライズは存在しない**（候補は全ユーザ共通で、ロールによる可視範囲制御のみ）。

- **(a) 期待効果**: (1) **ロールベース**: 既存の roles を「可視範囲フィルタ」だけでなく「ランキングの文脈（このロールがよく使う語を上げる）」にも使い、ロール文脈に合った候補を上位化。(2) **履歴ベース**: ログインユーザの過去検索・クリック履歴を文脈として、本人が再訪しやすい語を優先。エンタープライズ検索では部署/職種（ロール）単位のパーソナライズが特に費用対効果が高い。
- **(b) 実現難易度**: **低〜中**。ロール文脈は roles 属性が既にインデックスにあるため、ランキング要素への転用は比較的軽い（`ScoringStrategy` の加点項を足す）。個人履歴ベースは履歴の蓄積・保持基盤（どこに履歴を持つか）とプライバシー設計が新規に必要で重くなる。
- **(c) 実装位置**: **E5 = `SuggestQueryService`（`0005` §3.2）** が検索コンテキスト（呼び出しユーザのロール集合・ペルソナ）を受け取る入力経路を持つ（権限の roles 受け渡しは §10 `AuthorizationFilter` が既に担うため、その文脈を**ランキング用にも渡す**形）。ランキング反映は **E2 = `ScoringStrategy`（§9.2）**。履歴/ペルソナ属性をインデックス側に持つ場合は **E3 = スキーマ（§6）**。
- **(d) 要確認の前提**: 個人履歴の保持はプライバシー・データ保持ポリシー（GDPR 等）の要確認事項。ロール文脈ランキングは、ロール集合が大きいときのスコア計算コスト（P3 検索レイテンシ）への影響を 3-5 と連携して確認。fess 本体側のユーザ/履歴連携 API の有無は要確認（移行はステップ4）。
- **ISS との関係**: ISS-11（roles 含む蓄積属性の活用）の一面。権限フィルタの責務（ISS-06）は §10 が主担当で、本機能は「roles を可視範囲だけでなくランキング文脈にも使う」拡張という切り分け。

### 2.3 文脈・セマンティック（ベクトル/埋め込み）サジェスト（E1/E3/E2、TBD-01 要確認）

**現状 [事実]**: 現行のマッチングは前方一致（keyword に対する prefix・function score の `weightFactorFunction`、`legacy/03` 3.4）と読み変換による表記ゆれ吸収が中心で、**意味的類似（埋め込みベクトルによる近傍）でのサジェストは存在しない**。

- **(a) 期待効果**: 表層が一致しなくても**意味が近い**候補を出せる（例: 「pc 不調」→「パソコン 故障 修理」）。タイプの綴り・語順に依存しない意図ベースのサジェスト。エンタープライズ文書の専門語・言い換えに強い。
- **(b) 実現難易度**: **高**。(1) 埋め込み生成基盤（モデル・推論経路）が新規に必要、(2) ベクトル近傍検索（`knn` 等）の OpenSearch プラグイン/バージョン依存、(3) サジェスト特有の低レイテンシ・高 QPS 要件（`0005` §9.2、逐次入力追従）下でベクトル検索のコストが許容内かの検証、が揃って初めて成立する。本書の新機能の中で最も重い。
- **(c) 実装位置**: **E1 = `SuggestSource` 抽象（`0005` §4.2、`SemanticSource`）** ＋ **E3 = スキーマ（§6、ベクトルフィールド）** ＋ **E2 = `ScoringStrategy`（§9.2、セマンティック類似度の加点）**。3-1 は §4.2 のレイヤ図（`0005` 81行）で `[新]SemanticSource` を、§9.2（299行）で「セマンティック類似度の加点」を**明示的に拡張点として予約済み**であり、セマンティックは「載せる席」が設計に最初から確保されている。
- **(d) 要確認の前提（TBD-01）[要確認]**: **`knn`／ベクトル近傍検索／埋め込み連携 API の利用可否は OpenSearch/Lucene の数値バージョン未解決（TBD-01, `0002` TBD-01）に依存し、断定しない**。埋め込み生成の運用コスト（インデックス時/クエリ時）、ベクトル次元・インデックス容量（P5）、QPS 下のレイテンシ（P3）はいずれも実測・前提確認が必要。本書は「セマンティックは E1/E3/E2 の拡張点に載る」という設計上の道筋のみを示し、実現可否は要確認とする。
- **役割分担**: Google 比較を起点にした「セマンティック/意図理解」の差分は **3-7 の領分**。本書は「3-1 の拡張点に内包できる」立場を示し、3-7 は比較起点の打ち手として本書の実装位置を参照する（再掲しない）。

### 2.4 タイプミス補正（fuzzy／あいまい一致）（E4/E3/E2）

**現状 [事実]**: 表記ゆれ（全角半角・かな/カナ・ローマ字）は Normalizer/ReadingConverter で吸収するが（`0005` §5）、**綴り誤り（タイプミス）に対する fuzzy/編集距離ベースの補正は持たない**。`text` は keyword 非解析（ISS-04, `mappings-default.json:48-50`）で、前方一致が主。

- **(a) 期待効果**: 「komyunike-syon」「コミニュケーション」のような綴り誤り・揺れに対しても正しい候補（「コミュニケーション」）を提示。入力途中の打ち間違いに強くなり、UX が向上。
- **(b) 実現難易度**: **中**。fuzzy（編集距離）・edge n-gram アナライザは OpenSearch の標準機能で実装可能だが、(1) 誤補正（出すべきでない語を拾う）と前方一致精度のトレードオフ、(2) keyword 中心の現行スキーマに fuzzy 用フィールド/アナライザを足す設計、が要る。誤補正リスクの調整が品質上の肝。
- **(c) 実装位置**: **E4 = テキスト処理パイプライン（`0005` §5.2、タイプミス正規化を Chain に追加）** ＋ **E3 = スキーマ（§6.2.1、edge n-gram/fuzzy 用フィールド追加。現行 keyword は維持しつつ補完用フィールドを併設）** ＋ **E2 = `ScoringStrategy`（§9.2、fuzzy ヒットは完全一致より低い重みにする）**。
- **(d) 要確認の前提**: fuzzy のマッチ方式（`fuzzy` クエリ／edge n-gram／日本語のかな誤りに効く方式）と weight 設計は OpenSearch バージョン依存 API・スキーマ詳細に関わるため TBD-01／3-5 と連携で要確認。誤補正の許容度は実データでのチューニングが必要。
- **役割分担**: Google 比較起点の「タイプミス補正・fuzzy」差分は **3-7 の領分**。本書は設計内包の道筋（E4/E3/E2）を示し、3-7 は比較起点の打ち手として参照する。

### 2.5 人気急上昇語（トレンド/サージ）（E1/E2/E3）

**現状 [事実]**: 頻度は `queryFreq`/`docFreq` を**累積加算**でマージし（`legacy/03` 3.4、49行）、`@timestamp` は最新で置換する。人気語（popularWords）は `Kind=query`・単一語・`queryFreq>=10` の**累積頻度ベース**で、時系列の急上昇（直近で伸びた語）という概念がない（ISS-12, `PopularWordsRequest.java:212-214`）。

- **(a) 期待効果**: 「累積でよく検索される語」だけでなく「**直近で急に増えた語**」を提示できる。社内の話題・季節性・インシデント語など、鮮度の高いサジェストでカバレッジと有用性を高める。
- **(b) 実現難易度**: **中**。現行は累積 freq のみで時系列バケットを持たないため、(1) 時間窓ごとの頻度集計（time-bucketed freq）または rolling window の集計ロジック、(2) 急上昇スコア（直近 window / 過去平均の比など）の設計、が新規に必要。ただし @timestamp と freq 集約という既存資産の延長に載るため、ゼロからではない。
- **(c) 実装位置**: **E1 = `SuggestSource`（`0005` §4.2、時系列集計を行う `TrendingSource` 的供給）** ＋ **E2 = `ScoringStrategy`（§9.2、time-decay/急上昇加点）** ＋ **E3 = スキーマ（§6、時系列 freq/timestamp フィールド）**。人気語の対象条件（Kind/語数/freq 閾値）を `ScoringStrategy`／クエリ構成の調整可能パラメータにする方針（`0009` §2.6）の上に、時間軸を足す形。
- **(d) 要確認の前提**: 時間窓のサイズ・急上昇の定義（閾値）は運用/実データ依存で要設計。時系列バケットを持つとインデックス容量・集計コスト（P5/P1）が増えるため 3-5 と連携。
- **ISS との関係**: ISS-12（人気語のカバレッジ・表現力）の**新機能展開側**（累積→鮮度/急上昇への拡張）。現行人気語条件の硬直を緩める品質側は 3-4 §2.6 が主担当。鮮度/トレンドの Google 比較差分は 3-7。

### 2.6 多言語強化（E4 中心、踏襲資産の拡張）

**現状 [事実]**: テキスト処理は日本語特化（`KatakanaConverter`・`KatakanaToAlphabetConverter`・`HankakuKanaToZenkakuKana` 等、`0005` §5.1）。Normalizer→ReadingConverter→Analyzer の Strategy+Composite 構成は**責務分割が良好な踏襲資産**だが、言語別 Chain の切り替え機構は明文化されていない。

- **(a) 期待効果**: 日本語以外（英語以外の欧州言語・中韓・東南アジア言語等）の正規化・読み/転写変換を足し、多言語コーパスでのマッチ精度（表記ゆれ・転写ゆれの吸収）を高める。グローバル運用のエンタープライズ検索でカバレッジを広げる。
- **(b) 実現難易度**: **中**。パイプライン自体は拡張容易な踏襲資産（原則7）で土台が既にあるため、機構面は軽い。重いのは各言語の正規化規則・辞書整備（言語ごとの品質作り込み）。
- **(c) 実装位置**: **E4 = テキスト処理パイプライン（`0005` §5.2）**。3-1 が「言語判定 → 言語別 Chain 選択」「新機能(3-6)の多言語強化の土台」と明示的に予約済み（`0005` 190行）。言語別ソースが要るなら **E1** も併用。
- **(d) 要確認の前提**: 言語判定の方式・精度、言語別辞書の入手/整備コストは要確認。OpenSearch 側の言語別アナライザのバージョン対応は TBD-01 に一部依存。
- **役割分担**: 「多言語・かな/ローマ字・表記ゆれの吸収」の Google 比較差分は 3-7。テキスト処理精度（Q5）という品質基盤としての位置づけは 3-4 §2.8（踏襲資産）が扱済みで、本書は「多言語を新機能として展開する」面に集中（再掲せず参照）。

### 2.7 蓄積属性（reading/kinds/freq 等）を活かした UI/API（E5 中心、ISS-11 主担当）

**現状 [事実]**: `SuggestItem` は reading（読み, String[][]）/kinds/queryFreq/docFreq/userBoost/roles/tags/languages 等の豊富な属性を持つ（`legacy/03` 3.5、71-73行）が、**UI に最終的に出るのは `text` と `tags`（types）のみ**で、読み・頻度・kinds は API レスポンスに含めない（ISS-11, `legacy/04` 4.5）。蓄積データが UI で死蔵している。

- **(a) 期待効果**: 蓄積属性を UI/API で活かした新機能を展開できる。例: (1) **種別バッジ**（kinds で「人気検索語」「文書由来」「登録語」を区別表示）、(2) **頻度可視化**（freq で確からしさ・人気度をヒント表示）、(3) **読み活用 UI**（reading でかな入力中のグルーピング・補助表示）。候補の情報量と選びやすさ（UX）を高める。
- **(b) 実現難易度**: **低**。属性は既にインデックスに蓄積済みで、必要なのは「レスポンスに選択的に載せる」ことと UI 側の表示。新基盤は不要で、本書の新機能の中で最も着手しやすい。
- **(c) 実装位置**: **E5 = `SuggestQueryService` のレスポンス整形（`0005` §3.2）＋ `SuggestSource` が produce する属性の選択的露出（§4.2）**。3-1 は §4.2（164行）で「ソースが produce する `SuggestItem` の属性（reading/kinds/freq 等）を、レスポンス整形側が選択的に露出できるようにし、ISS-11 の死蔵属性を新機能に転用可能にする」と明示している。
- **(d) 要確認の前提**: どの属性をどの粒度で露出するかは UI 要件依存（fess 本体側の表示設計と連携）。レスポンスサイズ増（detail 取得）と検索レイテンシのトレードオフは軽微だが 3-5 と整合確認。`suggestDetail` の既定挙動（ISS-03、`items` が常に返る）への暗黙結合を新設計では断つ（`0005` §3.2）。
- **ISS との関係**: **ISS-11（蓄積属性の死蔵）の新機能展開側の主担当**。「蓄積属性を品質材料に転用する素地」までは 3-4 §2.6 が扱い、本書が「種別バッジ・頻度可視化・読み活用 UI という新 UI/API 機能」を主担当として引き受ける（`0009` §6.2 が本書に明示的に譲っている）。
