# 作業プラン: 20261109_suggest_improve_quality

## 概要

改善点 #2「複合語・固有名詞が候補にならない」（`agent_docs/global/improvement_points/20261109/suggest_quality_evaluation.md`）を、原因調査 → 改善案の比較 → 実装 → 実機確認の順で改善する。修正は原則 `modules/fess-suggest` で完結させる。

## 前提・スコープ

- 対象: 文書（content/title）由来の候補生成。主な実装箇所は `DefaultContentsParser#parseDocument`（解析トークン1件を1候補にしている）。
- 前提となる事実 [確認]
  - 文書解析は OpenSearch の `_analyze` API（`AnalyzerSettings.DefaultContentsAnalyzer`）で `contents_analyzer[_ja]` を使う。
  - fess 実行時のアナライザー定義は fess 側の `modules/fess/src/main/resources/suggest_indices/suggest_analyzer.json`（`fess_japanese_normal` = normal モード、`pos_filter` で `名詞-接尾`・`接頭詞`・`名詞-数` 等を除去）が使われる。fess-suggest 同梱の定義は使われない。
  - `_analyze` の応答トークンは term / position / startOffset / endOffset を持つ。品詞は通常応答に含まれない。
- スコープ外: #1（複数語入力）、#3 以降のノイズ除去、並び順調整。ただし本改善がそれらを悪化させないことは確認する。

## 方針

- 解決対象語: `新型コロナ`・`高市早苗`・`石破首相`・`ワクチン接種`。`大統領選`・`円安` のように `名詞-接尾` 除去で構成語が消える語は、ステップ1の結果を見て対象にするか判断する（対象にする場合は案C/Dが必要で、fess-suggest 内完結と両立しない可能性がある）。
- 既定値: 結合機能は設定キーで有効/無効を切り替え可能とし、既定は有効。無効時は従来と同一の結果になる。
- 構成語（`新型`・`コロナ` など）は従来どおり候補に残す。
- ノイズ対策: 結合数の上限（3語まで）と長さ上限（30文字）のみ。頻度条件（案B）は入れず、実機結果を見て必要なら再検討する。
- 実機比較: 評価時と同じクロールデータを使い、サジェスト索引だけを作り直して改善前後を比較する。

## ステップ

### ステップ1: 原因調査
- 担当: tech-architect（必要に応じ debugger）
- 成果物: `0002-cause-investigation.md`
- 確認すべき点
  1. 評価で0件だった語（`新型コロナ`、`大統領選`、`高市早苗`、`石破首相`、`ワクチン接種`、`円安`）を fess の `contents_analyzer_ja` / `contents_reading_analyzer_ja` で実際に解析し、分割単位・除去されるトークン（例: `選`、`安` が `名詞-接尾` で消えるか）・position/offset の連続性を確認する。
  2. `parseDocument` で隣接判定に使える情報（position の飛び、offset の連続、`text.split("\\s")` とバッファ分割 `maxAnalyzedContentLength` による境界）を確認する。読みトークンとの件数一致前提（`readingTokens.size() != tokens.size()`）が結合時にどう扱えるか。
  3. クエリ側（`SuggestQueryBuilder`、`reading_term_analyzer` 等）で `新型コロナ` のような入力がどう解析・照合されるか。複合語を索引しても照合で落ちないか。
  4. 頻度・閾値（`suggest.min.hit.count`、docFreq 等）による欠落の有無。
  5. 既存単体テスト（`DefaultContentsParserTest` 等）と、OpenSearch を使う統合テストの実行可否。
- 完了条件: #2 の原因が「分割」「品詞除去」「クエリ側」「閾値」のどれ（複数可）か、事実で説明できている。

## 検証方針

- 単体テスト: `AnalyzeToken` を模したトークン列を `SuggestAnalyzer` のスタブで与え、`parseDocument` の出力候補（語・読み・件数）を検証する。OpenSearch を使う既存統合テストが動く場合は日本語文での結合も確認する。

## リスク

- 頻度閾値（案B）を入れる場合、小規模データ（100件）では閾値が効きすぎる恐れがある。

- 候補件数・索引サイズの増加と、それに伴うサジェスト生成時間の増加。
- 結合語のノイズ化（`日本経済新聞社長` のような過結合）。結合上限で抑える。
- 読みトークン件数が一致しない場合の読み付与（現状は読み変換にフォールバック）。
- 再索引が必須となるため、確認手順に既存索引の削除を含める必要がある。
