# ステップ3-3: 変更容易性の向上が To-Be でどう実現されるか

## 0. 本ドキュメントの位置づけ・前提・読み方

### 0.1 位置づけ

本ドキュメントは、fess-suggest 抜本的改善提案タスク（`20260622_improvement_proposal`）の **ステップ3-3「変更容易性の向上が To-Be でどう実現されるか」** の成果物である。

- **目的**: ステップ3-1（`0005-step3-1-to-be-architecture.md`）で設計したゼロベース To-Be アーキテクチャが、要件目的②「**コードの変更容易性の向上**」をどう満たすかを照合・補強する。
- **主眼**: 新しいアーキテクチャを設計し直すことではない。**3-1 の各設計判断を「変更容易性」という観点で読み解き、現行課題（ISS）がどの設計判断でどう解消されるかの対応を明示する**ことが本ステップの役割である。
- **姉妹ステップ 3-2（可読性）との観点の違い**: 直前の 3-2（`0006-step3-2-readability.md`）が可読性=「**読めばわかるか**」を担当したのに対し、本書 3-3 は変更容易性=「**変えやすいか**」を担当する。同じ設計判断（例: §3.2 のファサード分離、§7.2.1 の単一マージ規則）を扱っても、3-2 は「読み手の理解コスト」を、3-3 は「変更を加えるときの作業コスト・波及範囲・事故リスク」を評価軸とする。両者は相補的で、重複する ISS は観点を分けて扱う（役割分担は §7 に明記）。
- **スコープ**: 提案（設計の検討と文書化）。コード実装はスコープ外。移行戦略そのものは**ステップ4の領分**であり、本書での「漸進案との対比」は**変更容易性観点の対比メモ**にとどめ、移行経路の詳細には踏み込まない。
- **ゼロベース＝全置換ではない**: 流用価値ある資産（特に充実した既存テスト群、責務分割の良いテキスト処理パイプライン）は「あるべき姿でも踏襲・再利用する資産」として位置づける（原則7, `0005` §11）。変更容易性の観点では、これら資産は「回帰を恐れず変えるためのセーフティネット」「拡張点として活かす土台」として積極的な役割を持つ。

## 1. 「変更容易性」の評価軸の定義（何をもって"変えやすい"とするか）

変更容易性を抽象論で終わらせないため、本書では「変えやすい」を次の5つの具体的な評価軸に分解する。各設計判断は「どの軸で変更コスト・波及範囲・事故リスクを下げるか」で評価する。3-2 が可読性を R1〜R5 に分解したのと対をなす、変更容易性の軸 **M1〜M5** である。

| # | 評価軸 | 定義（"変えやすい"の具体） | 主に効く現行課題 |
| --- | --- | --- | --- |
| **M1** | **拡張点の存在（Open-Closed / Pluggable）** | 新規のサジェストソース・スコアラ・コンバータ・語管理規則を、**既存コードを触らずに追加だけで載せられる**。機能追加が「経路の改造」ではなく「実装クラスを足す」になる。 | ISS-01, ISS-04, ISS-15 |
| **M2** | **変更の局所性（Single Source of Truth / Locality）** | ある規則（マージ・権限・ランキング）の変更が**1箇所の編集で完結**し、複数箇所の同期を要しない。ある用途の変更が他用途へ波及しない（影響範囲が予測可能で狭い）。 | ISS-05, ISS-06, ISS-13 |
| **M3** | **結合度の低減（Low Coupling）** | 暗黙のデフォルト依存・二重担保・過渡シムを排し、**遠隔のサイレント破壊**（既定値変更が遠くの Handler を壊す）や**二箇所同期の強制**が起きない。変更の影響が型・シグネチャで可視化される。 | ISS-03, ISS-06, ISS-17 |
| **M4** | **標準化・一貫性（Standardization & Uniformity）** | 独自基盤ではなく標準機構（`CompletableFuture`・型付き設定）を使い、同期/非同期境界や設定の単位が一貫する。**標準知識で変更でき、単位の取り違え等の事故が構造的に起きない**。非同期化の追加・設定追加が一律のやり方で済む。 | ISS-09, ISS-02 |
| **M5** | **テスト容易性（Testability）** | 充実した既存テスト資産をセーフティネットとして活かし、`internal` 化と公開 API 縮小でテスト対象（公開契約）を安定させる。**回帰を恐れずに内部実装を変えられる**。 | 横断（全 ISS の変更を支える土台） |

> 補足: M1〜M5 は独立ではなく相補的である。「拡張点（M1）」は「変更の局所性（M2）」の前提（拡張点があれば既存を変えずに済む＝局所性が最大化）であり、「結合度の低減（M3）」と「標準化（M4）」は「テスト容易性（M5）」を助ける（依存が薄く標準的なほどテストしやすい）。`0005` §1 の設計原則（拡張点ファースト＝原則2／単一の真実＝原則3／デッドコードを持たない＝原則4／一貫した同期非同期＝原則6／流用価値ある資産は踏襲＝原則7）が、ここで言う変更容易性軸とほぼ一対一で対応している。**変更容易性は 3-1 設計の副産物ではなく、設計原則そのものに織り込まれている。**

## 2. 各設計判断 × 変更容易性の整理

3-1 のレイヤ設計（§3〜§10）を、変更容易性観点で読み解く。各項に **(a) どう変えやすくなるか（評価軸 M1〜M5 で）** / **(b) 解消される ISS** / **(c) 漸進案との変更容易性対比** を添える。設定の一元化・型安全（ISS-02）とテスト容易性は、それぞれ可読性版が ISS-02／参考節を専節化したのと同様、本書でも §3／§4 に専節を設ける。

### 2.1 §3 用途別 API 分離 — 変更影響範囲の局所化と過渡コードの不在

3-1 §3.2 は、肥大化した単一ファサード（`Suggester` 507行/public約18、`SuggestIndexer` 547行/public約28、出典: ISS-13, `0005` §3.1）を、用途別の4インタフェース（`SuggestIndexLifecycle` / `SuggestQueryService` / `SuggestWordAdmin` / `SuggestIngestService`）へ再編し、Operations 群・Writer・Serializer・Store 実装を `internal` 化する。

- **(a) どう変えやすくなるか**
  - **M2（変更の局所性）**: 現状は1つのファサードに lifecycle・query・word-management・indexing の全責務が同居するため、ある用途（例: 語管理 API の引数追加）を変えると、同じクラスを共有する他用途（検索・ライフサイクル）にも**コンパイル単位・テスト単位の影響が及ぶ**（507/547行クラスを再ビルド・再テスト）。用途別 IF へ分離すると、**「`SuggestWordAdmin` の変更は word-management 利用者にしか波及しない」**と影響範囲が IF 境界で区切られる。変更の影響予測が容易になり、誤って無関係の用途を壊すリスクが下がる。
  - **M3（結合度の低減）**: `@Deprecated` 委譲シム（ISS-17, 出典: `SuggestRequest.java:243-326`）を最初から作らないため、**変更時に「旧シムとの整合を保つ」作業が不要**になる。現状は `buildQuery`/`buildFunctionScoreQuery` 等が `SuggestQueryBuilder` へ抽出済みだが本体に委譲メソッドが残るため、クエリ構築ロジックを変えるたびに「抽出先と委譲シムの両方が整合しているか」を気にする必要がある。To-Be では過渡コードが存在しないため、この二重メンテナンスが消える。
  - **M1（拡張点）への波及**: 公開面が用途別に絞られることで、内部実装（Operations・Store）を**公開契約を変えずに差し替え**られる。例: 書き込み機構を Get-then-update から upsert（§7.2.2）へ変えても、`SuggestIngestService` の公開シグネチャが不変なら利用側は無改修。
- **(b) 解消される ISS**: ISS-13（ファサード肥大→変更影響の局所化）、ISS-17（Deprecated 委譲シムの二重メンテナンス排除）。
- **(c) 漸進案との変更容易性対比**: 漸進案（`0005` §3.3(c)）は「28メソッドを用途別 IF へ切り出して `Suggester` から委譲し、`@Deprecated` シムを段階削除する」。移行過渡期は**内部委譲（Operations）／新公開 IF／旧ファサードの三層が併存**するため、その期間はむしろ「変更を3層に伝播させる」コストが一時的に増す。ゼロベース To-Be は最初から三層併存がない分、変更容易性のゴール状態が明快。ただし過渡期コストの実際の重さは移行戦略（ステップ4）の論点。

### 2.2 §4 データソース抽象 — 新規ソースを「既存を触らず追加」できる拡張点

3-1 §4.2 は、現行4経路（うち ISS-01 のクエリログ経路はデッドパス）を `SuggestSource` プラグイン抽象へ再設計する。各ソースは「外部入力 → `SuggestItem` ストリーム」への変換だけを担い、書き込み・集約・スコアリングはソース非依存の共通機構（§7〜§9）が担う。

- **(a) どう変えやすくなるか**
  - **M1（拡張点）— 本書の中核**: 現状はサジェスト語の供給が「閉じた4経路の `indexFromXxx` メソッド群」で、同義語は独立データソースですらなくアナライザ任せ（出典: ISS-01 周辺, `legacy/03` 3.2）。新しい語源（同義語・関連語・セマンティック）を加えるには**既存の経路コードを改造**する必要があり、Open-Closed 原則に反する。To-Be では `SynonymSource`/`RelatedWordSource`/`SemanticSource` を**`SuggestSource` 実装として足すだけ**で載り、共通機構（マージ・スコアリング・書き込み）には一切手を入れない。これが「変えやすさ」の最大の源泉であり、新機能（3-6）の追加容易性そのものを支える。
  - **M3（結合度の低減）への波及**: ISS-01 のクエリログ経路を「標準実装として持たず、必要なら `QueryLogSource` を追加するだけの拡張点にする」（`0005` §4.2）ことで、**デッドパスを保守し続ける負債が消える**。「使われない経路を残したまま他を変える」際に発生していた「この経路にも影響しないか」という確認作業が不要になる。
- **(b) 解消される ISS**: ISS-01（デッドパスを最初から作らず、未実装の拡張点に転換）。
- **(c) 漸進案との変更容易性対比**: 漸進案（`0005` §4.3(c)）は「②を削除し残り3経路を `SuggestSource` に後付け切り出し（アダプタで包む）」。デッドパス削除（ISS-01）は漸進でも達成でき、新規ソース追加の拡張点も「アダプタ＋新実装」で得られる。差が出るのは拡張の純度: アダプタ経由だと旧 `indexFromXxx` の形が透けて残り、新ソース追加時に「アダプタ層の作法に合わせる」一手間が残る。ゼロベースの素直な `SuggestSource` 実装ほどには追加が軽くならない。

### 2.3 §3.2 detail 設計 — 暗黙のデフォルト依存（ISS-03）を型で断つ

ISS-03 は「`SuggestWordsHandler` が `items`（text/tags）を参照するが `setSuggestDetail(true)` の明示呼び出しを持たず、`SuggestRequest.suggestDetail` の既定値 `=true`（出典: `SuggestRequest.java:103`）に暗黙結合している」課題である。変更容易性の観点では、この暗黙結合は **「1箇所の既定値変更が、明示呼び出しを持たない遠隔の Handler をサイレント破壊しうる」** という、変更の影響が局所化されていない典型例である。

- **(a) どう変えやすくなるか**
  - **M3（結合度の低減）**: 現状、`SuggestRequest.suggestDetail` の既定値を `false` に変えると、明示的に `true` を設定していない `SuggestWordsHandler` が突然 `items` を受け取れなくなる — **変更箇所（`SuggestRequest`）と破壊される箇所（Handler）が離れており、コンパイラも警告しない**。3-1 §3.2 は detail 取得を API 名/型から自明にする設計（`suggestWithDetail(...)` と最小レスポンス版を型で分ける）を採るため、**「detail が必要な呼び出し側は detail 版を呼ぶ」が型契約として固定**される。既定値という遠隔の暗黙パラメータが消え、detail の有無を変えても影響が型シグネチャの変更として可視化される（呼び出し側がコンパイルエラーで気づく）。「サイレント破壊」が「コンパイル時検出」へ変わるのが本質。
- **(b) 解消される ISS**: ISS-03（detail 既定値への暗黙結合）。
- **(c) 漸進案との変更容易性対比**: 漸進案は「Handler 側で `setSuggestDetail(true)` を明示呼び出しする」。これで暗黙結合は解消し、既定値変更で壊れなくなる — 変更容易性（M3）は改善する。ゼロベース案との差は「明示呼び出しを**書き忘れられる**余地が残るか否か」。型で分ける（`suggestWithDetail` を呼ばないと items 型が手に入らない）と、新たな呼び出し箇所を追加する将来の変更でも書き忘れがコンパイル時に防がれる。漸進案のフラグ明示は実行時の規律にとどまり、新規呼び出し追加時に再発しうる。

### 2.4 §7.2.1 単一マージ規則 — 規則変更を1箇所に集約

3-1 §7.2.1 は、現状2クラスに重複実装されたマージ規則を、**ただ一つの `SuggestItemMergePolicy`** に統一する。

- **(a) どう変えやすくなるか**
  - **M2（変更の局所性）— 本書の中核**: 現状、マージ規則は `SuggestItemMerger.merge`（`:59-96`、オブジェクト同士）と `SuggestItemSerializer.toUpdatedSource`（`:142-185`、item と OpenSearch Map）に**二重実装**され、readings の走査基準すら非対称（前者=text 語数 `:70-75` / 後者=新 item の reading 配列長 `:146-158`、出典: ISS-05）。この状態で「マージ規則を変える」（例: 新フィールドを集合和に加える、頻度の加算方法を変える）には、**2クラスを同期して編集し、走査基準の差が結果に与える影響まで両方で検証**しなければならない。片方だけ直せば二段マージ（バルク内／既存doc）で挙動が食い違う。To-Be では規則が1箇所にあるため、**「マージ挙動を変える＝1つの `SuggestItemMergePolicy` を編集する」**で完結し、二段あっても適用規則は同一定義を参照する。二重メンテナンスによる不整合リスク（ISS-05 が指摘する取りこぼし疑いの温床）が構造的に消える。
  - **M5（テスト容易性）への波及**: 規則が1箇所なら、マージのテストも1つの `SuggestItemMergePolicy` に対する単体テストへ集約でき、既存の両クラス向けテスト資産（`0005` §11、main vs test 比から手厚い）を統合・流用しやすい。
- **(b) 解消される ISS**: ISS-05（マージ規則の二重実装・走査基準非対称・取りこぼし疑い）。
- **(c) 漸進案との変更容易性対比**: 漸進案（`0005` §7.3(c)）は「2クラスのマージ規則を共通ヘルパに抽出して呼び分ける」。変更容易性（M2）の改善は漸進でも本質的に達成できる — 規則本体が共通ヘルパ1箇所に集約されれば、「規則を変える＝ヘルパを変える」で足り、呼び出しが2箇所でも規則は単一。ゼロベースとの差は小さく、ここは「漸進でゴールに到達しやすい」課題。

### 2.5 §10.2 権限フィルタの責務集約 — 二箇所同期の排除

3-1 §10.2 は、権限フィルタの責務を**単一の `AuthorizationFilter`**（Domain Core）へ集約し、ライブラリ側とアプリ側で同じフィルタを二重に組まない設計にする（fess 本体は「ロール集合を渡す」責務、ライブラリは「ロール集合をクエリへ反映する＝`_guest_` 補完含む」責務、と1回ずつに分ける。デフォルト deny をフェイルセーフとして要件化）。

- **(a) どう変えやすくなるか**
  - **M2（変更の局所性）＋ M3（結合度の低減）**: 現状は権限フィルタが二重担保 — ライブラリ側 `_guest_` 補完（`SuggestRequest.java:354-356`）＋ API 側 `RoleQueryHelper` の `addRole`（`SuggestWordsHandler.java:83`、出典: ISS-06）。権限ロジックを変える（例: ゲストの扱いを変更、新しいロール条件を追加）には**ライブラリ側とアプリ側の二箇所を同期して変更**する必要があり、片方だけ変えると安全側／非安全側どちらかに崩れる。責務境界が曖昧で「どちらが本体か」が決まっていないため、変更の置き場所自体が判断を要する。To-Be では権限条件構築が `AuthorizationFilter` 1箇所に集約され、**「権限の挙動を変える＝`AuthorizationFilter` を変える」**で完結する。アプリ／ライブラリの責務が「渡す／反映する」と一文で割れるため、変更をどちらに置くかが自明になる。
  - **安全性を変更容易性のために犠牲にしない**: フェイルセーフ（デフォルト deny、`0005` §10.2）を要件化することで、二重担保が結果的に担保していた「アプリ側の受け渡し漏れでも露出しない」安全性を、一元化後も型／設計で保証する。**変更容易性の向上が安全性の後退を招かない**点が設計上の肝。
- **(b) 解消される ISS**: ISS-06（権限フィルタの二重担保・二箇所同期）。
- **(c) 漸進案との変更容易性対比**: 漸進案（`0005` §10.3(c)）は「二重担保の一方を残し他方を薄くして責務を片側に寄せる」。変更容易性（M2/M3）は「変更の置き場所が片側に寄る」ことで改善するが、ゼロベースの「単一 `AuthorizationFilter` への明確な集約」ほどには綺麗に割れず、fess 連携 API を変えない範囲に留めるため責務の中途半端な分担が残りうる。**[要確認]** fess 本体 `RoleQueryHelper` との責務再配置は連携 API の変更を伴い、fess 連携部のテストが手薄な可能性（`0005` §10.2, `0003` §3.2）があるため、移行時のテスト補強が必要（ステップ4）。

### 2.6 §8.2 同期/非同期モデルの統一 — 一貫した並行モデルへ（ISS-09, 本書の主担当）

3-1 §8.2 は、独自 `Deferred`/`Promise` を標準機構（`CompletableFuture` 等）へ統一し、同期/非同期境界の規則を一本化する（I/O 操作は非同期を基本、同期版は非同期版の `.join()` ラッパとして一箇所で提供）。**ISS-09 は変更容易性軸の主担当課題であり、本書が正面から扱う。**

- **(a) どう変えやすくなるか**
  - **M4（標準化・一貫性）— 本書の中核**: 現状は「検索は常に非同期、登録は Reader 系のみ非同期、単発系（`index`/`indexFromSearchWord` 等）は同期」と**API ごとに境界が不均一**（出典: ISS-09, `legacy/01`/`02`）。この不均一さは変更容易性を二重に毀損する。第一に、**あるメソッドを新たに非同期化したい／逆に同期化したい**とき、独自 `Deferred`/`Promise` の作法を学んで個別に実装する必要があり、追加・変更のたびに「このメソッドはどちらの流儀か」を判断させられる。第二に、独自基盤そのものの保守（バグ修正・機能追加）が**標準ライブラリの進化から取り残された自前コードの維持コスト**を生む。To-Be では「I/O は非同期、同期版はラッパ」という**単一規則**と標準 `CompletableFuture` を採るため、(1) 新規メソッドの並行モデルは規則から自動的に決まり（判断不要）、(2) 非同期合成（`thenCompose`/`allOf` 等）が標準 API で書け、(3) 独自基盤の保守負担が消える。**「非同期化の追加・変更が一律のやり方で済む」**のが変更容易性の本質。
  - **M5（テスト容易性）への波及**: 標準 `CompletableFuture` は標準的なテスト手法（`join()`/`get()` での同期化、`CompletableFuture.completedFuture(...)` でのスタブ）が使えるため、独自 `Promise` 用の特殊なテスト足場が不要になり、テスト追加が容易になる。
- **(b) 解消される ISS**: ISS-09（同期/非同期境界の不均一）。なお「検索＝非同期」という現行思想自体は合理的（UI レスポンス性）なので踏襲し、変えるのは「不均一さ」であって「非同期であること」ではない（`0005` §8.2）。
- **(c) 漸進案との変更容易性対比**: 漸進案（`0005` §8.3(c)）は「独自 `Deferred`/`Promise` を維持しつつ境界規則だけ統一（全メソッドに非同期版を用意し同期版はラッパ）」。基盤置換を伴わないため fess 本体側の互換影響が小さく、ISS-09 の「不均一さ」自体は漸進でも解消できる。ゼロベースとの差は「独自基盤の保守コストが残るか否か」と「標準知識で変更できるか否か」。標準 `CompletableFuture` なら新規開発者が既存知識で変更でき、要件の課題感（「高度な Java スキルを要する」独自基盤の学習）に直接効く。**[要確認]** 既存利用側（fess 本体）が独自 `Promise` のコールバック API に依存している可能性があり、標準型への全面置換の互換影響はステップ4で要確認（`0005` §8.2）。

### 2.7 §9 スコアリング・語管理の拡張点 — 規則を差し替え可能にする（ISS-04 / ISS-15 の変更容易性面）

3-1 §9.2/§9.3 は、ランキング源を検索時 function score 単系統に統一しつつ、**function score の構成を `ScoringStrategy` として抽象化**し（`0005` §9.2）、bad word 削除を term 完全一致化・論理削除・ドライランを持つ語管理として再設計する（`0005` §9.3）。本書は ISS-04・ISS-15 の **変更容易性面**（拡張点として差し替え可能になるか）を扱い、品質面（誤削除の排除・boost 精度）は 3-4 に主担当を譲る。

- **(a) どう変えやすくなるか**
  - **M1（拡張点）— ISS-15**: 現状 `userBoost<=1` はコンストラクタで一律に1へ丸められ（`SuggestItem.java:131-135`、出典: ISS-15）、document/query 経路は実質 boost=1 に固定される。ブースト規則がコンストラクタにハードコードされているため、**ブーストの効かせ方を変える**には `SuggestItem` の不変条件そのものを書き換える必要がある。To-Be では function score の構成（前方一致 weight・freq の modifier・userBoost の効かせ方）を `ScoringStrategy` 抽象に外出しするため、**ブースト規則・ランキング規則を `ScoringStrategy` 実装の差し替えで変更・実験**でき、`SuggestItem` のコア型を触らずに済む。セマンティック類似度の加点など新しいスコア要素も実装追加で載る（新機能 3-6 の素地）。
  - **M1（拡張点）— ISS-04**: 現状 bad word 削除は `wildcardQuery(TEXT,"*badword*")` の部分一致削除がロジックに固定され（出典: ISS-04, `WordManagementOperations.java:77-84`）、**判定ロジックを差し替える余地がない**。To-Be で語管理を `SuggestWordAdmin`（§3）の責務として抽象化し、削除条件（完全一致 term／論理削除フラグ／ドライラン）を構成可能にすることで、**「bad word の判定・削除ロジックを差し替え可能」**になる。将来「正規表現で除外」「カテゴリ単位で除外」等の新しい語管理規則も、語管理の拡張点に載せられる。
- **(b) 解消される ISS（変更容易性面）**: ISS-15（boost 規則の硬直→ `ScoringStrategy` で差し替え可能に）、ISS-04（語管理ロジックの硬直→ 語管理抽象で差し替え可能に）。
- **(c) 漸進案との変更容易性対比**: 漸進案（`0005` §9.4(c)）は「userBoost 丸めを撤廃」「bad word を term 完全一致に変更」など局所変更で、既存テストを活かしつつ**個別の課題は解消**できる。ただし漸進案は「今の規則を直す」にとどまり、`ScoringStrategy`／語管理抽象という**将来の差し替え余地（拡張点）は生まれない**。ゼロベースとの差は「次の変更も容易か」にあり、ここは拡張点化の価値が漸進案より明確に出る論点。**[要確認]** function score の重み設計は OpenSearch バージョン依存 API に関わるため TBD-01。

### 2.8 §5 テキスト処理パイプライン — 踏襲資産を「読み変換の拡張点」として活かす

3-1 §5 のテキスト処理パイプライン（Normalizer→ReadingConverter→Analyzer の Strategy+Composite）は**責務分割が良好で直接の ISS を持たない踏襲資産**（出典: `0005` §5.1, `0003` §3.1/§3.3）。変更容易性の観点では、この構成は既に M1（拡張点）の好例であり、To-Be はこれを `TextProcessor` 抽象として明文化し多言語拡張点を加える。

- **(a) どう変えやすくなるか**
  - **M1（拡張点）**: 単機能の小さな converter/normalizer が Chain（Composite）で合成される構成は、**新しい読み変換・正規化・言語処理を「Chain に1つ足す」だけ**で拡張できる。現状でこの拡張容易性を既に備えており、To-Be は `TextProcessor` 抽象として明文化し、言語別 Chain の切り替え（言語判定→言語別 Chain 選択、`0005` §5.2）を加えることで多言語強化（新機能 3-6）の追加も容易にする。
  - **M5（テスト容易性）**: 各 converter/normalizer に専用テストが手厚く存在する（`0005` §11, `0003` §3.2）。単機能ごとに独立テストがあるため、**新規コンバータを足す変更も既存テストを壊さず（回帰を恐れず）追加**でき、テスト資産がそのまま拡張のセーフティネットになる。
- **(b) 解消される ISS**: 直接解消する ISS はない（このレイヤは現状でも健全）。間接的に「変更容易性（読み変換の拡張容易性）」と新機能（多言語）に寄与する。**踏襲・再利用資産の明示**（完了条件）をこのレイヤが担う。
- **(c) 漸進案との変更容易性対比**: 漸進案＝現行パイプライン維持。To-Be との差は「`TextProcessor` 抽象としての明文化＋多言語拡張点の追加」程度であり、**このレイヤはゼロベースでも漸進でもほぼ同一**（全置換不要・流用価値の高い資産の好例）。

## 3. ISS-02: 設定の一元化・型安全化（M3 結合度低減 ＋ M4 標準化）

ISS-02 は 3-1 では構造設計の直接対象外とされ「3-2 で扱う」とされたが（`0005` §12, 378行）、設定の**変更容易性**は本書の射程でもある。可読性版（`0006` §3）が「コメントに頼らず読めばわかるか（R5）」を扱ったのに対し、本書は「**設定を安全に変えられるか／設定を追加するのが1箇所で済むか**」を扱う。

### 3.1 現状（アンチパターンの実例）

- **[事実]** `suggest.popular.word.cache.expire` は `PopularWordHelper.java:77` で `TimeUnit.MINUTES`（既定60→60分）として実装されているが、`fess_config.properties` のコメントは「秒」と記す。**実装値（分）が正だが、コメントが誤っている**（出典: ISS-02, `legacy/05` 5.2, `legacy/04` 4.2）。

変更容易性の観点で問題なのは、**この設定を運用者が「変えよう」としたときに事故る**点である。コメントを信じて「300（＝5分のつもりで秒指定）」と書けば、実際には300分＝5時間として解釈され、意図と乖離する。単位がコメントという腐りやすい注釈に依存しているため、設定変更が安全に行えない（M4 標準化・型安全の毀損）。

### 3.2 To-Be 設計判断 [提案] — 型安全な設定と単一設定ソース

ゼロベース設計では、設定の意味・単位・既定値を**コメントではなく型・名前・構造で表現**し、設定変更の事故余地と設定追加の手間を構造的に減らす。具体策は次の3点（可読性版 `0006` §3.2 と同一の設計判断を、変更容易性の効能で読み解く）。

1. **単位を型で表現する（Typed Settings）** [提案]
   - `int expire`（単位不明・コメント頼み）ではなく `Duration cacheExpiry`（`java.time.Duration`）のような**単位を内包する型**で保持する。`Duration.ofMinutes(60)` と書けば単位が型に焼き込まれ、**運用者が単位を取り違えて変更する事故が構造的に起きない**（M4）。プロパティ文字列から読む場合も `PT60M` / `60m` の単位サフィックス付き値でパースする。
2. **単一の設定ソース（Single Source of Truth for Config）** [提案]
   - 設定の「名前・型・既定値・説明」を**1箇所**（設定スキーマ/定数定義）に定義する。これにより、**新しい設定を追加する変更が1箇所の編集で済み**（M3 局所性の設定版）、「プロパティファイルのコメント」と「コード内の参照」という二系統を同期させる必要がなくなる。設定追加・変更の作業コストが下がる。
3. **既定値と単位をコードに集約し、プロパティはオーバーライドのみ** [提案]
   - 既定値（60分）と単位を型付きでコード側に持ち、プロパティは「上書きしたい場合だけ書く」位置づけにする。一次情報をコード（型）に寄せることで、設定の意味を変える際に編集すべき正本が1つに定まる。

- **(a) どう変えやすくなるか**: 設定の単位が型で固定されるため**変更時の単位取り違え事故が消え**（M4）、設定の追加・変更が単一ソースの1箇所編集で済む（M3）。「設定を安全に・少ない手数で変えられる」状態になる。
- **(b) 解消される ISS**: ISS-02（cache.expire のコメントと実装の不一致＝安全に変更できない設定）。
- **(c) 漸進案との変更容易性対比**: 漸進案は「コメントを実装に合わせて『分』に修正する」。即座に乖離は直るが、**将来また実装の単位が変われば再びコメントが腐り、変更事故が再発**する（構造的な再発防止がない）。型化（`Duration` 化）は「単位をコメントに書く必要がない＝乖離しようがない」状態を作るため、変更容易性の持続性で優る。なお ISS-02 は単体では体感重大度「低」（`0002` §4.1）だが、「コメント頼みの設定」という同型の脆さは他設定項目にも潜在するため、型化は ISS-02 単体を超えた予防的価値を持つ。**[要確認]** fess 本体の設定基盤（`fess_config.properties` / Lasta 系 Config 生成）が `Duration` 型・単位付き文字列をどこまで扱えるかは連携依存。型化の具体手段はステップ4/連携部の確認。

## 4. テスト容易性（M5）— 充実した既存テスト群をどう活かすか

変更容易性は「変えてもすぐ回帰を検知できる」ことに支えられる。本節は M5（テスト容易性）を専節で扱い、3-1 が踏襲資産として明示した既存テスト群（`0005` §11）が、ゼロベース To-Be でどう「回帰を恐れず変えられる土台」になるかを整理する。

### 4.1 現状（活かすべき資産）

- **[事実]** テストは **main 64ファイル/11,591行 に対し test 77ファイル/15,194行** と手厚い。マージ両クラス・テキスト処理（converter/normalizer/analysis）・クエリ構築・設定に専用テストがある（出典: `0005` §11, `0003` §3.2）。
- **[事実]** 一方、fess 連携部（`SuggestHelper`／`RoleQueryHelper` 周辺）のテストは手薄な可能性がある（出典: `0005` §10.2, `0003` §3.2）。

### 4.2 To-Be でのテスト容易性向上 [提案]

- **公開 API 縮小がテスト対象（契約）を安定させる（M5 ＋ M1/M2 連携）**: §3.2 の `internal` 化により、テストすべき公開契約が用途別4インタフェースに絞られる。**内部実装（Operations・Writer・Store）を差し替えても、公開 IF のテストが通れば回帰なしと判断**でき、「内部を自由に変える」ための安定した検査点ができる。現状は public 28メソッド（`SuggestIndexer`）が全てテスト対象になりうるため、内部変更がテストに波及しやすい。
- **単一規則化がテストを集約する（M2 連携）**: マージ規則の単一化（§7.2.1）・権限の単一化（§10.2）・ランキングの単系統化（§9.2）により、テストも「1つの規則に対する単体テスト」へ集約でき、現状の二重実装ぶんの重複テストを統合できる。既存の両クラス向けテスト資産は、新しい単一規則のテストへ流用する（`0005` §11）。
- **標準機構がテスト足場を簡素化する（M4 連携）**: §8.2 の `CompletableFuture` 化により、独自 `Promise` 用の特殊なテスト足場が不要になり、標準的な非同期テスト手法が使える（§2.6）。
- **テキスト処理の単機能テストを拡張のセーフティネットに（M1 連携）**: §5 の converter/normalizer 単位の手厚いテストは、新規コンバータ追加時の回帰検知にそのまま使える（§2.8）。
- **[要確認] 移行時のテスト補強**: fess 連携部（権限・detail 受け渡し）のテストが手薄なため、§3（API 再編）・§10（権限集約）の移行時はテスト補強が必要（ステップ4の領分）。本書はゴール状態のテスト容易性を論じ、移行過程のテスト整備はステップ4へ送る。

> **テスト容易性は「変更容易性の保険」**: M1〜M4 が「変える作業を軽くする」のに対し、M5 は「変えた結果が壊れていないと即座に確認できる」を担う。3-1 がテスト群を踏襲資産として明示した（`0005` §11）のは、ゼロベース再設計であっても**回帰検知の土台を捨てない**という変更容易性上の判断である。

## 7. 残課題・後続ステップへの引き継ぎ（他ステップとの役割分担）

### 7.1 [要確認] ステップ4 / 連携部の確認が必要な点

- **§2.5（ISS-06 権限集約）・§2.1（ISS-13/17 API 再編）**: 公開 API・fess 連携 API の変更を伴うため、変更容易性のゴール状態に至る**過渡期コスト**（三層併存・責務の中途半端な分担）と互換影響はステップ4の移行戦略で評価する。本書はゴール状態の変更容易性のみ論じた。
- **§2.6（ISS-09 同期/非同期統一）**: 独自 `Promise` → 標準 `CompletableFuture` の全面置換は、fess 本体側のコールバック依存があれば互換影響が出る。互換性込みの判断はステップ4（`0005` §8.2）。
- **§3（ISS-02 設定型化）**: fess 本体の設定基盤（`fess_config.properties` / Lasta 系 Config 生成）が `Duration` 型・単位付き文字列をどこまで扱えるかは連携依存。型化の具体手段は要確認。
- **§4（テスト容易性）**: fess 連携部（権限・detail 受け渡し）のテストが手薄なため、移行時のテスト補強が必要（ステップ4）。
- **§2.7（ISS-04/15 拡張点）**: `ScoringStrategy` の function score 重み設計は OpenSearch バージョン依存（TBD-01）に関わるため、利用可否は断定しない。

### 7.2 他ステップとの役割分担（重複論点の整理）

- **3-2（可読性）**: ISS-01/02/03/05/06/13/14/16/17 を担当。本書と重なる **ISS-01/02/03/05/06/13/17** は、3-2 が「**読めばわかるか**（R1〜R5）」、本書 3-3 が「**変えやすいか**（M1〜M5: 拡張点・局所性・結合低減・標準化・テスト容易性）」と観点を分ける。例: §3.2 のファサード分離は、3-2 では「用途名から読むべき IF に直行できる（R1）」、本書では「ある用途の変更が他用途に波及しない（M2）」。
- **3-4（品質）**: ISS-04/05/10/11/12/14/15 を担当。本書と重なる **ISS-04（bad word 誤削除）・ISS-15（boost 表現力）** は、本書が**変更容易性面（語管理・スコアリングが拡張点として差し替え可能になる M1）**を、3-4 が**品質面（誤削除を起こさない語管理・boost の精度）**を主担当する。ISS-05（マージ取りこぼし疑い）の品質面も 3-4 の領分（本書はマージ規則の単一化による変更容易性 M2 のみ）。
- **3-5（性能）**: ISS-09 の性能面（同期/非同期の実行性能）・ISS-07/08/10/16 を担当。本書は ISS-09 の変更容易性面（並行モデルの一貫性 M4）のみ扱った。書き込み I/O のバルク化（§7.2.2）は性能が主担当で、本書ではマージ規則単一化（§7.2.1）の変更容易性面のみ扱った。
- **ステップ4（移行戦略）**: 各節の「(c) 漸進案との対比」は移行経路の候補メモにとどめ、移行コスト・後方互換・フェーズ分けの本格検討はステップ4の領分。

### 7.3 変更容易性の定量化（任意の発展）

本書は変更容易性を M1〜M5 の定性軸で論じた。ステップ5（提案ドキュメント統合）以降で必要なら、次のような**「変更コストの量的指標」**を補助エビデンスとして添えられる。

- 規則の実装箇所数（マージ 2→1、権限 2→1、ランキング源 2見え→1）＝「1規則変更に要する編集箇所」。
- 拡張点の有無（新規サジェストソース・スコアラ・語管理規則の追加が「既存改造」か「実装追加」か）。
- 過渡コード件数（`@Deprecated` 委譲シム 複数 → 0）＝「変更時に整合を保つ二重メンテ対象」。
- 独自基盤への依存（独自 `Deferred`/`Promise` → 標準 `CompletableFuture`）＝「変更に要する固有知識の量」。
