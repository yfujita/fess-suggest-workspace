## 1. 「性能」の評価軸の定義（何をもって"性能が良い"とするか）

性能を抽象論で終わらせないため、本書では「性能が良い」を次の5つの具体的な評価軸に分解する。各設計判断は「どの軸で性能を向上させるか」で評価する。3-2 が可読性を R1〜R5、3-3 が変更容易性を M1〜M5、3-4 が品質を Q1〜Q5 に分解したのと対をなす、性能の軸 **P1〜P5** である。

| # | 評価軸 | 定義（"性能が良い"の具体） | 主に効く現行課題 |
| --- | --- | --- | --- |
| **P1** | **書き込み/集約スループット（Ingest Throughput）** | 大量のサジェスト語を登録・集約する際の OpenSearch 往復回数・1リクエストあたり処理件数が効率的で、全件再構築・リアルタイム反映が高スループットで完了する。 | ISS-10, ISS-08, ISS-09（ISS-16 を書き込みコスト面で） |
| **P2** | **インデックス再構築コスト・ゼロダウンタイム（Rebuild Cost）** | 全件再構築（毎日12:00）が短時間・低リソースで完了し、再構築中も検索が止まらない。スキーマ変更時の再構築・切替が安全。 | ISS-07/TBD-05（再構築側）、ISS-16（書き込み量・容量を通じて再構築コスト） |
| **P3** | **検索レイテンシ・クエリコスト（Query Latency）** | サジェスト検索（逐次入力に追従）が低レイテンシ・低クエリコストで応答する。検索時のスコア計算コストが要件 QPS 下で許容範囲。 | ISS-16（検索時計算 vs 事前計算のトレードオフ）、ISS-07（QPS とシャード） |
| **P4** | **スケーラビリティ/水平拡張余地（Scalability）** | 語彙規模・検索 QPS の増大に対し、シャード/レプリカ/ノードの追加で水平拡張できる設計余地がある。 | ISS-07/TBD-05, ISS-09 |
| **P5** | **リソース効率（Resource Efficiency）** | インデックス容量・JVM/CPU・キャッシュを無駄なく使う。死蔵データ・過剰な同期往復・不要な計算でリソースを消費しない。 | ISS-16（容量/書込コスト）、ISS-08（CPU 負荷）、ISS-10（往復による CPU/ネットワーク） |

> 補足: P1〜P5 は独立ではなく相補的である。「書き込みスループット（P1）」が低い（N回同期 Get）と「再構築コスト（P2）」も増大し（全件再構築が遅い）、同時に「リソース効率（P5）」も毀損する（往復ごとの CPU/ネットワーク消費）。「死蔵 score（ISS-16）」は P5（容量）と P1（書き込みコスト）の両方を無駄に消費し、その「廃止 vs 検索時計算」の選択は P3（検索レイテンシ）と P1/P5（書き込み/容量）のトレードオフになる。`0005` §1 の設計原則（バルク効率優先＝原則5／死蔵物を持たない＝原則4／一貫した同期非同期＝原則6／流用資産の踏襲＝原則7）が、性能軸にも一対一に近く対応する。**性能は 3-1 設計の副産物ではなく、バルク効率・死蔵排除・一貫した並行モデルという設計判断そのものに織り込まれている。**

## 2. 各設計判断 × 性能の整理

3-1 のレイヤ設計（特に §7 書き込み・集約、§6 インデックス設計/スキーマ、§8 同期/非同期、§9 スコアリング、§4 データソース）を、性能観点で読み解く。各項に **(a) 性能がどう向上するか（評価軸 P1〜P5 で）** / **(b) 解消される ISS** / **(c) 既存維持の漸進案との性能面の対比** を添える（0009 §2 各項と同じ三点構成）。

### 2.1 §7.2.2 書き込み・集約モデル — Get-then-update の往復コストを排す（P1/P5, ISS-10）

3-1 §7.2.2 は、アプリ側 Get-then-update（ISS-10）をやめ、**第一候補として OpenSearch 側集約（`scripted_upsert` 等）、フォールバックとして multiGet バルク化**で集約を実行する。本論点が ISS-10 の**性能面の主担当**である（品質に波及する並行集約の正確性面は 3-4 §2.5 が扱済みなので参照に留め、本書は往復コストを正面から扱う）。

- **(a) 性能がどう向上するか（P1 書き込みスループット／P5 リソース効率）**
  - **[事実]** 現状 `SuggestIndexWriter.write` は mergedItems を**1件ずつループ**し、各件で `client.prepareGet().setIndex(index).setId(item.getId()).get(...)` を**同期実行**する（`SuggestIndexWriter.java:54-55`）。その結果でバルクの index リクエストを組み立て、最後に1回だけ bulk 実行する（`:69`）。すなわち N アイテム登録で **N 回の同期 Get + 1 回の bulk** となり、**往復回数が登録件数に線形**（multiGet ですらない）。出典: ISS-10, `0003` §2。
  - 性能上の問題は **「往復回数が件数に線形に増える＝大量登録時のボトルネック」** である。各 Get は同期 round-trip のため、ネットワーク遅延 × N が直接スループット上限を決める。全件再構築（毎日12:00、`SuggestCreator`）のように語彙全件を登録する処理では、この線形往復が再構築時間（P2）と CPU/ネットワーク消費（P5）を直撃する。
  - To-Be 第一候補の **`scripted_upsert`（OpenSearch 側で「既存があれば加算、なければ新規」を原子的に実行）** は、アプリ側の Get を**ゼロ**にし、bulk update 1回に集約する。これにより往復は「N回 Get + 1回 bulk」から「1回の bulk update（内部で原子的集約）」へ削減され、P1（スループット）が往復回数の観点で件数非線形に改善する。**[要確認]** `scripted_upsert`・スクリプト集約の利用可否は OpenSearch バージョン依存（TBD-01）。
  - To-Be 第二候補（フォールバック）の **multiGet バルク化** は、スクリプト集約が使えない場合でも N回の同期 Get を `multiGet` 1回にまとめ、Get の往復を「N回 → 1回」に削減する。原子的集約ほどではないが、往復線形コスト（ISS-10 の核心）は解消する。
  - **静的スクリプトによる CPU 保全** [要確認]: `scripted_upsert` を採る場合、スクリプト本体を語ごとに変えず**静的（不変）に保ち `params` のみ動的に渡す**方針とする（`0005` §7.2.2）。語ごとに動的スクリプトを生成するとスクリプトのコンパイル/実行キャッシュが枯渇し CPU 負荷（P5）を招くため。定量的な負荷検証は実測が必要（§5）。
- **(b) 解消される ISS**: ISS-10（Get-then-update の往復線形コスト）の**性能面**（主担当）。並行集約の正確性面は 3-4 §2.5 が主担当。
- **(c) 漸進案との性能面の対比**: 漸進案（`0005` §7.3(c)）は「1件ずつ同期 Get を `multiGet` 1回にまとめる」。これだけでも往復は N回→1回に削減でき、**P1（スループット）の大半は漸進で到達できる**。ゼロベース（`scripted_upsert` 原子的集約）との性能差は、(1) Get 自体を完全排除できる（multiGet すら不要）点、(2) read-modify-write のアプリ側往復が消えることで再構築時間（P2）がさらに縮む点。ただし upsert/スクリプト集約への移行はインデックス更新挙動が変わるため、移行可否は**ステップ4**で判断。

### 2.2 §7.2.2 バルク件数の適正化 — 極小デフォルトを脱し CPU と両立（P1/P5, ISS-08）

3-1 §7.2.2 は、`doc.per.request=2`（ISS-08）のような極小デフォルトをやめ、CPU 負荷調整（`calibrateCpuLoad` 相当）と両立する適切な既定値・動的調整にする。

- **(a) 性能がどう向上するか（P1 書き込みスループット／P5 リソース効率）**
  - **[事実]** document バッチの1リクエスト件数は `suggest.update.doc.per.request=2`（既定2件）で**極小**（出典: ISS-08, `legacy/04` 4.2）。バルク1リクエストあたり2件しか送らないため、全件再構築のスループット（P1）に対しバルク化の利得をほとんど得られていない（OpenSearch のバルク API はリクエストあたりの件数を増やすほど往復あたりの効率が上がる）。
  - 性能上の問題は **「バルク粒度が小さすぎて、バルク API の往復削減効果を活かせていない」** こと。極小バルクはリクエスト数（＝往復数）を増やし、P1（スループット）と P5（リクエストごとのオーバヘッド）の双方を毀損しうる。
  - To-Be ではバルク件数を適切な既定値・動的調整にし、**1リクエストあたりの件数を増やしてスループット（P1）を上げる**。ただし件数を増やすほど1リクエストのピーク CPU/メモリ負荷（P5）が上がるため、**スループット（P1）とリソース負荷（P5）のトレードオフ**を `calibrateCpuLoad` 相当の負荷調整と両立させる必要がある。
  - **[要確認] TBD-04 / TBD-05 関連の設計意図**: 現状の `doc.per.request=2` という極小値が「検索性能影響を抑えるための意図的な CPU 負荷抑制」（バッチは本体 Tomcat と別 JVM プロセスで動き `calibrateCpuLoad` で検索性能影響を抑える、`0002` TBD-04）なのか「単にデフォルトのまま」なのかは**未確定（TBD-04 [要確認]）**。意図的な抑制であれば、バルク件数を上げる際は「再構築スループット（P1）を上げつつ検索レイテンシ（P3）への CPU 干渉を増やさない」両立点を実測で決める必要があり、断定しない。
- **(b) 解消される ISS**: ISS-08（バッチ1リクエスト件数が極小）。
- **(c) 漸進案との性能面の対比**: 漸進案は「`suggest.update.doc.per.request` の既定値を引き上げる（または環境に応じて設定する）」局所変更。設定値1つの変更で P1（スループット）は相当改善でき、**ここは漸進で性能ゴールに大きく近づく課題**。ゼロベースとの差は「バルク件数を CPU 負荷に応じて**動的調整**する機構を最初から組み込むか」で、静的な値設定（漸進）でも実用上は足りる可能性が高い。最適値は実測依存（TBD-04）で、移行時の調整は**ステップ4**。

### 2.3 §6.2.2 シャード/レプリカの可変設計 — 水平拡張余地と再構築の両立（P4/P2/P3, ISS-07/TBD-05）

3-1 §6.2.2 は、単一シャード固定（ISS-07）をやめ、語彙規模・QPS に応じて `number_of_shards` を構築時に決定できる可変設計とし、レプリカも検索可用性に応じて選べるようにする。

- **(a) 性能がどう向上するか（P4 スケーラビリティ／P2 再構築／P3 検索レイテンシ）**
  - **[事実]** 現状は `number_of_shards=1`, `number_of_replicas=0`, `auto_expand_replicas=0-1`, `refresh_interval=10s`（`suggest.json`）で、**単一シャード前提の小規模専用設計 [推測]**（出典: ISS-07 / TBD-05, `0002` §3.5）。**[要確認] 単一シャードが「設計上の意図」か「デフォルトのまま」かは未確定（TBD-05）。**
  - 性能上の問題は **「語彙規模・検索 QPS が増大したときの水平スケール余地が設計上限定的」**（P4）であること。単一シャードでは1ノードの容量・スループットが上限になり、複数ノードへ分散できない。レプリカ0は検索 QPS をレプリカで分散できず（P3/P4）、可用性も低い。
  - To-Be では `number_of_shards` を**規模に応じて選べる**設計にし、P4（水平拡張余地）を確保する。サジェストは前方一致が主で集約は決定的 ID（`SuggestUtil.createSuggestTextId`）で完結するため、**OpenSearch デフォルトの ID ハッシュルーティングにより同一語が常に同一シャードへ集約され、複数シャードでもクロスシャード集約を必要とせず集約整合が保たれる**（`0005` §6.2.2）。レプリカを `>=1` 選べるようにすれば検索 QPS をレプリカで分散でき（P3/P4）、可用性も上がる。
  - 再構築（P2）との両立: シャード/レプリカは二重エイリアスによるゼロダウンタイム再構築（§2.6）と独立に選べるため、規模拡張と無停止再構築を両立できる。
  - **[要確認] ホットスポット検証観点**: 決定的 ID ベースの更新は同一語を同一シャードへ集約するため、**人気サジェスト語への更新集中が特定シャードへの書き込みホットスポット（P1/P5 の偏り）を生まないか**という検証観点を持つ（`0005` §6.2.2）。最適シャード数の根拠・現行が意図かデフォルトか（TBD-05）・最適レプリカ数（運用ノード構成依存）はいずれも実測/運用前提に依存し、断定しない。
- **(b) 解消される ISS**: ISS-07（単一シャード固定のスケール上限）/ TBD-05（意図かデフォルトか）。
- **(c) 漸進案との性能面の対比**: 漸進案は「`suggest.json` の `number_of_shards`/`number_of_replicas` を固定値から設定可能にする」局所変更。設定の外出しだけで P4（拡張余地）は確保でき、**現状規模では単一シャードで十分という可能性も高い**（TBD-05 が「意図」なら現状維持が妥当）。ゼロベースとの差は「シャード戦略を `SuggestStore` 抽象の責務として明確化し、ホットスポット検証込みで規模に応じた構築を最初から想定するか」程度。インデックス設定変更は再構築を伴うため、移行コストは**ステップ4**。

### 2.4 §8.2 一貫した同期/非同期モデル — バルク化と誤用回避（P1/P3, ISS-09）

3-1 §8.2 は、不均一な現行境界（ISS-09）に代わり、標準機構（`CompletableFuture` 等）で同期/非同期境界を一貫させる（「I/O を伴う操作は非同期を基本とし、同期版は非同期版の `.join()` ラッパとして一箇所で提供する」）。

- **(a) 性能がどう向上するか（P1 書き込みスループット／P3 検索レイテンシ）**
  - **[事実]** 現状は独自の `Deferred`/`Promise` を非同期基盤とし、**検索は常に非同期**だが、登録は **Reader 系2メソッドのみ非同期、単発系（`index`/`indexFromSearchWord` 等）は同期**で、**API ごとに同期/非同期境界が不均一**（出典: ISS-09, `legacy/01`/`02`）。
  - 性能上の問題は **「利用側が境界を理解しないと性能/挙動を誤りやすい」** こと。単発系が同期であるため、利用側がループ内で単発登録 API を呼ぶと「同期往復 × 件数」のアンチパターン（§2.1 の Get-then-update と同種の線形往復）に陥りやすく、バルク化の機会を逃す。逆にどの API が非同期かが不均一だと、非同期前提でスループットを引き出す書き方ができない。境界の不均一さ自体が、**バルク化・並列化という性能最適化を利用側が適用しにくくする**（P1）。
  - To-Be では境界規則を1つに統一し、「I/O 操作は非同期を基本、同期版はラッパ」とすることで、**利用側が一貫した非同期 API でバルク登録・並列実行を素直に書ける**（P1）。検索も「非同期が基本」という現行の合理的思想（UI レスポンス性＝P3）を踏襲しつつ、不均一さだけを正す。
  - **[要確認]** 独自 `Promise` を標準 `CompletableFuture` へ全面置換する場合、既存利用側（fess 本体）がコールバック形式等に依存している可能性があり、互換影響は**ステップ4で要確認**（`0005` §8.2）。性能上の方向性（一貫した非同期境界でバルク化を促す）は本書で示すが、基盤置換可否は断定しない。
- **(b) 解消される ISS**: ISS-09（同期/非同期境界の不均一）の**性能面**（バルク化・スループットを引き出しやすくする、利用側の誤用回避）。
- **役割分担の明示**: ISS-09 の**主たる影響軸は変更容易性**（API の一貫性・利用側の認知負荷）であり、その整理は **3-3（変更容易性）が主担当**である。本書は ISS-09 の**性能に波及する面**（一貫した非同期境界がバルク化・スループット最適化を可能にする）に限って扱う。
- **(c) 漸進案との性能面の対比**: 漸進案（`0005` §8.3(c)）は「独自 `Deferred`/`Promise` を維持しつつ、全メソッドに非同期版を用意し同期版はラッパにする（境界規則だけ統一）」。基盤置換を伴わないため互換影響が小さく、**性能面（一貫した非同期境界によるバルク化促進）は漸進でほぼ達成できる**。ゼロベース（標準機構へ置換）との性能差は小さく、差は主に変更容易性・保守性側にある。基盤置換は**ステップ4**で互換性込みで判断。

### 2.5 §6.2.1 スキーマ: 死蔵 score の廃止と「検索時計算 vs 書き込み時計算」のトレードオフ（P5/P1/P3, ISS-16）— 本書の最重要論点

3-1 §6.2.1 は、ランキングを検索時 function score 単系統（§9.2）に統一するため、**書き込み専用の死蔵 `score` フィールドをスキーマから除外する**。同時に「持たない」か「持って必ず使う（sort/rescore に使う）」の二択にし、「持つが使わない」現状（ISS-16）は採らない、とする。**この「検索時 function score 計算 vs 書き込み時 score 事前計算」の性能トレードオフは 3-5 の最重要論点であり、3-4 §2.1 がここに委譲している。**

- **(a) 性能がどう向上するか（P5 リソース効率／P1 書き込みコスト／P3 検索レイテンシ）**
  - **[事実]** 事前計算 `score` は **書き込みのみ4箇所**（`SuggestItemSerializer.java:73,182,217`, `SuggestItem.java:360`, `SuggestUtil.java:214`）で生成され、mapping に `score: double`（`mappings-default.json:36-38`）が定義されているが、**検索 (`SuggestQueryBuilder.java:141-167`)・人気語 (`PopularWordsRequest.java:210-246`)・ソートのいずれからも参照されない死蔵フィールド**である（grep で read/sort/query 参照ゼロ）。ランキングは検索時 function score 単系統で決まる（出典: ISS-16/ISS-14, `0003` §2, [[project-suggest-scoring]]）。
  - **死蔵 score 廃止による直接の性能改善（P5/P1）**: `score` フィールドを廃止すると、(1) 書き込み時に `score` を毎回再計算（`SuggestItemSerializer.java:182` で `(updatedQueryFreq + updatedDocFreq) * userBoost` を更新ごとに算出）するコストが消える（P1 書き込みコスト）、(2) インデックスに double フィールドを保持しない分、インデックス容量が減る（P5 容量）。これは「書くなら読む、読まないなら書かない」（原則4）の素直な性能上の利得であり、ISS-16 の「容量・書き込みコストの無駄」を直接解消する。
  - **最重要トレードオフ: 検索時計算 vs 書き込み時計算（P3 ⇔ P1/P5）** [提案/要確認]: 単系統を保ったまま、ランキング計算を「検索時にするか書き込み時にするか」を一択にする（両方持って片方死蔵は採らない、`0005` §6.2.1/§9.2）。
    - **案A（廃止＝検索時計算に寄せる）**: 死蔵 `score` を廃止し、ランキングは検索時 function score（DOC_FREQ/QUERY_FREQ の LOG2P modifier + USER_BOOST + 前方一致 weight）で都度計算する。**メリット**: 書き込みコスト・容量（P1/P5）が下がる。鮮度が高い（最新の freq がそのまま反映、再計算不要）。**デメリット**: 検索クエリごとに function score 計算が走るため検索クエリコスト（P3）が増える。
    - **案B（保持＝書き込み時計算に寄せる）**: `score` を**検索で実際に sort/rescore に使う**設計（書くなら読む）にし、検索時は事前計算済みの score でソートしてクエリ時計算を削減する。**メリット**: 検索レイテンシ（P3）が下がる（ソートのみ）。**デメリット**: 書き込み時計算・容量（P1/P5）が増える。freq 更新のたびに score 再計算が必要で鮮度・書き込み負荷とのトレードオフ。
  - **サジェスト特有のレイテンシ/QPS 要件が選択を左右する** [要確認]: サジェスト API は逐次入力に追従するため、通常検索よりシビアな低レイテンシ・高 QPS が求められる（`0005` §9.2）。検索時 function score（や `script_score` 等）の実行時計算はクエリごとにコストが増えるため、**想定 QPS 下でレイテンシ要件（P3）を満たせるかの検証が、案A（検索時計算）vs 案B（書き込み時計算）の選択を左右する**。一般に語彙規模が中小・QPS が穏当なら案A（廃止）が総コスト最小で素直、検索 QPS が極めて高くレイテンシが厳しいなら案B（sort 用 score 保持）が有利になりうる、という定性的な対比にとどめ、**定量評価は実測が必要（§5）**。`script_score`/function score の具体 API はバージョン依存（TBD-01）で断定しない。
- **(b) 解消される ISS**: ISS-16（死蔵 score フィールドの容量・書き込みコストの無駄）。補助的に ISS-14（スコア源の混乱）の性能側面（死蔵フィールドの書き込み/容量コスト）。
- **(c) 漸進案との性能面の対比**: 漸進案（`0005` §6.3(c)/§9.4(c)）は「(1) `score` フィールドを mapping から削除し書き込みを止める（案A 相当）」または「(2) `score` を sort に使うよう検索側を変更する（案B 相当）」。**どちらの方向でも、死蔵という無駄（ISS-16 の核心）は局所変更で解消でき、性能ゴールに漸進で到達できる**。ゼロベースとの差は「`ScoringStrategy` 抽象（`0005` §9.2）の中で計算位置（検索時/書き込み時）を差し替え・実験できるか」程度。いずれもスキーマ変更（`score` 削除 or sort 利用）を伴い再構築が必要なため、移行コスト・後方互換は**ステップ4**。

### 2.6 §6.2.3 二重エイリアス再構築 — 踏襲する性能資産（P2, 踏襲資産）

3-1 §6.2.3 は、二重エイリアス（検索エイリアス `{base}` / 更新エイリアス `{base}.update`、物理 `{base}.{timestamp}`）によるゼロダウンタイム再構築を**踏襲する資産**として位置づける。

- **(a) 性能がどう向上するか（P2 再構築・ゼロダウンタイム）**
  - **[事実]** 現状、全件再構築は物理インデックス `{base}.{timestamp}` を新規構築し、完了後にエイリアスを切り替えることで、**再構築中も検索を止めない**（出典: `legacy/02`, `0005` §6.2.3/§11）。これはサジェストの可用性（再構築中もサジェストが応答する＝実質的な P2/P3 の両立）を支える良い資産。
  - To-Be はこれを踏襲し、「物理インデックス世代管理」を `SuggestStore` 抽象の責務、エイリアス切替を `SuggestIndexLifecycle`（`0005` §3）の公開面に限定して露出するよう明確化する。**性能機構そのものは変えず、責務境界だけ整理する**。
- **(b) 解消される ISS**: 直接解消する性能 ISS はない（このレイヤは現状でも健全な性能資産）。**踏襲・再利用資産の明示**（完了条件）をこのレイヤが担う。
- **(c) 漸進案との性能面の対比**: 漸進案＝現行の二重エイリアス方式を維持。To-Be との差は「`SuggestStore`/`SuggestIndexLifecycle` の責務として明文化する」程度で、**このレイヤはゼロベースでも漸進でもほぼ同一**（全置換不要・流用価値の高い性能資産の好例、原則7）。安易な作り直しはゼロダウンタイム再構築という既存の性能保証を損なうリスクのほうが大きい。

## 5. 性能改善の量的サマリ（補助エビデンス）

本書は性能を P1〜P5 の定性軸で論じた。ステップ5（提案ドキュメント統合）以降で必要なら、次のような**性能の代理指標**を補助エビデンスとして添えられる（0009 §5 と同趣旨の任意発展）。

- **書き込み/集約スループット（P1）**: N件登録時の OpenSearch 往復回数 ＝「**N回 Get + 1回 bulk**（現状, `SuggestIndexWriter.java:54-55`）→ 1回 multiGet + 1回 bulk（漸進）→ 1回 bulk update（原子的集約, ゼロベース [要確認 TBD-01]）」。往復回数の件数線形 → 定数化。
- **バルク粒度（P1/P5）**: document バッチ1リクエスト件数 ＝「**2件固定**（現状 `suggest.update.doc.per.request=2`）→ 適切な既定値/動的調整（可変）」。リクエスト数（往復数）の削減。
- **スケーラビリティ（P4）**: シャード数 ＝「**1固定**（現状 `number_of_shards=1`）→ 規模に応じて可変 [要確認 TBD-05]」、レプリカ数 ＝「**0固定**（現状）→ `>=1` 選択可」。
- **リソース効率（P5）**: 死蔵 `score` フィールド ＝「**書き込み4箇所＋mapping double を保持するが read/sort/query 参照ゼロ**（現状, ISS-16）→ 廃止（書き込みコスト・容量削減）または sort で必ず使う」。書き込み時 score 再計算回数（更新ごと）→ 0（案A）。
- **検索レイテンシ（P3）**: ランキング計算位置 ＝「検索時 function score 都度計算（案A）」⇔「書き込み時事前計算＋検索時 sort（案B）」のトレードオフ（§2.5）。代理指標は「クエリあたりの function score 計算有無」と「想定 QPS 下のレイテンシ」。

> これらは「性能が良くなった」を測る**構造的な代理指標**（往復回数・バルク件数・シャード数・死蔵フィールド有無）であり、実際のスループット・レイテンシ・容量の**最終的な定量評価は実測（負荷試験・ベンチマーク）が必要であり、本タスクのスコープ外（後続）**である。特に (1) `scripted_upsert` vs multiGet の実スループット差、(2) バルク件数と CPU 負荷の最適両立点（TBD-04）、(3) 案A/案B の QPS 別レイテンシ（TBD-01）、(4) 複数シャードのホットスポット有無（TBD-05）は、いずれも実測で確定すべき事項である。

### 6.2 他ステップとの役割分担（重複論点の整理）

- **3-4（品質）との分担**: ISS-10 は本書（性能＝往復コスト P1/P5）が主担当で、**並行登録時の read-modify-write 競合＝集約取りこぼしという品質副次面は 3-4 §2.5 が扱済み**（本書は参照に留めた）。ISS-16 のランキング単系統の品質方向性は 3-4 §2.1 が扱い、その**性能トレードオフ（検索時計算 vs 書き込み時計算）を本書 §2.5 が主担当**として引き受けた。
- **3-3（変更容易性）との分担**: ISS-09 は**変更容易性（3-3）が主担当**（API の一貫性・拡張点・利用側の認知負荷）。本書は「一貫した非同期境界がバルク化・スループットを引き出す」性能副次面のみ扱った。
