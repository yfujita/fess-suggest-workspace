# ステップ3-4: サジェスト品質の向上が To-Be でどう実現されるか

## 0. 本ドキュメントの位置づけ・前提・読み方

### 0.1 位置づけ

本ドキュメントは、fess-suggest 抜本的改善提案タスク（`20260622_improvement_proposal`）の **ステップ3-4「サジェスト品質の向上が To-Be でどう実現されるか」** の成果物である。

- **目的**: ステップ3-1（`0005-step3-1-to-be-architecture.md`）で設計したゼロベース To-Be アーキテクチャが、要件目的③「**サジェスト品質の向上**」をどう満たすかを照合・補強する。

- **3-4 の固有の立場（内部課題起点）**: 本書は「**現行の内部品質課題（ISS/TBD）を起点に、ゼロベース設計の中で品質をどう作り込むか**」を導く。これは外部ベンチマーク（Google 検索サジェスト）との比較を起点に差分と打ち手を導く 3-7、新機能を後付けでなく設計に内包する 3-6 とは役割が異なる（役割分担は §6 に明記）。
- **スコープ**: 提案（設計の検討と文書化）。コード実装はスコープ外。移行戦略そのものは**ステップ4の領分**であり、本書での「漸進案との対比」は**品質観点の対比メモ**にとどめ、移行経路の詳細には踏み込まない。
- **ゼロベース＝全置換ではない**: 流用価値ある資産（特に責務分割の良いテキスト処理パイプライン、決定的 ID による集約、充実した既存テスト群）は「あるべき姿でも踏襲・再利用する資産」として位置づける（原則7, `0005` §11）。品質の観点では、これら資産は「読み変換精度・候補集合の正確性を支える既存の品質基盤」として積極的な役割を持つ。

## 1. 「サジェスト品質」の評価軸の定義（何をもって"品質が良い"とするか）

サジェスト品質を抽象論で終わらせないため、本書では「品質が良い」を次の5つの具体的な評価軸に分解する。各設計判断は「どの軸で品質を向上させるか」で評価する。3-2 が可読性を R1〜R5、3-3 が変更容易性を M1〜M5 に分解したのと対をなす、サジェスト品質の軸 **Q1〜Q5** である。

| # | 評価軸 | 定義（"品質が良い"の具体） | 主に効く現行課題 |
| --- | --- | --- | --- |
| **Q1** | **ランキング適合性（Ranking Relevance）** | 返す候補が「ユーザの意図に近い順」に正しく並ぶ。ランキング源が単一で、頻度・前方一致・boost が**意図どおりの重みで効く**。調整がランキング挙動に素直に反映される。 | ISS-14, ISS-15（ISS-16 を補助的に） |
| **Q2** | **候補集合の正確性（Candidate-Set Correctness）** | 候補集合が「正しく集約・重複排除され、属性（reading/freq 等）に欠落がない」。同一語が1候補に正しくまとまり（重複排除）、頻度・読みの累積に取りこぼしがない。前方一致が確実に拾われる。 | ISS-05, ISS-10 |
| **Q3** | **語管理の正しさ（Word-Management Correctness）** | 出すべきでない語を**意図した語だけ**抑制でき、出すべき語を巻き込み削除しない。語の除外・登録が予測可能で可逆的。 | ISS-04 |
| **Q4** | **カバレッジ（Coverage）** | 出すべき良質な候補を取りこぼさない。人気語・多語フレーズ・蓄積属性由来の候補が、語源やフィルタ条件で不当に切り落とされない。 | ISS-11, ISS-12 |
| **Q5** | **テキスト処理の精度（Text-Processing Precision）** | 表記ゆれ・読み（かな/ローマ字）・多言語の正規化と読み変換が正確で、入力と候補の**マッチ精度**が高い。 | （ISS 直結なし。踏襲資産 §5 の品質寄与を扱う） |

> 補足: Q1〜Q5 は独立ではなく相補的である。「候補集合の正確性（Q2）」が崩れると（集約取りこぼし＝頻度過少）「ランキング適合性（Q1）」も歪む（頻度がスコア要素のため）。「テキスト処理の精度（Q5）」が低いとそもそも候補が前方一致に拾われず Q2/Q4 を毀損する。`0005` §1 の設計原則（単一の真実＝原則3／拡張点ファースト＝原則2／死蔵物を持たない＝原則4／流用資産の踏襲＝原則7）が、品質軸にも一対一に近く対応する。**品質は 3-1 設計の副産物ではなく、ランキング源の単一化・集約の単一規則化・拡張点としての語源/スコアラという設計判断そのものに織り込まれている。**

## 2. 各設計判断 × サジェスト品質の整理

3-1 のレイヤ設計（特に §9 スコアリング・語管理、§7 書き込み・集約、§4 データソース抽象、§5 テキスト処理、§6 スキーマ）を、品質観点で読み解く。各項に **(a) 品質がどう向上するか（評価軸 Q1〜Q5 で）** / **(b) 解消される ISS** / **(c) 既存維持の漸進案との品質面の対比** を添える（0008 §2 各項と同じ三点構成）。

### 2.1 §9.2 スコアリングの検索時単系統化 — ランキングを「単一の真実」にする（Q1, ISS-14／ISS-16）

3-1 §9.2 は、事前計算 `score` フィールドを廃止（§6.2.1）し、**ランキング源を検索時 function score の単系統に統一**する（「ランキングは検索時に決まる」を唯一の真実にする）。

- **(a) 品質がどう向上するか（Q1 ランキング適合性）**
  - **[事実]** 現状の実態は「二系統が併存」ではなく「**ランキングは function score 単系統、事前計算 score は死蔵**」である。検索（`SuggestQueryBuilder.buildFunctionScoreQuery`, `:141-167`）も人気語（`PopularWordsRequest`, `:210-246`）も DOC_FREQ/QUERY_FREQ（LOG2P modifier）+ USER_BOOST + 前方一致 weight を都度評価し、書き込み時の `score=(queryFreq+docFreq)*userBoost` を**一切参照しない**（出典: ISS-14/ISS-16, `0003` §2, [[project-suggest-scoring]]）。
  - **品質上の問題は「調整可能性の毀損」である**: 死蔵 `score` が残っていると、ランキングを調整しようとした運用者・開発者が「どちらのスコアを直せば並び順が変わるのか」を誤りやすい。事前計算 `score` の式（線形）と検索時 function score の式（LOG2P で飽和、前方一致 weight 乗算）は**重み付けの思想が異なる**ため、死蔵側を直してもランキングは1ミリも動かず、調整が空振りする。これは「ランキング適合性を意図どおりに改善できない」という品質上の足かせである。
  - To-Be では `score` を廃し function score 1系統に統一するため、**「ランキングを良くする＝function score の構成（前方一致 weight・freq の modifier・userBoost の効かせ方）を調整する」**で完結し、調整がランキングに素直に反映される。`ScoringStrategy` 抽象（`0005` §9.2）により、頻度の飽和カーブや前方一致の強さを差し替え・実験でき、ランキング適合性の継続的改善が可能になる。
  - **[要確認]** function score の重み設計・代替 API（`script_score` 等）は OpenSearch バージョン依存（TBD-01）に関わるため、具体 API の利用可否は断定しない。「単系統に統一する」という方向性のみを示す。
- **(b) 解消される ISS**: ISS-14（スコア源の混乱＝ランキング調整の空振り）、ISS-16（死蔵 score の存在＝品質調整時の誤誘導）。
- **(c) 漸進案との品質面の対比**: 漸進案（`0005` §9.4(c)）は「(1) `score` フィールドを廃止 or sort 利用に倒す」「(2) function score の重みを直接チューニングする」。ランキング適合性（Q1）の改善は漸進でも達成できる — 死蔵 score を消し function score を調整すれば、ランキングは意図どおり動かせる。ゼロベースとの差は `ScoringStrategy` 抽象化の有無で、**「次のランキング改善（新スコア要素の追加・実験）も容易か」**という継続的な品質改善の素地が漸進案では生まれにくい点。なお検索時計算 vs 書き込み時計算（sort 用に score を持って必ず使う）の性能トレードオフは **3-5（性能）の最重要論点**であり、本書は「単系統という品質上の方向性」のみを扱う。

### 2.2 §9.2 boost 表現力の回復 — 連続値ブーストでランキングを微調整可能に（Q1, ISS-15）

3-1 §9.2 は、`userBoost<=1` の一律丸め（ISS-15）をやめ、ソース種別に依存しない連続値の boost を扱えるようにする（負値等のサニタイズは別途定義）。

- **(a) 品質がどう向上するか（Q1 ランキング適合性）**
  - **[事実]** 現状 `userBoost <= 1` はコンストラクタで強制的に1へ丸められる（`SuggestItem.java:131-135`、出典: ISS-15）。結果、document/query 経路は実質 userBoost=1 に固定され、**USER（elevate word）経路以外では boost による微調整が一切効かない**。「この語をやや下げたい（0.5 倍）」「ドキュメント由来のこの語をやや上げたい（1.3 倍）」といった連続的なランキング調整が、丸めによって不可能になっている。
  - 品質上の問題は **「ランキングの細粒度コントロールができない」** こと。現状の boost は「elevate で強制的に上げる（boost>1）か、何もしない（=1）」の事実上2値しか持てず、サジェスト結果の並びを意図どおりに微調整する表現力が乏しい。
  - To-Be では丸めを撤廃し、function score の userBoost を連続値で効かせられるようにするため、**語ごと・ソースごとの重み付けでランキング適合性を細かく作り込める**。これは Q1 を「2値の粗いコントロール」から「連続値の細粒度コントロール」へ引き上げる。
  - **[要確認]** 連続値 boost を function score の乗算項にどう載せるか（`weight` / `field_value_factor` の `missing`・`modifier` 設計）は OpenSearch バージョン依存 API に関わるため TBD-01。負値・ゼロのサニタイズ規則は別途定義が必要（提案）。
- **(b) 解消される ISS**: ISS-15（userBoost<=1 強制丸めによる boost 表現力の制約）。
- **(c) 漸進案との品質面の対比**: 漸進案（`0005` §9.4(c)）は「userBoost 丸めを撤廃する」局所変更で、boost 表現力（Q1）の回復という品質改善は漸進でもほぼ達成できる。ゼロベースとの差は、`ScoringStrategy` 抽象（`0005` §9.2）の中で boost の効かせ方そのものを差し替え・実験できるか否か。品質面では「丸め撤廃」だけで本課題は解消するため、ここは**漸進でゴールに到達しやすい品質課題**。なお boost 規則がコード上どこで差し替え可能になるか（拡張点としての側面）は**変更容易性（3-3 §2.7）の主担当**であり、本書は「ランキング適合性＝微調整の効き」という品質面に集中する。

### 2.3 §9.3 bad word 誤削除の機構的排除 — 出すべき語を巻き込まない語管理（Q3, ISS-04）

3-1 §9.3 は、`*badword*` 部分一致ワイルドカード削除（ISS-04）をやめ、**keyword 完全一致（`termQuery(TEXT, badword)`）で対象語だけを削除**し、さらに論理削除（フラグ）化・削除前ドライランを持つ語管理に再設計する。

- **(a) 品質がどう向上するか（Q3 語管理の正しさ）**
  - **[事実]** 現状 bad word 削除は `deleteByQuery(wildcardQuery(TEXT, "*badword*"))`（`WordManagementOperations.java:77-84`）で部分一致削除する。`text` は `keyword`（非解析）で多語フレーズも単一スペース区切りの1値（`mappings-default.json:48-50`, `SuggestConstants.java:37`）、両端ワイルドカードでアンカーが無いため、**短い bad word が他語の部分文字列であるだけで誤削除が機構上不可避**で、しかも `deleteByQuery` のため不可逆である（出典: ISS-04, `0003` §2, [[project-suggest-scoring]]）。重大度は品質軸の中で最も高い **中〜高**。
  - 品質上の問題は **「出すべき良質な候補が、無関係な bad word 登録の巻き添えで消える」** こと。例えば「ai」を bad word に登録すると「detail」「email」「campaign」等の語まで `*ai*` 一致で消える。これは Q3（語管理の正しさ）を直撃し、二次的に Q4（カバレッジ）も毀損する（出すべき語が消える＝取りこぼし）。
  - To-Be の term 完全一致化により、**「bad word に登録した語だけが、その語だけ消える」**という予測可能で正確な語管理になる。論理削除（`excluded` フラグ等）化で誤操作からの復元可能性を持たせ、削除前ドライラン（`SuggestWordAdmin` の責務、§3）で「この bad word は N 語に影響する」を事前提示することで、誤削除を**機構的に**（運用規律ではなく設計で）排除する。これは品質課題 ISS-04 を「実装の正しさ」ではなく「機構の正しさ」のレベルで解消する。
  - **[要確認]** 論理削除化はインデックス容量・検索時の除外クエリコストとのトレードオフがある（`0005` §9.3）。容量/レイテンシ面の定量評価は 3-5（性能）の領分。
- **(b) 解消される ISS**: ISS-04（bad word の部分一致誤削除＝出すべき語の巻き添え削除）。
- **(c) 漸進案との品質面の対比**: 漸進案（`0005` §9.4(c)）は「bad word を term 完全一致に変更する」局所変更。品質面（Q3 の誤削除排除）は漸進でも本質的に達成できる — `wildcardQuery` を `termQuery` に替えれば、巻き添え削除という最大の品質欠陥は消える。ゼロベースとの差は「論理削除・ドライランによる可逆性・事前可視化まで作り込むか」で、これは語管理を `SuggestWordAdmin` の独立責務として抽象化する構造変更を伴う。**誤削除の排除という核心は漸進で到達でき、可逆性・予防的 UX はゼロベースで上積みされる**。なお語管理ロジックを差し替え可能にする拡張点としての側面は**変更容易性（3-3 §2.7）の主担当**であり、本書は「誤削除を起こさない＝出すべき語を守る」品質面に集中する。

### 2.4 §7.2.1 単一マージ規則 — 集約の取りこぼしを構造的に消す（Q2, ISS-05）

3-1 §7.2.1 は、現状2クラスに重複実装されたマージ規則を、**ただ一つの `SuggestItemMergePolicy`** に統一する（集合和：reading/fields/tags/roles/languages/kinds、加算：queryFreq/docFreq、最新置換：userBoost/@timestamp、を単一定義する）。

- **(a) 品質がどう向上するか（Q2 候補集合の正確性）**
  - **[事実]** 現状マージ規則は `SuggestItemMerger.merge`（`:59-96`、オブジェクト同士）と `SuggestItemSerializer.toUpdatedSource`（`:142-185`、item と OpenSearch Map）に**二重実装**され、readings の走査基準が非対称（前者=text 語数 `:70-75` / 後者=新 item の reading 配列長 `:146-158`）。`mergeReadings` が `item1` の語数基準のため、**item2 側の超過スロット（読み）の取りこぼし疑い**が指摘されている（[推測]、出典: ISS-05, `0003` §2）。
  - 品質上の問題は **「集約結果の属性に欠落が生じうる」** こと。読み（reading）が取りこぼされると、その読みでの前方一致サジェストが効かなくなる（例: ある語の別読みが失われ、その読み入力でヒットしなくなる）。これは Q2（候補集合の正確性）の直接の毀損であり、二次的に Q5（読み変換の精度）の成果を無に帰し、Q4（カバレッジ）も損なう。さらに二段マージ（同一バルク内マージ／既存doc マージ）で**規則が食い違うと、同じ入力でも集約結果が経路依存でぶれる**（バルク内で集約されたか、既存 doc とマージされたかで読み配列が変わりうる）。
  - To-Be ではマージ規則が `SuggestItemMergePolicy` 1箇所に定義され、二段マージとも同一規則を参照するため、**走査基準の非対称が構造的に消え、読みの取りこぼしと経路依存のぶれが生じない**。これは Q2 を「実装次第で取りこぼす状態」から「定義上取りこぼさない状態」へ引き上げる。集約の正確性が「単一の真実」によって保証される。
- **(b) 解消される ISS**: ISS-05（マージ規則の二重実装・走査基準非対称・readings 取りこぼし疑い）の**品質面**。
- **(c) 漸進案との品質面の対比**: 漸進案（`0005` §7.3(c)）は「2クラスのマージ規則を共通ヘルパに抽出して呼び分ける」。品質面（Q2 の取りこぼし解消）は漸進でも達成できる — 走査基準を含む規則本体を共通ヘルパ1箇所に集約し、readings の走査を「両 item の和集合（最大語数基準）」に正す実装にすれば、取りこぼし疑いは解消する。ゼロベースとの差は小さく、ここは**漸進でも品質ゴールに到達しやすい課題**。ただし「現状の走査基準のどちらが正しいか」を確定し正す作業は必要で、その正しさの検証には既存テスト群（`0005` §11）がセーフティネットになる。なお、マージ規則を1箇所に集約することによる「変更容易性（規則変更が1箇所で完結 M2）」は **3-3 §2.4 の主担当**であり、本書は「集約結果に欠落がない＝候補集合の正確性」という品質面に集中する。

### 2.5 §7.2.2 書き込み・集約の実行モデル — 集約の正確性を保ちつつバルク化（Q2, ISS-10）

3-1 §7.2.2 は、アプリ側 Get-then-update（ISS-10）をやめ、**第一候補として OpenSearch 側集約（`scripted_upsert` 等）、フォールバックとして multiGet バルク化**で集約を実行する。

- **(a) 品質がどう向上するか（Q2 候補集合の正確性）— ただし主担当は 3-5（性能）**
  - **[事実]** 現状 `SuggestIndexWriter.write` は mergedItems を1件ずつループし、各件で `prepareGet().get()` を**同期実行**（`SuggestIndexWriter.java:54-55`）。N件登録で N回 Get + 1回 bulk（multiGet でない）。出典: ISS-10。
  - **役割分担の明示**: ISS-10 の**主たる影響軸は性能**（往復が件数に線形＝大量登録時のボトルネック）であり、その最適化は **3-5（性能）の主担当**である。本書が扱うのは ISS-10 の**品質に波及する面**に限る。
  - **品質面の論点**: 集約は「決定的 ID（`createSuggestTextId`）で同一語を1ドキュメントに集める＋既存 doc とマージして頻度を累積する」処理であり、**集約の実行モデルが集約の正確性（Q2）に影響しうる**。具体的には、(1) Get-then-update は「Get した時点のスナップショット」に対してアプリ側でマージするため、**同一語への並行更新があると last-writer-wins で頻度の加算が失われうる**（read-modify-write の競合）。これは「同じ語が短時間に複数経路から登録された際、頻度カウントが取りこぼされる」という Q2 の正確性リスクである。(2) To-Be 第一候補の `scripted_upsert`（OpenSearch 側で「あれば加算、なければ新規」を原子的に実行）は、この read-modify-write 競合を OpenSearch 側の原子的更新で解消するため、**並行登録下でも頻度集約が取りこぼされない**。集約の正確性が実行モデルのレベルで保証される。
  - **[要確認]** `scripted_upsert`・スクリプト集約の利用可否は OpenSearch バージョン依存（TBD-01）。スクリプトは静的に保ち `params` のみ動的に渡す方針（`0005` §7.2.2）。原子的集約が使えない場合の multiGet フォールバックは往復を減らすが read-modify-write 競合自体は残るため、競合の実害（並行登録の頻度・実発生率）の定量評価は **3-5（性能）と連携**して行う。
- **(b) 解消される ISS**: ISS-10（Get-then-update 依存）の**品質に波及する面**（並行更新時の集約取りこぼしリスク）。性能面（往復コスト）は 3-5 が主担当。
- **(c) 漸進案との品質面の対比**: 漸進案（`0005` §7.3(c)）は「Get を multiGet 化する」。multiGet は往復を1回に減らす（性能改善）が、read-modify-write の競合（並行更新時の頻度取りこぼし）という品質リスクは依然残る。原子的集約（`scripted_upsert`）への移行が、品質面（並行登録下の集約正確性）でゼロベースが漸進案に明確に優る点。**ただし ISS-10 は元来性能課題であり、品質面はその副次的側面**であることを明記する（過大評価しない）。

### 2.6 §4.2 データソース抽象 ＋ §9.2 スコアラ — 人気語・蓄積属性のカバレッジ拡張（Q4, ISS-11／ISS-12）

3-1 §4.2 は、サジェスト語の供給を「閉じた4経路」から `SuggestSource` プラグイン抽象へ転換し、同義語・関連語等を独立ソースとして追加可能にする。ソースが produce する `SuggestItem` の属性（reading/kinds/freq 等）をレスポンス整形側（§3 `SuggestQueryService`）が選択的に露出できるようにする。

- **(a) 品質がどう向上するか（Q4 カバレッジ）**
  - **ISS-12（人気語カバレッジ）** [事実]: 現状の人気語は `must(termQuery(KINDS,"query"))` を強制し、`reading_1` 不在（=単一語）かつ `queryFreq >= threshold`（既定10）のみを対象とする（`PopularWordsRequest.java:212-214, 242-246`、出典: ISS-12, `legacy/03` 3.4）。つまり**多語フレーズの人気語・document 由来の人気語が人気語結果から構造的に除外される**。品質上の問題は「実際によく検索される良質なフレーズが人気語に出ない＝カバレッジの取りこぼし」である。
    - To-Be では、(1) 人気語の対象条件（Kind/語数/freq 閾値）を `ScoringStrategy`／クエリ構成の調整可能なパラメータにし、(2) 同義語・関連語を独立ソース化することで、**多語フレーズや別語源の候補も人気語・サジェスト候補に載せられる**。これは Q4（カバレッジ）を「query・単一語・freq>=10 に限定」から「語源・語数・条件を選べる」状態へ拡張する。
  - **ISS-11（蓄積属性の活用）** [事実]: `SuggestItem` には reading/kinds/freq/roles 等の豊富な属性があるが、API レスポンスは text と tags のみで蓄積属性は UI で死蔵している（出典: ISS-11, `legacy/04` 4.5, `legacy/03` 3.5）。品質面では、これら属性は**候補の質を高める材料**（例: kinds で「人気検索語」と「文書由来語」を区別して提示、freq で確からしさを示唆）になりうるのに活かされていない。
    - To-Be のデータソース抽象＋選択的属性露出（`0005` §4.2）により、蓄積属性を候補の品質情報として転用できる素地ができる。
  - **役割分担の明示（重要）**: ISS-11・ISS-12 は**新機能（3-6）と重複する論点**である。本書 3-4 は「**現行の品質課題＝出すべき候補のカバレッジ取りこぼしの解消**」として扱い、(i) 人気語条件の硬直（query/単一語/freq>=10 限定）を緩めて取りこぼしを減らすこと、(ii) 蓄積属性を候補品質の材料に転用する**素地**があること、までを品質面の成果とする。一方、**蓄積属性を使った新しい UI/API 機能（種別バッジ・頻度可視化・読み活用 UI 等）や、同義語/関連語/セマンティックといった新しいサジェストソースそのものの設計は 3-6（新機能）の主担当**であり、本書は再掲せず 3-6 に譲る（§6 役割分担）。さらに、外部ベンチマーク（Google）との比較を起点にしたカバレッジ差分（ロングテール補完・トレンド等）は **3-7 の領分**である。
- **(b) 解消される ISS**: ISS-12（人気語の対象限定によるカバレッジ取りこぼし）、ISS-11（蓄積属性の死蔵＝候補品質材料の未活用）の**品質面（カバレッジ）**。
- **(c) 漸進案との品質面の対比**: 漸進案は「人気語クエリの Kind/語数/freq 条件を設定可能にする」「レスポンスに既存の蓄積属性を追加で含める」局所変更。Q4（カバレッジ）の改善は漸進でも相当程度達成できる — 人気語条件を緩めれば多語フレーズも拾え、属性をレスポンスに足せば UI で使える。ゼロベースとの差は「同義語/関連語/セマンティックを**独立ソースとして追加**できる拡張点（`SuggestSource`）の有無」で、これは新規語源によるカバレッジ拡張（＝新機能 3-6）の土台。**現行課題の取りこぼし解消は漸進で届き、新語源によるカバレッジ拡張はゼロベースの拡張点に載る**、と切り分ける。

### 2.7 §6.2.1 スキーマ ＋ §9 function score — 重複排除と先頭一致優先の作り込み（Q2/Q1, 踏襲資産＋設計判断）

作業内容で明示された「重複排除・先頭一致優先」を、3-1 の設計判断と踏襲資産の組み合わせで品質面から整理する。

- **(a) 品質がどう向上するか**
  - **重複排除（Q2 候補集合の正確性）** [事実踏襲]: 決定的 ID（`SuggestUtil.createSuggestTextId`）で同一テキストを1ドキュメントに集約する仕組みが、**重複排除の基盤**である（出典: `legacy/02`, `0005` §6/§11）。同じ語が複数経路・複数回登録されても1候補にまとまり、頻度はマージ規則（§2.4）で累積される。To-Be はこの決定的 ID 集約を**踏襲する資産**として明示し（`0005` §11）、その上でマージ規則を単一化（§2.4）することで「1候補へ正しくまとめる（重複排除）＋属性を取りこぼさず累積する」を両立させる。重複排除の正確性は「決定的 ID（同一語の同定）」と「単一マージ規則（属性の正しい統合）」の二点で品質保証される。
  - **先頭一致優先（Q1 ランキング適合性／Q2 候補集合）** [事実]: 現状、前方一致は function score の `weightFactorFunction(prefixMatchWeight)`（既定2.0）でランキング上に優遇され（出典: `legacy/03` 3.4, `0005` §9.1）、サジェストの本質である「入力途中のプレフィックスに合う候補を上に出す」を実現している。To-Be では `text` を keyword に維持しつつ前方一致サジェストを成立させる設計（§6.2.1）を踏襲・明確化し、前方一致 weight を `ScoringStrategy`（§9.2）の調整可能な要素として扱う。これにより**「先頭一致をどれだけ強く優先するか」をランキング適合性（Q1）の調整軸として作り込める**。
  - **[要確認]** 前方一致のマッチ方式（keyword に対する prefix query／edge n-gram アナライザ等）と weight の載せ方は OpenSearch バージョン依存 API・スキーマ設計に関わるため TBD-01／スキーマ詳細設計（3-5 と連携）。本書は「先頭一致優先をランキング調整軸として持つ」方向性を示す。
- **(b) 解消される ISS**: 直接の品質必達 ISS には1対1で対応しないが、**重複排除は ISS-05（集約の正確性）と表裏**（決定的 ID 集約＋単一マージ規則）であり、**先頭一致優先は ISS-14（ランキング単系統化）の中で調整可能になる**。
- **(c) 漸進案との品質面の対比**: 重複排除（決定的 ID）も先頭一致優先（prefixMatchWeight）も**現状で既に機能している良い資産**であり、ゼロベースでも漸進でも踏襲する（全置換不要）。差が出るのは「先頭一致 weight を `ScoringStrategy` の調整軸として明示化するか」程度で、品質面ではこのレイヤは**現状が健全で、To-Be は維持・微増**。過剰に作り直す対象ではない（原則7）。

### 2.8 §5 テキスト処理パイプライン — 多言語・読み変換の精度（Q5, 踏襲資産）

3-1 §5 のテキスト処理パイプライン（Normalizer→ReadingConverter→Analyzer の Strategy+Composite）は**責務分割が良好で直接の品質 ISS を持たない踏襲資産**だが、サジェスト品質の Q5（テキスト処理の精度）を支える中核であるため、品質面から明示的に位置づける。

- **(a) 品質がどう向上するか（Q5 テキスト処理の精度）**
  - **[事実]** 共通テキスト処理は Normalizer(Chain)→ReadingConverter(Chain)→SuggestAnalyzer の構成で、converter/normalizer/analysis 計約1,369行、各処理は単機能・小規模（責務分割良好）。実体として `ICUNormalizer`・`FullWidthToHalfWidthAlphabetNormalizer`・`HankakuKanaToZenkakuKana`（表記ゆれ正規化）、`KatakanaConverter`・`KatakanaToAlphabetConverter`（読み変換）等があり、ドキュメント側とクエリ/メタ側で別々の `ReadingConverter`（`readingConverter` / `contentsReadingConverter`）を使い分ける（出典: `0003` §3.1/§3.3, `legacy/02`）。専用テストが手厚い（`0005` §11）。
  - 品質上の意味: この正規化と読み変換の精度が、**入力（かな/ローマ字/全角半角ゆれ）と候補のマッチ精度（Q5）を直接左右**する。例えば「ｶﾞｯｺｳ」「がっこう」「gakkou」のいずれの入力でも同じ候補にマッチするのは、この正規化＋読み変換が正確だからである。Q5 が崩れると、前方一致に拾われず Q2（候補集合）・Q4（カバレッジ）まで連鎖的に毀損する。**現状この品質基盤は既に良好**であり、To-Be はこれを踏襲・再利用する資産として保全する（原則7）。
  - **多言語の精度向上 [提案]**: To-Be は `TextProcessor` 抽象として明文化し、**言語別の Normalizer/Converter セットを切り替え可能**にする（言語判定→言語別 Chain 選択、`0005` §5.2）。これにより日本語特化（カタカナ→アルファベット等）に加え、他言語の正規化・読み変換を Chain に足すだけで Q5（多言語のマッチ精度）を拡張できる。**役割分担**: 多言語強化を「新機能」として展開する設計は 3-6 の主担当であり、本書は「テキスト処理の精度＝マッチ精度という品質基盤を踏襲し、多言語拡張の素地を持つ」品質面に集中する。
- **(b) 解消される ISS**: 直接解消する品質 ISS はない（このレイヤは現状でも健全）。間接的に Q2/Q4/Q5 を支える品質基盤として、**踏襲・再利用資産の明示**（完了条件）をこのレイヤが担う。
- **(c) 漸進案との品質面の対比**: 漸進案＝現行パイプライン維持。To-Be との差は「`TextProcessor` 抽象としての明文化＋多言語拡張点の追加」程度で、**このレイヤはゼロベースでも漸進でもほぼ同一**（全置換不要・流用価値の高い品質資産の好例）。品質面では現状の読み変換精度をそのまま温存することが最善であり、安易な作り直しは既存のマッチ精度・テスト資産を損なうリスクのほうが大きい。
