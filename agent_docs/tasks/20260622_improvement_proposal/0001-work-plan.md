# 作業プラン: 20260622_improvement_proposal

## 概要

fess-suggest の「メジャーバージョンアップ級の抜本的改善」を行うための **改善案（提案ドキュメント）** を作成する。
本タスクのゴールは実装ではなく、抜本的改善のための提案を体系立てて文書化することである。

要件定義（`0000-requirements-definition.md`）が掲げる5つの目的（可読性 / 変更容易性 / サジェスト品質 / 性能 / 新機能）を検討軸とし、
既存タスク `20260622_analyze_suggest` の現状分析（`agent_docs/global/references/legacy/` 配下）を一次インプットとして活用しながら、
要件定義の方針（既存モジュール構成にとらわれずゼロベースで「あるべき姿」を目指す）に沿って、
「現状の課題（As-Is）の把握 → ゼロベースでの『あるべき姿（To-Be アーキテクチャ）』の設計 → 既存からの移行戦略・優先度・ロードマップ」という流れで提案をまとめる。

最終成果物は本タスクディレクトリ（`agent_docs/tasks/20260622_improvement_proposal/`）配下の改善提案ドキュメント群とする。

## 前提・スコープ

### 対象範囲
- `modules/fess-suggest`: サジェスト用ライブラリ本体（中心）。
- `modules/fess`: fess 本体側の連携（呼び出し経路・設定・UI/API）に対する改善も、サジェストに関わる範囲で対象とする。
- 検討軸（要件定義の目的に対応）:
  1. コードの可読性の向上
  2. コードの変更容易性の向上
  3. サジェスト品質の向上
  4. 性能面での向上
  5. サジェスト関連の新機能の検討

### スコープ外
- 改善案の **実装** そのもの（コード変更・リファクタリングの実施）。本タスクは提案作成まで。
- 実装の詳細設計レベルの完全な仕様化（提案として方向性・選択肢・トレードオフを示すレベルにとどめる。詳細設計は後続タスク）。
- fess 本体のサジェスト以外の機能改善。

### 重要な前提（既存分析の活用）
- 関連タスク `20260622_analyze_suggest` により、fess-suggest の現状分析が完了している。改善案はこれを再調査せず再利用する（重複調査を避ける）。
  - グローバルリファレンス: `agent_docs/global/references/legacy/`
    - `01-overview.md`（概要）
    - `02-architecture.md`（全体アーキテクチャ：コンポーネント図 / インデックス構造 / 登録・検索フロー / 公開 API）
    - `03-suggest-contents.md`（種別 Kind / データソース4経路 / スコアリング / 表示項目）
    - `04-fess-integration.md`（fess 本体連携：呼び出し経路 / 設定 / バッチ・リアルタイム / UI・API）
    - `05-issues.md`（発見済みの課題・未確定事項）
- 既知の主要課題（`05-issues.md` および分析より、改善案の起点となるもの）:
  - ② 検索クエリログ経路（`indexFromQueryLog`）は fess 本体で未使用のデッドパス（削減・整理の候補）。
  - `suggest.popular.word.cache.expire` のコメント（秒）と実装（分）の不一致。
  - `SuggestWordsHandler` の `suggestDetail` 設定主体が暗黙的で未確定。
  - bad word の wildcard 部分一致削除（`*badword*`）が意図より広く語を消す可能性。
  - 二段マージ・二重権限フィルタなど、把握に高度な読解を要する複雑性。
  - 機能が10年以上据え置き（種別は DOCUMENT/QUERY/USER の3種、データソース4経路のみ。同義語は解析側で独立データソースではない）。

## ステップ

### ステップ1: 既存分析ドキュメントの読み込みと課題インベントリ化
- 目的: 改善案の事実ベースを固める。再調査を避け、既存分析を改善の起点に変換する。
- 対象モジュール/ファイル:
  - `agent_docs/global/references/legacy/01〜05`（全ファイル）
  - `agent_docs/tasks/20260622_analyze_suggest/0002〜0005`（中間成果物。必要に応じ補足参照）
- 作業内容:
  - 5ファイルを読み、改善に効く事実（アーキテクチャ上の制約・スコアリング規則・連携経路・設定項目・既知課題）を抽出する。
  - 既知課題・気づきを「課題インベントリ」として一覧化する（各項目に: 課題内容 / 根拠（ファイル:行 or 出典）/ 影響する検討軸（可読性・変更容易性・品質・性能・新機能のどれか）/ 体感重大度）。
- 完了条件: 課題インベントリ表が作成され、各課題が5つの検討軸のいずれかに紐づいている。
- 注意点/リスク: 分析時点のバージョン（fess-suggest `15.7.1-SNAPSHOT` / OpenSearch 系 / Java 21+）を前提として明記する。分析で「未確定」とされた事項は、改善案でも前提確認が必要な事項として扱う。

### ステップ2: コードベースの補足確認（改善案の根拠強化、必要範囲のみ）
- 目的: 既存分析でカバーされていない、または改善案の妥当性判断に追加確認が必要な箇所だけをピンポイントで確認する。
- 対象モジュール/ファイル（必要に応じて）:
  - `modules/fess-suggest/.../suggest/`（特に `index/operations/` の複雑なクラス、`request/suggest/`、`entity/SuggestItemSerializer`、`converter`/`normalizer`/`analysis` 系のテキスト処理パイプライン）

  - `modules/fess/.../helper/SuggestHelper.java` ほか連携箇所
- 作業内容:
  - 可読性・変更容易性の評価のため、クラスの責務分割・依存関係・行数規模・テストの有無を確認する。
  - 品質改善の検討に必要な範囲で、スコアリング（function score）・読み変換・正規化の実装を確認する。
  - テスト（`src/test`）の有無・カバレッジ感を確認し、変更容易性の根拠とする。
- 完了条件: ステップ1の課題インベントリに、コードベース確認で得た補足根拠が追記されている。
- 注意点/リスク: 本タスクは提案作成であり、調査は「提案の根拠付けに必要な最小限」にとどめる。全コードの網羅読解はしない。既存分析で十分な項目は再確認しない。

### ステップ3: ゼロベースでの「あるべき姿（To-Be アーキテクチャ）」の設計

要件定義（`0000-requirements-definition.md`）が明示するとおり、本タスクは「既存モジュールの構成を維持する必要はなくゼロベースで検討を行い、あるべき姿を目指す」。
そこでステップ3は、**「既存の課題を一つずつ直す」漸進的リファクタリングの発想を起点にせず、「もし fess-suggest をゼロから作り直すなら、どうあるべきか」という理想形（To-Be アーキテクチャ）を主軸として設計する**。

- ステップ3の主軸: **ゼロベース To-Be アーキテクチャの設計**（ステップ3-1）と、それが要件の5目的をどう満たすかの照合（ステップ3-2〜3-6）。
- 既存課題（ISS-01〜17 / TBD-01〜05）は「直す対象」ではなく、**「ゼロベース設計が回避・解消すべきアンチパターンの実例」**として参照する（あるべき姿の各設計判断に対し、対応する ISS/TBD を「この設計で解消される現行課題」として紐づける）。
- 漸進的改善案を完全には捨てない。各設計判断に対し**「ゼロベース To-Be 案（主）」と「既存構成を維持した場合の漸進案（従・対比用）」を併記**し、両論を意思決定材料として残す。ただし**既存からの差分・移行戦略そのものはステップ4で扱う**（ステップ3は「あるべき姿」の設計に集中し、移行可能性は対比メモにとどめる）。
- 既存資産の扱い: ゼロベースであっても、流用価値の高い資産（ステップ2で確認した充実したテスト群＝main 64ファイル/11,591行に対し test 77ファイル/15,194行、責務分割が良好なテキスト処理パイプライン＝converter/normalizer/analysis 計約1,369行 等）は「あるべき姿でも踏襲・再利用する資産」として明示的に位置づける。

- ステップ3共通の対象: ドキュメント検討（コードは参照のみ）。インプットはステップ1〜2の課題インベントリ（`0002`/`0003`）と要件定義（`0000`）。

#### ステップ3-1: To-Be アーキテクチャ全体像の設計（主軸）
- 目的: 現行の制約に縛られず、fess-suggest の理想アーキテクチャをゼロから描く。以降の3-2〜3-6（5目的の照合）の土台とする。
- 作業内容: 以下のレイヤ／論点について「あるべき姿」を設計し、各設計判断に対して (a) 設計意図、(b) 解消される現行課題（対応 ISS/TBD）、(c) 既存維持の漸進案との対比、を添える。
  - **コンポーネント構造**: 肥大化したファサード（ISS-13: `Suggester` 507行/public18、`SuggestIndexer` 547行/public28）に代わる、用途別（lifecycle / query / word-management / indexing）に分離した API 境界の設計。公開 API 表面積を抑える原則。
  - **データソース抽象**: 現行4経路（うち ISS-01 のクエリログ経路はデッドパス）を、プラグイン可能な「サジェストソース」抽象として再設計。新規ソース（同義語・関連語・セマンティック等）を後付けでなく最初から追加可能にする拡張点。
  - **テキスト処理パイプライン**: 現行の Normalizer→ReadingConverter→Analyzer の Strategy+Composite 構成は責務分割が良好なため、**あるべき姿でも踏襲する資産**として位置づけつつ、多言語・拡張容易性の観点で理想形を整理。
  - **インデックス設計**: 単一シャード固定（ISS-07 / TBD-05）・`refresh_interval`・決定的 ID 集約・二重エイリアス再構築を、規模拡張とゼロダウンタイムを両立する理想設計として再検討。事前計算 `score` フィールド（ISS-14/16 の死蔵）を持つか持たないかを含むスキーマ設計。
  - **書き込み／集約モデル**: Get-then-update（ISS-10: 1件ずつ同期 Get）・二段マージ（ISS-05: マージ規則の二重実装）を排した、単一のマージ規則・バルク効率の高い集約モデル（upsert/スクリプト集約・multiGet 等）の理想形。
  - **同期／非同期モデル**: 不均一な現行境界（ISS-09）に代わる一貫した同期/非同期モデル。独自 `Deferred`/`Promise` を踏襲するか標準機構（`CompletableFuture` 等）へ置き換えるかの方針。
  - **スコアリング機構**: 登録時事前計算と検索時 function score の関係（ISS-14: 実態は function score 単系統、事前計算 score は死蔵）を整理し、ランキング源を一系統に統一した理想設計。bad word の誤削除機構（ISS-04: 完全一致でなく `*badword*` 部分一致）を排した語管理設計を含む。
  - **権限・フィルタ**: 二重担保（ISS-06）を排した、責務境界の明確な権限フィルタ設計。
- 完了条件:
  - 上記レイヤ／論点すべてについて「あるべき姿」の設計判断が記述され、各判断に**解消される現行課題（対応 ISS/TBD）が紐づいている**。
  - 各設計判断に**ゼロベース To-Be 案と既存維持の漸進案の対比**が併記されている。
  - 踏襲・再利用する既存資産（テスト群・テキスト処理パイプライン等）が明示されている。
  - TBD（特に TBD-01: OpenSearch/Lucene 数値バージョン未解決）に依存する設計判断は「要確認」を付し断定しない。
- 注意点/リスク: ゼロベースとはいえ「全置換が常に最善」ではない。流用価値のある資産まで安易に捨てる設計にしないこと。技術選定の置換（非同期基盤・OpenSearch 依存 API 等）は TBD-01 の前提制約を引き継ぎ、実現可否は「要確認」で示す。

#### ステップ3-7: Google 検索サジェストとの比較による差分分析と打ち手の検討
- 目的: 外部ベンチマークとして広く知られる **Google 検索のサジェスト** を比較対象に置き、fess-suggest（現状 As-Is）および本タスクで設計した **あるべき姿（To-Be、3-1）** との差を考察する。fess-suggest／To-Be が劣る軸については、その差を **どのあるべき姿アーキテクチャ（3-1 の拡張点）に載せて埋めるか** を検討する。3-4（品質）・3-6（新機能）が「内部課題（ISS/TBD）起点」で改善を導くのに対し、3-7 は **「外部ベンチマーク（Google）との比較を起点に差分と打ち手を導く」** 位置づけとし、両者の役割分担を明記する。
- 位置づけ・前提:
  - Google 検索サジェストは **大規模な独自クエリログ・トレンドデータとプロプライエタリ技術** を前提とする。一方 fess は **オンプレ／エンタープライズ検索で対象コーパスが限定的** であり、前提条件が根本的に異なる。したがって **すべてを模倣する必要はなく**、「埋めるべき差」と「fess の文脈では不要・非現実的な差」を切り分ける視点を必須とする。
- 作業内容:
  - **比較軸の整理**: Google 検索サジェストの代表的特性を比較軸として整理する。少なくとも以下を含める。
    - 入力途中のプレフィックス補完／インクリメンタル性・低レイテンシ
    - タイプミス補正・あいまい一致（fuzzy）
    - 人気度・トレンド（急上昇）・鮮度（時系列）の反映
    - パーソナライズ（履歴・文脈・地域）
    - クエリ補完だけでなく関連クエリ・ロングテール補完
    - 多言語・かな/ローマ字・表記ゆれの吸収
    - セマンティック／意図理解
    - 安全性フィルタ（不適切語の抑制）
  - **三者比較の考察**: 各比較軸について「**fess-suggest 現状（As-Is）／あるべき姿（To-Be、3-1）／Google 検索サジェスト**」の三者を対比し、差（できていること・劣っていること・前提差）を考察する。劣っている軸はギャップを明示する。
  - **差を埋める打ち手の検討**: fess-suggest／To-Be が劣る軸について、差を埋める方法を **3-1 のどの拡張点に載せるか**（データソース抽象＝新規サジェストソース追加、スコアリング機構＝人気度/鮮度/fuzzy のランキング反映、インデックス設計＝補完用スキーマ/アナライザ、テキスト処理パイプライン＝表記ゆれ吸収 等）として具体化する。各打ち手に「期待効果 / 実現難易度 / あるべき姿での実装位置 / 要確認の前提」を付す。
