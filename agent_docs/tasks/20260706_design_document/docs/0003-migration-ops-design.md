## 0. エグゼクティブサマリ

本書は「fess-suggest をどう動かし、どう入れ替えるか」を確定させる。**`0001` が公開契約の正、`0002` がデータの形の正であるのに対し、本書は手順の正である。**

**中核は §1 である。** 二重エイリアス機構そのものは健全であり、壊れているのは呼び出し側の制御フローである。この切り分けを外すと以降の手順が的を外す。

## 1. 現行の再構築フローと 4 つの欠陥

### 1.1 何が壊れていて、何が壊れていないか

> **二重エイリアス機構そのものは健全である。** エイリアス付替は `Suggester.java:318-324`（`switchIndex`）と `:262-267`（`createNextIndex`）のいずれも **add / remove を 1 リクエストに束ねており atomic** である。検索は検索エイリアス（`Suggester.java:160,168`）、登録は更新エイリアス（`:408`）を見るため、再構築中も検索は旧世代で継続する。
>
> **壊れているのは、この機構を呼び出す側の制御フロー**である。`(fess) exec/SuggestCreator.java:297-301` は取り込みの成否を一切見ずに切替と旧世代削除を実行する。

`legacy/02-architecture.md:91` の「切替が原子的になる [確認]」は**エイリアス付替単体については正しい**が、**4 ステップ全体はアトミックではない**。両者を混同すると「原子的だから安全」という誤読が生じる（付録 A.1 の G-2）。

### 1.4 `removeDisableIndices()` の実際の判定範囲 [確認]

### 2.5 冪等性・リトライ・purge の順序依存 [確認]

- **リトライ機構は存在しない。** `job/`・`exec/` 配下に retry 相当の実装は無く、失敗しても次回 cron まで再実行されない（K-15）。
- **`create()` は冪等である。** 毎回まっさらな次世代インデックスを作るため、途中失敗後の再実行が前回の残骸に影響されない（唯一の例外が §2.4 の増分書き込みの取り残しである）。
- **`purge()` は `switchIndex()` の後でなければならない。** `(fess) exec/SuggestCreator.java:236-239` は `create()` が 0 を返したときだけ `purge(startTime)` を呼ぶ。purge の実体（`(fess) helper/SuggestHelper.java:314,331`）は `suggester.getIndex()`（＝**検索エイリアス** — `Suggester.java:416-418`）を対象とするため、**切替前に呼ぶと旧世代を削ることになる**。この暗黙の順序依存を §3 の手順変更で壊してはならない。

> **是正の実利は 1 行目にある。** 第 5 版までの契約では「付替がタイムアウトしたが実際は適用済み」というケースが `SuggesterException` になり、**S2 が実行されないまま「更新エイリアスが空の新世代を指す」状態が残っていた**。この状態では以後のリアルタイム増分書き込み（`indexFromSearchWord` / `addElevateWord` / `addBadWord`）がすべて空の新世代に入り検索側に現れない（§2.4 の注記の状態そのものである）。post-condition で判定すれば、**適用済みなら S2 へ進んで正常な再構築として完走する。**

#### S4. 旧世代への保持用エイリアス付与 ＋ 検索エイリアスの切替

| 項目 | 内容 |
| --- | --- |
| **何をするか** | 現在の検索エイリアスが指すインデックスへ `{baseIndex}.prev` を付け替えつつ、検索エイリアスを新世代へ移す。**両者を 1 リクエストで行う** |
| **実装箇所** | **`lifecycle.switchIndexRetainingPrevious()`**（`0001` §2.2 / §2.2.1 の D-21）。実装は既存 `Suggester.java:282-334`（`switchIndex`）の検査（`:286` / `:298` で両エイリアスの対象が**ちょうど 1 個**であること、`:308-313` で同一なら no-op return）を踏襲し、`:318-324` の aliases actions に **`.prev` の remove / add を加えた 1 リクエスト**にする。呼び出し元は `(fess) exec/SuggestCreator.java:298` の**1 箇所のみ** |

> **第 4 版での変更（MO-17）**: 第 3 版までは (1) `.prev` 付与を fess 側で `SearchEngineClient` を用いて行い、(2) `switchIndex()` を呼ぶ、という **2 リクエストの 2 段構成**だった。**`0001` 第 4 版が `switchIndexRetainingPrevious()` を primitive として追加したため 1 リクエストに束ねられる。**
>
> **第 3 版が 1 リクエスト化を見送った理由（「`switchIndex()` の変更が必要になり MO-1 に反する」）は成立しない。** MO-1 は「**再構築を束ねる高水準 API を新設しない**」であって「fess-suggest に一切手を入れない」ではない（§4.2.1 が `validateNext` について既に同じ整理をしている）。**エイリアス遷移の atomic primitive は再構築の制御フローを持たず、判定も順序制御も fess 側に残る**ため MO-1 と衝突しない。

>

> **エイリアス操作の失敗を「状態は変わっていない」と読み替えてはならない**（第 4 版で追加。`0001` §2.2.2 と対）。**aliases request がタイムアウトで例外を返しても、サーバ側では適用済みでありうる。**
>
> **第 5 版（MO-20）で、この判定はライブラリ側へ移した。** 第 4 版は fess 側に「`GET /_cat/aliases/{baseIndex}*` で再取得して post-condition で決める」手順を書いていたが、**判定に必要な読み取り面が `0001` の公開契約に存在しなかった**（同書 §10 の申し送り 11 として実装タスクへ送られていた）ため、手順として成立していなかった。`0001` 第 5 版の **D-23** が `switchIndexRetainingPrevious()` 自身の正常完了を post-condition の成立として定義したことにより、**fess 側の分岐は例外型の 3 分岐になる。**
>
> | 例外 | 意味 | fess 側の行動 |
> | --- | --- | --- |
> | **なし（正常完了）** | post-condition が成立している（下位リクエストが失敗しても、再取得で適用済みと確認された場合を含む） | **S5 へ進む** |
> | `SuggesterException` | **未適用と確定した** | `exitCode = 1` で終了する。**次回実行で S1 からやり直せる** |
> | **`SuggestAliasStateUnknownException`** | **成否を判定できない**（状態の再取得自体が失敗した／状態が post-condition とも pre-condition とも一致しない） | **切替を進めず `exitCode = 1` で終了し、手順書の調査手順（§12 の K-18）へ回す。自動リトライしない** |
>
> **「失敗したから元に戻っている」という前提での無条件リトライを禁止する。** 二重適用（`.prev` が 2 世代前を指す）と未適用（保持されない切替）を取り違える。**この規則は S1 の更新エイリアス付替と §5.3 の R3 にも同じく適用する** — **S1 については第 6 版（MO-21）で `0001` 側の D-23 の対象が拡張され、契約として成立した**（それまでは本書だけが規則を主張し、ライブラリの契約が追随していなかった）。
>
> **調査時に状態を読むには `lifecycle.aliasState()` を使う**（`0001` §2.2）。`GET /_cat/aliases/{baseIndex}*` を fess 側や手順書から直接叩く形は採らない — **`{baseIndex}` は設定インデックスに永続化された値であり、`fess_config.properties` の設定値から組み立てられない**（§3.1 の注記 ／ `0004-corrections.md` の G-1）。運用者が手で確認する場合に `_cat/aliases` を使うことは妨げないが、**そのときも baseIndex の実値は `aliasState()` または設定インデックスから得ること。**

#### S5. 孤児インデックスの回収

| 項目 | 内容 |
| --- | --- |
| **何をするか** | エイリアスを 1 つも持たないサジェストインデックスを物理削除する |
| **実装箇所** | `Suggester.java:339-360`（`removeDisableIndices`）。判定範囲は §1.4。呼び出し元は `(fess) exec/SuggestCreator.java:301` の**1 箇所のみ** |
| **成功判定** | 検索エイリアス・更新エイリアス・`.prev` のいずれかを持つインデックスだけが残る |
| **失敗時の分岐** | 例外は `create()` を抜けて exit≠0 になる。**データは失われない**（削除に失敗しただけ）。次回実行で回収される |

**S4 で `.prev` を付けたことにより旧世代は S5 の削除対象から外れる。** 回収されるのは §2.4 の孤児インデックスと、`.prev` を解除した 2 世代前だけである。

### 3.3 保持世代の付け替え

**`.prev` を付けっぱなしにしてはならない。** 解除しないと 2 世代前が残り続け、世代が増えるたびに `.prev` が複数インデックスを指す。

> **規則**: `switchIndexRetainingPrevious()` は「**既存の `.prev` を全インデックスから remove し、現在の検索対象に add し、検索エイリアスを次世代へ移す**」を**1 リクエストの aliases actions で**行う。これにより保持世代は常に 1 つに保たれ、2 世代前は S5 で回収される。

**この付け替えをライブラリ側の primitive に持たせた理由でもある**（MO-17）。「`.prev` は常にちょうど 1 インデックスを指す」という不変条件は、付与と解除が別々の呼び出し元に散らばると守れない。**`removeDisableIndices()` の削除判定（エイリアスを 1 つも持たない）と対になる不変条件であり、両方を同じ層に置く。**

## 4. 事前条件と検証基準（切替可否の判定）

### 4.1 前提: 新旧の件数は単純一致しない

**「旧世代と件数が一致すること」を切替条件にしてはならない。** ID 方式とデータモデルの変更により、初回の再構築では両方向にずれる。

| 要因 | 向き | 根拠 |
| --- | --- | --- |
| ID のハッシュ化による衝突解消 | **増える** | 現行は先頭 333 バイトが一致する長文が同一 ID に合流していた（`0002` §4.3） |
| 語数上限 N による切り捨て | **減る** | N 語で切った結果、異なる長文が同一 `text` になり同一 ID に合流しうる（`0002` §2.3(b)） |
| `ElevateWord` 格納形の変更 / `score` 廃止・`excluded` 追加 | 変わらない | 語自体の増減もフィールド以外の増減も無い |
| **bad word 該当語を保存するようになったこと**（第 7 版で追加） | **増える** | `0002` DM-21。現行は取り込み時に drop していた語が、新設計では `excluded = true` のドキュメントとして保存される。**bad word を多く登録している環境ほど増分が大きい** |

**2 回目以降の再構築でも一致は保証されない。** 元ドキュメントと検索ログの増減がそのまま反映されるためである。

> **`wordCountStats()` は `excluded = true` のドキュメントを含む** [確認]。したがって **G1（件数の絶対下限）の判定は増える方向にしか影響を受けず、誤って不合格になることは無い。** ただし**運用者が移行前後で件数を目視比較する場合、bad word の登録数によっては見た目の増加が大きくなる**ため、移行手順の説明に含めること（§10.1）。**除外語を数から外した統計が必要になった場合は `WordCountStats` の改訂（`0001` §2.5）にあたり、本設計では行わない。**

### 4.2 判定基準（MO-3）

| # | 判定 | 内容 | 取得方法 |
| --- | --- | --- | --- |
| **G1** | **件数の絶対下限** | 次世代の登録語数が **0 でない**こと、かつ**旧世代の件数の一定割合（既定 50%）以上**であること | `(fess) helper/SuggestHelper.java:340`（`getAllWordsNum()`。To-Be は `lifecycle.wordCountStats()` — `0001` §2.2）。**旧世代の件数は S1 の直前に取得して保持する** |
| **G2** | **スモーククエリ** | 代表語のサジェストが 1 件以上返ること。**更新エイリアスに対して**実行する。**否定形フィルタ（`0002` DM-14）を適用する** — 検証クエリだけフィルタ無しだと bad word で除外された語が「合格」を出しうる。**メジャー移行時は必須**、平常時の再構築は運用者が未設定ならスキップしてよい（第 7 版 / MO-22 — §4.2.3） | **`lifecycle.validateNext(SuggestQuery)`**（`0001` §2.2 / D-15）。§4.2.1 |
| **G3** | **取り込み失敗なし**（第 4 版で定義を拡張 — MO-18） | `exitCode == 0` **かつ** 取り込み経路・語管理経路の**項目単位の失敗が 0 件**であること | `create()` 内のローカル状態。項目単位の失敗は `IngestResult.hasFailures()` を `exitCode` へ落として合流させる（§4.2.2） |

#### 4.2.2 G3 が「例外なし」だけでは穴になる（MO-18・第 4 版で追加）

> **`0001` D-4 により、bulk の項目単位の失敗は future を例外完了させない。全項目が失敗しても正常完了する。** したがって「例外が出なかったこと」を切替条件にすると、**欠損したままの世代が公開される。**

**成立する経路** [確認]:

| # | 事象 |
| --- | --- |
| 1 | 100 万件を投入し、そのうち 10 万件が bulk の item failure になる |
| 2 | `IngestResult.failures` に 10 万件が積まれるが **future は正常完了する**（`0001` §4.3 の 3 行目「全項目が失敗した場合も正常完了」） |
| 3 | `(fess) helper/SuggestHelper.java:294-297` の継続が `success.accept(true)` を呼ぶ |
| 4 | `(fess) exec/SuggestCreator.java:271,282,293` の `exitCode.set(1)` は**どれも発火しない**（いずれも例外経路にしかない — §1.2） |
| 5 | **G3 が合格する。** G1 は欠損 10% では 50% の下限に掛からず、G2 は未設定ならスキップされる（§4.2）※**第 7 版でメジャー移行時のスキップは禁じたが**（MO-22 / §4.2.3）、**G2 は「代表語が引けるか」の検査であり 10% 欠損は検知できない**。この穴を塞ぐのは引き続き MO-18 である |
| 6 | **不完全な新世代が検索エイリアスへ昇格し、S5 で旧世代（`.prev` を持つもの以外）が回収される** |

**塞ぎ方**: **`0001` §9.2.1 の置換形**（`result.hasFailures()` なら継続内で `SuggestIndexException` を投げる）により、部分失敗が `error.accept(...)` 経路へ落ち `exitCode = 1` になる。**G3 の判定式そのものは `exitCode == 0` のままでよく、`exitCode` に載る事象が増える**という形で接続する。

| 判断 | 理由 |
| --- | --- |
| **`0001` D-4 を変えない** | 汎用ライブラリの API として「部分失敗はレスポンスの一部として報告する」は妥当である。**変えるのは呼び出し元の読み替えであり、ライブラリの契約ではない**（`0001` D-22） |
| **全件再構築では 1 件の失敗でも不合格とする** | 再構築は「全件を作り直す」操作であり、**欠損の許容水準を設ける根拠が無い**。閾値を設けると「何件までなら公開してよいか」を実測なしに決めることになる（C-04） |
| **語管理経路（`storeAllBadWords` / `storeAllElevateWords`）も同じ扱いとする** | §10.4 が既に「1 件の変換失敗で全体を止めず、末尾で失敗件数を `exitCode` に反映する」と定めており、**同じく G3 に合流する**。取り込みと語管理の両方が 1 つのガードに集まる |

**回帰テストは §11.1 の T-S9 とする。**

**割合の下限（既定 50%）を採る理由**: 絶対値の閾値は環境ごとに意味が変わり運用できない。一方「前回の半分未満になった」は元データの正常な増減では通常起きず、部分失敗を高い確度で捕まえる。**この 50% は実測に基づかない**（C-04）ため**設定可能とする**（§13 の 5）。**旧世代が存在しない初回は割合判定を適用しない。**

#### 4.2.1 G2 の実行経路（ステップ 7 で確定）

> **`validateNext(SuggestQuery)` を `SuggestIndexLifecycle` に新設して実行する**（`0001` 第 3 版の D-15）。**本番と同一のクエリ生成をライブラリ内部で更新エイリアスへ向ける。**

初版・第 2 版の時点では、G2 は「更新エイリアスに対して実行する」ことが正しさの条件であるにもかかわらず、**その経路が公開 API に存在しなかった** [確認]。

| 層 | 初版時点の現状 [確認] |
| --- | --- |
| 現行 API | `Suggester.suggest()`（`Suggester.java:159`）が返す `SuggestRequestBuilder` は `Suggester` が保持する**検索エイリアスに束縛**されている（`Suggester.java:416-418` の `getIndex()`） |
| 新 API（第 2 版時点） | `0001` §2.1 の `SuggestQueryService.suggest(SuggestQuery)` は**対象インデックスを引数に取らない**。`0001` §2.5 の `SuggestQuery` の 12 要素にも**対象インデックスに相当する項目が無い** |

**ステップ 7 で検討した 3 案と決着**:

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(a)** | `SuggestQuery` に対象世代を指定する要素を足す | **却下**。運用専用の要素を通常の検索契約に混ぜることになり、fess の `SuggestWordsHandler` 等、検索の呼び出し元すべてに意味のない項目が見える |
| **(b)** | fess 側で `SearchEngineClient` を用いて低レベルクエリを直接組む | **却下**。サジェストのクエリ構築（`request/suggest/SuggestQueryBuilder`）を fess 側で再実装することになり、**本番経路と検証経路でクエリが乖離しうる**。乖離すると G2 は「本番で返るか」を検証しなくなり判定として無意味になる |
| **(a′)** | **`SuggestIndexLifecycle` に検証専用メソッド `validateNext(SuggestQuery)` を置く**。内部で `suggest()` と同一のクエリ生成を使い、向き先だけを更新エイリアス（`Suggester.java:408`）へ差し替える | **採用**。検索の公開契約（`SuggestQuery` / `SuggestQueryService`）を変えずに済み、かつクエリが本番と同一であることが**実装上保証される** |

**MO-1 との関係**: MO-1 は「**再構築を束ねる高水準 API を新設しない**」であって「fess-suggest に一切手を入れない」ではない。`validateNext` は再構築の制御フローを持たず、**判定は呼び出し元である fess 側のガード（§4.3）が行う**。ライブラリは合否を決めない。したがって MO-1 と衝突しない。

**検証語の設定と否定形フィルタ**: 検証語は fess 側の設定値として与える（§13 の 9 の実装位置に含める）。`validateNext` が返す `SuggestResult` は通常の検索結果と同じ経路で作られるため、**否定形フィルタ（`0002` DM-14）は自動的に適用される** — 検証クエリだけがフィルタを外す事故が構造的に起きない。これが (b) を採らなかった実利でもある。

#### 4.2.3 メジャー移行時は G2 を必須にする（MO-22・第 7 版）

##### 第 6 版の穴 [確認]

**第 6 版の G2 は「未設定ならスキップ」であり、運用者が検証語を設定しない限り常にスキップされた。** その理由（「設定必須にすると初期導入の障壁になる」）は平常時については妥当だが、**今回の移行には当てはまらない。**

**G1 と G3 が検知できない事故がある。**

| 状況 | G1 | G3 | G2 |
| --- | --- | --- | --- |
| 取り込みが 1 件も成功しない | **検知する**（0 件） | 検知する | — |
| 10% が item failure | 通過してしまう | **検知する**（MO-18） | — |
| **100% 正常に index でき、件数も十分。しかし検索が 0 件を返す** | **通過する** | **通過する** | **検知する** |

**3 行目が現実的である理由は、今回の移行で同時に変わるものの多さである。**

| 同時に変わるもの | 検索が 0 件になりうる経路 |
| --- | --- |
| mapping（`0002` §2.1） | `reading_i` のフィールド型・`dynamic` 方針の誤りで、索引はされるが検索側の想定と合わない |
| `reading_i` の付帯規則（INV-1 / INV-4） | 読みの位置対応がずれ、クエリ側の `reading_i` 参照と一致しない |
| 語数上限 N（INV-3） | N の設定ミスでクエリ側の語数が上限を超え、AND 連結が 0 件になる（K-5） |
| ID 方式（`0002` §4.1） | ドキュメントは作られるが、想定と違う粒度で合流している |
| **`excluded`**（`0002` DM-14 / DM-21） | **否定形フィルタの実装ミスや初期値の誤りで全件が除外される。DM-21 により `excluded = true` のドキュメントが実際に存在するようになったため、この経路は第 6 版より起こりやすい** |
| クエリ生成（`ScoringPlan` / `ScoringStrategy`） | 生成されるクエリ自体が誤っている |

**「全件正常に index できたのに検索だけ 0 件」は、この 6 つのいずれかが 1 つ外れれば成立する。** そして G1・G3 は**書き込み側しか見ていない**。

##### 採る形

> **メジャー移行（初回の 15 → 次メジャー）では G2 を必須とする。平常時の再構築では従来どおり任意でよい。**

| # | 規則 |
| --- | --- |
| 1 | **メジャー移行の再構築では、G2 を実行せずに切替へ進んではならない。** スキップは不合格と同じ扱い（切替中止）である |
| 2 | **検証語は運用者が設定するのが第一である**（`index.document.suggest.validation.words` 相当。§13 の 9） |
| 3 | **未設定の場合は自動採取にフォールバックする**（下記）。**「設定必須」にはしないため、初期導入の障壁は生じない** |
| 4 | **平常時の再構築では第 6 版のまま**（未設定ならスキップし G1・G3 で判定する）。メジャー移行かどうかは**運用者が起動時に指定する**（§4.3 のガードが読む） |

##### 未設定時の自動採取

> **S2 で実際に投入した語から数件を採り、それをスモーククエリの入力にする。**

| 項目 | 内容 |
| --- | --- |
| **採取元** | S2 の取り込み中に通過した `SuggestCandidate.text` を数件保持する（`create()` 内のローカル状態。G3 の失敗件数を数えているのと同じ位置） |
| **件数** | 1 件以上・数件程度。**多くしても検出力は上がらない**（同じ経路を通るため） |
| **採取条件** | **`excluded = false` として保存された語に限る**（bad word 該当語は否定形フィルタで正しく 0 件になるため、スモークの入力にすると必ず不合格になる） |
| **判定** | 採取した各語について `validateNext` が 1 件以上を返すこと。**1 語でも 0 件なら不合格** |
| **採取できなかった場合** | S2 が 1 件も投入していないということであり、**G1 が既に 0 件で不合格にしている** |

**自動採取が「自明に成功するテスト」にならない理由**: 検証するのは「その語が存在すること」ではなく、**「保存された語が本番と同一のクエリ生成経路で見つかること」**である（§4.2.1 の (a′) を採った理由がまさにこれである）。上表の 6 経路はいずれも「保存はされたが見つからない」形の破綻であり、**投入したことが分かっている語で引く**のは検出手段として適切である。

##### 却下した代替案

| 案 | 却下理由 |
| --- | --- |
| **常に G2 を必須にする（平常時も）** | 平常時に「検証語を設定していないだけ」で再構築が止まる。**自動採取があるので技術的には可能だが、平常時は G1（前回比 50%）が既に強い**ため、追加の停止リスクに見合わない |
| **メジャー移行でも「警告を出してスキップ」にする** | 警告はジョブログに出るだけであり、**切替が済んだ後に読まれる**。切替可否のガードとして機能しない |
| **G2 の代わりに「検索エイリアス切替後に検証し、失敗したらロールバック」にする** | 一度公開してからの切戻しになる（R1〜R4）。**S3 の位置で止められるものを、切替後の障害対応に格下げする理由が無い** |

## 5. ロールバック手順と旧世代の保持

### 5.1 保持方法: 保持用エイリアス `{baseIndex}.prev`（MO-4）

| 観点 | 保持用エイリアス（**採用**） | `removeDisableIndices()` を呼ばない（却下） |
| --- | --- | --- |
| 既存の削除判定への影響 | **無し**。判定が「エイリアスを 1 つも持たない」（`Suggester.java:345-353`）なので、付けるだけで対象外になる ※第 3 版までは「fess-suggest のコード変更は不要」と書いていたが、**第 4 版で付与自体を primitive 化したためライブラリ側の変更を伴う**（MO-17）。**削除判定のロジックが無変更である**という点は変わらない | 不要 |
| **孤児インデックスの回収** | **継続する**（§2.4 の中断ケースが自動回収される） | **止まる。中断のたびにインデックスが溜まり続ける** |
| 保持世代数の制御 | `.prev` の付け替え（§3.3）で常に 1 世代 | 制御手段が無い |
| 意図の可読性 | 「`.prev` が付いている＝意図的に残している」が名前から読める | 「消えていない＝忘れられている」と区別できない |

**却下側の決定的な欠点は 2 行目である。** `removeDisableIndices()` は §2.4 の孤児インデックス回収を担う唯一の機構であり、止めると別の運用問題を作る。

### 5.2 保持期間

**世代ベース（常に直前の 1 世代のみ、§3.3）を採る。** 時間ベース（`.prev` の自動解除）は、解除タイミングを判断する常駐機構が新たに要るため採らない。日次バッチ（`0 12 * * *`）の既定では実質「直近 24 時間」が保持期間になる。

延ばす場合は、`.prev` の付け替えを止めるのではなく**追加のエイリアス（例 `{baseIndex}.keep`）を手動で付ける**こと。**逆に、エイリアスを付けない手動退避インデックスは次回ジョブで削除される**（§1.4）。手順書には「退避するなら必ずエイリアスを付ける」と明記すること。

### 5.3 ロールバック手順（R1〜R4）

**適用条件**: `.prev` が旧世代を指しており、その世代が物理削除されていないこと。

| # | 手順 | 実装／操作 | 成功判定 | 失敗時 |
| --- | --- | --- | --- | --- |
| **R1** | **再構築ジョブを停止する** | 管理画面またはジョブ停止 API（§2.2）。実行中の切替と競合させない | プロセスが存在しない | 強制終了後に R2 へ |
| **R2** | **`.prev` の対象を確認する** | **`lifecycle.aliasState().previousIndex`**（`0001` §2.2 / D-23） | `.prev` がちょうど 1 インデックスを指す（`previousIndex` が present かつ `multiplyAssigned` に含まれない） | 0 個なら**ロールバック不可**（§5.4）。2 個以上なら §3.3 の付け替え不変条件が破れており、**ロールバックせず調査へ回す** |
| **R3** | **検索エイリアスを戻す** | **`lifecycle.rollbackToPrevious()`**（`0001` §2.2 / D-21）。内部で `remove(現世代, {baseIndex})` ＋ `add(prev 対象, {baseIndex})` を**1 リクエストに束ねる**。**更新エイリアスには触れない** | 検索エイリアスが旧世代を指す | リクエスト単位で atomic なので中途状態は生じない。**例外時は「未適用」と決めつけない — 判定は `rollbackToPrevious()` 自身が post-condition で行う**（`0001` D-23）。`SuggesterException` なら未適用、`SuggestAliasStateUnknownException` なら判定不能であり、**後者では R4 へ進まず調査へ回す**（§3.2 の S4 と同じ規則） |
| **R4** | **更新エイリアスの扱いを決める** | 下記。**R4-A（既定）／ R4-B の二択であり、その中間は取らない** | — | — |

> **R3 で `switchIndex()` を使ってはならない。** 同メソッドは「更新エイリアスの対象を検索エイリアスに設定する」方向にしか動かない（`Suggester.java:318-324`）。逆方向の遷移は `rollbackToPrevious()` が担う（第 3 版まではこの primitive が無く、fess 側でエイリアス操作を直接行う手順だった — MO-17）。

#### R4: 更新エイリアスの扱い（MO-19・第 4 版で二分）

> **新しい fess-suggest バイナリが動いたまま、更新エイリアスを旧世代へ戻してはならない。**

**理由** [確認]: 新コードは ID を `Base64URL(SHA-256(text))` で生成する（`0002` §4.1）が、旧世代インデックスのドキュメントは旧方式（Base64 生値・445 文字で切り詰め — `util/SuggestUtil.java:66,84-90`）の ID を持つ。**新コードが旧インデックスへ同じ語を書くと、旧 ID のドキュメントと新 ID のドキュメントが併存する。**

```text
旧世代インデックス
  ├─ id = "5p2x5Lqs"（旧方式）        text = "東京"   queryFreq = 12000
  └─ id = "qFj3...43文字"（新方式）   text = "東京"   queryFreq = 1      ← 切戻し後に増える
```

- **`0002` DM-15 / §4.7 が「共存は成立しない」と定めているのはこの状態である。** 本設計が守ろうとしている **text 単位の頻度集約（KEEP-03）が壊れる。**
- 検索結果には**同一 `text` が 2 件現れうる**（`skipDuplicateWords` は語の重複を除くが、`queryFreq` の分裂は戻らない）。
- **mapping も異なる。** 旧世代は `dynamic: true` のため書き込み自体は通り、**エラーにならずに壊れる**。

| 選択肢 | 内容 | 前提 | 増分の扱い |
| --- | --- | --- | --- |
| **R4-A: 検索のみ切戻し（既定）** | 検索エイリアス → 旧世代（R3）。**更新エイリアスは新世代を指したまま**。バイナリは新しいまま | R1〜R3 のみ。**追加作業なし** | 増分書き込みは新世代に入り続け、**検索結果には現れない**。次回 `createNextIndex()` が全件から作り直すため新世代ごと破棄される |
| **R4-B: 完全切戻し** | **fess / fess-suggest のバイナリを旧版へ戻す**。そのうえで更新エイリアスを旧世代へ戻す | **バイナリのロールバックが先**。順序を逆にすると上記の ID 分裂が起きる | 増分は旧世代に入り、検索にも反映される。新世代はエイリアス 0 個となり次回 `removeDisableIndices()` で削除される |

- **R4-A は「緊急縮退モード」である。** サジェストの検索結果を直前の健全な状態へ戻すことだけを目的とし、その間の増分（検索ログ由来の頻度・新規 elevate word / bad word の反映）は**取り込まれない状態が続く**。**長期間この状態で運用しない。**
- **R4-B はリリースのロールバックであり、ロールバック手順ではなくデプロイ手順である。** L2（`0003` §10.1）を巻き戻すことを意味し、**fess 本体側の変更（新 API への切り替え）も同時に戻る**。判断には運用側の合意が要る。
- **「必要なら更新エイリアスも戻す」という第 3 版の書き方を採らない。** バイナリの状態に言及せずに更新エイリアスの切戻しを選択肢として提示すると、**R4-B の前提（バイナリを先に戻す）を欠いた操作を誘導する。**
- **`rollbackToPrevious()` が更新エイリアスに触れないのは、この禁止を API の形で表すためである**（`0001` §2.2.1）。R4-B の更新エイリアス操作は、**旧バイナリに戻したうえで行う手動のエイリアス操作**である（旧バイナリには当該 primitive が無い）。

### 5.4 エイリアスを戻すだけでは済まない範囲

> **新世代に書いた内容を旧世代へ戻す経路は存在しない。**

| 対象 | 切戻し後の状態 |
| --- | --- |
| **切替後に追加された elevate word / bad word** | **新世代にのみ存在する**（反映先は更新エイリアス — `(fess) helper/SuggestHelper.java:482,520`）。ただし**設定インデックス（`fess_suggest-badword` / `-elevateword`）には残る**ため、次回再構築の S2 で復元される |
| **切替後に蓄積された検索ログ由来の頻度** | **失われる。復元経路は無い。** R4-A では切戻し後の増分も検索に反映されないため、**縮退している間の蓄積も同様に失われる**。**これは「問題にならない」のではなく、緊急ロールバック時に許容する損失である**（第 4 版で表現を是正） |
| `purge()` による削除 | **切替に失敗した実行では走らない**（`(fess) exec/SuggestCreator.java:236-239`。§2.5） |
| 設定インデックス（`fess_suggest*`） | **世代を持たない。** ロールバックの影響を受けず常に最新 |

**ロールバックは「検索結果を直前の健全な状態に戻す」操作であり、データの完全な巻き戻しではない。** 手順書にこの限界を明記すること。

### 5.5 切戻し時にも否定形フィルタが必須である理由

> **`0002` §6.2（DM-14）の `mustNot(termQuery("excluded", true))` は切戻し中も含めて常に適用されていなければならない。`must(termQuery("excluded", false))` は禁止である。**

**移行手順の側から見た理由**: 切戻し先の旧世代ドキュメントは **`excluded` フィールドを持たない**（MIG-13 適用前に作られたため）。肯定形フィルタは「フィールドが存在しないドキュメント」に一件も一致しないため、**切り戻した瞬間にサジェスト結果が全滅する**。

**これはロールバックが最も必要な局面で発動する。** 新世代に問題があって切り戻したのに切戻し先で 0 件になる、という二重障害になる。**否定形フィルタは、切替が成功している間はコードの正しさとしてしか観測されず、切戻し時に初めて実害の有無が分かる**性質の規則である。だからこそ手順書とテスト（§11.2 T-R3）の両方で押さえる。

### 6.2 移行手順の側の帰結

| # | 帰結 | 理由 |
| --- | --- | --- |
| 1 | **経路は 1 本しかない。** 「新スキーマ・新 ID で全件再投入 → 検証 → エイリアス切替」以外の形を取らない | 同じ語が新旧で別 ID になるため、旧インデックスに書き足しながらの移行が成立しない（`0002` DM-15） |
| 2 | **部分移行・段階適用の選択肢は存在しない。** 「まず ID だけ」「まず mapping だけ」はいずれも不可 | 4 変更のいずれも既存ドキュメントを読み替えられない。1 つでも先行させればその時点で全件再構築が要り、残りを別の再構築に回す意味が無い |
| 3 | **ロールバックはエイリアスを戻すのみ**（§5.3）。新世代のデータを旧スキーマへ変換して戻す経路は設けない | ID もフィールド構成も異なるため、変換は事実上の再構築になる |
| 4 | **切替前検証で「旧世代との件数一致」を条件にできない**（§4.1） | 衝突解消で増え、語数上限で減る |

### 6.3 前提条件: OpenSearch 2.16 以上（`0002` §9 の 2 の消化）

`0002` §2.2 が採用した `dynamic: "strict_allow_templates"` は **OpenSearch 2.16 で追加された OpenSearch 独自値**であり Elasticsearch には存在しない。

> **再構築の事前条件として、対象クラスタが OpenSearch 2.16 以上であることを確認する**（`GET /` の `version.number`）。
>
> 満たさない場合は **S1（`createNextIndex()`）の `prepareCreate` が mapping を拒否して失敗する**。**取り込みが進んでから失敗するのではなく S1 で失敗するため、旧世代には影響が出ない**（§2.4 の 1 行目）。事前条件違反の検知としては好都合である。
>
> 影響を受けるのは AWS OpenSearch Service で 2.16 未満を固定運用している環境であり、**fess 本体の動作要件そのものが上がる**（§13 の 6）。

## 7. refresh 戦略（MIG-16）

### 7.1 3 層に分ける（MO-7）

**MIG-16 を `index/operations/ContentIndexingOperations.java:345` の 1 箇所の問題として扱わない。** refresh は 3 つの独立した層で発行されており、再構築 1 回あたりのクラスタ影響はむしろ (b) のほうが大きい可能性がある [推測]。

| 層 | 現状 | 本設計での扱い |
| --- | --- | --- |
| **(a) 取り込みバッチごと** | `index/operations/ContentIndexingOperations.java:345` の**1 箇所**。`indexFromDocument` のループ（`:331-350`）で `docs.size() >= docPerReq` または末尾に達するたび**無条件に**発行する。既定 `docPerReq=2`（`(fess res) fess_config.properties:1441`）＝**2 ドキュメントごとに 1 回** | **廃止する** ＋ 再構築中は `refresh_interval = -1`（§7.3） |
| **(b) `Suggester.refresh()` のインデックス無指定** | `Suggester.java:179` が `prepareRefresh()` を**インデックス名を渡さずに**呼ぶ ＝ **クラスタ全インデックスの refresh** | **suggest インデックス限定に是正する**（§7.2）。**MIG-16 に含める** |
| **(c) 管理操作ごと** | `(fess) helper/SuggestHelper.java:538-543` の `refresh()` が **12 箇所**（`:258, :295, :372, :387, :402, :423, :440, :451, :486, :511, :522, :532`）から呼ばれる | **`RefreshPolicy`（`0001` §6.3）で制御する**（§7.5） |

### 7.2 (b) が最も影響が大きい理由 [確認]

**(b) と (c) は掛け合わさる。** `Suggester.refresh()` がインデックス無指定であるため、(c) の 12 箇所はすべて**クラスタ全インデックス（`fess.crawler.*` や `fess_log.*` を含む）の refresh** を発行する。

> `(fess) helper/SuggestHelper.java:411-424`（`storeAllElevateWords`）はループ内で `addElevateWord` を呼び、その各回が `:486` で `refresh()` する。**elevate word が N 語なら N+1 回のクラスタ全体 refresh** が発行され、これが `(fess) exec/SuggestCreator.java:258` から**再構築のたびに実行される**。`storeAllBadWords`（`:501-512` → `:509` → `:522`）も同じ構造である。

**是正は `0001` §2.2 で既に決まっている**（新 `SuggestIndexLifecycle.refresh()` は Javadoc で「suggest インデックスのみ」と規定）。**本書はこれを MIG-16 の構成要素 (b) として明示的にスコープに入れる**（`0001` §10 申し送り 5 の消化）。**既存資料はこの層を捉えていない** [確認]（付録 A の 2）。

### 7.3 再構築時の `refresh_interval = -1`（MO-8 ／ 申し送り 3 の消化）

> **定石**: 取り込み中は `refresh_interval = -1`（自動 refresh 停止）とし、**完了後に既定値へ戻してから 1 回だけ明示 refresh する。**

| 段階 | 実現 |
| --- | --- |
| **停止側** | **S1 で次世代インデックスを `refresh_interval: -1` として作成する。** `0001` §6.2 の `IndexSchema.refreshInterval` に `RefreshInterval.disabled()` を渡し、`createNextIndex(IndexSchema)`（`0001` §2.2）が受け取る |
| **復帰側** | **S3 の直前に `lifecycle.updateRefreshInterval(generation, RefreshInterval.every(既定値))`**（`0001` §2.2 / D-18）**で既定値（`(res) suggest_indices/suggest.json:3` の `10s`）へ戻し、明示 refresh を 1 回発行する** |

> **第 3 版での訂正**: 初版・第 2 版は「停止側は既存の受け口で足り、**新規 API を要しない**」「復帰側だけが新規実装である」としていたが、**どちらも成立していなかった** [確認]。`0001` 第 2 版の `IndexSchema.refreshInterval` は `Optional<Duration>` であり、**`-1`（自動 refresh 無効）を表現できない**（`Duration.ofSeconds(-1)` が「無効」を意味するという約束が型に無い）。また復帰側の `_settings` 更新メソッドは `SuggestIndexLifecycle` にも `SuggestStore` にも存在せず、実装先が特定されていなかった。ステップ 7 の通し整合レビューでこれを検出し、**`0001` 第 3 版が `RefreshInterval`（`Every` / `Disabled` の sealed interface）と `updateRefreshInterval` を新設した**（D-18）。**新規に要るのは停止側の型と復帰側のメソッドの 2 つである。**

> **`refresh_interval` を動的に変更する経路は現状まったく存在しない** [確認]。`refresh_interval` という文字列は fess-suggest の `src` 配下・fess の `src/main/java` 配下の **Java コードに 1 件も無く**（JSON リソースのみ）、`prepareUpdateSettings` / `UpdateSettingsRequest` の使用箇所も**両モジュールの main で 0 件**である。

**復帰を S3 の直前に置く理由**: S3 の検証（G1 の件数・G2 のスモーク）は refresh 済みでなければ正しい結果を返さない。

**失敗時の分岐**: 復帰に失敗したら **S4 を実行しない**。`-1` のまま検索エイリアスに昇格させると、**明示 refresh されるまで更新が見えない**インデックスが公開される。取り込み中に中断した場合も次世代は `-1` のまま残るが、次回再構築で作り直されるため実害は無い。

### 7.5 `RefreshPolicy` との使い分け（`0001` §10 申し送り 8 の消化）

| 層 | 制御手段 | 既定 |
| --- | --- | --- |

**`PER_BATCH` に相当する値は存在しない**（`0001` §6.3）。C-12 が廃止すると決めた挙動を選択肢として残さないためである。**現行 `ContentIndexingOperations.java:345` の同期 refresh がこの廃止の対象そのものである。** 再構築時の組み合わせは `refreshInterval = -1`（S1）＋ `refreshPolicy = NONE`（S2）＋ 復帰と明示 refresh（S3 直前）。

### 7.6 バッチ件数と CPU 負荷制御のトレードオフ

**CPU 負荷制御は `waitController` の責務であり、バッチ件数に負荷制御の意味を持たせない**（C-12）。この主張は**コード上正しい** [確認] — インタフェースは `index/SuggestIndexer.java:367-370`、実行位置は `index/operations/ContentIndexingOperations.java:348`（refresh の直後、**バッチごと**）、実体は `(fess) helper/SuggestHelper.java:291-293` の `calibrateCpuLoad()` ＋ `sleep(interval)`、CPU 判定は `(fess) helper/SystemHelper.java:999-1001,1009-` で閾値 `adaptive.load.control=50`（`(fess res) fess_config.properties:207`）、`timeoutInMillis=0` のため**閾値を下回るまで無期限に待機**する（`:1022-`）。

> **ただしバッチ拡大は CPU 制御の粒度を落とす** [推測]。`waitController` は**バッチごとに 1 回**呼ばれる（`:348`）ため、既定 `docPerReq=2` を 500 に上げると `calibrateCpuLoad()` の呼び出し頻度が **250 分の 1** になる。**バッチ件数の引き上げと CPU 制御粒度はトレードオフである。** 両立させるには `waitController` の呼び出し位置を bulk 単位から切り離す（件数ではなく経過時間で呼ぶ等）必要があるが、**本設計では位置の変更を決定せず後続の実測タスクへ引き渡す**（§13 の 5）。

### 7.7 トレードオフ: 取り込み途中の逐次可視性

> **refresh を減らすと、取り込み途中の内容が検索から見えなくなる。**

**再構築（S2）では実害が無い。** 書き込み先は更新エイリアスであり検索は旧世代を見ているため、利用者から見える結果は変わらない。**実害があるのは (c) の管理操作**（elevate word を追加した直後にサジェストで確認する操作）であり、§7.5 で個別操作の既定を `ON_COMPLETION` としているのはこのためである。

**マージの正しさは refresh に依存しない** [確認]。`0002` §4.5 のとおり既存ドキュメントの取得は ID 指定 GET（既定 realtime ＝ translog 読み）であり、**refresh を止めても頻度集約は壊れない**。この非依存性が MIG-16 を独立に進められる根拠である。

### 7.8 スコープ外: 最適値と読み出し側

- **具体的な最適値は決めない**（C-04 / C-12）。`docPerReq` の既定値、`refresh_interval` の値、`waitController` の呼び出し頻度はいずれも実測依存である（§13 の 5）。
- **`ESSourceReader` の scroll size は本設計のスコープ外とする。** 既定は `suggest.source.reader.scroll.size=1`（`(fess res) fess_config.properties:1449`。実装既定も `index/contents/document/ESSourceReader.java:99` で 1）であり、**元ドキュメントを 1 件ずつ scroll している**。

> **ただしこれは MIG-16 の効果を打ち消しうる** [推測]。**refresh を減らしても、読み出しが 1 件ずつの scroll のままでは再構築時間は改善しない。** 書き込み側だけを最適化しても律速が読み出し側にあれば所要時間は変わらない。**MIG-16 の効果測定を行う後続タスクは、必ず `scroll.size` を同時に変数として扱うこと**（§13 の 5）。

## 9. `knn_vector` を後から追加する手順（MIG-24 の予約 / P5）

**`0002` §2.1 の To-Be mapping に `embedding` は含めない**（P5）。本節は「後から載る」ことを手順として示す予約であり、**実施は Phase 4 である**。**現在の実装にベクトル関連の記述は一切存在しない** [確認]（`knn_vector` / `index.knn` / `knn` の検索は fess-suggest の `src/main` 配下および fess の `src/main/java` / `src/main/resources` 全体で **0 件**）。

### 9.1 なぜ再構築が必要か

| 変更 | 既存インデックスへの適用 |
| --- | --- |
| `embedding` フィールドの追加 | mapping へのフィールド追加自体は動的に可能（§7.4） |
| **`index.knn: true`** | **静的設定であり既存インデックスに設定できない** |
| 既存ドキュメントへのベクトル付与 | 全件の再取り込みが必要（推論の実行を伴う） |

> **したがって `knn_vector` の追加は §3 の二重エイリアス再構築を経由する。通常の再構築（S1〜S5）と同じ手順でよく、専用の手順を持たない。**

### 9.2 mapping への明示が必須である理由（MO-11）

> **`0002` §2.2 の `dynamic: "strict_allow_templates"` により、`embedding` は `properties` に明示するか `dynamic_templates` に載せなければ、書き込みが `StrictDynamicMappingException` で失敗する。**

**既存の `dynamic_templates` はこれをカバーしない** [確認]。`0002` §2.1 のテンプレートは `match: "reading_*"` → `keyword` の 1 本のみで `embedding` は名前が合致せず、現行 `(res) suggest_indices/suggest/mappings-default.json:2-12` の `match: "*"` テンプレートも `match_mapping_type: "string"` → `keyword` であり **`knn_vector` を生成できない**。したがって追加は `properties` への明示（`"embedding": { "type": "knn_vector", "dimension": ... }`）となる。

**`0002` §3.3 の `index.mapping.total_fields.limit: 100` への影響**: 固定フィールドが 11 → 12 になる。同 §3.4 の連動制約（固定 ＋ 語数上限 50 ＋ 余裕 ≤ 100）は 62 ≤ 100 で維持されるため **limit の見直しは不要**である。

### 9.3 `dimension` は予約に留める

`dimension` は `knn_vector` の必須パラメータであり埋め込みモデルによって決まる。モデルと推論基盤の選定はスコープ外である（`0000` §2.2）ため**実値を決めない**。

> **予約の内容**: 「`embedding` を `knn_vector` として `properties` に追加し、`index.knn: true` を settings に加え、二重エイリアス再構築で適用する」という**手順の形**までを確定する。`dimension`・`space_type`・エンジン（`nmslib` / `faiss` / `lucene`）・スコアへの合成方法はモデル選定後に決める。

**スコアへの合成は `0001` §3.2 の `ScoringContext` / `ScoringPlan` が受け皿である**（C-11）。ベクトル類似度を加点要素として受け取れる形が既にシグネチャで保証されているため、**本節が扱うのはインデックス側だけでよい。**

### 12.1 除外語の物理削除（MO-23・第 7 版）

**`0002` DM-21 により、bad word に該当する語は `excluded = true` のドキュメントとしてインデックスに残り続ける。全件再構築でも消えない。** 掃除が必要になった場合の手順を定める。

| 項目 | 内容 |
| --- | --- |
| **実行手段** | `SuggestIngestService.deleteByCondition(condition)` に `mustMatchAny("excluded", ["true"])` を持つ `QueryCondition` を渡す（`0001` §2.4 / §3.6）。**専用 API は無い** |
| **実行主体** | **運用者が明示的に実行する。** ライブラリも `SuggestCreator` も自動では行わない |
| **可逆性** | **不可逆である。** 削除された語は `deleteBadWord` で戻らない。**文書由来の語は次回の全件再構築で復活するが、検索ログ由来の頻度履歴は失われる** |
| **実行前の確認** | `previewBadWordImpact` ではなく、**削除条件そのものの件数**を `deleteByCondition` の前に確認すること。`previewBadWordImpact` は「1 つの bad word が支配する語の数」であり（`0002` §6.2）、`excluded = true` の総数とは別物である |
| **実行タイミング** | **再構築中に行わない。** S2 の取り込みと競合し、どちらが後に書いたかで結果が変わる。S5 の後、または再構築を止めている時間帯に行う |
| **実行後** | 削除した語が再び流入すると、その時点の bad word 集合に照らして再び `excluded = true` で保存される（`0002` §5.3）。**掃除は状態を作るのではなく、その時点のドキュメントを消すだけである** |

> **これを「定期的に自動実行する」設定を設けない。** 自動化すると DM-21 が回復した可逆性が、実行間隔に依存する形で再び失われる。**「捨てる」判断は毎回運用者が下すべきものであり、既定で捨てる設計に戻してはならない。**

### 12.2 K-2（`roles` への `_guest_` 混入）からの回復（第 7 版）

**`0002` K-2 / §8.1 のとおり、`roles` は集合和であり緩む方向にしか動かない。** 混入してしまった場合の回復手段を運用の側から明記する。

| # | 手順 |
| --- | --- |
| 1 | **混入源を止める。** `roles` を空で返している供給元（`SuggestSource` 実装・`roles` 未指定の elevate word 登録）を特定して修正する。**これを先にしないと以降が無意味である** |
| 2 | **全件再構築を実行する**（§3.2 の S0〜S5）。**新世代は空のインデックスから作られるため、`roles` の集合和もそこからやり直しになる。これが唯一の回復手段である** |
| 3 | 再構築後、混入していた語の `roles` に `_guest_` が含まれないことを確認する |
