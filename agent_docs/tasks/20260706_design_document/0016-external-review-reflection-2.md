### 2.1 指摘 1（Blocker）— alias の post-condition 判定に必要な公開面が閉じていない

#### 検証 [確認]

**指摘は成立する。** 突き合わせたのは次の 3 箇所である。

| # | 箇所 | 記述 |
| --- | --- | --- |
| 1 | `docs/0001` §2.2.1 の末尾（第 4 版） | 「失敗を検知したら現在のエイリアス状態を再取得し、post-condition で次の行動を決める」 |
| 2 | 同 §2.2.1 の直後（第 4 版） | 「再取得に使う読み取り面は `currentIndexName()` である。**保持世代・更新エイリアスの解決結果も引けるようにする必要があるが、`currentIndexName()` は検索エイリアスしか返さない。** これは §10 の申し送り 11 とし、実装タスクで決める」 |
| 3 | `docs/0003` §3.2 の S4（第 4 版） | 失敗時の手順 1 が「`GET /_cat/aliases/{baseIndex}*` で現在のエイリアス状態を再取得する」 |

**1 が要求する操作を 2 が「提供できない」と認めたうえで実装タスクへ送り、3 が公開契約を経由しない生の API 呼び出しで埋めている。** 手順としては書けているが、**設計として閉じていない。**

**さらに `0003` §3.2 の記述には独立した問題がある** [確認]。`{baseIndex}` は `(fess res) fess_config.properties:591` の `index.document.suggest.index=fess` から組み立てられない。実値は `fess.suggest` であり（`settings/SuggestSettings.java:486`）、しかも**初回 `init()` 時に設定インデックスへ永続化される**ため設定値を後から変えても変わらない（`0004-corrections.md` の G-1、`0003` §3.1 の注記）。**fess 側にエイリアス名を組み立てさせる手順は、この 1 点だけで壊れうる。**

#### 判断: レビューの推奨案を採る

レビューは「fess 側に `AliasState` を読ませるより、`SuggestIndexLifecycle` 内で『タイムアウト → 状態再取得 → post-condition 成立なら正常完了』まで吸収する。正常完了の意味を『alias API が 200 を返した』ではなく『目的の状態になっている』にする。判定不能だけ typed exception。運用確認用に `aliasState()` を追加するのはあり」としている。

**3 案を比較した。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(A) 判定をライブラリが吸収 ＋ `aliasState()` を運用用に公開** | レビューの推奨案 | **採用** |
| (B) `aliasState()` だけ追加し、判定は呼び出し元 | 申し送り 11 の 2 択のうち「`AliasState` を足す」側 | 却下 |
| (C) `currentIndexName()` を一般化（引数でエイリアス種別を指定） | 同 2 択のうちもう一方 | 却下 |

**(B) を却下する理由**: 判定を呼び出し元に置くと、**失敗時分岐の正しさが呼び出し元ごとの規律に依存する**。`0003` §3.2 が定める「二重適用（`.prev` が 2 世代前を指す）と未適用（保持されない切替）を取り違えない」という不変条件は、**遷移を発行した主体と同じ層でしか担保できない**。呼び出し元は現時点で `SuggestCreator` 1 箇所だが、公開契約は「1 箇所しか呼ばない」を前提にできない。

**(C) を却下する理由**: 3 エイリアスを 3 回引くと、**その間に状態が変わりうる**。post-condition の判定は 3 者の関係（「検索と更新が同一を指し、かつ `.prev` が切替前を指す」）で決まるため、**1 回の取得でスナップショットを得る形でなければならない**。`AliasState` を record にしたのはこのためである。

#### MO-1 との関係の整理

**この判断は `0003` MO-1（fess-suggest に再構築を束ねる高水準 API を新設しない）に抵触しないか**を確認した。

- MO-1 と `0001` §2.2 の冒頭が fess 側に残すと定めているのは、**再構築の制御フロー**である — 「いつ切り替えるか」「切り替えてよいか」（G1 / G2 / G3 のガード）。
- **今回ライブラリへ移したのは「この alias 遷移が適用されたか」の判定**であり、**遷移メソッド自身の効果の確認**である。
- 両者は層が違う。`0003` §4.2.1 が `validateNext` について既に同じ整理をしている（「ライブラリは合否を決めない。向き先だけを内部で差し替える」）。

**したがって MO-1 は維持したまま D-23 を置ける。** `0003` §4.3 の根拠 2 にこの整理を追記した。

### 2.3 指摘 3（High）— bad word の重複マッチで解除が壊れる

#### 検証 [確認]

**指摘は成立する。** 第 4 版の記述:

- `docs/0001` §2.3: 「`deleteBadWord` — bad word を取り消し、**該当語の `excluded` を false へ戻す**」
- 同 §3.5: 「`matchCondition(normalizedBadWord)` — 指定 bad word に該当する既存語を選び出す条件。**`excluded` の付与・解除とドライランが共有する**」
- 同 §3.7: `updateExcluded(QueryCondition condition, boolean excluded)` — **一律 true / false 更新**
- 同 §3.5 の D-6: 判定意味論は**正規化後テキストの部分一致**

**レビューの例（`foo` / `bar` / `foobar`）はそのまま成立する。** `foobar` は `foo` にも `bar` にも該当するため、`foo` だけを削除して `matchCondition("foo")` の対象を一律 `excluded = false` にすると、**まだ `bar` に該当している `foobar` まで復活する**。

**付与側は問題にならない。** `excluded = true` の設定は単調であり、既に `true` の語へ再度 `true` を書いても意味が変わらない。**非対称なのは解除だけである。**

#### 判断: 単一パスの `releaseCondition` を採る

レビューは「削除後の bad word 集合に照らして、もうどの bad word にも該当しない語だけ解除する必要がある」としている。**そのとおりであり、実現方法を 3 案比較した。**

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **(A) `releaseCondition` ＋ `mustNotContain`** | `mustContain(text, removed)` かつ `mustNotContain(text, b)` for all b ∈ 残存集合。**1 回の update-by-query** | **採用** |
| (B) 解除 → 残存 bad word で再付与の 2 パス | 実装は単純だが、**2 パスの間に除外されるべき語が検索に現れる窓**ができる | 却下 |
| (C) `excluded` を「該当する bad word のリスト」に変更 | 正確だが、`0002` DM-14 の除外フィルタ（`mustNot(term(excluded, true))`）が `exists` 判定に変わり、**旧世代ドキュメント共存の前提が崩れる**。データモデルの変更コストが解除の正確さに見合わない | 却下 |

**(A) には `QueryCondition` への述語追加が要る。** 第 4 版の 4 種には否定形の部分一致が無かったためである。`mustNotMatchAny` と同じ向き（要素間が AND ＝ 各否定の連言）で `mustNotContain` を定義した。**`SubstringPredicate` を再利用するため、翻訳規則もエスケープの必須化（F-09 の解消）もそのまま適用される。**

**順序制約が生じる。** `releaseCondition(removed)` は**削除後の集合**を見る必要があるため、`policy.remove(word)` を**先に**呼ばなければならない。逆にすると `removed` 自身が `mustNotContain` に入り、条件が充足不能になって 1 件も解除されない。**この順序制約を `releaseCondition` の Javadoc に書いた。**

**`deleteAllBadWords` は `releaseCondition` を使わない。** 集合が空になるため、`excluded = true` の全ドキュメントを一律 `false` に戻す。これは fess 側の全件同期（`storeAllBadWords`）が「全削除 → 全登録」の形を取ることに対応する。

### 2.4 指摘 4（High）— スレッドセーフ契約とロストアップデートの衝突

#### 検証 [確認]

**指摘は成立する。** 衝突しているのは次の 2 箇所である。

| 箇所 | 記述 |
| --- | --- |
| `docs/0001` §4.4（第 4 版） | 「`api` 4 IF と `spi` 7 IF の実装は**スレッドセーフ**でなければならない（複数スレッドからの同時呼び出しを許す）」 |
| `docs/0002` §4.6 / §8 の K-1 | 「multiGet → merge → index に `setIfSeqNo` / `setIfPrimaryTerm` が無い。**異なる呼び出し元が同一 ID を含むバッチを同時に書くとロストアップデートが起きる**」 |

**レビューの整理が正確である** — 「Java オブジェクトとして壊れない」という意味で thread-safe と呼べなくはないが、**このライブラリでは `queryFreq` / `docFreq` の集約が本質**であるため、利用者が「並行して `index()` してよい」と読めば普通は頻度も失われないと期待する。

#### 判断: 契約を限定する。F-10 の解消は前倒ししない

レビューは 2 つの選択肢を挙げている — 「契約を明示まで限定する」か「MIG-15 第 2 段を前倒しする」か。**前者を採る。**

**前倒ししない理由は 2 つあり、いずれも本設計書の外にある。**

1. **`scripted_upsert` は Painless スクリプトの仕様確定を要し、`0000` §2.2 が明示的にスコープ外としている**（C-03 / E-03）。合成規則の正が Java 側（`SuggestItemMergePolicy`）にある状態で Painless 版を先に載せると、**同じ規則が 2 言語で二重管理される期間**が生じる。これは MIG-01（マージ規則の単一化）が解消しようとしている状態そのものである。
2. **`bulkUpsert` は差し替え点として設計されており**（§3.7 の C-03）、第 2 段は**公開契約を変えずに載る**。前倒しの利得は「今回のリリースで直る」ことだけで、**API 設計上の後戻りは発生しない**。

**したがって本版で行うのは契約の是正だけである。** レビューが提示した文言（「concurrent invocation safe。ただし同一 text への write は atomic / linearizable ではなく、頻度更新を失う可能性がある」）をほぼそのまま採った。

**あわせて「同一呼び出しの中では競合しない」ことを契約に書いた。** `parallel` フラグはパース処理のみを並列化し書き込みは逐次である（`0004-corrections.md` の E-20）。**これを書かないと、利用者が `parallel` を危険なフラグと誤解する。**

### 2.5 指摘 5（High 寄り）— `SuggestSource` の順序非依存は成立しない

#### 検証 [確認]

**指摘は成立する。** 第 4 版 `docs/0001` §3.9.3 は「同一 `text` の候補が複数ソースから来た場合、マージ規則が合成するため**結果は順序に依存しない**（`queryFreq` / `docFreq` は加算、集合は和、**`userBoost` は指定ありが勝つ**）」としていた。

しかし `docs/0002` §5.3 の合成規則は「**present の incoming のみが上書き。empty なら existing を保持**」である。**present の incoming が 2 つ来ると後勝ちになる** — boost 2.0 の A と boost 5.0 の B では、A → B なら 5.0、B → A なら 2.0。**交換則を満たさない。**

**レビューの「現状では elevate word だけが `userBoost` を指定する想定なので通常運用では偶然問題になりにくい。ただし `SuggestSource` を外部拡張点として公開するなら話が変わる」という整理が正確である。**

#### 判断: `SuggestSource` に `userBoost` を指定させない

レビューは 3 案を挙げている — (a) `SuggestSource` は boost 指定禁止、(b) 複数指定時の競合規則を定義、(c) Source 順序は意味を持つ。**(a) を採る。**

**(b) を却下する理由**: max / min / 平均のいずれを選んでも別の破綻を生む。**`0002` §5.3 の却下表がこれを検討済みである** — max を採ると「管理者が boost を 5.0 → 2.0 に引き下げられない」。**`userBoost` は「集約する値」ではなく「管理者の最新の指示」であり、複数の供給元が同時に指示を出す状態そのものを設計から排除するのが正しい。**

**(c) を却下する理由**: 順序に意味を持たせると、**C-11 が「織り込まない」と決めたソース別重み付け（MIG-19 / MIG-20）を順序という形で半端に導入する**ことになる。(a) の禁止は拡張点を弱めるのではなく、**拡張点の役割を「候補の供給」に限定し続ける**ための制約である。

#### この制約は型では守れない [確認]

**`SuggestCandidate.elevate(...)` を非 public にできない。** 呼び出し元 `entity/ElevateWord` は `org.codelibs.fess.suggest.entity` にあり、`SuggestCandidate` は `org.codelibs.fess.suggest.api` にある（`0001` §1 のパッケージ規約）。**パッケージが違うため package-private にできない。**

**したがってこれは契約で守る制約であり、D-17（`excluded` をフィールドごと持たない）とは性質が異なる。** この違いを `0001` §2.6.2 の表に明記し、**回帰テスト T-20 を `0002` §7.2 に置いた**（既定 2 ソースおよび任意の実装が返す候補の `userBoost` がすべて `empty` であること）。

#### 反映

| 文書 | 変更 |
| --- | --- |
| `docs/0001` | **D-27** を新設。§3.9.3 を「順序と可換性」へ改題し、**`userBoost` だけが可換でない**ことと 4 項目の契約・却下案を記載。§3.1 の `produce` Javadoc と §2.6.2 の表に制約を追加 |
| `docs/0002` | **DM-19** を新設（§5.3 の `userBoost` 節）。§7.2 に **T-20** を追加 |

### 2.6 指摘 6（非 Blocker）— Strangler Fig の互換性の範囲

#### 検証 [確認]

**指摘は成立する。** `docs/0001` §8.3 は「旧 `Suggester` / `SuggestIndexer` は**クラスとして残し、public シグネチャを 1 つも変えない**」としている。一方 D-20 により `entity.SuggestItem` は `final class` ＋ private コンストラクタになる。

**シグネチャとしては維持されるが、型が構築できなくなる。** `SuggestIndexer.index(SuggestItem)` は残るものの、**fess-suggest の外部から引数を作る手段が無い**。配列 getter（`String[][] getReadings()` 等）も `List` 系へ変わる。

#### 判断: 破壊を受容し、範囲を明文化する

**レビューは「メジャーアップデートなので壊して構わない、という判断も十分ある。ただ、それなら C-01 の『旧 public signature 維持』は『`Suggester` / `SuggestIndexer` と fess 本体の移行だけを対象にした互換性』と明記すると誤読がなくなる」としている。これをそのまま採る。**

**破壊を受容する理由**:

1. **本設計は既に無停止のドロップイン置換ではない。** `0002` §4.7 が全件再構築を必須としている時点で、外部利用者もデータ移行を伴う更新を要求される。
2. **D-19 / D-20 の型分離は `SuggestItem` の生成を閉じることで成立している。** public コンストラクタを残すと `0001` §2.6.1 の 3（生成 API の分離では型として守れない）に逆戻りする。

**新規の決定ではなく、既にコミット済みの決定（D-20）の帰結を明文化する作業である。**

## 5. V7（文書間整合）の検査手順に対する申し送り

**2 回連続で、外部レビューの Blocker が V7 の取りこぼしであった。**

| 回 | V7 が拾えなかった指摘 |
| --- | --- |
| 第 1 回 | 1（型の 4 役兼務）・3（部分失敗とガードの接続）・5（alias 操作の所在）・10（メソッド数） |
| 第 2 回 | 1（alias state）・2（`SuggestSource` の実行点） |

**両回とも同じ型である** — **「一方の文書が要求する操作を、他方の公開面が提供していない」**。V7 の従来の検査は「節どうしの参照が整合しているか」（`0001` §2.2 を参照している箇所が実在するか等）であり、**参照先の節が存在すれば pass になる**。第 2 回の指摘 1 では、参照先（`0001` §2.2.1）は実在し、しかも「読み取り面が足りない」と**自ら書いていた**。**参照整合だけでは検出できない。**

> **後続タスクへの申し送り**: V7 の検査に **「手順書が要求する操作 → 公開契約に存在するか」の逆引き**を加えること。具体的には、`0003` の各手順ステップ（S0〜S5 / R1〜R4）と `0002` の各規則について、**それを実行するために呼ぶメソッドを `0001` の公開面から名指しできるか**を 1 件ずつ確認する。名指しできない箇所（生の API 呼び出し・「実装タスクで決める」）が残っていれば **fail** とする。
>
> **`[要確認]` の不在（V3）は、この検出には効かない。** 第 2 回の指摘 1 は `[要確認]` ではなく**申し送り**として書かれており、V3 は pass のままだった。**「決めたうえで引き渡す事項」と「決めないと手順が成立しない事項」を申し送りの中で区別する必要がある。**
