### 2.1 指摘 1（Blocker）— `SuggestItem` の 3 役兼務

#### 検証 [確認]

矛盾は実在した。突き合わせたのは次の 3 箇所である。

| 文書 | 記述 |
| --- | --- |
| `docs/0001` 第 3 版 §2.5 | 「`SuggestItem` は入力 DTO であると同時に、ストアからの読み出し結果でありマージ結果でもある」 |
| 同 §5.1 | 「実装は `_source` の取得対象を絞るため、**選択しないフィールドはストアから読み出されない**」／ 既定は `Set.of(TEXT, TAGS)` |
| `docs/0002` §5.2 / §2.3(b) | INV-1（`readings` の第 1 次元長 ＝ W）を **`entity/SuggestItem` のコンストラクタで強制する** |

**既定の検索では `readings` を読み出さないのに、`SuggestItem` は `readings.length == W` を満たさなければ構築できない。** レビューが挙げた四択（`null` / `[]` / ダミー / 実値を読む）はいずれも成立しない。

**副次的な破綻も確認した**: `SuggestIngestService.index(List<SuggestItem>)` の引数型が検索結果と同一であり、部分的にしか埋まっていない `SuggestItem` を取り込み API へ渡せた。

#### 判断の経緯

初回はレビュー案（2 型 `SuggestItem` / `SuggestHit`）と 3 型（`SuggestInput` / `StoredSuggestItem` / `SuggestHit`）をユーザーに諮った。**ユーザーから指摘の精密化を受け、最終的に次の 3 型構成を採った。**

```text
SuggestCandidate ──merge──┐
                          ↓
                    SuggestItem        ← Store GET / PUT はこの 1 型
                   （完全な状態）
                          │
                          ↓ search / projection
                     SuggestHit
```

**採否の分岐点は「Put と Get を分けるかどうか」だった。**

| 案 | 判定 |
| --- | --- |
| 2 型（`SuggestItem` / `SuggestHit`） | **不十分。** projection の問題は解けるが、`SuggestItem` に `userBoostSpecified`（＝更新指示）が残る。ストアから読み出した現在状態に `userBoostSpecified()` と問うても意味が定まらない |
| 3 型（`SuggestInput` / `StoredSuggestItem` / `SuggestHit`） | **過剰。** Put / Get を別型にすると `store.get(id)` → 合成 → `store.put(item)` が同一型で書けなくなる。**永続化の Put / Get を同じ entity で扱えること自体は良い性質であり、捨てる理由が無い** |
| **3 型（`SuggestCandidate` / `SuggestItem` / `SuggestHit`）** | **採用。** 境界を「取り込み意思」「永続状態」「検索 projection」の間に置く。Put / Get は `SuggestItem` のまま |

**名前は `SuggestInput` ではなく `SuggestCandidate` を採った。** 実態が「文書・検索語・elevate word から生成された、サジェスト辞書へ集約される候補」であり、`Stream<SuggestCandidate> produce(...)`（MIG-19/20 で同義語・トレンドのソースが増えても自然）と読める。

### 2.2 指摘 2（Blocker）— `public record` では生成制約を型で強制できない

#### 検証 [確認]

**両方とも成立していた。**

1. `public record SuggestItem(... boolean userBoostSpecified, boolean excluded ...)` の canonical constructor は public である。第 3 版の D-16 / D-17 が課した「`withUserBoost` 以外から `true` にしない」「取り込み経路から `excluded=true` に到達できない」は**文章上の規約にとどまっていた**。
2. `record` が不変にするのは参照だけであり、`String[][] readings` / `String[] roles` / `Kind[] kinds` の中身は書き換え可能である。**`docs/0001` §4.4 の「DTO はすべて不変 record であり共有してよい」という契約が成立していなかった。** `ScoringContext.queryEmbedding`（`Optional<float[]>`）と `VectorSimilarityFactor(float[])` も同じ。

#### 判断

- **1 は指摘 1 の型分割でほぼ解ける。** `SuggestCandidate` に `excluded` フィールドが無ければ、取り込み経路から書けないことが型として成立する。`userBoost` も `OptionalDouble` にすれば補助 boolean が要らなくなる。
- **ただし完全には解けない。** `SuggestItem` 自体も INV-1〜INV-4 をコンストラクタで強制する必要があるため、**`record` をやめ `final class` ＋ private コンストラクタ ＋ static ファクトリ**とした。
- **2 は `List` / `Set` ＋ `List.copyOf` へ寄せた。** ただし `float[]` は次元数が大きく `List<Float>` のボクシングが割に合わないため、**`final class` にしてコンストラクタと getter の両方で `clone()` する**という意識的な例外とし、理由をシグネチャの近くに書いた。

#### D-16 の反転について

**第 3 版の D-16 は `OptionalDouble` を明示的に却下していた。** これを反転させたため、改訂履歴に理由を残した。

> 第 3 版の却下理由（「`OptionalDouble` を公開 record のフィールドに持ち込まない」）は、**`userBoost` を保持する型が「保存されている現在状態」であるという前提に依存していた**。取り込み側を `SuggestCandidate`（状態ではなく更新の意思）へ分離した結果、`OptionalDouble` の意味論が型の役割と一致する。**`SuggestItem` には引き続き `OptionalDouble` を置かない**ため、第 3 版の懸念そのものは維持されている。

### 2.4 指摘 4（High）— R4 の旧世代書き込み

#### 検証 [確認]

`docs/0002` DM-15 / §4.7 が「新旧で ID 方式が違うため旧インデックスに書き足しながらの移行は成立しない」と明記している一方、`docs/0003` 第 3 版 §5.3 の R4 は「旧世代で運用を継続し増分も旧世代に入れたい場合は更新エイリアスも戻す」を**バイナリの状態に言及せずに**選択肢として提示していた。

### 2.5 指摘 5（High）— alias lifecycle の責務漏れ

#### 検証 [確認]

`docs/0001` §2.2 が `SuggestIndexLifecycle` の責務に「エイリアス管理」を挙げている一方、`.prev` 付与は fess 側の `SearchEngineClient` 直呼び（`docs/0003` §3.2 の S4-(1)）、ロールバックも逆方向 API が無いため fess 側での直接操作（同 §5.3 の R3）だった。

### 2.7 指摘 7（Medium）— `ScoringStrategy` の拡張可能範囲

**指摘は事実であり、制約自体は正しい。** `ScoringPlan.ScoringFactor` が `sealed` である以上、外部実装は core が知る 4 種の組み合わせしか作れない。

**制約を変えず、記述を実態に合わせた。**

> `ScoringStrategy` は任意のスコアリング方式を追加する SPI ではなく、**ライブラリがサポートする scoring vocabulary の組み合わせを差し替える SPI である。**

**制約を維持する根拠も併記した**: `sealed` を外すと翻訳できない `ScoringFactor` が `SuggestStore` 実装に届いて実行時に落ちる。語彙を増やす変更は利用者ではなくライブラリ側の改訂であり、`permits` 節と翻訳の追加が対になる（`FuzzyMatchFactor` / `VectorSimilarityFactor` を C-11 の予約として先に語彙へ入れてあるのはこのため）。

**この段落を `ScoringStrategy` の Javadoc にも書くこと**を指示に含めた。

### 2.9 指摘 9（Medium）— INV-5 の書き方

**指摘は正しい。** SHA-256 で単射性は保証できない。

**書き改めた**: 「ID は `text` のみから決定的に導出され、実用上十分な衝突耐性を持つ」。決定性（保証できる）と単射性（保証できない）を表で分けた。

**レビューが提案した検査も採用した。** multiGet 後に `existing.text()` と `candidate.text()` を突き合わせ、不一致なら例外にする。

**採用理由をレビューより 1 段深めた**: この検査が捕まえるのは (a) SHA-256 の衝突（実用上ゼロ）だけでなく (b) **ID 生成の実装バグ**であり、**実際に起こりうるのは圧倒的に (b) である**（ID 生成箇所は `docs/0002` §4.4 のとおり 3 箇所ある）。さらに、現行に同型の欠陥（`index/writer/SuggestWriter.java:76-102` が ID の一致だけで重複判定し `text` を確認していない）が実在し、**2 つの別の語を無言でマージして一方の text を失わせている**（同 §4.3）。**新方式でも「ID が一致すれば同一語」という前提は変わらない**ため、前提を検査する場所を 1 つ持つ。

**バッチ内の重複判定にも同じ検査を置く**ことを追記した（既存ドキュメントとの突き合わせだけでは同一バッチ内の衝突を捕まえられない）。

#### 反映

`docs/0002` **DM-16** 新設 ／ §1 の INV-5 行と注記 ／ **§4.4.1 を新設** ／ §7.2 の T-15
