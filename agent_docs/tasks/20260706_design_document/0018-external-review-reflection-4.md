## 1. レビューの総評と本作業の位置づけ

**判定は「条件付き承認」である。** レビューは骨格について次のとおり述べており、作り直しは求められていない。

> アーキテクチャの骨格を作り直す必要はない。特に `SuggestCandidate / SuggestItem / SuggestHit` の 3 型分離は非常に良く、以前の「取り込み入力・永続状態・検索 projection を全部 `SuggestItem` が背負う」問題をかなりきれいに解消している。

**そのうえで 5 件が指摘された。**

| # | 重大度 | 指摘 | 判定 |
| --- | --- | --- | --- |
| 1 | **Blocker** | `SuggestStore` と `SuggestItemMergePolicy` の責務境界が閉じていない | **反映** |
| 2 | **Blocker** | bad word の「可逆な論理除外」と「取り込み時 drop」が意味的に矛盾する | **反映** |
| 3 | High | メジャー移行時だけでも G2 スモーククエリを必須にすべき | **反映** |
| 4 | High（既知リスク） | K-2 を「後続スコープ」で済ませるのは危うい | **反映** |
| 5 | Medium | `Kind` を `SuggestItem` の内側から出す | **反映** |

**却下・保留は 0 件。** レビューが示した優先順位（1・2 を実装着手前に決める → 3・4・5）どおりに実施した。

### 1.1 ユーザー判断を仰いだ 2 件

**指摘 1 と 2 はいずれも「どちらを選ぶか」で後続の実装範囲が変わるため、着手前にユーザーへ確認した。** 両方ともレビューが推した案が選ばれた。

| --- | --- | --- |

**(B) 側もレビューは「仕様として選ぶならあり」としていた。** 記録として、それぞれの却下理由は `docs/0001` §3.7.1 と `docs/0002` §6.5 の却下表に残した。

## 2. 指摘 1（Blocker）— `SuggestStore` を永続化境界にする

### 2.1 指摘の検証 [確認]

**レビューの主張は文書内の直接的な不整合であり、そのとおりだった。**

| 出典 | 記述 | 判定 |
| --- | --- | --- |
| 第 6 版 `0001` §0 の D-19 | 「**ストアの Put / Get は同じ `SuggestItem` のまま**」 | 主張 |
| 第 6 版 `0001` §2.6 | 「`item = store.multiGet(id)` → 合成 → `store.put(item)` が同一型で成立する」 | 主張（具体的なコード片） |
| 第 6 版 `0001` §3.7 のシグネチャ | GET: `multiGet(List<String>) -> Map<String, SuggestItem>` ／ WRITE: `bulkUpsert(List<SuggestCandidate>, SuggestItemMergePolicy)` | **`store.put(item)` は書けない** |

**`SuggestStore` に `SuggestItem` を書き込むメソッドは 1 つも存在しなかった。** すなわち Get は `SuggestItem`、Put は `SuggestCandidate` であり、**「Put / Get の間に境界を置かない」という §2.6 の主張と実際の公開面が食い違っていた。**

### 2.2 より深い問題 — カスタム MergePolicy は Painless 版で実行できない [確認]

**レビューが「ここにはもう一段深い問題があり」と指摘した点も正しい。**

| # | 事実 |
| --- | --- |
| 1 | `SuggesterBuilder` は `mergePolicy(...)` と `store(...)` を**独立に差し替えられる**（第 6 版 `0001` §3.9.1） |
| 2 | 第 6 版 §3.7 は第 2 段（`scripted_upsert`）について「**同じ `bulkUpsert` の別実装として載る**」「Painless 版を載せる場合、その挙動が `SuggestItemMergePolicy` と一致することを実装側の責務とする」としていた |
| 3 | **任意の Java 製 `SuggestItemMergePolicy` を Painless で実行する一般的な方法は存在しない** |

**2 の「実装側の責務とする」は、既定の 2 実装の組み合わせについてしか意味を成さない。** 利用者が書いたカスタム MergePolicy については**実現不能な要求**である。**まだ存在しない第 2 段のために、実現できない一般化を第 1 段の公開契約に持ち込んでいた。**

### 2.3 採った形

> **`SuggestStore` は「完全状態を読む／完全状態を書く／条件で消す・更新する／検索する」だけを持つ。read-modify-write の組み立ては `internal` の取り込み経路が所有する。**

```text
SuggestIngestService.index / indexFrom（internal 実装）
  ├─ 1. 候補を正規化し、text から ID を導出する
  ├─ 2. 同一 ID の候補をバッチ内で先に畳み込む
  ├─ 3. store.multiGet(ids)                    ← SuggestStore（読み出し）
  ├─ 4. ID ごとに畳み込む                        ← SuggestItemMergePolicy
  └─ 5. store.bulkPut(items)                   ← SuggestStore（書き込み）
```

**レビューの表現をそのまま採った** — 「Java 版では Service 側が `multiGet → merge → bulkPut(List<SuggestItem>)` を行い、Store を本当に永続化境界にする」。

### 2.4 C-03 との関係 — 何を維持し、何を撤回したか

**C-03（`0000` §5）の文言は変えていない。** 「`scripted_upsert`（第 2 段）は `SuggestStore` の拡張点だけ用意し、Painless 仕様は含めない」は成立し続ける — 第 2 段が差し替わる場所は引き続き `SuggestStore` の実装である。

**撤回したのは、第 6 版 §3.7 と §4.4.0 が C-03 に加えていた、より強い主張のほうである。**

| 版 | 主張 | 第 7 版 |
| --- | --- | --- |
| 第 5・6 版 §3.7 | 第 2 段は「**同じ `bulkUpsert` の別実装として載る**」 | **撤回**。第 2 段は `SuggestStore` への**原子マージ能力の追加**になる |
| 第 5・6 版 §4.4.0 の 2 | 第 2 段は「**公開契約を変えずに載る**」 | **弱めた**。`api` 4 IF は変わらないが `spi` の面は変わる |

**前倒ししない判断そのものは変わらない。** むしろ「第 2 段で何を決めるかが未定である」ことが明示された結果、前倒ししない理由は強くなっている。**第 2 段で必ず決める 3 点**を `docs/0001` §10 の申し送り 18 として登録した。

### 2.5 却下した代替案

| 案 | 却下理由 |
| --- | --- |
| **(B) `bulkUpsert` を維持し D-19 の「Put / Get は同じ型」を撤回する** | 文書の整合は取れるが **§2.2 の問題が解決しない**。さらに「`mergePolicy()` と `store()` は独立に差し替えられない」という組み合わせ制約を公開契約に書くことになり、**7 つの SPI のうち 2 つだけが暗黙に結合している**状態になる |
| `bulkUpsert` と `bulkPut` を両方置く | 合成の所有者が 2 箇所ある状態は MIG-01 が解消しようとしているものそのもの |
| `SuggestItemMergePolicy` を宣言的な `MergeSpec` に変える | 第 2 段の設計を第 1 段に前倒しすることになる。表現力（位置対応 `readings` 合成など）を DSL で表せるかが未検証であり、検証には Painless 側の実装が要る |

## 3. 指摘 2（Blocker）— bad word の取り込み時 drop を廃止する

### 3.1 指摘の検証 [確認]

**レビューの主張は 2 つの [確定] 事項が両立していないというものであり、そのとおりだった。**

| 出典 | 記述 |
| --- | --- |
| `0000` §5 の **C-02** | bad word の適用方式は「**即時・可逆な論理除外**」。①物理削除は明示オプションとしても残さない |
| 第 6 版 `0001` §3.5.1 | 「**取り込み時フィルタと `excluded` は両方残す**」。`isBadWord` の目的は「**新規流入の防止**」／ `excluded` の目的は「**既存語**の論理除外（可逆）」 |
| 第 6 版 `0002` §5.3 の表 ② | 取り込み時のフィルタ除外は「**維持**」 |
| 第 6 版 `0002` **DM-18** | `excluded == true` ⇔ 現在の bad word 集合のいずれかに該当する |

**レビューが挙げた例がそのまま成立する** [確認]:

```text
bad word 集合 = {foo}
  → 検索ログから "foobar" が 100 回入る
  → isBadWord("foobar") == true なので 100 回とも捨てられる
deleteBadWord("foo")
  → releaseCondition("foo") が選ぶ対象そのものが存在しない
  → 100 回ぶんの queryFreq は復元されない
```

**② も ① と同じ不可逆性を持つ。** ① は「既に保存された語を消す」、② は「保存されるべき語を作らない」であり、**どちらも `deleteBadWord` で元に戻せない**。第 6 版は ① の不可逆性を理由に物理削除を廃止しながら、② を「別の目的」として残していた。

**DM-18 も、正確には「保存されているドキュメントに限り」成立していた。**

### 3.2 採った形

> **bad word に該当する新規候補も保存する。ただし `excluded = true` を初期値として保存する。**

**判定位置は変わらない** — 現行 `index/operations/IndexingOperations.java:78` が配列から要素を取り除いていた位置が、そのまま「初期値を決める位置」になる。

**`SuggestItemMergePolicy.initialize` が `excluded` を引数で受ける形にした。**

```java
SuggestItem initialize(SuggestCandidate incoming, boolean excluded);
SuggestItem merge(SuggestItem existing, SuggestCandidate incoming);   // 変更なし
```

**この形を選んだ理由は 3 つある。**

| # | 理由 |
| --- | --- |
| 1 | **D-17（`SuggestCandidate` は `excluded` を持たない）を維持したまま新規語の初期除外を表現できる唯一の形である。** 候補側にフィールドを足すと `index(...)` の呼び出し元が任意に除外を指定できてしまう |
| 2 | **`SuggestItemMergePolicy` が `BadWordPolicy` を参照しなくて済む。** 既定実装がもう一方の SPI を保持すると、`badWordPolicy(...)` の差し替えで組み合わせ依存が生じる |
| 3 | **`merge` 側は引数が要らない。** 既存語の `excluded` は保持する（U4）ため、**「新規語だけが bad word 判定を受ける」という非対称がシグネチャに現れる** |

### 3.3 代償の扱い

**代償は、bad word 該当語がインデックスに残り続けることである。全件再構築でも消えない。**

| 影響 | 扱い |
| --- | --- |
| 検索レイテンシ | **述語数は変わらない**（DM-14 の否定形フィルタ 1 節のまま）。増えるのは転置索引の規模。計測項目に追加（`0002` §6.4 / §9 の 13） |
| ディスク・再構築時間 | 増える。増分は実測依存（C-04） |
| 語数統計 | `wordCountStats()` は `excluded = true` を含む。**G1 は下限判定なので誤判定を起こさない**が、運用者への説明が要る（`0003` §4.1 / §10.1） |
| 物理削除したい運用 | **`deleteByCondition(mustMatchAny("excluded", ["true"]))`**（`0001` §2.4 / §3.6）。**専用 API は置かない。不可逆であり自動実行しない**（`0003` §12.1 の MO-23） |

**C-02 の「①物理削除は明示オプションとしても残さない」には反しない。** C-02 が禁じたのは *bad word の適用方式として* 物理削除を選ぶことである。`addBadWord` は常に論理除外であり、物理削除は「インデックスを掃除する」という独立した運用操作になる。

### 3.4 却下した代替案

| 案 | 却下理由 |
| --- | --- |
| **(B) drop を維持し C-02 を「既存インデックス語の可逆な論理除外」に狭める** | 文書間の整合は取れるが**中心モデルに非対称が残る**。運用者が「除外は可逆」と「一部は不可逆」を両方覚える必要があり、`previewBadWordImpact` の件数も「これから除外される語」しか表さない |
| drop を維持し「失われるのは検索ログ由来の頻度だけ」と注記する | **事実としては正しいが契約として書けない。** 可逆性が `Kind` によって変わり（`QUERY` は永久に失われ、`DOCUMENT` は次回再構築で戻る）、復活時期が再構築の実行間隔に依存する |
| `excluded = true` で保存したうえで全件再構築のときだけ drop する | **再構築を境に不可逆性が発生する**。第 6 版より発見しにくい形の非対称になる |
| `SuggestCandidate` に `excluded` を持たせる | D-17 に反する。`excluded` の権威が `SuggestWordAdmin` 以外に増える |

## 4. 指摘 3（High）— メジャー移行時の G2 必須化

### 4.1 指摘の検証 [確認]

**第 6 版 `0003` §4.2 の G2 行は「未設定なら G2 をスキップし G1・G3 のみで判定する」であり、運用者が検証語を設定しない限り常にスキップされた。**

**レビューが指摘した事故（「100% 正常に index でき、件数も十分なのに検索だけ 0 件」）は G1・G3 で検知できない。**

| 状況 | G1 | G3 | G2 |
| --- | --- | --- | --- |
| 取り込みが 1 件も成功しない | 検知する | 検知する | — |
| 10% が item failure | 通過 | **検知する**（MO-18） | — |
| **全件正常・件数十分・検索 0 件** | **通過** | **通過** | **検知する** |

**今回の移行では 6 つのものが同時に変わる**（mapping / `reading_i` の付帯規則 / 語数上限 N / ID 方式 / `excluded` / クエリ生成）。**いずれか 1 つが外れれば 3 行目が成立する。**

**`excluded` については DM-21（指摘 2 の反映）により状況が悪化する** — `excluded = true` のドキュメントが実際に存在するようになるため、否定形フィルタの実装ミスや初期値の誤りで全件除外になる経路が第 6 版より起こりやすい。

### 4.2 採った形

**レビューが挙げた 2 案（「初回移行時だけ必須」「S2 で投入した語から自動採取」）を組み合わせた。**

| # | 規則 |
| --- | --- |
| 1 | **メジャー移行の再構築では G2 を実行せずに切替へ進んではならない。** スキップは不合格と同じ扱い |
| 2 | 検証語は運用者が設定するのが第一 |
| 3 | **未設定の場合は S2 で実際に投入した語から自動採取する。** 「設定必須」にしないため初期導入の障壁は生じない |
| 4 | **平常時の再構築では第 6 版のまま**（未設定ならスキップ）。レビューの「平常時の再構築だけ G2 任意という分離でもよい」を採った |

**自動採取の条件**: **`excluded = false` として保存された語に限る。** bad word 該当語は否定形フィルタで正しく 0 件になるため、スモークの入力にすると必ず不合格になる。**これは指摘 2 の反映（DM-21）と噛み合う点であり、両方を同時に反映したことで初めて見える制約である。**

**自動採取が「自明に成功するテスト」にならない理由**: 検証するのは「その語が存在すること」ではなく「**保存された語が本番と同一のクエリ生成経路で見つかること**」である。§4.2.1 が (a′) を採った理由がまさにこれであり、レビューも「`validateNext()` をわざわざ本番と同じクエリ生成経路へ向ける設計まで作っており、これは非常に良い」と述べている。

### 4.3 却下した代替案

| 案 | 却下理由 |
| --- | --- |
| 常に G2 を必須にする（平常時も） | 平常時は G1（前回比 50%）が既に強く、追加の停止リスクに見合わない |
| メジャー移行でも「警告を出してスキップ」 | 警告はジョブログに出るだけであり**切替が済んだ後に読まれる**。ガードとして機能しない |
| 切替後に検証し失敗したらロールバック | 一度公開してからの切戻しになる。**S3 で止められるものを障害対応に格下げする理由が無い** |

## 7. V7（文書間整合）では検出できない型の発見

**今回の Blocker 2 件は、前 3 回とは検出の型が違う。**

| 回 | 型 | 既存の検査手順で検出できるか |
| --- | --- | --- |
| 第 1・2 回 | 手順書が要求する操作が公開契約に存在しない | **できる**（`0016` §5 の逆引き検査） |
| 第 3 回 | 手順書と公開契約が同じ規則を主張しているが適用対象の列挙が食い違う | **できる**（`0017` §6 の全列挙検査） |
| **第 4 回 指摘 1** | **本文の説明と、同じ文書内のシグネチャが食い違う** | **できない** |
| **第 4 回 指摘 2** | **2 つの [確定] 事項が両立しない** | **できない** |

**どちらも「他文書との突き合わせ」では出てこない。** 指摘 1 は `0001` 1 文書の中で閉じており、指摘 2 は C-02 と設計の間の矛盾である。

**追加する検査手順**:

> **検査 A（説明文とシグネチャの突き合わせ）**
>
> 1. 説明文が**具体的なコード片**（`store.put(item)` のような）を含む箇所を列挙する。
> 2. その式が**本当に書けるか**を、同じ文書のシグネチャ定義で確認する。
> 3. 書けない場合、**説明文を直すのではなくどちらが正しいかを判断する** — 今回は説明文（D-19 の意図）が正しく、シグネチャのほうを直した。

> **検査 B（[確定] 事項の形容詞の検証）**
>
> 1. C 番号の結論に含まれる**形容詞**（「可逆な」「原子的な」「安全な」「単一の」）を列挙する。
> 2. その形容詞が**成立しない経路**が設計内に無いかを列挙して確認する。
> 3. 成立しない経路がある場合、**設計を変えるか、[確定] 事項の側を狭めるかを明示的に選ぶ**。

**検査 B で今回検出されたのが指摘 2 である** — C-02 の「可逆」は既存語については成立していたが、取り込み経路では成立していなかった。**同じ観点を C-03 の「拡張点だけ用意し」に当てはめると指摘 1 にも届く** — 「拡張点」が実際に拡張できるかは検証されていなかった。
