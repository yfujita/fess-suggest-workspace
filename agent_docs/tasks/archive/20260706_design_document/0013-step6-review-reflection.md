## 2. 指摘 1: G2 の実行経路（最重要）

### 2.1 何が欠落していたか

初版 §4.2 は G2 の判定内容として「**更新エイリアスに対して**実行する」ことを正しく定めていた。しかし取得方法の欄は「`request/suggest/` のサジェスト経路」とだけ書いており、**その経路が更新エイリアスを指定できるかを確認していなかった。**

### 2.2 確認結果 [確認]

| 層 | 事実 |
| --- | --- |
| 現行 API | `Suggester.suggest()`（`Suggester.java:159`）が返す `SuggestRequestBuilder` は `Suggester` が保持する**検索エイリアスに束縛**されている（`Suggester.java:416-418` の `getIndex()`） |
| 新 API | **`0001` §2.1 の `SuggestQueryService.suggest(SuggestQuery)` は対象インデックスを引数に取らない。** `0001` §2.5 の `SuggestQuery`（`docs/0001-api-design.md:216-232`）の 12 要素（`query` / `size` / `tags` / `roles` / `fields` / `kinds` / `languages` / `prefixMatchWeight` / `matchWordFirst` / `skipDuplicateWords` / `responseFields` / `accessScope`）にも**対象インデックスに相当する項目が無い** |

> **したがって「更新エイリアスに対して検証クエリを発行する」手段は、現行 API にも新 API にも存在しない。**

### 2.3 なぜ重大か

**S3（検証）の設計全体がこの 1 点に乗っている。** G1（件数）と G3（例外なし）は既存の手段で足りる一方、**G2 だけが経路を持たない**。しかも G2 は「不完全なインデックスが公開される」ことを防ぐ 3 判定のうち、**唯一「実際に検索が成立するか」を見る判定**である。件数が足りていてもクエリが返らないケース（analyzer の破損など）は G1・G3 では捕まらない。

### 2.4 反映内容

**本書では決めなかった。** 選択肢の提示と、決着をステップ 7 に引き渡すところまでを行った。

| 案 | 内容 | 代償 |
| --- | --- | --- |
| **(a)** | `0001` に検証用の対象指定を追加する（`SuggestQuery` に対象世代の要素を足すか、`SuggestIndexLifecycle` に検証専用の read メソッドを置く） | **公開契約の改訂**。`0001` §2.1 / §2.5 の再判断が要り、**MO-1（fess-suggest に手を入れない）と衝突しうる** |
| **(b)** | fess 側で `SearchEngineClient` を用いて低レベルクエリを直接組む | `0001` の改訂は不要で MO-1・MO-2 と整合する。一方**サジェストのクエリ構築を fess 側で再実装することになり、本番経路と検証経路でクエリが乖離しうる。乖離すると G2 は判定として無意味になる** |

**決めなかった理由**: (a) は `0001` の公開契約に触れるため、ステップ 6 の裁量を超える。(b) は本書だけで完結するが、**「本番と同じクエリで検証する」という G2 の存在意義を損なう可能性**があり、`0001` 側の判断を仰がずに選ぶべきではない。

**暫定の運用**: G2 は「未設定ならスキップ」を既定としてあるため、**未確定のままでも G1・G3 で手順は完結する**。ただし §4.2.1 に「これは暫定であって設計の完成形ではない」と明記した。

## 3. 指摘 2: `auto_expand_replicas` の実効挙動

### 3.1 指摘の前提

> 「現行は `number_of_replicas: 0`（常にレプリカなし）、To-Be の既定 `0-1` は 2 ノード以上のクラスタで自動的にレプリカ 1 が割り当てられる。既存の複数ノード運用者にはアップグレードで黙って発生する変化である」

### 3.2 確認結果: 前提が成立しない [確認]

**現行の 7 ファイルには `number_of_replicas: 0` と `auto_expand_replicas: "0-1"` の両方が既に書かれている。**

```json
// (res) suggest_indices/suggest.json（現行・実物）
{
  "index": {
    "refresh_interval": "10s",
    "number_of_shards": 1,
    "number_of_replicas": 0,        // :5
    "auto_expand_replicas": "0-1"   // :6
  }
}
```

OpenSearch では `index.auto_expand_replicas` が設定されている場合、**クラスタがレプリカ数を自動で再計算し `number_of_replicas` を上書きする**。`~/.m2/repository/org/opensearch/opensearch/3.7.0/opensearch-3.7.0.jar` を展開し `javap -c -p org/opensearch/cluster/metadata/AutoExpandReplicas.class` で確認した:

- `SETTING` は `index.auto_expand_replicas` を `Setting$Property.Dynamic` ＋ `IndexScope` で定義する
- `getAutoExpandReplicaChanges` が `SETTING.get(indexMetadata.getSettings())` から得た値と `getDesiredNumberOfReplicas(...)` の結果でレプリカ数の変更を算出する

> **したがって 2 ノード以上のクラスタでは、現時点で既にレプリカ 1 が割り当てられている。`number_of_replicas: 0` は一度も効いていない。**

### 3.3 帰結

- C-14 による `number_of_replicas: 0` の削除は**死蔵設定の除去**であって挙動変更ではない（設計原則 4「死蔵コード・死蔵データを持たない」）。
- §8.2 の新設キーの既定 `0-1` は**その実効値をそのまま引き継ぐ**。**アップグレードで黙って発生する変化は無い。**
- したがって**リリースノート項目にはしない**。§13 の 6（最小 OpenSearch バージョンが 2.16 に上がる）とは性質が異なる — あちらは実際に動作要件が変わる。

### 3.4 ただし記録は必要だった

**指摘が想定した誤解そのものは、既存資料に実在する。** 改善提案書 `§2.2` ISS-07 は「単一シャード固定（`number_of_shards=1`/`replicas=0`）のスケール上限」としており、**`replicas=0` の部分が事実誤認**である。

この訂正は **`0001-unresolved-items-resolution.md:187` と同 §2.14 が既に提出済み**であるため、`0003` 付録 A には新たに加えていない。ただし **`0003` §8.2 を読んだ人が同じ誤解に至らないよう**、注記として実効挙動と根拠を本文に置いた。**指摘は「本文に書くべき」という点で有効であり、書くべき内容が「変化する」ではなく「変化しない」だっただけである。**

## 4. 指摘 3: V6 の分量超過への対処

**同意する。** `0003` §14.1 として推奨を明文化した。要旨は 4 点。

1. **分量目標はもともと転記防止の代理指標である。** 作業プラン §5 の V6 は検証項目名が「根拠の非転記」であり、バイト数はその代理にすぎない。**代理指標が目的と乖離したら、代理指標のほうを改める。** 転記ゼロは 3 文書とも個別に検証済みである。
2. **超過は執筆の冗長さではなく作業定義に由来する。** (a) 完了条件が手順書の粒度を求めたこと、(b) 一次資料が 12 行しかなく新規書き起こしであること（作業プラン §6.2 のリスク欄が予見していた）。
3. **分割は凝集性を下げる。** §11（テスト仕様）は §3 の手順と §5 のロールバックの検証であり、§12（既知の制約）は同じ手順の限界である。**手順・検証・限界は一体で読まれるべきもの**である。
4. **3 文書とも同傾向で超過している**（`0001` 126.0% ／ `0002` 86.6% ／ `0003` 99.7%）。個々の執筆ではなく **V6 の目安が P1 の 4 文書構成と噛み合っていない**。

**推奨**: 4 文書構成（P1）は維持し、**V6 の目標値を「提案書比 20% 前後」から「転記ゼロ ＋ 非重複」という質的基準に改める**。

**併せて申し送った留保**: これは本書の自己弁護になりうる位置の主張であるため判断はステップ 7 に委ねる。**分割を採る場合でも §11・§12 を §3〜§7 から引き離すことは避ける**こと。

## 5. 指摘 4: 細部 2 件

### 5.1 (a) T-S 系テストのホスト先

初版は §11.1（T-S1〜T-S8）と §11.3（T-F1〜T-F4）を別表として並べており、**両者の対応を書いていなかった**。実装タスクが「T-S1 をどこに書くのか」で迷う。

**反映**（`0003` §11.1 に注記）:

| テスト | ホスト先 | 理由 |
| --- | --- | --- |
| **T-S1〜T-S4, T-S8** | **T-F2 の内訳**（fess 側 `SuggestCreatorTest` 系） | 検証対象（失敗時ガード・`.prev` 操作・`refresh_interval` の復帰）は**すべて `(fess) exec/SuggestCreator.java` にある**（MO-2） |
| **T-S5〜T-S7** | **T-F4 の内訳**（統合テスト） | `.prev` の付け替え・保持世代の非削除・孤児インデックスの回収は**エイリアスの実際の解決結果**を見るため実クラスタが要る |

**fess-suggest 側の runner テストには置かない。**

### 5.2 (b) 先行リリース時の G1 実装

初版 §10.1 は「MO-2 / MO-4 は fess 本体側の変更のみで完結するため L1 を待たずに先行リリースできる」と書いたが、**その時点で G1 が何を呼ぶのかを書いていなかった**。先行版と本設計版の差分が追跡できない。

**反映**（`0003` §10.1 に差分表）:

| 要素 | 先行リリース時（L1 以前） | L2 以降 |
| --- | --- | --- |
| **G1 の件数取得** | 現行 API `suggester.getAllWordsNum()`（`Suggester.java:424`、fess 側は `(fess) helper/SuggestHelper.java:340`）を同期で用いる | `lifecycle.wordCountStats()` へ移す（`0001` §2.2 ／ 同 §8.3 の P-a「同期化委譲」と同じ形） |
| **G2** | §4.2.1 が未確定のため**スキップ**（G1・G3 のみ） | §4.2.1 の決着に従う |
| **G3・`.prev` 操作・ガードの配置** | 変更なし | 変更なし |

**これは妥協ではない。** `getAllWordsNum()` は `wordCountStats().total()` の前身であり（`0001` §8.1 の対応表 16）、L2 の切り替えは呼び出し形の置換に閉じる。
