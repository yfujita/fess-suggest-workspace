## 3. レビューで新規に検出した不整合（2 件）

**どちらも「各文書は個別には正しいが、組み合わせると壊れる」型の不整合**であり、どの文書の申し送りにも載っていなかった。ステップ 7 の通し整合レビューが検出した唯一の実質的な収穫である。

### 3.1 `SuggestItem` が `excluded` を持たないと、取り込みのたびに bad word 除外が消える

| 文書 | 記述 | 単独での正しさ |
| --- | --- | --- |
| `0001` §2.5（第 2 版） | 「`SuggestItem` は **`excluded` をフィールドに持たない**」。理由は「取り込み側は `excluded` を書かない（U4）ため、入力 DTO に置くと死蔵フィールドになる」 | **入力 DTO としては正しい** |
| `0002` §5.3 | `excluded` の `merge` は **existing を保持**、`initialize` は `false` で初期化（U4） | **合成規則としては正しい** |
| `0002` §5.6 | `SuggestItemMergePolicy` が完全な source を返すため **`OpType.INDEX` の全置換を維持する** | **書き込み方式としては正しい** |

**組み合わせると破綻する** [確認]。`merge` の戻り値型は `SuggestItem` である（`0001` §3.4）。その型に `excluded` が無ければ、全置換で書く source に既存の `excluded` を載せられない。**結果として通常の取り込みが走るたびに bad word 除外が解除される** — U4 が防ごうとした事故そのものである。`initialize` が `false` を書くことも型の上で不可能だった。

**`0001` の除外理由は「入力 DTO」としての議論であり、同じ型が `merge` の引数と戻り値でもあることを見落としていた。**

**解消**: `SuggestItem` に `excluded` を**読み取り専用フィールドとして持たせる**（`0001` D-17）。取り込み側から書けないことは**生成 API の分離**で保証する — 正準ファクトリ `of(...)` は `excluded` を受け取らず常に `false` を入れ、`true` を生じさせるのはストアからの読み出しと `SuggestItemMergePolicy`、および `BadWordPolicy` が駆動する専用経路だけである。**判断 4（`userBoost`）と同じ手段で解いた。**

### 3.2 `refresh_interval = -1` が型で表現できず、復帰側の経路も存在しなかった

`0003` §7.3（MO-8）は「停止側は `0001` §6.2 の `IndexSchema.refreshInterval` に受け口があり**新規 API を要しない**」「**新規に要るのは復帰側だけ**」と断言していた。**どちらも成立していなかった** [確認]。

| 主張 | 実際 |
| --- | --- |
| 停止側は既存の受け口で足りる | `IndexSchema.refreshInterval` は `Optional<Duration>` であり、**`-1`（自動 refresh 無効）を表現できない**。未指定は「JSON の既定値を使う」と定義済みで、`Duration.ofSeconds(-1)` が「無効」を意味するという約束は型に無い |
| 新規に要るのは復帰側だけ | 復帰側（`_settings` による動的変更）の**実装先が特定されていなかった**。`SuggestIndexLifecycle` にも `SuggestStore` にも settings 更新メソッドが無く、`0003` §13 の 9（実装位置の申し送り）にも `_settings` は含まれていない |

**解消**: `RefreshInterval`（`sealed interface` ＋ `Every(Duration)` / `Disabled()`）と `SuggestIndexLifecycle.updateRefreshInterval(IndexGeneration, RefreshInterval)` を新設した（`0001` D-18）。**新規に要るのは停止側の型と復帰側のメソッドの 2 つである**と `0003` §7.3 を訂正した。

`sealed interface` を選んだのは、**無効化を `Disabled` 以外の書き方で表現できなくするため**である。汎用の settings 更新 API は設けなかった（死蔵の設定変更経路を作らない）。

## 4. 引き渡されていた設計判断の決着

### 4.1 G2 スモーククエリの実行経路（`0003` §13 の 2b）

**`0003` は「S3 の設計全体がこの 1 点に乗っている」として未決のままステップ 7 へ引き渡していた。** 切替前の更新エイリアスに検証クエリを打つ必要があるのに、`0001` の `SuggestQuery` には対象インデックスの指定要素が無い [確認]。

| 案 | 判定 | 理由 |
| --- | --- | --- |
| (a) `SuggestQuery` に対象世代を追加 | **却下** | 運用専用の要素を通常の検索契約に混ぜることになる。検索の呼び出し元すべてに意味のない項目が見える |
| (b) fess 側で低レベルクエリを直接組む | **却下** | `SuggestQueryBuilder` を fess 側で再実装することになり、**本番経路と検証経路でクエリが乖離しうる**。乖離した時点で G2 は「本番で返るか」を検証しなくなり判定として無意味になる |
| **(a′) `SuggestIndexLifecycle.validateNext(SuggestQuery)`** | **採用** | 検索の公開契約を変えずに済み、**クエリが本番と同一であることが実装上保証される**。否定形フィルタ（`0002` DM-14）も自動的に適用される |

**MO-1 との関係を整理した。** MO-1 は「**再構築を束ねる高水準 API を新設しない**」であって「fess-suggest に一切手を入れない」ではない。`validateNext` は制御フローを持たず、**判定は呼び出し元の fess 側ガード（`0003` §4.3）が行う**。ライブラリは合否を決めない。したがって衝突しない。

### 4.2 `userBoost` の「指定あり／なし」（`0002` §9 の 5）

| 案 | 判定 |
| --- | --- |
| **生成 API の分離**（`of(...)` は受け取らない ／ `withUserBoost(double)` でのみ指定あり） | **採用**。`null` 意味論を公開 record に持ち込まず、**パーサ経路が誤って「指定あり」を作ることが型として起きない** |
| `Double`（null 許容） | 却下。公開 record に null 意味論が入り、呼び出し側の NPE 経路が増える |
| `OptionalDouble` | 却下。record のフィールド型として一般に推奨されず、シリアライズ経路にも影響する |

判別は `userBoostSpecified`（boolean）が担う。**この 2 フィールドは常に組で扱い `withUserBoost` 以外から `true` にしない**ことを `0001` §2.5 に明記した。
