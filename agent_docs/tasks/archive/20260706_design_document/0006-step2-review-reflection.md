## 2. 指摘ごとの検証と対応

### 2.1 指摘 1（表の構文エラー）— 不再現

`0005-design-overview-skeleton.md` と `docs/0000-design-overview.md` の**全テーブル区切り行を正規表現で照合したが、`| --- | ... | --- |` の形から外れる行は 0 件**であった [事実]。両ファイルに文字列 `|a` は存在しない。

```
for f in 0005-design-overview-skeleton.md docs/0000-design-overview.md; do
  grep -nE '^\| *-' "$f" | grep -vE ':\| (--- \| )*--- \|$'
done
# → 出力なし（exit 1）
```

**対応なし。** レビュー時の引用・貼り付け過程で生じた表示上の混入と判断する。ただし指摘の意図（自己検証が書式崩れを取りこぼす可能性）は妥当であり、**ステップ 7 の書式確認では上記の全テーブル一括照合を用いる**ことにする。

### 2.2 指摘 4（宣言フォーマットの欄の曖昧さ）— 1 欄に統合

**問題の実体** [事実]: 改訂前の §3.2 は「依存する [確定] 番号: `0000` §5 の C-XX」と「依存する前提: P6, P11, P13（作業プラン §1.1）」を別欄にしていた。ところが `0000` §5.1 が P5/P6/P9/P11/P12/P13/U3/U4 を**本書側に取り込んでいる**ため、執筆者が「ID 再設計は P11 に依存」と書くときにどちらの欄に入るかが決まらない。ステップ 7 の第 1 観点（宣言が埋まっているかの検査）が形式検査として成立しなくなる。

**取った方針**: レビューが挙げた 2 案のうち「**C/P/U いずれの番号も可**と欄の定義に明記する」を採り、さらに**2 欄を 1 欄に統合**した。「C-15 以降を続番で振る」案を採らなかった理由:

- C 番号は `0001` §2 の 14 件と 1:1 対応しており（`0000` §5 の「原典」欄）、この対応が壊れると `0001` に遡る経路が読めなくなる。
- P/U は原典が作業プラン §1.1 / §6.1 であり、`0001` 由来の C とは出自が異なる。同一系列に混ぜると `0000` §5 と §5.1 を 2 表に分けた意味が失われる。

規則として `0000` §3.2 に 4 点を明記した: ①C/P/U を同じ欄に書く ②書くのは `0000` §5 / §5.1 に載っている番号だけ（原典の節番号は設計書側に書かない）③P/U に C 番号を振り直さない・C-15 以降を新設しない ④ステップ 7 は「欄が埋まっていること」と「書かれた番号がすべて §5 / §5.1 に存在すること」を検査する。あわせて §5 冒頭と §8.1 の 7-4 に同じ制約を書き、3 箇所が食い違わない状態にした。

**副産物: `R1` という番号は存在しなかった** [事実]。`0005` §5 の 6 が「ステップ 7 の R1 が fail する」と書いていたが、作業プラン内に `R1` の定義はない（レビュー観点は §3 ステップ 7 作業内容 4 の箇条書きで番号を持たない）。`0005` の当該行を「作業プラン §3 ステップ 7 作業内容 4 の第 1 観点」に修正し、**`R` 系番号が存在しないことを §3.4 の台帳に明記**した。指摘 2 の台帳が必要である実例そのものである。

### 2.4 指摘 3（P9 の「正の二重化」）— タスク外への申し送りを新設

指摘のとおり、既存の申し送り 6 件はすべてタスク内（ステップ 3〜7）宛てで、**タスク外への出口が無かった** [事実]。凍結（P9）自体は設計タスク期間中の判断として妥当だが、その帰結として「課題インベントリの正は提案書／訂正の正は `0000` §6」という二重状態が恒久化する。本タスクを知らない将来のタスクが提案書だけを読めば、E-06（KEEP-03 の無条件踏襲）や ISS-07 の旧記述を**そのまま再継承する**。

反映内容:

- `0000` §6 の前置きに、二重化が起きている事実と再継承のリスクを明記した。
- `0000` §8.1 に **7-6** を追加。完了条件は「E-01〜E-12 を提案書第 5 版・関連文書へ還流する後続タスクが起票されている、**または**『還流しない』判断と理由が提案書側に残されている」の**いずれか**とした。還流を強制せず、どちらであれ判断が文書に残ることを条件にしている（P9 の凍結は本タスク中の制約であり、タスク後の扱いを本タスクが一方的に決めるべきではない）。
- `0005` §5 に申し送り **7** を追加（引き継ぎ先＝本タスク完了後）。

### 2.5 指摘 5（分量）— 発動条件付きに格上げ、ただし基準値は 40%

指摘のとおり「再点検する」には基準が無かったため発動条件を設けた。**ただしレビューが挙げた 35% はそのまま使えない** [事実]:

| 時点 | 文字数 | 提案書（60,700 文字）比 |
| --- | --- | --- |
| 骨組み完成時（`0005` の計測） | 18,716 | 30.8% |
| **本レビュー反映後** | **21,829** | **36.0%** |
| （参考）§6 を分離した場合 | 17,877 | 29.5% |

本反映で追加した §3.4 台帳・§3.2 の規則・§6 注記・チェックリスト 2 行で約 3,100 文字増えており、**ステップ 7 を待たずに 35% を超えている**。35% を発動点にするとベースラインで即発動し「成長の検知」として機能しないため、**24,000 文字（提案書比 40%）**を発動点とした。§6 は本書全体の 18.1%（3,952 文字）を占めており、分離すれば 29.5% に落ちる分量的な余地はある。

**分離実施はユーザー判断とした** [要確認]。§6 の分離は 4 文書構成（P1 [確定]・要件定義由来）と `0000` §0.1 が宣言する「本書が持つ 4 つ」の変更にあたるため、ステップ 7 で機械的に実行するのではなく、判定結果を出してユーザーに諮る形にした。

### 2.6 指摘 6（ID-01 の 0003 への波及）— 既に届いていた／記述を補強

**指摘の懸念は既に解消されている** [事実]。`0000` §4.2 の ID-01 行は改訂前から担当先に `0003 §6-1` を含んでおり、0002 単独の担当ではない。また作業プラン側で以下が確定している:

- ステップ 5-4 注意点: 「ID 方式の変更は**旧世代インデックスとの共存が成立しない**（同じ語が新旧で別 ID になる）。したがって『旧インデックスに書き足しながら移行する』形は取れず、**必ず全件再構築＋エイリアス切替**になる」（作業プラン `:260`）
- ステップ 6 作業内容 4: 「ID が変わると新旧で同じ語が別 ID になるため、**旧世代インデックスとの共存・部分移行は成立しない**。…『新スキーマ・新 ID で全件再投入 → 検証 → エイリアス切替』以外の経路を取らないことを手順として明記する」（同 `:282`）

つまり指摘が心配した「二重エイリアス共存期に旧世代へ新 ID の増分更新が入るケース」は、**そのような経路を取らないと決めることで消えている**。ただし `0000` の ID-01 行は「MIG-02 の再構築に相乗り。ロールバック条件」としか書いておらず、この最も重要な帰結が索引から読み取れなかった。**「新旧で同じ語が別 ID になるため旧世代との共存・部分移行が成立せず、全件再投入以外の経路を取らない」旨と切替前の件数検証基準を ID-01 行に明記した。**
