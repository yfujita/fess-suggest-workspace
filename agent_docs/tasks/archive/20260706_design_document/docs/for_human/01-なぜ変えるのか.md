# 01. なぜ変えるのか

> 元: `improvement-proposal.md` §1〜§2 ／ `0003-migration-ops-design.md` §1
> ざっくり版です。根拠となるコードの行番号は元の文書にあります。

---

## 出発点

fess-suggest は **10 年以上、機能がほぼ据え置かれています**。サジェストの種別は DOCUMENT / QUERY / USER の 3 種、データの供給元は 4 経路のまま。保守するには高度な Java の知識が要り、サジェストの品質も「悪くはないが良いとも言えない」。

そこで **可読性・変更容易性・サジェスト品質・性能・新機能** の 5 つを軸に、いったん既存構成を忘れて「あるべき姿」を描き、そこへ現実的に到達する道筋を引いたのが今回の設計です。

**ただし調査の結論は「壊れてはいない」でした。** 重大度「高」と断定できる課題は 1 件もなく、大半が「中」。**アーキテクチャは健全で、改善は段階的に行える**というのが全体評価です。だから全面書き直しではなく、部分ごとの置き換えを選んでいます。

---

## そのまま使うもの（残す価値があると判断したもの）

| | 内容 |
| --- | --- |
| **テキスト処理パイプライン** | 正規化 → 読み変換 → 解析の 3 段構成。責務分割が良く、テストも手厚い（約 1,369 行） |
| **ゼロダウンタイム再構築** | 検索用と更新用の 2 つのエイリアスを使い分ける仕組み。**機構そのものは正しく動いている** |
| **決定的 ID による集約** | 同じ語なら同じ ID になるので、頻度が自然に足し合わさる。**考え方は残し、作り方だけ直す** |
| **テスト資産** | 本体 64 ファイル / 11,591 行に対し、**テストが 77 ファイル / 15,194 行**。捨てるには惜しい |

この 4 つを捨てないことが、「一気に全部入れ替える」案を採らなかった一番の理由です。

## 困っていること

### 1. 公開している面が大きすぎる

入口が `Suggester`（507 行・public 約 18）と `SuggestIndexer`（547 行・public 約 30）の 2 つの巨大クラスに集約されており、**利用者から見て「どれを呼べばいいか」が分かりません**。しかも OpenSearch の型（`QueryBuilder` など）がそのまま公開面に出ているので、ストレージを差し替える余地もありません。

### 2. 同じことを決める場所が 2 つ以上ある

- **マージ規則が二重実装**されており、しかも「何語あるか」の数え方が場所によって違う。条件が揃うと**読み仮名フィールドが静かに消えます**。
- **NG ワードの判定が 2 系統**。取り込み時は Java の `contains`、削除時は OpenSearch の `wildcard`。後者は `*` や `?` をエスケープしていないため、**NG ワードに記号が混ざると意図しない範囲まで一致します**。
- **権限フィルタが二重担保**。ライブラリ側とアプリ側の両方でロールを足している。

### 3. 書いているのに誰も読んでいないデータがある

登録時に `score = (queryFreq + docFreq) * userBoost` を計算して保存していますが、**検索・人気語・ソートのどこからも参照されていません**。ランキングは実際には検索時の function score だけで決まっています。読まないものを書き続けているだけでなく、「スコアの源が 2 つあるように見える」という誤解も生んでいます。

### 4. 性能上の明らかなムダ

- **書き込みが 1 件ずつの同期 Get**。N 件登録すると N 回の Get が直列に走ります（multiGet ですらない）。
- **バッチごとに refresh を同期発行**しています。1 バッチの既定が **2 件**なので、**100 万ドキュメントで 50 万回の refresh**。性能上の主因は「バッチが小さいこと」より、こちらでした。
- **シャード数が 1 に固定**されていて、fess 本体から上書きできません（2018 年に 5 → 1 へ意図的に下げられたまま 8 年放置）。ついでに `number_of_replicas: 0` は隣に書かれた `auto_expand_replicas` に負けて**一度も効いていない死蔵設定**でした。

### 5. ID の作り方が壊れている

ドキュメント ID は「`text` を Base64 して 445 文字で切る」形です。ここに 3 つ問題があります。

1. 約 334 バイトを超える語は**切り詰められる**
2. 445 は 4 の倍数でないので、**Base64 として不正な位置で切れる**
3. 結果として、**先頭が同じ長文どうしが同じ ID に衝突する**

さらに ID の材料が `text` だけなので、同じ語の DOCUMENT / QUERY / USER が 1 つのドキュメントに合流し、**管理画面で設定した `userBoost` が通常の取り込みで上書きされて消えます**。

### 6. NG ワードを消しても元に戻せない

NG ワードを「適用」すると `*ワード*` の wildcard で**物理削除**します。あとから NG ワードを取り消しても、消えた語は戻りません。

> ※ 実は **fess 本体からこの物理削除は発火していません**。管理画面も API もすべて「適用しない」で呼んでおり、唯一の適用箇所は再構築直後の空インデックスに対してなので実質何もしません。実害があるのは、ライブラリを直接使って稼働中インデックスに適用している利用者だけです。

### 7. 再構築の切り替えにガードがない

ここが**一番怖いところ**です。fess 側の再構築処理は次のようになっています。

| 起きること | 実際の挙動 |
| --- | --- |
| 取り込みが失敗した | エラーコードを立てるだけで**処理は続行** |
| 切り替え | **エラーコードを見ずに無条件で検索エイリアスを切り替える** |
| 切り替え直後 | **エイリアスの付いていない旧インデックスを即座に物理削除** |
| 検証 | **存在しない**。合格条件は事実上「例外を出さずに完走したこと」だけ |
| ジョブの記録 | 失敗の例外が握り潰され、**ジョブログには `OK` が残る** |

つまり **0 件のインデックスでも公開されうるうえ、その瞬間に戻り先も消えており、ログ上は成功に見えます**。

**ただし、二重エイリアスの仕組み自体は正しく動いています。** エイリアスの付け替えは 1 リクエストにまとめられていて原子的です。**壊れているのは、それを呼び出す側の制御フロー**。この切り分けが今回の移行設計の中核です。

## 設計の指針（7 原則）

上の課題を個別に潰すのではなく、次の 7 原則で構造的に消す方針を採っています。

1. **公開 API 最小化** — 用途別の小さなインタフェースにする
2. **拡張点ファースト** — ソース・スコアリング・テキスト処理を最初から差し替え可能に
3. **単一の真実** — マージ規則・ランキング源・権限フィルタを 1 箇所に
4. **死蔵を持たない** — 書くなら読む、読まないなら書かない
5. **バルク効率優先** — 1 件ずつの同期往復を基本にしない
6. **一貫した同期 / 非同期境界** — 標準機構に統一する
7. **価値ある資産は踏襲** — 全置換ではない
