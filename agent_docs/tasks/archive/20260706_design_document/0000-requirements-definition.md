# 20260706_design_document

## 要件

fess-suggest改善の設計書を作成する。
改善案は `agent_docs/tasks/20260706_desighn_document/docs/improvement-proposal.md` を参照。

## 設計書
- インターフェース・API設計書の作成
  - 肥大化している Suggester や SuggestIndexer をどのように分割するか（Lifecycle, Query, WordAdmin, Ingestなど）、各インターフェースとメソッドのシグネチャを設計する。
- データモデルとインデックス移行設計書の作成
  - 重複しているマージ規則の単一化仕様。
  - 二重エイリアスを活用した、ゼロダウンタイムでの新旧インデックス移行・切り替え手順の設計。

## アウトプット

設計書は`./docs/` 配下に出力する。

## 設計書構成

提案書の設計対象(Phase 1a+1b完全設計+例外のMIG-13/16/17)は自然に4文書に分かれます。

docs/
 ├─ 0000-design-overview.md          … 索引・前提・カバレッジ表(小さく保つ)
 ├─ 0001-api-design.md               … 公開契約: api/spi の全シグネチャ
 ├─ 0002-datamodel-design.md         … データの形: mapping とマージ規則
 └─ 0003-migration-ops-design.md     … 移行の手順: エイリアス運用と切替

0000(索引) には、全MIG→設計書の対応表(設計対象外のMIGは「対象外・理由」を明記)、提案書の[確定]事項のスナップショット(§5.2の結論だけを転記し、根拠は提案書へのリンクに留める)、共通凡例を置きます。これが「巨大な提案書を毎回読まずに済む」ための緩衝材で、エージェントに設計書を書かせる/読ませるときの入口をここに固定できます。

0001(API設計) — 一緒に決めないと矛盾する集合その1「公開契約」。4インタフェース(Query/Lifecycle/WordAdmin/Ingest)のシグネチャ、spi(SuggestSource / ScoringStrategy / SuggestItemMergePolicy / BadWordPolicy)、非同期・例外契約(CompletableFuture統一・Result型なし・CompletionExceptionラップ)、そして申し送りの apply引数の最終形の決定。旧公開メソッド→新IFの対応表(廃止理由付き)もここです。シグネチャと非同期契約とapplyの運命は全部「メソッドの形」の話なので、同一文書でないとレビューできません。

0002(データモデル設計) — 集合その2「データの形」。To-Be mapping(score廃止・excluded追加・死蔵number_of_replicas削除を1つのmapping定義に統合)、マージ規則の単一化仕様(ISS-05修正込みの走査基準、SuggestItemMergePolicyの挙動定義)、決定的ID・realtime get前提の明文化と回帰テスト仕様。スキーマとマージ規則は「1文書=1つの正」にする価値が最も高い部分です。

0003(移行運用設計) — 集合その3「動かし方」。二重エイリアスでの新旧切替手順、フェーズ内スキーマ変更を1回の再構築に束ねるルール、否定形フィルタルール、ロールバック手順、refresh戦略(MIG-16、refresh_interval=-1定石含む)、シャード/レプリカ設定の受け渡し(MIG-17)。0002が「静的な形」、0003が「その形へ無停止で到達する手順」という分担で、変更のリズムも異なります(mappingは滅多に変わらない、手順はリリース経験で更新される)。

当初のタスク要件は2文書(API+データモデル/移行)でしたが、データモデルと移行手順を分けたのは、混ぜるとexcludedのmapping定義とエイリアス切替手順のように抽象度の違う話が交互に出て、提案書と同じ「参照しづらさ」を設計書で再生産するためです。逆にこれ以上細かく(例えばbad word設計を独立文書に)すると、BadWordPolicyのシグネチャ(0001)・excludedのmapping(0002)・共存期フィルタ(0003)に散っている話を第4の文書がまた束ね直すことになり、重複が増えます。

運用ルールを2つだけ添えると: (1) 各設計書の冒頭に「対象MIG/消化する申し送り/依存する[確定]番号」を宣言する——これで提案書側の申し送り(apply、realtime回帰テスト、refresh_interval定石)がどこに着地したか機械的に検査できます。(2) 提案書の内容を設計書に転記しない——根拠・経緯は提案書とその付録に一本化し、設計書は結論と仕様だけを書く。設計書が肥大する最大の原因は根拠の重複転記なので、これを守れば各文書は提案書の1/5程度に収まるはずです。
