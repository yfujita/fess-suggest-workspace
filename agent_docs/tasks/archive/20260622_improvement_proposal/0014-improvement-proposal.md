## 1. エグゼクティブサマリ

### 1.1 提案の狙い

fess-suggest は10年以上機能が据え置かれ（種別 DOCUMENT/QUERY/USER の3種・データソース4経路）、保守運用に高度な Java スキルを要し、サジェスト品質も「悪くはないが良いとも言えない」状態にある（`0000`）。本提案は、要件定義の5目的（**可読性 / 変更容易性 / サジェスト品質 / 性能 / 新機能**）を検討軸に、**既存構成にとらわれずゼロベースで「あるべき姿（To-Be アーキテクチャ）」を設計し、そこへ現実的に到達する移行ロードマップ**を示す。

### 1.2 中心となる設計思想（7原則 — `0005` §1）

ゼロベース設計を貫く North Star は次の7原則であり、各原則が複数の現行課題（ISS）を構造的に解消する。

1. **公開 API 最小化**（用途別の小さなインタフェース）— ISS-13/17 回避
2. **拡張点ファースト**（サジェストソース・スコアリング・テキスト処理を最初から差し替え可能に）— ISS-01/11/12 回避、新機能の土台
3. **単一の真実**（マージ規則・ランキング源・権限フィルタを一箇所に）— ISS-05/06/14 回避
4. **死蔵コード・死蔵データを持たない**（書くなら読む、読まないなら書かない）— ISS-01/14/16/17 回避
5. **バルク効率優先**（1件ずつの同期往復を基本にしない）— ISS-08/10 回避
6. **一貫した同期/非同期境界**（標準機構へ統一）— ISS-09 回避
7. **流用価値ある資産は踏襲**（全置換ではない）— KEEP-01〜04

要点は **縦の分離**（Consumer → 用途別 API → Domain Core → Storage、Storage は `SuggestStore` 抽象で隔離）と **横の拡張点**（サジェストソース / スコアリング / テキスト処理を差し替え可能に並置し、新機能をここに載せる）。

### 1.4 推奨ロードマップの要約（`0013` §3/§7）

- **移行戦略は「段階的移行（Strangler Fig）」を推奨** [提案]。一括リプレース（Big-Bang）は、流用価値の高いテスト資産（main 64ファイル/11,591行 vs **test 77ファイル/15,194行**）・テキスト処理パイプライン・二重エイリアス再構築・決定的 ID 集約（KEEP-01〜04）を捨てるリスクが大きく、fess 本体連携を一斉破壊する。段階的移行は既存資産をセーフティネットに、互換破壊を MIG 単位で分散できる。**ただしスキーマ変更系は「新世代インデックスを並行構築し二重エイリアスで切替」する部分的並行構築を併用する**。
- **4フェーズに分割**（メジャー/マイナーのリリース節目に割り当て）:
  - **Phase 1 基盤**（可読性・変更容易性）: 用途別 API 分離・拡張点抽象・単一規則・標準並行モデル。**以降の全フェーズが載る土台**。
  - **Phase 2 品質**: bad word 論理削除・ドライラン、人気語カバレッジ拡張。
  - **Phase 3 性能**: 書き込み bulk 化、バルク件数適正化、シャード/レプリカ可変化。
  - **Phase 4 新機能**: 蓄積属性 UI・同義語/関連語・トレンド・fuzzy・パーソナライズ・多言語・（条件付き）セマンティック。
- **クイックウィン（フェーズ計画を待たず先行着手推奨）**: **MIG-03（bad word の term 完全一致化）が最優先**。唯一の「中〜高」重大度（`0002`）で、**不可逆な誤削除**を局所変更・依存なし・スキーマ変更なしで解消できる。

## 2. 現状と課題の整理

### 2.1 アーキテクチャの現状サマリ（改善に効く事実、`0002` §3）

- **エントリポイントは2つの肥大ファサード** [事実]: `Suggester`（507行/public 約18）と `SuggestIndexer`（547行/public 約28）。Indexer は4 Operations へ委譲する構造は保つが、**公開 API 表面積**が課題（ISS-13、`0003` §3.1）。
- **テキスト処理パイプラインは良好** [事実]: Normalizer(Chain)→ReadingConverter(Chain)→SuggestAnalyzer の Strategy+Composite 構成（計約1,369行）。責務分割が良好で専用テストも手厚い（踏襲資産＝KEEP-01）。
- **データソースは4経路**（うち②クエリログは fess 本体未使用のデッドパス）[事実]。同義語は独立ソースでなくアナライザ任せ。
- **ランキングは検索時 function score 単系統** [事実]: 登録時 `score=(queryFreq+docFreq)*userBoost` を事前計算するが、検索・人気語・ソートのいずれからも**参照されない死蔵フィールド**（ISS-14/16、`0003` §2）。
- **書き込みは Get-then-update** [事実]: N件登録で **N回同期 Get + 1回 bulk**（multiGet ですらない、`SuggestIndexWriter.java:54-55`）。
- **ゼロダウンタイム再構築は良好** [事実]: 二重エイリアス（検索/更新）＋物理 `{base}.{timestamp}`、決定的 ID（`createSuggestTextId`）による頻度集約（踏襲資産＝KEEP-02/03）。
- **全体評価** [事実/所感]: 重大度「高」と断定できる課題は0件、「中」が大半。**アーキテクチャは健全で、改善は段階的に行える**（`0002` §4.2）。

### 3.7 補論: Google 検索サジェストとの比較（`0012`）

外部ベンチマーク（Google）との三者比較（As-Is / To-Be / Google）から、品質・新機能の打ち手を**外部視点で再照射**する。**「Google に追いつく」ことは目的化せず**、fess（限定コーパス・エンタープライズ）の文脈で価値のある差に絞る。Google の記述はすべて [推測]（内部実装は非公開）。

**劣る軸と劣らない軸の特定**（`0012` §2）:

| 軸 | 評価 | 打ち手の所在（再掲せず参照） |
| --- | --- | --- |
| G1 プレフィックス/低レイテンシ | **ほぼ劣らない**（本質は達成済み。差は分散規模） | — |
| G2 タイプミス/fuzzy | **劣る** | §3.5 fuzzy（E4/E3/E2） |
| G3 トレンド/鮮度 | **部分的に劣る**（社内鮮度は埋める） | §3.5 トレンド／§3.3 人気語条件 |
| G4 パーソナライズ | **劣る**（ロール文脈は埋める） | §3.5 パーソナライズ |
| G5 関連クエリ/ロングテール | **劣る** | §3.5 同義語/関連語（E1） |
| G6 多言語/かな/ローマ字 | **日本語は強い／非日本語は限定的に劣る** | §3.5 多言語（E4） |
| G7 セマンティック/意図理解 | **大きく劣る**（条件付きで埋める） | §3.5 セマンティック [要確認 TBD-01] |
| G8 安全性フィルタ | **機構の質で劣る（誤削除）／機密抑制は逆方向の優位** | §3.3 bad word（§9.3） |

**3-7 固有の成果（`0012` §4）**:

- **埋めるべき差／不要な差の切り分け**: 全世界トレンド・地域/個人追跡・全行動ログ・全言語網羅・汎用意図理解・公共安全ポリシーは **fess 文脈で不要・非現実的**（Google の大規模独自データ・プロプライエタリ前提依存）。**社内鮮度・ロール文脈・自組織共起・専門語言い換え（条件付き）・誤削除排除が埋めるべき差**。
- **逆方向の差（Google にない fess 固有の価値）**: 権限フィルタ（roles）・機密語抑制・限定コーパスゆえの高精度・決定的 ID 集約。**打ち手はこれらを損なわない前提**（`AuthorizationFilter` のデフォルト deny を維持）。
- **外部比較から見た優先度示唆**: 高＝G8 誤削除排除・G2 タイプミス・G5 同義語・G4 ロール文脈・G3 社内鮮度（UX 直撃・難易度中以下・TBD 依存小）。低＝G7 セマンティック（高難度・TBD-01 依存）。
- すべての打ち手が **3-1 の拡張点 E1〜E5 に載る**（外部比較起点でも共通機構に手を入れない）。

### 4.5 依存関係の循環チェック結論（完了条件）

ハード依存（H）のみでグラフ化し、層に分割（`0013` §6）:

- **層0（前提なし）**: MIG-01,02,03,04,05,06,07,08,10,12,16,17,18
- **層1**: MIG-11(←02,04), MIG-15(←01), MIG-13(←03), MIG-09(←06)
