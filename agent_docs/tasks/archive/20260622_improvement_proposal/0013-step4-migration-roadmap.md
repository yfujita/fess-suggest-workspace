## 0. 本ドキュメントの位置づけ・前提・読み方

### 0.1 位置づけ

本ドキュメントは、fess-suggest 抜本的改善提案タスク（`20260622_improvement_proposal`）の **ステップ4「既存からの移行戦略・優先度付けとロードマップ化」** の成果物である。

- **スコープ**: 提案・文書化であり**実装ではない**。コード変更は一切しない。**優先度・順序は提案であり、最終判断はユーザーに委ねる**（判断材料＝根拠の提示を重視する）。

## 1. ステップ4の枠組み（移行単位の定義方法）

### 1.1 移行単位（MIG）の切り出し方

ステップ3-1（`0005`）のレイヤ設計（§3〜§10）と、3-6/3-7 の新機能（拡張点 E1〜E5）を、**「独立してリリース可能な最小の構造変更」** の粒度で移行単位 MIG-xx に分解する。切り出しの原則は次の3点。

1. **スキーマ変更の有無で割る**: インデックスの mapping を変える単位（再構築を伴う）と、コード内に閉じる単位（再構築不要）を分ける。再構築を伴う単位は「再構築サイクルに束ねて切り替える」運用上の都合があるため、独立に識別する。
2. **影響モジュールで割る**: fess-suggest 内部に閉じる単位と、fess 本体（`modules/fess`）の API 互換に波及する単位を分ける（作業プラン必須の「fess-suggest／fess 本体の区別」）。
3. **拡張点 vs 拡張点に載るもの で割る**: 拡張点そのものの新設（例: `SuggestSource` 抽象＝MIG-07、`ScoringStrategy` 抽象＝MIG-11）と、その拡張点に載る新機能（同義語＝MIG-19、セマンティック＝MIG-24 等）を分ける。後者は前者に依存する。

### 1.2 各移行単位に付与する属性（作業プラン準拠）

| 属性 | 意味 |
| --- | --- |
| **期待インパクト（高/中/低）** | 要件5目的（可読性・変更容易性・品質・性能・新機能）への寄与の大きさ |
| **実現コスト（高/中/低）** | 変更規模・テスト整備・連携調整を含む実装コスト |
| **リスク** | 後方互換破壊・データ移行・誤動作・TBD 依存等のリスク |
| **依存関係** | 前提となる他 MIG（**ハード**=必須前提／**ソフト**=推奨順序・効率上の前後関係） |
| **スキーマ変更** | インデックス mapping 変更＝**再構築要否**（二重エイリアスでゼロダウンタイム切替可能） |
| **fess 本体 API 互換** | fess 本体（`modules/fess`）側の改修を伴うか |

### 1.3 踏襲（移行不要）資産の明示 — KEEP

ゼロベース＝全置換ではない（`0005` 原則7 / §11）。以下は **「あるべき姿でも踏襲・再利用し、移行コストをかけない資産」** であり、移行単位から除外する（過剰設計の回避）。

| ID | 踏襲資産 | 根拠 [事実] | 移行上の扱い |
| --- | --- | --- | --- |
| **KEEP-01** | テキスト処理パイプライン本体（converter/normalizer/analysis、Strategy+Composite） | 計約1,369行・責務分割良好・専用テスト手厚い（`0003` §3.1/§3.2, `0005` §5） | 全置換しない。`TextProcessor` 抽象としての**明文化のみ**を MIG-12 で軽く行う |
| **KEEP-02** | 二重エイリアス ゼロダウンタイム再構築（検索/更新エイリアス、物理 `{base}.{timestamp}`） | `legacy/02`, `0005` §6.2.3 | **そのまま踏襲**。むしろスキーマ変更系 MIG の移行手段として活用（§8.1） |
| **KEEP-03** | 決定的 ID（`createSuggestTextId`）による頻度集約 | `legacy/02`, `0005` §6/§11 | 集約の基盤として踏襲。集約の**実行方式**のみ MIG-15 で改善 |
| **KEEP-04** | 「検索＝非同期」の思想 | `legacy/01`/`02`, `0005` §8 | 思想は踏襲。MIG-08 で変えるのは「不均一さ」であって「非同期であること」ではない |

## 3. 移行戦略の検討（一括リプレース vs 段階的移行）

### 3.1 二つの移行戦略

ゼロベース再実装を現実に到達させる経路として、二つの戦略を比較する。

#### 戦略A: 一括リプレース（Big-Bang Rewrite）

- **内容**: fess-suggest を新アーキテクチャで作り直し、旧ライブラリを丸ごと差し替える。新インデックスを並行構築し、一斉に切替。
- **メリット**: To-Be のゴール状態に最短で到達。過渡期の「旧構造と新構造の併存」（三層併存等）が発生しない。設計の純度が高い。
- **デメリット/リスク**:
  - **テスト資産（test 77ファイル/15,194行）の再利用が困難化**しやすい。全面書き直しは既存テストの前提（公開 API・クラス構造）を崩し、回帰検知の土台を一時的に失う。
  - **fess 本体連携の一斉破壊**。`SuggestHelper`/`SuggestWordsHandler`/`SuggestCreator` 等が同時に動かなくなり、fess 本体の大規模同時改修が必須。リリースが「全部できるまで何も出せない」一括投入になり、リスクが集中する。
  - 切替失敗時のロールバック範囲が大きい。

#### 戦略B: 段階的移行（Strangler Fig＝あるべき姿に向けた漸進）【推奨】

- **内容**: ステップ3 で各設計判断に併記された **「(c) 漸進案」を移行経路として使い**、既存資産（テスト群・テキスト処理・二重エイリアス）を活かしながら、移行単位 MIG をフェーズに分けて順次 To-Be へ寄せる。各 MIG は独立リリース可能な最小単位とし、内部実装を公開 API 契約を保ったまま差し替える（`internal` 化が効く）。
- **メリット**:
  - **既存テスト群をセーフティネットとして温存**しながら回帰を抑えて進められる（`0008` §4 のテスト容易性）。
  - **fess 本体への影響を MIG 単位で局所化・段階化**でき、互換破壊を一度に集中させない。
  - 各フェーズで価値を**逐次リリース**できる（誤削除排除のようなクイックウィンは早期に届く）。
  - スキーマ変更は既存の再構築機構（KEEP-02）に束ねて切替できる。
- **デメリット/リスク**:
  - 移行過渡期に「旧構造と新構造の併存」（例: 用途別 IF と旧ファサードの三層併存、`0005` §3.3(c)/`0008` §2.1(c)）が一時的に発生し、その期間は読む面・変更面が増える。
  - ゴール到達までの総期間は長くなりうる。漸進案にとどまり「ゼロベースの純度」に届かない単位が残る恐れがある（各 MIG で「漸進で十分か／ゼロベースまで踏み込むか」を都度判断する必要）。

### 3.2 推奨：戦略B（段階的移行）＋ 部分的な並行構築 [提案]

**本書は戦略B（段階的移行）を推奨する。** 根拠は次の通り。

1. **既存資産の価値が高い**: テスト群（test/main 比 >1）・テキスト処理パイプライン・二重エイリアス再構築・決定的 ID 集約は、ゼロベースでも踏襲すべき良好な資産（KEEP-01〜04, `0005` §11）。一括リプレースはこれらを捨てるリスクが大きく、過剰設計の典型（`0005` 原則7）に陥る。
2. **ステップ3 が移行経路を用意済み**: 各設計判断に「漸進案との対比」が併記されており（`0005`/`0006`/`0008` 等の各 (c)）、**段階的移行の経路が設計段階で既に検証されている**。多くの ISS は「漸進でゴールに到達しやすい」と評価されている（例: ISS-05/14/16/04 の核心、`0009`/`0006`）。
3. **メジャーバージョンアップは複数フェーズで分割リリース可能**: 「メジャーバージョンアップ級」は一度の一括投入である必要はなく、**フェーズ境界をメジャー/マイナーのリリース節目に割り当てる**ことで、抜本的改善を段階的に届けられる。
4. **リスク分散**: fess 本体連携の互換破壊（MIG-06/08/09/10）を各フェーズに分散し、一度に集中させない。

ただし、**スキーマ変更系と新インデックス構造（特に新機能のベクトル/時系列フィールド）は「新世代インデックスを並行構築して二重エイリアスで切替」という部分的な並行構築（KEEP-02 の活用）を併用する**（戦略Aの良い面の限定採用）。これにより「段階的移行」と「スキーマ刷新」を両立する。

> **両論を残す（最終判断はユーザー）**: もし「15.x 系の保守をやめ、別ライブラリ名で 2.0 を新規開発し、fess 本体側も次期メジャーで一斉に乗り換える」という製品戦略上の判断があるなら、戦略A（一括リプレース）も合理的になりうる。その場合でも KEEP-01〜04 の資産（テスト・テキスト処理・再構築機構）は**新実装へ移植して再利用**すべきで、ゼロから書き直す対象ではない。**戦略選択は技術判断だけでなくリリース・サポート方針に依存するため、最終判断はユーザーに委ねる。**

### 3.3 後方互換の3軸（移行コストの主要因）

## 6. 依存関係グラフと循環チェック（完了条件）

### 6.1 ハード依存グラフ（必須前提のみ）

ソフト依存（推奨順序）を除き、**ハード依存（H）のみ**でグラフを描く。矢印 `A → B` は「B は A を前提とする（A が先）」を表す。

```
（基盤・独立な起点：依存なし）
  MIG-01  MIG-02  MIG-03  MIG-04  MIG-05  MIG-10  MIG-12  MIG-16  MIG-17  MIG-06※
    │       │       │       │
    │       └───┐   │       │
    ▼           ▼   ▼       ▼
  MIG-15      MIG-11 ◄───────┘        MIG-03 ──► MIG-13
 (H:01)      (H:02, H:04)
                │
     ┌──────────┼───────────┬───────────┬──────────┐
     ▼          ▼           ▼           ▼          ▼
  MIG-14     MIG-19      MIG-20      MIG-21     MIG-24
 (H:11)     (H:07,11)   (H:07,11)   (H:11)     (H:07,11)

  MIG-07 ──► MIG-19, MIG-20, MIG-24   （H:07）
  MIG-06 ──► MIG-09                    （H:06）※MIG-06 自身は MIG-05 にソフト依存
  MIG-09, MIG-11 ──► MIG-22            （H:09, H:11）
  MIG-12 ──► MIG-23                    （H:12）
```

ハード依存を一覧化すると:

| MIG | ハード依存（前提） |
| --- | --- |
| MIG-11 | MIG-02, MIG-04 |
| MIG-15 | MIG-01 |
| MIG-13 | MIG-03 |
| MIG-09 | MIG-06 |
| MIG-14 | MIG-11 |
| MIG-19 | MIG-07, MIG-11 |
| MIG-20 | MIG-07, MIG-11 |
| MIG-21 | MIG-11 |
| MIG-22 | MIG-09, MIG-11 |
| MIG-23 | MIG-12 |
| MIG-24 | MIG-07, MIG-11 |
| MIG-01/02/03/04/05/06/07/08/10/12/16/17/18 | （ハード依存なし。起点またはソフト依存のみ） |

### 6.2 循環チェック結果

- **トポロジカル順序が存在することの確認**: 上の依存を層に分けると、
  - **層0（前提なし）**: MIG-01, 02, 03, 04, 05, 06, 07, 08, 10, 12, 16, 17, 18
  - **層1**: MIG-11（←02,04）, MIG-15（←01）, MIG-13（←03）, MIG-09（←06）
  - **層2**: MIG-14（←11）, MIG-19（←07,11）, MIG-20（←07,11）, MIG-21（←11）, MIG-22（←09,11）, MIG-23（←12）, MIG-24（←07,11）
  - すべての依存が「下位層 → 上位層」へのみ向き、**逆向き・同層内循環は存在しない**。
- **結論: ハード依存グラフは DAG（有向非巡回グラフ）であり、循環は存在しない。** ソフト依存（MIG-05→06, 06→08, 07→14, 12→21, 06→18/22, 17→20/24）も同様にフェーズ前→後ろへ向く一方向であり、循環を生まない。
- **矛盾チェック**: ある MIG が「自分より後のフェーズの単位を前提とする」逆転依存は存在しない（Phase4 の新機能はすべて Phase1 の拡張点 MIG-07/11/12 と Phase1 の API/権限 MIG-06/09 を前提とし、その逆はない）。**依存関係に矛盾はない。**

## 7. フェーズ別ロードマップ [提案]

「メジャーバージョンアップ」の単位として4フェーズに分ける。各フェーズは独立にリリース可能で、フェーズ境界をメジャー/マイナーのリリース節目に割り当てる。**フェーズ内のスキーマ変更は1回の再構築（KEEP-02）に束ねる**。

### Phase 1: 基盤の作り直し（可読性・変更容易性）

- **目的**: ゼロベース構造の骨格（用途別 API・拡張点抽象・単一規則・標準並行モデル）を据え、以降のフェーズが載る土台を作る。要件目的①②を中心に達成。
- **含む MIG**: MIG-01, 02, 03, 04, 05, 06, 07, 08, 09, 10, 11, 12（＋クイックウィンの MIG-03/04/05/16 は先行着手可）
- **成果物**:
  - 用途別4公開 IF（Lifecycle/Query/WordAdmin/Ingest）＋ internal 化（MIG-06）
  - `SuggestSource` 抽象・デッドパス排除（MIG-07）／`ScoringStrategy` 抽象（MIG-11）／`TextProcessor` 明文化（MIG-12）＝**新機能の拡張点が出揃う**
  - 単一マージ規則（MIG-01）／死蔵 score 廃止・ランキング単系統（MIG-02）／権限一元化（MIG-09）／`CompletableFuture` 統一（MIG-08）
  - bad word term 一致（MIG-03）・boost 連続値化（MIG-04）・シム除去（MIG-05）・設定型化（MIG-10）
- **前提依存**: なし（最初のフェーズ）。fess 本体の対応改修（MIG-06/08/09/10）を同期リリース。
- **スキーマ変更**: MIG-02（score 廃止）の1点。**この再構築に Phase 1 のスキーマ変更を集約**。
- **リスクと手当て**: fess 本体 API 互換破壊が集中するフェーズ。漸進案（旧 API 委譲シムを過渡的に残す）で互換を保ちつつ内部先行移行。fess 連携部のテスト補強を MIG-06/09 に含める。

### Phase 2: 品質の作り込み

- **目的**: Phase 1 の単一規則・単系統スコア・拡張点の上で、品質（要件目的③）を作り込む。
- **含む MIG**: MIG-13（bad word 論理削除・ドライラン）, MIG-14（人気語条件の調整可能化）
- **成果物**: 誤削除の可逆化＋事前可視化（ドライラン UI）、人気語カバレッジの拡張、集約正確性の検証（MIG-01 を活かす）。
- **前提依存**: MIG-03（→MIG-13）, MIG-11/07（→MIG-14）＝**Phase 1 完了が前提**。
- **スキーマ変更**: MIG-13（`excluded` フラグ）。Phase 2 の再構築に束ねる。

### Phase 3: 性能の最適化

- **目的**: 書き込み・集約・スケールの性能（要件目的④）を最適化。
- **含む MIG**: MIG-15（書き込み bulk 化）, MIG-16（バルク件数）, MIG-17（シャード/レプリカ可変）
- **成果物**: Get-then-update の往復線形コスト解消（`scripted_upsert`/multiGet）、再構築スループット向上、規模に応じた水平拡張余地。

## 8. 後方互換・移行コストの横断論点

### 8.1 スキーマ変更を既存再構築機構に束ねる（最大のコスト低減策）[提案]

- **[事実]** 現行は毎日12:00 に `SuggestCreator`（別 JVM）が全件再構築し、二重エイリアス（KEEP-02）でゼロダウンタイム切替している（`legacy/04` 4.1/4.6, `0005` §6.2.3）。
- **[提案]** スキーマ変更系（MIG-02, 13, 17, 20, 21, 24）は、**新スキーマで新世代インデックスを構築 → 再構築完了後にエイリアス切替**という既存フローに乗せれば、**再構築機構を新規開発せずにスキーマ移行できる**。これが「インデックススキーマ変更時の再構築」コスト（作業プラン明示の論点）を大きく下げる。
- **束ね戦略**: 同一フェーズ内のスキーマ変更は**1回の再構築に集約**し、再インデックス回数を最小化する（Phase 1=score 廃止、Phase 2=excluded、Phase 3=シャード、Phase 4=時系列/fuzzy/ベクトル）。

### 8.2 fess 本体 API 互換の段階化 [提案]

- fess 本体に波及する MIG-06/08/09/10/18/22 は、fess-suggest メジャーバージョンで破壊的変更を許容しつつ、**fess 本体側の対応 PR を同期リリース**する。
- 過渡期は漸進案（`0005` 各 (c)）の「旧 API を委譲で残し段階削除」を使い、**内部実装を先行移行しても fess 本体が動き続ける**状態を保つ。これにより一括破壊を避ける。
- **[要確認]** MIG-08（独自 `Promise` → `CompletableFuture`）と MIG-10（設定の `Duration` 化）は、fess 本体側の依存・設定基盤（Lasta Config）の対応可否に依存（`0008` §7.1）。互換影響の確定は連携部の確認が前提。

### 8.3 テスト資産の再利用と補強 [事実＋提案]

- **[事実]** fess-suggest 単体はテストが手厚く（test 77/15,194行）、マージ両クラス・テキスト処理・クエリ構築・設定に専用テストがある（`0003` §3.2）。ライブラリ内リファクタリング（MIG-01/02/07/11/15 等）は**回帰を抑えて進められる**。
- **[事実/推測]** 一方、**fess 連携部（`SuggestWordsHandler`/`SuggestHelper`/`RoleQueryHelper`）のテストは手薄な可能性**（`0003` §3.2, `0005` §10.2）。
- **[提案]** MIG-06（API 再編）・MIG-09（権限再配置）・MIG-18/22（fess 本体 UI/連携）の移行作業に**連携部のテスト補強を必須タスクとして含める**。単一規則化（MIG-01）はマージ両クラスのテストを統合・流用する。
