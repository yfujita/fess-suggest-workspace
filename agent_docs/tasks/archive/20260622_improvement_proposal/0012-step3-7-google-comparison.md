# ステップ3-7: Google 検索サジェストとの比較による差分分析と打ち手の検討

## 0. 本ドキュメントの位置づけ・前提・読み方

### 0.1 位置づけ

本ドキュメントは、fess-suggest 抜本的改善提案タスク（`20260622_improvement_proposal`）の **ステップ3-7「Google 検索サジェストとの比較による差分分析と打ち手の検討」** の成果物である。

- **目的**: 外部ベンチマークとして広く知られる **Google 検索のサジェスト** を比較対象に置き、fess-suggest（現状 As-Is）および本タスクで設計した **あるべき姿（To-Be、3-1 = `0005`）** との差を考察する。fess-suggest／To-Be が劣る軸については、その差を **3-1 のどの拡張点（E1〜E5）に載せて埋めるか** を検討する。
- **3-7 の固有の立場（外部ベンチマーク起点）**: 3-4（品質）が「現行の内部品質課題（ISS/TBD）起点」で、3-6（新機能）が「新機能を設計に内包する立場」で打ち手を導くのに対し、本書 3-7 は **「外部ベンチマーク（Google 検索サジェスト）との比較を起点に、差分（ギャップ）と打ち手を導く」** 位置づけである（役割分担は §5 に明記）。
- **3-7 が新たに生む固有価値**: 比較軸ごとの打ち手の多くは既に 3-4／3-6 が設計済みであり、本書はそれを **再掲せず参照に留める**。3-7 が固有に付加するのは次の4点である。
  1. **「埋めるべき差／fess の文脈では不要・非現実的な差」の切り分け**（§4）。Google の大規模独自データ・プロプライエタリ前提に依存する差を費用対効果で峻別する。これは内部課題起点の 3-4／3-6 が行っていない外部比較固有の三角測量である。
  2. **fess-suggest が劣っていない／むしろ強い軸の明示**（§2 の G1・G6 等）。「Google に追いつく」発想に流されず、サジェストの本質（前方一致・低レイテンシ）と日本語処理ではすでに目的を達していることを確認する。
  3. **逆方向の差（Google にない fess 固有の価値）の明示**（§4.3）。権限フィルタ・機密語抑制・限定コーパスゆえの高精度など、エンタープライズ検索固有の優位を打ち手の前提として残す。
  4. **外部ベンチマークから見た打ち手の優先度の示唆**（§4.2）。どのギャップが UX に効き、どれが単なる規模差かを整理する（優先度の本格化はステップ4）。
- **スコープ**: 提案（設計の検討と文書化）。コード実装・移行戦略そのものは **ステップ4の領分**であり、本書での「漸進案との対比」は対比メモにとどめる。

### 0.5 前提条件の根本差（全比較の土台）

Google 検索サジェストと fess-suggest は、比較する前に **前提条件が根本的に異なる**ことを押さえる必要がある。この前提差が、後述の「埋めるべき差／不要な差」の切り分け（§4）の判断基準そのものになる。

| 観点 | Google 検索サジェスト [推測] | fess-suggest（オンプレ／エンタープライズ） [事実] |
| --- | --- | --- |
| コーパス規模 | Web 全体（ほぼ無限・多言語） | 限定（社内文書・対象サイト）。`suggest.field.index.contents=content,title` 等（`legacy/04` 4.2） |
| クエリログ規模 | 全世界・全ユーザの膨大なログ・トレンド | 限定（自組織の検索ログ）。しかもクエリログ経路はデッドパス（ISS-01） |
| パーソナライズ基盤 | 地域・端末・ログイン履歴の大規模トラッキング | ロール（roles）による可視範囲制御が中心（`legacy/03` 3.5）。個人履歴トラッキングは無し |
| 技術基盤 | プロプライエタリ（独自 ML・専用インフラ・CDN） | OSS（OpenSearch）＋ライブラリ。バージョン依存 API は TBD-01 で要確認 |
| 主な価値 | 一般大衆の意図を当てる網羅性・鮮度 | **限定コーパス内の正確性・権限制御・機密性**（Google にない価値） |

> **本書の基本姿勢**: 「Google に追いつくこと」自体は目的化しない。前提が異なる以上、**すべてを模倣する必要はなく**、fess（限定コーパス・エンタープライズ）の文脈で **価値のある差** に絞って打ち手を導く。Google の大規模独自データ・プロプライエタリ前提に依存する差は、エンタープライズ検索では費用対効果が見合わないものとして §4 で切り分ける。

## 1. 比較軸の整理（Google 検索サジェストの代表的特性 G1〜G8）

作業プラン（`0001` 134-142行）が必須とする比較軸を、Google 検索サジェストの代表的特性として整理する。各軸は **[推測]**（公開された外形的挙動・一般に知られた特性に基づく）として扱う。

| 軸 | 名称 | Google 検索サジェストの代表的特性 [推測] |
| --- | --- | --- |
| **G1** | プレフィックス補完／インクリメンタル性・低レイテンシ | 入力1文字ごとに候補を即時更新。グローバル分散・CDN により体感レイテンシが極小 |
| **G2** | タイプミス補正・あいまい一致（fuzzy） | 綴り誤り（"did you mean"）・編集距離・キーボード配列誤りに頑健。誤入力でも正候補を提示 |
| **G3** | 人気度・トレンド（急上昇）・鮮度（時系列） | 累積人気だけでなく、直近の急上昇・時事性・季節性を反映。リアルタイムに近い鮮度 |
| **G4** | パーソナライズ（履歴・文脈・地域） | 個人の検索履歴・地域・端末・直前クエリ文脈で候補を個別最適化 |
| **G5** | 関連クエリ・ロングテール補完 | 単純なプレフィックス補完を超え、関連クエリ・共起・ロングテール（低頻度語）を補完 |
| **G6** | 多言語・かな/ローマ字・表記ゆれの吸収 | 全言語対応・自動言語判定。表記ゆれ・転写ゆれを広く吸収 |
| **G7** | セマンティック／意図理解 | 表層一致でなく意味・意図で候補を提示（言い換え・概念的近傍） |
| **G8** | 安全性フィルタ（不適切語の抑制） | 不適切語・センシティブカテゴリ・スパム・誤情報を大規模ポリシーで抑制 |

> これら8軸は独立ではなく相互に絡む（例: G2 タイプミス補正が弱いと G1 のインクリメンタル体験も損なう、G5 ロングテールは G3 人気度・G7 セマンティックと連動する）。次節 §2 で三者比較する。

## 2. 三者比較の考察（As-Is／To-Be／Google）

各軸 G1〜G8 について「**fess-suggest 現状（As-Is）／あるべき姿（To-Be、3-1）／Google 検索サジェスト**」を対比し、できていること・劣っていること・前提差を考察する。劣る軸はギャップを明示する。As-Is の事実には出典を付す。

### 2.0 三者比較サマリ表

| 軸 | As-Is [事実] | To-Be（3-1） [提案] | Google [推測] | fess/To-Be は劣るか |
| --- | --- | --- | --- | --- |
| **G1** プレフィックス/低レイテンシ | 前方一致 weight=2.0、検索は非同期、keyword 前提（`legacy/03` 3.4, ISS-09） | 前方一致を `ScoringStrategy` 調整軸化、一貫非同期、低レイテンシ検証は 3-5 最重要論点（§9.2/§8.2） | インクリメンタル＋CDN で体感極小 | **ほぼ劣らない**（本質は達成済み。差は分散規模＝§4(b)） |
| **G2** タイプミス補正/fuzzy | 綴り誤り補正なし。表記ゆれは Normalizer 吸収。keyword 非解析（ISS-04, `0011` §2.4） | fuzzy/edge n-gram を E4/E3/E2 に内包（`0011` §2.4）[要確認] | 強力な did-you-mean | **劣る**（打ち手は 3-6 §2.4） |
| **G3** 人気度/トレンド/鮮度 | 累積 freq のみ・時系列なし・人気語は query/単一語/freq>=10（ISS-12, `legacy/03` 3.4） | 人気急上昇語 E1/E2/E3、人気語条件の調整可能化（`0011` §2.5, `0009` §2.6） | 大規模トレンド・急上昇 | **部分的に劣る**（社内鮮度は埋める／全世界トレンドは§4(b)） |
| **G4** パーソナライズ | 個人履歴なし。roles は可視範囲フィルタのみ（`legacy/03` 3.5, ISS-06） | ロール文脈/履歴パーソナライズ E5/E2/E3（`0011` §2.2） | 地域・履歴で強くパーソナライズ | **劣る**（ロール文脈は埋める／地域・個人追跡は§4(b)） |
| **G5** 関連クエリ/ロングテール | クエリ補完のみ。同義語はアナライザ任せ。クエリログ経路デッドパス（ISS-01, `legacy/03` 3.2） | 同義語/関連語ソース E1（`0011` §2.1） | 関連クエリ・共起・ロングテール | **劣る**（共起関連語は埋める／全行動ログ規模は§4(b)） |
| **G6** 多言語/かな/ローマ字/表記ゆれ | 日本語特化で表記ゆれ・かな/ローマ字吸収は良好（踏襲資産、`0005` §5.1, `0009` §2.8） | 言語別 Chain で多言語強化 E4（`0011` §2.6） | 全言語・自動判定 | **日本語は劣らず強い／非日本語多言語は限定的に劣る**（§4 で限定） |
| **G7** セマンティック/意図理解 | 意味的近傍なし。前方一致＋読み変換のみ（`0011` §2.3） | SemanticSource E1/E3/E2（`0011` §2.3）[要確認 TBD-01] | 大規模意図理解 | **大きく劣る**（打ち手は 3-6 §2.3／条件付きで埋める・TBD-01） |
| **G8** 安全性フィルタ | bad word 機構あり。ただし `*badword*` 部分一致で誤削除・不可逆（ISS-04） | term 完全一致化・論理削除・ドライラン（`0009` §2.3, `0005` §9.3） | 大規模安全性ポリシー | **機構の質で劣る（誤削除）／公共安全ポリシーは§4(b)・機密抑制は逆方向の優位** |

以下、各軸の考察。打ち手の詳細は §3、切り分けは §4 に送り、本節は **三者差分の考察** に集中する。

### 2.1 G1: プレフィックス補完／インクリメンタル性・低レイテンシ — ほぼ劣らない軸

- **As-Is [事実]**: fess-suggest はそもそも前方一致サジェストを主目的とする。前方一致は function score の `weightFactorFunction(prefixMatchWeight)`（既定2.0）でランキング優遇され（`legacy/03` 3.4）、検索は常に非同期で UI レスポンス性を確保（ISS-09, `legacy/01`）。`text` は keyword でプレフィックスマッチに適する（`mappings-default.json:48-50`）。`refresh_interval=10s`（`suggest.json`）。
- **To-Be [提案]**: 前方一致 weight を `ScoringStrategy`（§9.2）の調整軸として明示化、同期/非同期を `CompletableFuture` で一貫化（§8.2）。サジェスト特有の低レイテンシ・高 QPS をレイテンシ要件として明示し、その定量検証を **3-5 の最重要論点**として送る（`0005` §9.2 302行）。
- **Google [推測]**: 入力1文字ごとのインクリメンタル更新。グローバル分散・CDN により体感レイテンシが極小。
- **考察（前提差）**: **サジェストの本質（前方一致を低レイテンシで返す）という核心において、fess-suggest はすでに目的を達成している。** Google との差は「全世界規模の分散・CDN による体感速度」であり、これはコーパス・トラフィック規模の差であって機能の差ではない。エンタープライズの想定 QPS では単一〜少数シャードでも要件を満たしうる（ISS-07/TBD-05 は規模拡張余地の問題であって、現状の体感速度が劣る根拠ではない）。**この軸は「Google に追いつく」対象ではなく、すでに同等の体験を提供できている軸**として明示する。劣るとすれば「大規模 QPS でのスケール上限」だが、それは §4(b) の規模差に分類される。

### 2.2 G2: タイプミス補正・あいまい一致（fuzzy） — 劣る軸

- **As-Is [事実]**: 表記ゆれ（全角半角・かな/カナ・ローマ字）は Normalizer/ReadingConverter で吸収するが（`0005` §5）、**綴り誤り（タイプミス）に対する fuzzy/編集距離ベースの補正は持たない**。`text` は keyword 非解析（ISS-04, `mappings-default.json:48-50`）で前方一致が主（出典: `0011` §2.4）。
- **To-Be [提案]**: fuzzy（編集距離）・edge n-gram を **E4（タイプミス正規化 Chain）＋ E3（fuzzy 用フィールド併設）＋ E2（fuzzy ヒットは低重み）** に内包する設計が 3-6 §2.4 で済んでいる。
- **Google [推測]**: 強力な did-you-mean / 編集距離 / キーボード配列誤りへの頑健性。
- **考察（ギャップ）**: **劣る軸。** Google は誤入力でも正候補を返すが、fess-suggest は綴り誤りに無力で、入力途中の打ち間違いで候補が消える。エンタープライズでも社員のタイプミスは日常的に起き、UX への影響は大きい。**ただし打ち手は 3-6 §2.4 が E4/E3/E2 として設計済み**であり、本書では再掲しない（§3 で参照）。3-7 固有に見える差分は「**日本語特有の誤り（送り仮名違い・かな/カナ混在・ローマ字綴り揺れ）に効く方式選定**」が Google の英語中心 did-you-mean とは別途必要、という観点（§3.1 (d) に整理）。

### 2.3 G3: 人気度・トレンド（急上昇）・鮮度（時系列） — 部分的に劣る軸

- **As-Is [事実]**: 頻度は `queryFreq`/`docFreq` を**累積加算**でマージし（`legacy/03` 3.4）、`@timestamp` は最新置換。人気語は `Kind=query`・単一語・`queryFreq>=10` の**累積頻度ベース**で、**時系列の急上昇（直近で伸びた語）という概念がない**（ISS-12, `PopularWordsRequest.java:212-214`）。
- **To-Be [提案]**: 時系列集計を行う `TrendingSource`（E1）＋ time-decay/急上昇加点（E2）＋ 時系列 freq/timestamp フィールド（E3）を 3-6 §2.5 で内包。人気語条件の調整可能化は 3-4 §2.6。
- **Google [推測]**: 大規模トレンドデータにより、急上昇・時事性・季節性をリアルタイムに近い鮮度で反映。
- **考察（ギャップと前提差）**: **部分的に劣る。** 「累積でよく検索される語」は出せるが「直近で急に増えた語」は出せない。一方、前提差として **Google の鮮度は全世界の検索トレンドという独自データに依存**しており、その規模そのものは fess には再現不能・不要（§4(b)）。**埋めるべきは「自組織内の鮮度」**——インシデント語・季節業務・社内の話題など、限定コーパスでも価値のある急上昇（§4(a)）。打ち手は 3-6 §2.5／3-4 §2.6 が設計済みで、本書は参照に留める。

### 2.4 G4: パーソナライズ（履歴・文脈・地域） — 劣る軸（ただし切り分け必須）

- **As-Is [事実]**: `SuggestItem` は `roles`（空なら `_guest_` 補完）を持ち、検索時は**権限フィルタとして roles でマッチを絞る**のみ（`legacy/03` 3.5, `0005` §10、二重担保 ISS-06）。**ユーザ個人の検索履歴・文脈に基づくパーソナライズは存在しない**（候補は全ユーザ共通、ロールによる可視範囲制御のみ）。
- **To-Be [提案]**: ロール文脈/履歴パーソナライズを **E5（検索コンテキスト受け取り）＋ E2（ランキング重み）＋ E3（履歴/ペルソナ属性）** に 3-6 §2.2 で内包。
- **Google [推測]**: 個人の検索履歴・地域・端末・直前クエリ文脈で強くパーソナライズ。
- **考察（ギャップと前提差・切り分け）**: **劣る軸だが、軸内で切り分けが必須。** Google のパーソナライズは **地域・端末・個人トラッキングという大規模追跡前提**で、エンタープライズではプライバシー・データ保持ポリシー（GDPR 等）の観点からも、地域・個人追跡型は大半が **不要・非現実的（§4(b)）**。一方、**ロール（部署/職種）単位のパーソナライズ**——既存の roles 属性を「可視範囲フィルタ」だけでなく「ランキング文脈（このロールがよく使う語を上げる）」にも使う——は、エンタープライズで特に費用対効果が高く **埋めるべき（§4(a)）**。打ち手は 3-6 §2.2 が設計済み。

### 2.5 G5: 関連クエリ・ロングテール補完 — 劣る軸

- **As-Is [事実]**: サジェスト語の供給は4経路（ドキュメント本文/クエリログ/検索語/elevate word）のみで、**クエリ補完が主**。同義語は独立データソースではなく OpenSearch アナライザ側の解析の一部にすぎず（`legacy/03` 3.2）、**関連クエリ・共起ベースのロングテール補完は持たない**。しかもクエリログ経路はデッドパス（ISS-01）。
- **To-Be [提案]**: 同義語/関連語を独立ソース化（`SynonymSource`/`RelatedWordSource`、E1）する設計が 3-6 §2.1 で済んでいる。
- **Google [推測]**: 「関連する検索」「People also search for」など、単純なプレフィックス補完を超えた関連クエリ・共起・ロングテール補完。
- **考察（ギャップと前提差）**: **劣る軸。** fess は入力プレフィックスに一致する語しか出せず、「車」→「車検/中古車」のような関連語展開ができない。前提差として、**Google のロングテールは全ユーザの膨大な共起ログに依存**し、その規模は再現不能（§4(b)）。だが **自組織の検索ログ・文書共起からの関連語生成は限定コーパスでも有効**で、エンタープライズの専門語ネットワークではむしろ精度が出やすい（§4(a)）。打ち手は 3-6 §2.1 が E1 として設計済み。3-7 固有の差分として、**「同義語をアナライザ任せにせず第一級の語源（E1）に昇格させる」ことが、Google 比較で初めて『関連クエリ補完の欠如』という形で顕在化する**点を明示する。

### 2.6 G6: 多言語・かな/ローマ字・表記ゆれの吸収 — 日本語は強い／非日本語多言語は限定的に劣る

- **As-Is [事実]**: テキスト処理は日本語特化（`ICUNormalizer`・`FullWidthToHalfWidthAlphabetNormalizer`・`HankakuKanaToZenkakuKana`・`KatakanaConverter`・`KatakanaToAlphabetConverter` 等、`0005` §5.1）。**かな/カナ/ローマ字/全角半角の表記ゆれ吸収は責務分割が良好な踏襲資産で、品質基盤として既に良好**（`0009` §2.8）。一方、**言語別 Chain の切り替え機構（非日本語の多言語）は明文化されていない**。
- **To-Be [提案]**: `TextProcessor` 抽象＋言語別 Chain 切替で多言語強化（E4）を 3-6 §2.6 で内包。
- **Google [推測]**: 全言語対応・自動言語判定・広範な表記ゆれ吸収。
- **考察（前提差・劣らない面の明示）**: **この軸は二分して評価すべき。** (1) **かな/ローマ字/表記ゆれの吸収という、日本語サジェストの核心では fess-suggest は Google と同等以上にできている**（「ｶﾞｯｺｳ」「がっこう」「gakkou」が同一候補にマッチ）。むしろ日本語特化の読み変換は汎用エンジンより作り込まれている強み。(2) **非日本語の多言語対応は劣る**が、エンタープライズの対象言語は限定的（自組織の運用言語）なので、Google のような全言語網羅は不要——**対象言語に絞れば埋めるべき範囲は限定的**（§4(a) 限定）。打ち手は 3-6 §2.6。**「劣っていない軸（日本語表記ゆれ）」を明示することが 3-7 固有の意義**（Google 追従の発想を排する）。

### 2.7 G7: セマンティック／意図理解 — 大きく劣る軸（TBD-01 要確認）

- **As-Is [事実]**: マッチングは前方一致（keyword に対する prefix・function score の `weightFactorFunction`、`legacy/03` 3.4）と読み変換による表記ゆれ吸収が中心で、**意味的類似（埋め込みベクトルによる近傍）でのサジェストは存在しない**（`0011` §2.3）。
- **To-Be [提案]**: `SemanticSource`（E1）＋ベクトルフィールド（E3）＋セマンティック類似度加点（E2）を 3-6 §2.3 で内包。ただし埋め込み生成基盤・`knn` 等のベクトル近傍検索は **OpenSearch バージョン依存（TBD-01）で [要確認]**、特定 API の利用可否は断定しない。
- **Google [推測]**: 表層が一致しなくても意味・意図が近い候補を提示（言い換え・概念的近傍の理解）。
- **考察（ギャップ・前提差・要確認）**: **8軸中で最も大きく劣る軸。** 「pc 不調」→「パソコン 故障 修理」のような意図ベースのサジェストができない。**ただし切り分けが最も難しい軸でもある**。前提差として、**Google の汎用意図理解は大規模 ML・専用インフラ前提**で、その網羅性そのものは再現不能・不要（§4(b)）。一方、**エンタープライズ文書の専門語・社内固有の言い換え（製品コード↔正式名称等）にはセマンティックの価値があり、限定コーパスゆえに埋め込みの精度も出やすい（§4(a) 条件付き）**。だが実現難易度は高く（埋め込み生成基盤・`knn` の TBD-01 依存・QPS 下レイテンシ＝3-5）、**本書は「3-1 の拡張点 E1/E3/E2 に載る道筋がある」ことと「TBD-01 を要確認として引き継ぐ」ことのみを示し、実現可否は断定しない**（完了条件）。打ち手の設計は 3-6 §2.3。

### 2.8 G8: 安全性フィルタ（不適切語の抑制） — 機構の質で劣る／公共ポリシーは不要／機密抑制は逆方向の優位

- **As-Is [事実]**: bad word による抑制機構は存在する（`addBadWord`）が、**`deleteByQuery(wildcardQuery(TEXT,"*badword*"))` の部分一致削除で誤削除が機構上不可避・不可逆**（ISS-04, `WordManagementOperations.java:77-84`）。「ai」を登録すると「detail/email/campaign」まで消える。
- **To-Be [提案]**: term 完全一致化・論理削除（`excluded` フラグ）・削除前ドライランで誤削除を機構的に排除（`0009` §2.3, `0005` §9.3）。
- **Google [推測]**: 不適切語・センシティブカテゴリ・スパム・誤情報を大規模ポリシーで抑制（autocomplete policies）。
- **考察（多面的）**: この軸は三面で評価する。(1) **「意図した語を正確に抑制する」基本品質では fess は機構の質で劣る**（ISS-04 の誤削除）が、打ち手は **3-4 §2.3／3-1 §9.3 が設計済み**で本書は参照に留める（§4(a)）。(2) **Google の公共安全性ポリシー（センシティブカテゴリ・誤情報抑制）はエンタープライズでは大半不要（§4(b)）**——対象が社内文書で公衆向けの誤情報リスクが小さいため。(3) **逆方向の差として、fess は「機密語・社外秘の抑制」「roles による権限フィルタ」という Google にない安全性価値を持つ**（§4.3）。**安全性軸は「Google に追いつく」より「fess 固有の安全性（誤削除の排除＋機密制御）を正しく作り込む」方向が価値**、という結論が 3-7 固有の考察。

### 3.2 拡張点別の負荷観察（どの拡張点に打ち手が集中するか）

## 4. 埋めるべき差／不要・非現実的な差の切り分け（3-7 固有の中核成果）

各軸を「**(a) fess の文脈でも埋めるべき差**」「**(b) fess の文脈では不要・非現実的な差**」に分類し、理由を添える。**この切り分けこそ、内部課題起点の 3-4／3-6 が行わない外部ベンチマーク比較固有の三角測量であり、本書の中核成果である。** 多くの軸は「軸内で両者が混在」するため、軸を一律に分類せず**軸内で要素分解して切り分ける**。

### 4.3 逆方向の差（Google にない fess 固有の価値）— 打ち手の前提として保全

3-7 は「fess が Google に劣る差」だけでなく、**「Google にない fess 固有の価値」（逆方向の差）** も明示する。これらは「Google に追いつく」打ち手で **損なってはならない前提**であり、外部比較固有の重要な気づきである。

- **権限フィルタ（roles による可視範囲制御）** [事実]: fess は roles で「誰に何を見せるか」を制御する（`legacy/03` 3.5, `0005` §10）。Google の公開サジェストにない、エンタープライズ必須の価値。**G4 パーソナライズ・G7 セマンティック等の打ち手は、この権限境界を必ず維持する**（`AuthorizationFilter` のデフォルト deny 要件＝`0005` §10.2）。
- **機密語・社外秘の抑制（G8 の逆方向）**: Google の安全性は「公衆に不適切な語の抑制」だが、fess の安全性は「**組織として出してはならない語（機密・社外秘）の正確な抑制**」。誤削除を排した term 完全一致＋論理削除（`0005` §9.3）は、この機密制御の正確性に直結する。
- **限定コーパスゆえの高精度**: Web 全体を相手にする Google と異なり、fess は対象が限定されるため、**関連語の共起・セマンティック埋め込み・人気語の意味が「自組織の文脈」で安定して効く**。ノイズが少なく、少ないデータでも精度が出やすい——これは限定コーパスの弱みではなく強み。
- **決定的 ID による集約・ゼロダウンタイム再構築**: 二重エイリアス・決定的 ID 集約（`0005` §11）は、限定コーパスを正確・確実に運用するための堅実な基盤。Google のような近似・確率的処理に頼らず、**正確性を担保できる**。

> **結論**: 3-7 の打ち手は「Google に似せる」ことではなく「**fess 固有の価値（権限・機密・正確性）を保全したまま、UX に効く差（タイプミス・関連語・鮮度・ロール文脈）を埋める**」ことを指針とする。
