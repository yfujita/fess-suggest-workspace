## 2. 配布・運用モデル（**第 2 版で確定**）

**本タスクの設計判断はすべてこの 3 前提の上に立つ。** 前提が崩れた場合は要件定義から見直す。

| # | 前提 | 帰結 |
| --- | --- | --- |
| **R-P1** | **fess 本体と fess-suggest はパッケージとして同時に配布され、同時に更新される。** 「fess-suggest だけが新版」という本番状態は作らない | 中間状態（旧 L1 期間）を安全にするための設計・コード・運用手順が不要になる |
| **R-P2** | **更新時のサービス停止を許容する** | 停止中に破壊的変更を適用できる |
| **R-P3** | **停止中に、インデックス再構築の完走・検証・エイリアス切替まで実施できる** | 新バイナリが旧世代インデックスへ通常トラフィックを書き込む時間帯が存在しない |

**決定者**: ユーザー ／ **決定日**: 2026-08-31

## 3. リリース段（**第 2 版で全面改訂**）

| 段 | 内容 | 更新対象 | サービス停止 |
| --- | --- | --- | --- |
| **R0**（準備リリース） | fess 本体側の安全網のみ。**fess-suggest は現行のまま変更しない** | `modules/fess` のみ | 不要（通常リリース） |
| **R1**（メジャー更新） | **fess 本体と fess-suggest を同時更新**し、停止中に再構築・検証・切替まで行う | 両方 | **必要** |
| **R2** | 旧ファサード（`Suggester` / `SuggestIndexer`）の除去 | fess-suggest | 不要 |

**R0 と R1 の間に fess-suggest の新版を本番へ入れてはならない**（R-P1）。これが唯一のリリース順序制約である。

> **旧 L1 / L2 / L3 との対応**: **旧 L1 と旧 L2 は R1 に統合された。** 旧「フェーズ A の先行リリース」が R0 に、旧 L3 が R2 に対応する。
> **旧 L1 期間（「新 fess-suggest ＋ 旧 fess 本体」が本番に同時に存在する区間）は R-P1 により消滅した。**

### 3.1 旧ファサードの互換ポリシー [確定]

**R1 では旧 `Suggester` / `SuggestIndexer` ファサードを `@Deprecated` で維持し、R2 で除去する。**
**決定者**: ユーザー ／ **決定日**: 2026-08-31

**理由**: `modules/fess-suggest` は `maven.codelibs.org` へ deploy される公開 artifact であり（`modules/fess-suggest/pom.xml:92-103`）、fess 本体以外の利用者を 1 リリースぶん猶予するコストは小さい。**ただし維持するのは `Suggester` / `SuggestIndexer` の public シグネチャに限る**（`0001` D-28 / §8.3.1。`entity.SuggestItem` の private コンストラクタ化により外部利用者への source / binary compatibility は元から維持されない）。

## 4. 本タスクのゴール

**R0 をリリース可能な状態にし、続けて fess-suggest 側の実装（新 `api` / `spi` / `internal` ＋ 旧ファサードの委譲）を完了させる。**

| # | 到達点 |
| --- | --- |
| 1 | **R0 が出せる** — フェーズ A（fess 本体側の安全網）が完了している |
| 2 | **fess-suggest 側の実装が完了している** — `api` 4 インタフェース・`spi` 7 インタフェース・`internal` 実装・データモデル決定（DM-1〜DM-21）・正式なライフサイクル API（`switchIndexRetainingPrevious` / `rollbackToPrevious` / `aliasState` / `validateNext` / `wordCountStats`） |
| 3 | **旧ファサードが新部品へ委譲している**（Strangler Fig 第 2 段） |
| 4 | **`modules/fess` を無変更でビルドできる** — §3.1 の互換ポリシーが成立していることの検査として行う。**「fess 本体を無変更のまま本番稼働させる」という運用要件ではない** |

**スコープ外**: **fess 本体の新 API 切り替えと R1 のリリース手順（停止中の移行手順書・G2 の fess 側実装）は後続タスク**とする。R2（旧ファサード除去）も後続。

## 6. 逸脱手続き

実装中に設計の誤り・不足を発見した場合、黙って実装で吸収しない。
該当設計書の改訂（版追記＋変更理由）を先に行い、作業履歴に記録してから実装する。

> **第 2 版の改訂そのものは逸脱手続き（X 番号）の対象外である。** 逸脱手続きは「実装中に発見した**設計の**誤り・不足」を扱うものであり、本改訂は**ユーザーによる前提の確定＝要件変更**に起因する。**ただし波及する設計書の改訂と作業履歴への記録は同じ厳密さで行う**（`0011`）。
