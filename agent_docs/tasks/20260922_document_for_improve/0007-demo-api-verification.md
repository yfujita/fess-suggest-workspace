## 1. 検証環境と前提（重要）

| 項目 | 内容 |
| --- | --- |
| エンドポイント | `https://search.n2sm.co.jp/api/v1/suggest-words`、`.../api/v1/popular-words`（`.claude/skills/fessdemo/` 記載のデモ環境） |
| リクエスト数 | 計 **75**（HTTP 200 が 66、429 が 8、500 が 1）。429 のうち `q=store` 以外の 7 件は再試行して成功 |
| 生データ | セッション用一時領域の `evidence-raw.txt`（`### <ラベル>` 区切り + 応答 JSON + `[http <code>]`）。**一時領域なので永続しない**ため、本書の §3 に結果を要約して残す |

- **デモ環境のバージョンは不明で、本タスクの対象（fess-suggest `f7a8039` / fess `8a9e1e15c`）と一致する保証がない。** 本書と `improve_point.md` の実機記述はすべて「デモ環境での観測」として扱う。
- **バージョンが古いことの具体的な証拠を 2 つ確認した。**
  1. デモ環境は **v1 API**（`/api/v1/suggest-words`、応答が `{"record_count":..,"data":[{"text":..,"labels":[..]}]}` 形式）を提供するが、**ローカル HEAD に v1 API は存在しない**（`modules/fess/src/main/java/org/codelibs/fess/api/` 配下は `engine` と `v2` のみ。v2 の応答キーは `suggest_words` / `types`）。
  2. `num` の入力検証がデモ環境には無いが、HEAD には `resolveSize`（`fess:api/v2/handlers/SuggestWordsHandler.java:142-155`、fess `6023d02eb` "enforce input bounds on v2 REST API"）で上限 clamp と非正値の 400 が入っている。
- したがって **API 層（パラメータ検証・エラー応答）の観測は HEAD の評価に使えない。** 使えるのは suggest index の中身と検索挙動（fess-suggest 側の振る舞い）に関する観測である。
- デモ環境のレート制限は厳しい。1.2 秒間隔では 13 リクエスト程度で 429（`Server is busy. Please retry after 60 seconds.`）になる。**3〜4 秒間隔が必要。**

## 2. クエリ設計の考え方（方法論）

**0 件応答は「引けない」と「候補が存在しない」を区別できない。** 公開デモ環境の索引内容は事前に分からないので、単に「`koohii` が 0 件だった」ことからは何も結論できない。そこで次の原則でクエリを組んだ。

1. **対照ペアを作る。** 同じ候補語を別の綴りで引き、**一方がヒットすること**を確認してから、もう一方の 0 件を「引けない」と判断する。
   - 例: `kennsaku` → 4 件（候補の存在を確認）／ `kensaku` → 0 件（引けないと断定できる）。
   - 例: `fess` → 58 件（存在を確認）／ `fesss` → 0 件・`ess` の 4 件に `fess` が含まれない（誤字補正と中間一致が無いと断定できる）。
2. **対照が取れない 0 件は [推測] / [要確認] に留める。** `koohii` / `lasticsearch` / `elasitc` / `fess 検索` などが該当する。
3. **件数だけでなく並び順を見る。** 件数が同じで並び順だけ変わるケース（Z-04）は、件数比較では見えない。
4. **仕様の有効/無効は「効いている対照」で確認する。** `label=zzz` → 0 件だけでは実装不備と区別できないので、`label=dbflute` → 1 件（該当ラベルのみ）と組で確認した。

この原則は `improve_point.md` の凡例にも明記した。

## 3. 検証結果

### 3-1. ローマ字読みの撥音（Z-01）— 機構が決定的に確認できた

| クエリ | 件数 | 解釈 |
| --- | --- | --- |
| `kensaku` / `kensak` | 0 | 自然な綴り |
| `kennsaku` | 4（検索 / 検索結果 / ケンサク / 検索漏れ） | `ン→nn` で生成された読み |
| `senmon` | 0 | 自然な綴り |
| `sennmon` / `sennmonn` | 1（専門） | `sennmonn` への前方一致 / 完全形 |
| `nihon` / `nihonn` | 4（日本語 / 日本テレビ / ニホンウナギ / 日本コロムビア） | **語末の撥音なので自然な綴りでも前方一致する** |
| `gijutsu` | 1（技術） | 撥音を含まないので正常 |
| `koohii` / `kohi` / `kensakku` | 0 | **対照が取れず未実証**（長音・促音） |

**確定した機構**: 読みのローマ字は撥音を `nn` で格納するため、自然な綴りは「語中の最初の撥音より前」までしか一致しない。撥音が語末にしか無い語（にほん）は前方一致で救われ、語中にある語（けんさく・せんもん）は一切引けない。日本語では語中の撥音が頻出なので影響は広い。

### 3-2. 複数語クエリ（Z-02）— 既存記述が誤りだった

| クエリ | 件数 | 備考 |
| --- | --- | --- |
| `fess n2sm` | 1（`text: "fess n2sm"`） | 複数語候補は**存在すれば正しく引ける** |
| `fess n` | 1（同上） | **途中入力でも前方一致する** |
| `fess 検索` / `full text` / `fess conf` | 0 | 対照なし＝「その組み合わせの候補が無い」だけ |

旧記述「複数語クエリは構造的にヒットしない」は誤り。制約は検索側ではなく**供給側**（文書から複数語候補が作られず、検索ログだけが供給源）にある。→ **Y-03 の重みが上がる**（全員ログイン環境では複数語サジェストが恒久的に空になる）。

### 3-3. prefix ブースト（Z-04）— 対象が違っていた

- 大文字・全角: `fess` / `Fess` / `FESS` / `ｆｅｓｓ` の 4 つが **record_count 58・上位 5 件の並び順まで完全一致**。→ 旧記述の「大文字・全角で無効」は**実機で実害を観測できなかった**。[推測] `fess` の候補はほぼ全件が `text` も `fess` 始まりなので、ブーストが均等に掛かり順位差が出ない条件だった。
- かな種別: 件数は同じで**並び順だけが変わる**。

| クエリ | 件数 | 並び順（上位） |
| --- | --- | --- |
| `けんさく` | 4 | 検索, 検索結果, **ケンサク**, 検索漏れ |
| `ケンサク` | 4 | **ケンサク**, 検索, 検索結果, 検索漏れ |
| `けんさ` | 6 | 検索, 検索結果, 検審, **ケンサク**, 検索漏れ |
| `ケンサ` | 6 | **ケンサク**, 検索, 検索結果, 検審, 検索漏れ |
| `検索` | 4 | 検索, 検索結果, 検索漏れ, ケンサク |

`isHiraganaQuery` でブーストが切れる（ひらがな = 頻度順）／`prefixQuery(text, 生クエリ)` が一致した候補だけ 2.0 倍される（カタカナ・漢字）というコード読解と**正確に一致**した。

### 3-5. `lang` の実害（Y-04）

`lang` 自体の直接検証は失敗した（比較用の `q=search` が全滅したため。§3-7）。ただし実害は別の形で観測できた。`q=fe&num=5000` の 165 件に、ドイツ語・フランス語が大量に混在する（`fehler`, `fehlerbehebung`, `fehlermeldung`, `fehlersuche`, `festgelegt`, `feldbeschreibungen`, `fenêtre`, `feuilles`, `fermer`, `fermés` など）。日本語利用者がこれを `lang` で絞れないことが Y-04 の実害にあたる。

### 3-6. ラベル・フィールド絞り込み（Y-19 / Z-18 / Z-11）

- **`label` は効いている**（当初の推測を訂正）。suggest: `label=dbflute&q=fess` → 1 件（`labels` に `dbflute` を含む語だけ）。人気語: `label=buzzfeed` と `label=elasticsearch` で内容が変わり、`label=zzz` → 0 件（`data: []`）。`label=fess` は label 無しと完全一致で、[推測] fess ラベルが支配的なため。
- 人気語は `seed=1` / `seed=2` で内容が総入れ替えになり（random_score の確認）、`field=title` でも内容が変わる。観測 8 回のうち 7 回は `record_count` が 10。
- フィールド: `q=fess` 58 件に対し `field=content` → 56 件、`field=title` → **1 件（`fess` のみ）**。56 + 1 < 58 で、どちらにも属さない語が 2 件ある。→ コードを突き合わせると、**検索ログ由来の語と優先語の `fields` は `suggest.field.contents`（既定 `_default`）固定**で、文書由来の `content` / `title` とは別語彙（Z-18）。
- 誤指定は無言で 0 件（`field=zzz` / `label=zzz`）。タイポと「候補なし」が区別できない（Y-19）。

## 6. 検証の限界（できなかったこと）

- **デモ環境の設定・バージョン**: NG ワード一覧、`suggest.*`、対象フィールド、fess のバージョンはいずれも不明。**API 層の観測は HEAD の評価に使えない**（§1）。

- **書き込み系は一切触っていない**: 公開デモ環境なので参照 API（GET）のみ。elevate word / bad word（X-01〜X-07）は未検証。
- テスト・ビルドは実行していない（`mvn test` / `mvn compile` とも未実行）。コード側の確認は読解・`grep`・JSON パース・`git log` / `git blame` に限る。
