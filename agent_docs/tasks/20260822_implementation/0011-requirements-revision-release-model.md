## 2. 何が変わったか — **中間状態の消滅**

**第 13 版までの設計の複雑さの大半は、次の本番上の中間状態を安全に成立させるためのものだった。**

```text
[fess 本体だけ先行] → [新 fess-suggest だけ入る L1] → [あとから fess 本体が新 API へ移る L2]
                             ↑
                    この区間（L1 期間）が問題だった
```

**R-P1 によりこの区間が生じない。** L1 と L2 は **R1** に統合される。

```text
R0: 準備リリース（fess 本体のみ）
  ↓
  ↓ 開発上はフェーズ B〜F を好きな粒度で進める（本番には出さない）
  ↓
R1: [サービス停止] → 両モジュール更新 → 再構築 → G1/G2/G3 → .prev 保持付き切替 → 検証 → [サービス開始]
  ↓
R2: 旧ファサード除去
```

### 2.3 **根拠だけを差し替えた項目** — 見落としやすい点

**「新バイナリが INV-1 未強制のドキュメントを読む」経路は、L1 期間が消えても残る** [確認]。

| # | 経路 | 根拠 |
| --- | --- | --- |
| **1** | **ロールバック後**は、新バイナリが旧世代インデックスへ書き込む状態になる | `0003` §5.4 ／ MO-19（R4 の二分） |
| **2** | **切替可否が不合格のまま旧世代でサービスを開始した場合** | `0003` 第 14 版 §10.6.3 の 2 |
| **3** | **backup 復元経由の不正データ** | `0003` §10.4（MO-25 が対処している経路そのもの） |

**したがって `0002` §5.2 の [確定]（欠損スロットは空配列として復元し、例外にしない）は維持する。** **ただし第 10 版までの却下理由は「M-1 は運用手順であり飛ばされうる」だったため、M-1 の撤回に伴って根拠が宙に浮く。** **第 11 版で根拠を `0003` §10.4（backup 復元経路）に差し替えた。**

> **これは今回の簡素化で唯一、外部レビューの提案に含まれていなかった論点である。** レビューは A-2 / A-3 の維持を正しく指摘したが、**`0002` §5.2 の [確定] が L1 期間を根拠にしていたこと**には触れていない。**根拠ごと消すと、ロールバック後や backup 復元時に 1 件の旧形式ドキュメントで再構築が落ちる**（撤回してはならない決定だった）。

**外部レビューは「A-4 は R1 でもよい」としたが、R0 に残す。**

| # | 理由 |
