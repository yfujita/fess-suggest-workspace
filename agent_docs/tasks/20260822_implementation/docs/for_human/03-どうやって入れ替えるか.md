# 03. どうやって入れ替えるか

> 元: `0003-migration-ops-design.md`
> ざっくり版です。実際に手を動かすときは元の文書（手順の正）を見てください。

---

## 大前提: 壊れているのは「呼び出し方」

二重エイリアスによるゼロダウンタイム再構築の**仕組みそのものは正しく動いています**。エイリアスの付け替えは 1 リクエストにまとめられていて原子的です。

**壊れているのは、それを呼び出す側の制御フロー**です。ここを取り違えると、以降の手順が全部的を外します。

現状の 4 つの欠陥:

| | 欠陥 | 結果 |
| --- | --- | --- |
| **D-a** | 取り込みの成否を見ずに切り替える | 不完全なインデックスが公開される |
| **D-b** | 切り替えた直後に旧世代を物理削除する | **同じ実行の中で戻り先が消える** |
| **D-c** | 検証ステップがない | **0 件のインデックスでも公開されうる** |
| **D-d** | 例外が握り潰される | **ジョブログには `OK` が残る** |

**D-a と D-b は連鎖します。** D-a だけなら「旧世代に戻せばいい」で済みますが、D-b があるので戻り先が同時に消えます。だから「ガードを入れる」と「旧世代を保持する」は 1 セットです。

---

## 再構築 1 回の手順（S0〜S5）

```
S0. 初回のみ: インデックスを作り、検索・更新の両エイリアスを付ける
     ↓
S1. 次世代インデックスを作り、更新エイリアスだけを新世代へ移す
     ↓   ※この時点で、検索は旧世代・書き込みは新世代
S2. 全件を再投入する（NG ワード・優先語の反映を含む）
     ↓   ※取り込み中は自動 refresh を止めておく
S3. 【新設】検証する ← 更新エイリアス経由で新世代を検査する
     ↓
S4. 旧世代に .prev を付けつつ、検索エイリアスを新世代へ移す（1 リクエスト）
     ↓
S5. どのエイリアスも指していない古いインデックスを削除する
```

**新しく増えたのは S3 の検証**と、**S4 で旧世代に `.prev` を付けること**の 2 つです。

---

## 切り替えてよいかの判定（3 つのガード）

**S3 でこの 3 つを全部通過したときだけ S4 へ進みます。** 落ちたら切り替えず、エラー終了します。

| | ガード | 内容 |
| --- | --- | --- |
| **G1** | **件数の下限** | 語数が 0 でなく、かつ**旧世代の 50%（既定）以上**あること |
| **G2** | **スモークテスト** | 代表的な語で実際に検索して、1 件以上返ること |
| **G3** | **取り込み失敗ゼロ** | 例外が出ていない**かつ**1 件単位の失敗も 0 件であること |

### なぜ「旧世代と件数が一致すること」を条件にしないのか

**新旧の件数は一致しません**。ID の作り方を変えるので両方向にずれます。

- 衝突していた語がほぐれる → **増える**
- 語数上限で切り捨てた結果、別の長文が同じ語に合流する → **減る**
- NG ワード該当語も保存するようになる → **増える**（NG ワードが多い環境ほど）

だから「絶対的な下限」と「前回比の割合」で見ます。50% という数字は**実測に基づいていない**ので設定可能にしてあります。

### G3 が「例外なし」だけでは足りない理由

**ここが見落としやすい穴です。**

100 万件投入して 10 万件が失敗したとします。1 件単位の失敗は例外にならないので、処理は正常完了します。エラーコードも立ちません。G1 は 10% 欠損では 50% の下限に掛かりません。**結果、10% 欠けたインデックスがそのまま公開されます。**

そこで G3 を「例外なし **かつ** 項目単位の失敗もゼロ」に拡張しました。全件再構築に「何件までなら許容」という水準を設ける根拠がないので、**1 件でも失敗したら不合格**です。

### G2 はメジャー移行では必須

普段の再構築では G2 は任意（未設定ならスキップ）でよいのですが、**今回のメジャー移行だけは必須**にしました。

mapping・読み仮名の規則・語数上限・ID・除外フラグ・クエリ生成が**同時に変わる**ため、「**全件正常に投入できて件数も十分なのに、検索だけ 0 件**」が現実に起こりえます。G1 も G3 もこれを検知できません。

運用者が検証語を設定していない場合は、**S2 で実際に投入した語から自動で採取**します（設定必須にはしないので、導入の手間は増えません）。

## 失敗したときに戻す（ロールバック）

### 旧世代の保持

切り替えるときに旧世代へ **`.prev` エイリアス**を付けます。古いインデックスの削除判定が「エイリアスを 1 つも持たないもの」なので、**付けるだけで削除対象から外れます**（判定ロジックは変更不要）。

保持するのは**常に直前の 1 世代だけ**。日次バッチ運用なら実質「直近 24 時間」です。

> **手動で退避インデックスを作るときは必ずエイリアスを付けてください。** 付けないと次回のジョブで消えます。

### 手順

| | 手順 |
| --- | --- |
| **R1** | 再構築ジョブを止める |
| **R2** | `.prev` がどこを指しているか確認する |
| **R3** | **検索エイリアスだけ**を `.prev` の世代へ戻す（更新エイリアスは触らない） |
| **R4** | 更新エイリアスをどうするか決める（下記の二択） |

### R4 は二択で、中間はない

| | 内容 | いつ使うか |
| --- | --- | --- |
| **R4-A: 検索だけ戻す（既定）** | 新しいバイナリのまま。書き込みは新世代に入り続け、**検索には現れない** | **緊急の縮退**。長期運用しない |
| **R4-B: バイナリごと戻す** | fess / fess-suggest を旧版に戻してから、更新エイリアスも戻す | リリースそのものの巻き戻し |

> **新しいバイナリのまま更新エイリアスを旧世代へ戻してはいけません。** ID の作り方が違うので、同じ語が旧 ID と新 ID の 2 ドキュメントに分裂し、**頻度の集約が壊れます**。しかも旧世代の mapping は緩いので**エラーにならずに壊れます**。
> この禁止を API の形で表すため、`rollbackToPrevious()` は更新エイリアスに触らない設計になっています。

### 戻せないもの

ロールバックは「**検索結果を直前の健全な状態に戻す**」操作であって、データの完全な巻き戻しではありません。

| 対象 | 切戻し後 |
| --- | --- |
| 切替後に追加した NG ワード / 優先語 | 新世代にしかないが、**設定インデックスには残る**ので次回再構築で復元される |
| 切替後に貯まった検索ログ由来の頻度 | **失われる。復元経路はない**（緊急時に許容する損失） |
| 設定インデックス | 世代を持たないので影響を受けない |

### 落とし穴: 切戻し先には `excluded` フィールドがない

旧世代のドキュメントは `excluded` フィールドを持ちません。だから検索条件を「`excluded` が `false` のものだけ」と書くと、**切り戻した瞬間にサジェストが全滅します**。必ず「`excluded` が `true` のものを除く」と書いてください。

**これはロールバックが一番必要な場面で発動する種類のバグです。** 切替が成功している間はコードを読まないと気づけません。

## エイリアス操作の失敗をどう扱うか

エイリアスの付け替えは、**タイムアウトしてもサーバ側では適用済みのことがあります**。「例外が出た＝適用されていない」と決めつけると、成功していたのに失敗扱いして中途半端な状態を残します。

そこで呼び出し元は**必ず 3 分岐**で書きます。

| 結果 | 意味 | やること |
| --- | --- | --- |
| **正常完了** | 目的の状態になっている（例外が出た後に再確認して成立した場合も含む） | 次へ進む |
| **`SuggesterException`** | 未適用と確定した | エラー終了。**次回実行でやり直せる** |
| **`SuggestAliasStateUnknownException`** | 適用されたか判断できない | エラー終了し、**調査手順へ回す。自動リトライしない** |

---

## refresh の扱い

3 層に分けました。

1. **バッチごとの同期 refresh を廃止**し、再構築中は次世代の自動 refresh を止める（切替直前に戻す）
2. **`refresh()` がクラスタの全インデックスを refresh していた**のを、suggest インデックスだけに限定する
3. 管理操作の refresh は、操作ごとにポリシーで指定する

**最適値は決めていません**（性能実測は後続タスク）。

## リリースの順番

| 段 | 内容 |
| --- | --- |
| **L1** | fess-suggest をリリース。新 API を追加し、**旧クラスの公開シグネチャは維持**するので fess 本体は無変更で動く |
| **L2** | fess 本体を新 API へ切り替える（main 4 クラス）。**この初回再構築がメジャー移行** |
| **L3** | fess-suggest の旧クラスを除去する |

> **切替ガード（G1 / G3）は L1 を待たずに単独で先行リリースできます。** fess 本体側の変更だけで完結し、しかも「部分失敗が切替を通過する」穴は**現行コードにも存在する**ので、先に塞ぐ価値があります。
> ただし **G2 と `.prev` 保持は L1 が要ります**（ライブラリ側の新メソッドが必要なため）。

### L2 の初回再構築で運用者に伝えること

1. **G2 が必須になる**ので、「不合格で切り替わらなかった」が起こりうる
2. **語数が移行前より増える**（ID 衝突の解消 ＋ NG ワード該当語も保存するようになるため）。検索結果には出ないが、管理画面の語数表示には載る
3. **除外語の物理削除は運用者が明示的に実行する操作**であり、自動では走らない

---

## 一緒にやらないといけない変更

ID の作り方が変わるので、**新旧のインデックスを混ぜて使う道はありません**。段階適用も部分移行もできず、**「新しい形で全件入れ直す → 検証する → 切り替える」の一本道**だけです。

したがって、スキーマに関わる変更は**1 回の再構築にまとめて載せます**（mapping 変更・語数上限・ID 方式・除外フラグ）。

## 既知の制約（今回は直さないもの）

| | 内容 |
| --- | --- |
| **K-1** | **同じ語に同時に書くと頻度の更新が失われることがある**（楽観ロックがない）。まとめて取得する改善では解決しない。後続フェーズで扱う |
| **K-2** | **`roles` は集合和なので、一度 `_guest_` が混ざると全員に見える**。回復手段は「混入源を止めてから全件再構築」だけ |
| **K-11** | 多重起動防止はスケジューラ側の仕組みに委ねる |
| **K-12** | 削除が `_delete_by_query` API ではなく手動ループのまま |
| **K-13** | 再構築の中断が自動検知されない（監視項目として定義するのみ） |
| **K-14** | **失敗してもジョブログには `OK` が出る**。判定には別の手段を使う |
| **K-15** | リトライ機構がない（失敗すると次回スケジュールまで待つ） |
| **K-17** | エイリアスのない手動退避インデックスは次回ジョブで消える |
| **K-18** | エイリアス状態が判定不能になりうる。自動復旧は設計しない（調査手順あり） |

## リリース前に「この状態で出してよいか」を判断する項目

**「既知の制約だから後で」で流さず、リリース時に明示的に判断します。**

| | 項目 | 判断すること |
| --- | --- | --- |
| **R-1** | K-2（`_guest_` 混入） | この挙動のままメジャー版を出してよいか。出すなら実装ガイドと回復手順が文書に載っているか |
| **R-2** | K-1（頻度のロストアップデート） | 後続フェーズへ持ち越すことを確認。契約が README に反映されているか |
| **R-3** | 外部利用者への非互換 | コンストラクタ廃止・型の移動などを CHANGELOG に列挙したか |
| **R-4** | 語数の増加 | NG ワードが多い環境で語数が増えることをリリースノートに書いたか |

**いずれも「設計を変える」判断ではなく、「この状態で出す」ことの明示的な確認です。**
