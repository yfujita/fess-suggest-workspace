## 1. エグゼクティブサマリ

### 1.1 提案の狙い

fess-suggest は10年以上機能が据え置かれ（種別 DOCUMENT/QUERY/USER の3種・データソース4経路）、保守運用に高度な Java スキルを要し、サジェスト品質も「悪くはないが良いとも言えない」状態にある（`0000`）。本提案は、要件定義の5目的（**可読性 / 変更容易性 / サジェスト品質 / 性能 / 新機能**）を検討軸に、**既存構成にとらわれずゼロベースで「あるべき姿（To-Be アーキテクチャ）」を設計し、そこへ現実的に到達する移行ロードマップ**を示す。

### 1.2 中心となる設計思想（7原則 — `0005` §1）

ゼロベース設計を貫く North Star は次の7原則であり、各原則が複数の現行課題（ISS）を構造的に解消する。

1. **公開 API 最小化**（用途別の小さなインタフェース）— ISS-13/17 回避
2. **拡張点ファースト**（サジェストソース・スコアリング・テキスト処理を最初から差し替え可能に）— ISS-01/11/12 回避、新機能の土台
3. **単一の真実**（マージ規則・ランキング源・権限フィルタを一箇所に）— ISS-05/06/14 回避
4. **死蔵コード・死蔵データを持たない**（書くなら読む、読まないなら書かない）— ISS-01/14/16/17 回避
5. **バルク効率優先**（1件ずつの同期往復を基本にしない）— ISS-08/10 回避
6. **一貫した同期/非同期境界**（標準機構へ統一）— ISS-09 回避
7. **流用価値ある資産は踏襲**（全置換ではない）— KEEP-01〜04

### 1.4 推奨ロードマップの要約（`0013` §3/§7）

- **移行戦略は「段階的移行（Strangler Fig）」に確定** [確定・第3版]（`0001解消` §2.1。第2版までは「推奨」だったが、ユーザー判断により確定）。一括リプレース（Big-Bang）は、流用価値の高いテスト資産（main 64ファイル/11,591行 vs **test 77ファイル/15,194行**）・テキスト処理パイプライン・二重エイリアス再構築・決定的 ID 集約（KEEP-01〜04）を捨てるリスクが大きく、fess 本体連携を一斉破壊する。段階的移行は既存資産をセーフティネットに、互換破壊を MIG 単位で分散できる。**ただしスキーマ変更系は「新世代インデックスを並行構築し二重エイリアスで切替」する部分的並行構築を併用する**。
- **移行は Strangler Fig で「部品単位に置換 → 委譲 → 呼び出し切替 → 旧除去」**（§4.1.1）。To-Be 実装は `api`/`spi`/`internal` の新パッケージに並置し、既存 `index`/`request`/`Suggester` は当面残置。過渡期の技術ルール（データ再構築＝二重エイリアス、非同期/例外はファサードでアダプト、`scripted_upsert`/`knn` 等の性能・実現性は任意の先行 PoC）は §4.1.2。
- **Phase 0＋4フェーズに分割**（メジャー/マイナーのリリース節目に割り当て）:
  - **Phase 0 性能・実現性検証（PoC）→ [確定・第3版] 実施しない**（`0001解消` §2.4）: OpenSearch 3.7.0 で `scripted_upsert`/`knn`/`fuzzy` 等の利用可否は確定済み（[事実]）のため**バージョン検証は不要**。残る性能実測（`scripted_upsert` の実スループット、セマンティックの QPS 別レイテンシ／容量等）は**後続タスクに回し、設計判断は本書の既定値で断定する**（案A 採用・multiGet 優先など）。これにより設計書に「PoC 結果待ちの未確定項目」を持ち込まない。
  - **Phase 1 基盤**（可読性・変更容易性）: 用途別 API 分離・拡張点抽象・単一規則・標準並行モデル。**以降の全フェーズが載る土台**。**リスク分散のため 1a（内部完結系）／1b（fess 連携系）に二分割**する（§4.4）。
  - **Phase 2 品質**: bad word 可逆化（論理除外）・ドライラン、人気語カバレッジ拡張。
  - **Phase 3 性能**: 書き込みの往復削減（**multiGet に確定。`scripted_upsert` は拡張点のみ用意** — `0001解消` §2.3）、**バルク件数適正化＋ refresh 発行頻度の分離**（`0001解消` §2.12）、シャード/レプリカ可変化（`0001解消` §2.13）。
  - **Phase 4 新機能**: 蓄積属性 UI・同義語/関連語・トレンド・fuzzy・パーソナライズ・多言語・（条件付き）セマンティック。
- **クイックウィン（フェーズ計画を待たず先行着手推奨）**: **MIG-15第1段（multiGet 化）・MIG-16（バルク件数＋refresh 分離）・MIG-03（bad word のマッチ規則統一）** の3件。いずれも局所変更・依存なし・スキーマ変更なしで、性能と保守性に即効する。
  - なお **MIG-03 の位置づけは本書レビューで下方修正した**: 当初「唯一の中〜高重大度・最優先」としていたが、**fess 本体からは不可逆な物理削除が発火しない**ことを追検証で確認したため（§2.1・§2.2 ISS-04）、fess 運用に対する即効性は当初想定より小さい。残る価値は「`contains`/`wildcard` のマッチ実装二重化とメタ文字誤爆の解消（保守性）」と「ライブラリ直接利用者への破壊性除去」であり、**性能クイックウィン（MIG-15第1段・MIG-16）の方が投資対効果は高い**。即時・可逆な論理除外は MIG-13 で上積み。

## 2. 現状と課題の整理

### 2.1 アーキテクチャの現状サマリ（改善に効く事実、`0002` §3）

- **エントリポイントは2つの肥大ファサード** [事実]: `Suggester`（507行/public 約18）と `SuggestIndexer`（547行/public 約28）。Indexer は4 Operations へ委譲する構造は保つが、**公開 API 表面積**が課題（ISS-13、`0003` §3.1）。
- **テキスト処理パイプラインは良好** [事実]: Normalizer(Chain)→ReadingConverter(Chain)→SuggestAnalyzer の Strategy+Composite 構成（計約1,369行）。責務分割が良好で専用テストも手厚い（踏襲資産＝KEEP-01）。
- **データソースは4経路**（うち②クエリログは fess 本体未使用のデッドパス）[事実]。同義語は独立ソースでなくアナライザ任せ。
- **ランキングは検索時 function score 単系統** [事実]: 登録時 `score=(queryFreq+docFreq)*userBoost` を事前計算するが、検索・人気語・ソートのいずれからも**参照されない死蔵フィールド**（ISS-14/16、`0003` §2）。
- **書き込みは Get-then-update** [事実]: N件登録で **N回同期 Get + 1回 bulk**（multiGet ですらない、`SuggestIndexWriter.java:54-55`）。
- **document 取り込みは別 JVM の子プロセスで動く** [事実]（第3版で追検証、TBD-04）: `SuggestJob` が `java` コマンド＋`-cp`＋`jvm.suggest.options` を組み立てて子プロセスを起動し `waitFor()` する（`SuggestJob.java:92,99,185,203,220`）。エントリは `SuggestCreator.java:115 main()` → `:266 indexFromDocuments(...)`。**ヒープが fess 本体と隔離されている**ため、バッチ件数を上げてもアプリ本体の GC 圧には直結しない。
- **取り込みループが「バッチ件数」と「refresh 頻度」を癒着させている** [事実]（第3版の新規発見）: `ContentIndexingOperations.java:331-350` は `docPerReq` 件ごとに bulk index した直後、**同期的に index refresh を発行する**（`:345`）。既定 `doc.per.request=2`（`fess_config.properties:1441`）では **100万ドキュメントで50万回の refresh** が走る。ISS-08 の実体は「バルク件数が小さい」ことより**この refresh 頻度**にある（→ MIG-16 の定義を拡張）。
- **suggest インデックスのシャード固定は意図的な選択だったが設定化されていない** [事実]（第3版で追検証、TBD-05）: `number_of_shards` は 2017 年時点で `5`（`2de2559`）、2018-04-19 の `d8b5ccc` で `auto_expand_replicas: "0-1"` 追加と同時に **`1` へ意図的に引き下げ**られた（同日 fess 本体側は逆に `aed8385fc` でシャード数を設定可能化している）。ただし `Suggester.java:476-483` は `suggest.json` を読むだけで**プレースホルダ置換機構を持たない**ため、fess 側から上書きできない。
- **bad word は「部分一致」の2機構** [事実]: ①**登録時フィルタ** `SuggestItem.isBadWord`（`text.contains(badWord)` の部分一致、`SuggestItem.java:455-462`）＝ `IndexingOperations.index` が新規登録アイテムを非破壊的に除外（インデックスしないだけ）。②**登録時削除** `WordManagementOperations.addBadWord(apply=true)`＝ `wildcardQuery(TEXT, "*badword*")` の deleteByQuery で**既存インデックス済み文書を物理削除**（`WordManagementOperations.java:81`）。両者とも部分一致だが、①は可逆・非破壊、②は**不可逆・破壊的**。かつ ①は Java `contains`、②は OpenSearch `wildcard` と**マッチ実装が二重化**（ISS-04）。
  - **ただし fess 本体の呼び出し実態では ② は発火しない** [事実]（本書レビューで追検証）。管理 UI・管理 API はいずれも `apply=false` で呼ぶ（`AdminBadwordAction.java:322,349,403` / `ApiAdminBadwordAction.java:133,155,211`）。`apply=true` は `SuggestCreator.java:255` の `storeAllBadWords(true)` **1箇所のみ**で、これは直前の `Suggester.createNextIndex()`（`SuggestCreator.java:253`）で**新規作成された空の物理インデックス**に更新エイリアスを張り替えた直後の呼び出しであり、deleteByQuery の対象が空 → **実質 no-op**。以降のバルク投入時に ① の登録時フィルタが効くため、fess から見た現行挙動は既に「再構築で反映＝可逆」に近い。②の破壊性が実害となるのは、ライブラリを直接 `apply=true` で稼働中インデックスに対して呼ぶ利用者のみ。**この事実は ISS-04 の重大度と MIG-03 の優先度根拠に影響する（後述）**。
- **ゼロダウンタイム再構築は良好** [事実]: 二重エイリアス（検索/更新）＋物理 `{base}.{timestamp}`、決定的 ID（`createSuggestTextId`）による頻度集約（踏襲資産＝KEEP-02/03）。
- **全体評価** [事実/所感]: 重大度「高」と断定できる課題は0件、「中」が大半。**アーキテクチャは健全で、改善は段階的に行える**（`0002` §4.2）。

>
> サジェストは逐次入力追従で**低レイテンシ・高 QPS がシビア**。一般に語彙中小・QPS 穏当なら案A、QPS 極大なら案B が有利。
>
> **[提案・本書レビューで確定] 案A（死蔵 score 廃止）を既定として明示的に採用する。** 従来「実測に依存し断定しない」としつつ Phase 1 で MIG-02（＝案Aの実行）を計画しており、任意扱いの Phase 0 負荷試験をスキップすると「未決定のはずの選択が既成事実化する」矛盾があった。これを次のとおり解消する:
> - 現行の `score` は**参照ゼロの死蔵フィールド**（ISS-16）であり、案Aは「実質的に使われていないものを消す」変更で、現行比の検索レイテンシ増は `function_score` 単系統化の分のみ（現行も検索時 function score で採点しているため**増分はほぼゼロ**）。よって案Aは現状維持に近く、リスクは小さい。
> - 案Bへ切り戻す場合のコストは「mapping への `score` 復帰＋再構築1回＋ソート経路の実装」。**二重エイリアス再構築（KEEP-02）がある以上ダウンタイムなしで実施でき、切り戻しコストは受容可能**と判断する。
> - したがって **MIG-02 の着手に負荷試験の完了を前提条件として課さない**。**[第3版] Phase 0 は実施しないことが確定した**（`0001解消` §2.4）ため、案A は本書の判断として断定する。案A/案Bの比較計測は後続タスク（§5.3）に移し、極大 QPS 要件が判明した時点で案Bへ切り替える。
>
> **[追記] MIG-13（`excluded` 論理除外）の検索時コスト（P3）**: `excluded` 方式は全サジェストクエリに除外条件が常時付与されることを意味する。**`mustNot(termQuery(excluded, true))` の term filter として実装**すればフィルタキャッシュに載る単純な boolean 条件であり、レイテンシ増は実用上無視できる見込み [提案]。それでも「低レイテンシ・高 QPS がシビア」という本軸の前提に照らし、**MIG-13 実施時は除外フィルタ付与前後のレイテンシ差分を計測項目に含める**こと。旧世代インデックス（`excluded` 未定義）との共存期の扱いは §4.1.2 を参照。

### 3.7 補論: Google 検索サジェストとの比較（`0012`）

外部ベンチマーク（Google）との三者比較（As-Is / To-Be / Google）から、品質・新機能の打ち手を**外部視点で再照射**する。**「Google に追いつく」ことは目的化せず**、fess（限定コーパス・エンタープライズ）の文脈で価値のある差に絞る。Google の記述はすべて [推測]（内部実装は非公開）。

**劣る軸と劣らない軸の特定**（`0012` §2）:

| 軸 | 評価 | 打ち手の所在（再掲せず参照） |
| --- | --- | --- |
| G1 プレフィックス/低レイテンシ | **ほぼ劣らない**（本質は達成済み。差は分散規模） | — |
| G2 タイプミス/fuzzy | **劣る** | §3.5 fuzzy（E4/E3/E2） |
| G3 トレンド/鮮度 | **部分的に劣る**（社内鮮度は埋める） | §3.5 トレンド／§3.3 人気語条件 |
| G4 パーソナライズ | **劣る**（ロール文脈は埋める） | §3.5 パーソナライズ |
| G5 関連クエリ/ロングテール | **劣る** | §3.5 同義語/関連語（E1） |
| G6 多言語/かな/ローマ字 | **日本語は強い／非日本語は限定的に劣る** | §3.5 多言語（E4） |
| G7 セマンティック/意図理解 | **大きく劣る**（条件付きで埋める） | §3.5 セマンティック（`knn` は 3.7.0 で利用可、要確認は埋め込み基盤・実測） |
| G8 安全性フィルタ | **機構の質で劣る（不可逆な物理削除・マッチ二重化）／機密抑制は逆方向の優位** | §3.3 bad word（§9.3） |

**3-7 固有の成果（`0012` §4）**:

- **埋めるべき差／不要な差の切り分け**: 全世界トレンド・地域/個人追跡・全行動ログ・全言語網羅・汎用意図理解・公共安全ポリシーは **fess 文脈で不要・非現実的**（Google の大規模独自データ・プロプライエタリ前提依存）。**社内鮮度・ロール文脈・自組織共起・専門語言い換え（条件付き）・bad word 削除の可逆化が埋めるべき差**。
- **逆方向の差（Google にない fess 固有の価値）**: 権限フィルタ（roles）・機密語抑制・限定コーパスゆえの高精度・決定的 ID 集約。**打ち手はこれらを損なわない前提**（`AuthorizationFilter` のデフォルト deny を維持）。
- **外部比較から見た優先度示唆**: 高＝G8 bad word 可逆化・G2 タイプミス・G5 同義語・G4 ロール文脈・G3 社内鮮度（UX 直撃・難易度中以下・追加基盤依存小）。低＝G7 セマンティック（高難度。`knn` は 3.7.0 で利用可だが埋め込み基盤の用意と容量/レイテンシの実測が必要）。
- すべての打ち手が **3-1 の拡張点 E1〜E5 に載る**（外部比較起点でも共通機構に手を入れない）。

### 4.1.1 段階的移行の具体化（Strangler Fig: パッケージ構成と手順）[提案]

段階的移行を、「新旧が同一コードベースで共存し、内部実装を**部品単位で置換**したのち最後に旧を除去する」Strangler Fig パターンとして具体化する [提案]。To-Be の新実装は既存パッケージを壊さずに **新パッケージ（NEW）** として並置し、旧構成（`index`/`request`/`Suggester`）は当面そのまま残す。

**パッケージ構成（To-Be を NEW として並置）**:

```
src/main/java/org/codelibs/fess/suggest/
 ├─ api/       ← [NEW] To-Be の公開IF（SuggestQueryService / SuggestIndexLifecycle
 │                    / SuggestWordAdmin / SuggestIngestService 等。§1.3・§3.2）
 ├─ spi/       ← [NEW] To-Be の拡張点（SuggestSource(§4.2) / ScoringStrategy(§9.2)
 │                    / SuggestItemMergePolicy(§7.2.1) / BadWordPolicy(§9.3) 等）
 ├─ internal/  ← [NEW] To-Be の新実装クラス群（api/spi を実装。SuggestStore 実装(§6/§8) 等）
 │
 ├─ index/     ← (既存) SuggestIndexer / *Operations。当面はそのまま
 ├─ request/   ← (既存) SuggestRequest。当面はそのまま
 └─ Suggester.java ← (既存) 巨大ファサード。当面はそのまま
```

**手順（NEW 実装 → 委譲 → 呼び出し切替 → 旧除去）**:

1. **NEW に To-Be を実装し、既存テストを流用して等価性を担保する。** 例: 単一マージ規則 `SuggestItemMergePolicy`（MIG-01）を `spi`（実装は `internal`）に作り、既存 `SuggestItemMergerTest` 等をコピー・修正して**現行と同一のマージ結果**になることを回帰確認する（ISS-05 の二重実装を1規則へ収束させる際の安全網）。テスト資産（test 77ファイル/15,194行）がここで効く。
2. **既存の巨大ファサードのメソッド中身を、新部品への委譲に書き換える。** `Suggester` / `SuggestIndexer` の**公開シグネチャは維持**したまま、内部で `internal` の新実装を呼ぶ。fess 本体から見た API は不変で、互換を保ったまま実装だけが入れ替わる。
3. **内部部品がすべて To-Be へ置換されたら、fess 本体側の呼び出しを新 API へ切り替える。** 古い `SuggestIndexer` から新しい `SuggestIngestService` 等へ（MIG-06/08/09。fess 本体 PR を同期リリース）。
4. **誰も使わなくなった旧 `index`/`request` パッケージ・`Suggester` を、ここで初めて安全に除去する**（または `@Deprecated` で次期メジャーまで残置し、そこで削除）。

この順序により、各 MIG は「NEW 実装＋等価テスト（内部完結・fess 無影響）」→「委譲（互換維持）」→「呼び出し切替（fess 同期リリース）」→「旧除去」という**同一ライフサイクル**で進み、fess 本体への互換破壊を最終段階まで遅延・局所化できる。§4.4 のフェーズは、このライフサイクルを MIG 群に対して束ねたものである。

### 4.1.2 移行における技術的ルール（過渡期の扱い）[提案]

過渡期に新旧が共存するため、①データ、②非同期/例外、③高度 API（`scripted_upsert`/`knn` 等）の性能・実現性検証の3点で明示的な規則を置く。

- **データの移行（インデックス再構築）**: スキーマ変更を伴う部品（MIG-02 死蔵 score 廃止 / MIG-13 `excluded` / MIG-17 シャード / MIG-20・21・24 新世代インデックス）へ委譲を切り替える際は、既存の **二重エイリアス再構築機構（KEEP-02）** を活用する。新スキーマで物理インデックス `{base}.{timestamp}` を**並行構築**し、検証後に検索エイリアスを切替（`switchIndex`）、旧インデックスは `removeDisableIndices` で除去する。ダウンタイムなし・ロールバック可能（エイリアスを戻すだけ）。**フェーズ内の複数スキーマ変更は1回の再構築に束ねる**（§4.4 脚注、`0013` §8.1）。
  - **新規フィールド追加時の共存期ルール（MIG-13 `excluded` 等）** [提案]: 検索エイリアスが旧世代（当該フィールド未定義）を指し得る期間があるため、**除外条件は必ず「否定形」で書く**——`mustNot(termQuery("excluded", true))` を用い、`must(termQuery("excluded", false))` は使わない。後者はフィールドを持たない旧世代文書が一件も一致せず、**サジェスト結果が全滅する**。ロールバック（エイリアスを旧世代へ戻す）時も同じ理由で否定形が必須。あわせて mapping に `"excluded": {"type": "boolean"}` を追加し、書き込み側は明示的に `false` を格納する（`null_value` に依存しない）。
- **非同期基盤・例外の変換（アダプターの責務）** [確定・第3版、`0001解消` §2.6/§2.7]: NEW の部品は標準の `CompletableFuture` で実装する（§8.2）。**`Result` 型（例外を投げず成功/失敗を戻り値で表現）の導入は取り下げる**——API の学習コストと実装量を抑え、fess 側の修正量を最小化するため。**エラーは従来どおり `SuggesterException` を throw する**（非同期経路では `CompletionException` でラップされる）。既存ファサードから委譲する過渡期は、**ファサード内をアダプタ層**と位置づけ「`CompletableFuture` → 独自 `Promise`」の変換をファサード内で行い、新旧の並行モデル差をファサードで吸収する（MIG-08 の互換の肝）。
  - **fess 本体への露出は行わない**（第2版で [要確認] としていた判断をクローズ）。追検証により **fess 本体に `Deferred`/`Promise` 型の変数・フィールド・引数の宣言は 0 件**で、コールバック依存も `SuggestHelper.java:294-297` の 1 箇所のみと判明した（§5.2）。したがって **`SuggestHelper.indexFromDocuments(Consumer<Boolean>, Consumer<Throwable>)` のシグネチャを維持したまま**内部の `.then`/`.error` を `.thenAccept`/`.exceptionally` 相当へ書き換え、`SuggestWordsHandler.java:104`／`PopularWordHelper.java:120` は `getResponse()` → `join()` 相当の1行置換で済む。`SuggestCreator.java:263-276` の `CountDownLatch` もそのまま維持する。
- **先行 PoC（Phase 0 性能・実現性検証）→ [確定・第3版] 実施しない**（`0001解消` §2.4）: OpenSearch 3.7.0 で `scripted_upsert` / `script_score` / `knn` / `fuzzy` はいずれも利用可能（[事実]）であり、**バージョン確定目的の PoC は不要**（TBD-01 はクローズ）。残る性能実測は後続タスク（§5.3）に回し、設計判断は本書の既定値で断定する。なお multiGet を第1段に置く段階構成（§3.4）は**バージョンとも実測とも独立に**維持する——`scripted_upsert` はスクリプト複雑度が高く、低リスクの multiGet で往復削減の大半に到達してから原子的集約へ進む方が安全だからである（可用性・後方互換の観点でも multiGet 経路の保持は無駄にならない）。**第3版では `scripted_upsert` を「`SuggestStore` の差し替え可能な実装として拡張点だけ用意する」に留め、Painless スクリプト仕様・冪等性・失敗時挙動は設計対象外とすることが確定した**（`0001解消` §2.3）。
